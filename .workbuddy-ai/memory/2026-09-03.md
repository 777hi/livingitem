## 红电系统架构复审（只审查，未改代码）
用户问「重新实现是否有更好的框架」。重读 `ContainerRedstoneData`(1237行) / `LivingWaxedCopperFunction`(804行) / `ChannelState` / `PowerMath` 后的结论，按性价比排序：

### 【真 bug，待修】相位域 offset 只增不减 → 移除振荡器后 n 被永久高估
- 位置：`ChannelState.PhaseDomain`（`offsets: Set<Integer>` 与 `deltaByOffset: Map`），只有 `add`/`merge(max)`，无任何逐 offset 清理。
- 唯一清理是 `tickCleanup` 的 `domains.values().removeIf(d -> currentTick - d.lastEventTick > timeout)`（timeout = max(32, pref*2)），按**整域**超时删除。
- 触发路径：域内只要还剩任一同周期振荡器在发事件，`d.lastEventTick` 就持续更新 → 域永不删 → 被拆掉的振荡器其 offset 永久留在 `offsets` → `n()` 虚高 → `effDeltaSum` 与 `unlock` 双双虚高 → `combinedFactor` 虚高 → **长期白拿发电量**。
- 复现：搭 4 路同周期 → 识别到 n=4 → 拆掉 3 路留 1 路 → n 仍为 4。全部拆光才会因整域超时（32+ tick）清空。
- 修法方向：给每个 offset 记 `lastSeenTick`，`tickCleanup` 里逐 offset 剪枝；或改为「每 tick 按窗口重算 offset 集合」而非累积集合。

### 【框架】电力层感知单元选错：应按网络遍历，不是按发电机
- `tickContainerData` 里 `for (var e : active.entrySet()) runBfs(genSlot, ...)` —— 每台发电机各跑一次 BFS。
- 同锈蚀级连通块内的 G 台发电机 → 同一网络被重复遍历 G 次，O(G×N)；切制形态每发电机还跑 H/V 两次 BFS。
- 附带：同一 edgeKey 的 `tracker.onRisingEdge` 在同 tick 被调 G 次，靠 `if (interval > 0)` 守卫才没污染周期估计（属偶然安全，非设计保证）。
- 提议：按 (锈蚀级, 拓扑键) 分连通块 → 每块遍历一次收集跳变 → 扇出给块内所有发电机。O(N+G)，且同一网络内各发电机感知结果天然一致。

### 【框架】信号层是「阶段 × 类型」矩阵，不是组件抽象
- `ContainerRedstoneData` 1237 行的主因：phase1/3/4/5 各有一串 `for (slot : torchSlots) / leverSlots / comparatorSlots ...` 的 switch-on-type 展开。
- 新增一种元件要同时改 buildSlotMask + 位常量 + 4~5 个阶段。
- 提议：抽 `RedstoneComponent` 多态钩子（emit / recheck / charge / display），阶段只做分派。

### 【调度】固定 6 阶段 → 工作队列
- 之前两个坑（比较器输出只传一格、phase3 `!=` 兜底）根因相同：固定阶段对「源何时就绪」的假设是错的（phase1 收集源时后方粉链还没传播）。
- 提议：事件/工作队列驱动 + 显式延迟调度（中继器档位天然是延迟事件），跑到不动点为止。

### 【耦合】数字优先级 → 声明依赖
- `LivingWaxedCopperFunction.getPriority()=3` 依赖红石层 priority=2 先跑完（要读 edgeGrid/prevEdgeGrid 双缓冲）。魔数耦合，重排即静默出错。

### 【接口】轮询 → 推送
- 电力层每 tick 轮询网络内每条边的 `getEdgeValue`/`getPrevEdgeValue` 判跳变；改由信号层每 tick 输出 `List<EdgeTransition>` 更省、依赖更显式。

### 零散
- `ChannelState.bestDomain(pref)` 被 `bestFactor/bestPeriod/bestN/bestEffDeltaSum` 各调一次 → 每发电机每 tick 约 5 次全域线性扫描，可缓存一次。
- `runBfs` 每次 new `HashSet<Integer>` + `LinkedList<Integer>`（装箱）；槽位上限 ~54，`boolean[] visited` + `int[] queue` 即可。
- `effDeltaSum()`/`maxDelta()` 用 stream 每 tick 跑，可缓存。

### 已经做好、不建议动
- `PowerMath` 纯函数零 MC 依赖，标定常数（K=1/16、C、RESONANCE_EXPONENT=2）集中。
- 共振「单遍前馈、绝不回灌」不变量健全。
- 每槽自有出边模型（v15 刚重构）已干净。
- `FakeContainerContext` 让信号/电力层可脱离 Level 单测。
- 统计式推断周期/相位（而非解析计算）正是 n>4 涌现的来源，用户认可该手感，**不要**改成解析式。

### 结论
不建议整体重写：测试覆盖尚可（信号层 17 + 电力层 65），公式层已是最优形态，共振不变量健全，重写主要风险是丢掉已调好的标定与涌现手感。建议顺序：先修 offset 剪枝 bug（正确性）→ 再做网络中心遍历（性能+概念）→ 组件多态与工作队列按需渐进。

### 【发现但故意未改，待用户决策】域级超时也用错了时钟
- `tickCleanup` 的域级超时 `max(32, preferredPeriod * 2)` 用的是**偏好周期**（发电机堆叠数），不是本域周期。
- 后果：长周期 / 稀疏网络（如 P=130、pref=16）在两次心跳间隙（>32 tick 无事件）被判为「静默」→ 整域被删 → n 每次重建都从 1 开始 → **n 堆不起来**，多相涌现被抑制。短周期（P=20 < 32）不受影响，域能跨心跳存活。
- 不改的原因：**会显著改变平衡**。域存活 → `accountEnergy` 每 tick 都按 `bestFactor` 付一次 `factor × P`，长周期网络从「每 130 tick 付约 33 次」变成「每 tick 都付」，约 3.9× 增幅。属于 buff，需用户拍板。
- 修法（若要做）：域级超时也改成 `max(32, d.period * 2)`，与偏移级统一。注意两者届时同值，可合并简化。

## 框架层复用盘点（用户问「别每个活物品各造一套轮子」）
读 `container/` + `api/` 共 2494 行后的结论：

### 框架已提供、红电系统【已在用】
- `tick.getFunctionSlots(functionId)`：按功能预分组槽位，避免各子系统重复扫全容器。
- 跨 tick 容器级数据缓存：`REDSTONE_DATA_CACHE` / `POWER_DATA_CACHE` / `FLUID_DATA_CACHE`（`LinkedHashMap<containerKey,...>` + `POS_TO_CACHE_KEY` 反向索引 + LRU 清理）。
- **脏槽位批量同步**：`SimpleContainerContext.syncSlotToClients` 只往 `TickContext.dirtySlots`(Set) 记槽位号，`flushDirtySlots()` 在 tick 末统一发，且用 tick 末最终状态 —— **同 tick 同槽位 N 次同步只发 1 个包**。
- `HasContainerData` + 优先级调度；`SlotInfoProvider.getWidth()`（支持 13 列模组容器）。

### 框架已提供、但红电【没用 / 造了轮子】
- `ContainerContext.getNeighbors(slot,size,width)`：静态邻居工具。红电手写了 `ContainerRedstoneData.resolveSlot`。**原因合理**：`getNeighbors` 每次 new 一个 `int[]`，而 `resolveSlot` 零分配且按方向返回（越界 -1）。→ 框架缺「非分配 + 按方向」变体，逼得热路径子系统各自造轮子。
- `ContainerSnapshot`：SoA「每 tick 编译一次、跨子系统共享」模式（int[] sourceOf/targetOf + FilterData[]/ChestSnapshot[]）。红电没用，**因为 `capture()` 硬编码了漏斗/箱子/流体**（`container/` 包直接 import `LivingHopperFunction`/`LivingChestFunction`/`HopperFilterBuilder`）——分层违规，没有扩展点。

### 框架【缺失】的能力（应加在框架层，不是各子系统各造一套）
- 容器 revision / 变更检测：完全没有。`ContainerSnapshot` 每 tick 重建（TickContext 是 per-tick 的，"lazy" 只在单 tick 内有效），无跨 tick 缓存。
- 跨 tick 同步节流：只有 tick 内去重，没有「每 N tick 最多同步一次」。
- 可扩展快照注册表。

### 结论（复用优先的三条框架改动）
1. `ContainerContext` 加容器 revision 计数（setItem 时 bump）→ 解锁跨 tick 快照缓存 + 稳态跳过，所有域受益。
2. `ContainerSnapshot` 改为注册表驱动（各域注册 SnapshotProvider 产出自己的 SoA 数组）→ 红电注册 kindOf/dirOf/capOf 即可白拿每 tick 共享；配合 1 还能跨 tick 缓存。
3. `ContainerContext` 加非分配的方向邻居 API（如 `resolveNeighbor(slot,dir,size,width)` 返回 int，越界 -1），`getNeighbors` 改为委托它 → 红电的 `resolveSlot` 可以删掉。

### 对我上一轮性能分析的更正
