## 活红石比较器 I/O 机制 + 两个现象根因（读码分析，非改动）
- 边模型（v15 后）：`edgeGrid[slot][dir]` = 该槽**自己朝 dir 发出的出边**；`inputAt(slot,dir)` = `edgeGrid[邻居(dir方向)][opposite(dir)]`（读邻居发来的边）。
- 比较器输入（`computeComparatorOutput`，ContainerRedstoneData.java:1188）：
  - 主输入 signalA = `inputAt(slot, opposite(朝向))` → **后方（尾部）那条边**；signalA==0 时兜底读后方物品的容器输出 `readComparatorOutput`（读箱子填充度那套）。
  - 侧输入 signalB = `perpendicularEdges(inputDir)` 两条**侧边**的最大值，同样为 0 时兜底读邻居容器输出。
  - 输出：`edgeGrid.set(slot, edgeIndex(朝向), output)` → 写**朝向方向那条出边**。比较模式 `signalA>=signalB ? signalA : 0`（原样透传、**不衰减、不受 signalCap 限制**）；减法模式 `max(0, signalA-signalB)`。
- 现象1「粉 15→15→14」（比原版 15/14/13 白赚一跳）根因：`powerConductiveNeighbor`（:900）对导体邻居是**整体充能**——`for d2=0..3 if signal>edgeGrid[neighbor][d2] set(...)`，即把 signal 刷进该粉/铜的**全部 4 条边**并把其粉/铜邻居入队。故比较器输出 15 会把紧邻那格粉的 4 条边全刷成 15，下一格粉 `maxInput` 仍读到 15 → 显示 15；再下一格才吃 `output = maxInput-1` 的衰减 → 14。粉自身衰减规则 `output = maxInput - 1`（phase2 :572 / phase4 :772），显示值 = `maxInputOfSlot`（收到的最大值，phase5 :1067）。
- 现象2「比较器链最多 3 个、第 4 个死」根因（三者叠加）：
  1. `reset()`（:175）swap 后 `edgeGrid.zero()`——**每 tick 从零重算**，无跨 tick 累积，链断了不会自愈。
  2. `powerConductiveNeighbor` 对元件位（含 BIT_COMPARATOR）直接 return（:908）→ 上游比较器**不会把下游比较器入队**，链式传播只能靠 phase4 里 `for (slot : comparatorSlots)` 单循环的遍历顺序推进。
  3. `comparatorSlots` 是 `new HashSet<>()`（`ContainerLivingItemHandler:431`）→ 迭代顺序是**哈希桶序而非槽位顺序**。
  ⇒ 链能亮几级 = HashSet 顺序碰巧与链几何方向吻合的长度，不是写死的 3；换摆放位置/方向（改变槽位索引的桶序）亮起的个数会变。
- 修法候选（未做，待用户定）：① 治标——repeaterSlots/comparatorSlots 改按槽位升序（LinkedHashSet/TreeSet），仅让沿槽位递增方向的链可靠；② 正解——元件（比较器/中继器）改**迭代到稳定**（多轮循环至无边变化）或按依赖拓扑排序后计算，顺带解决一般元件链。

## BOM 问题深挖（用户追问「这是什么问题」）
- **结论：不是 bug，已向用户解释清楚。** 证据链两层：
  1. 实测：拿项目实际 gson-2.10.1.jar，`new JsonReader(new InputStreamReader(in, UTF_8))` + `setLenient(false)` 解析 8 个 lit 文件 → 全部 PARSE OK。
  2. 源码：`gson-2.10.1-sources.jar` 的 `JsonReader.fillQueue()` 第 1354-1359 行无条件消费 BOM
     （`if (lineNumber==0 && lineStart==0 && limit>0 && buffer[0]=='\ufeff') { pos++; lineStart++; minimum++; }`）。
