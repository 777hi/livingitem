## 修复：Create 跨区块传送带 → 服务端线程死锁

**报告**：living_item 1.3.2 + Create 6.0.10，进世界即服务端线程卡死（GUI 能动、不能合成、不能 tp、
玩家掉虚空）；单个传送带不卡，跨区块传送带必卡。
堆栈 `ContainerChunkCache.onChunkLoad → BeltBlockEntity.initializeItemHandler → ServerChunkCache.getChunk`。

**根因（已用原版/NeoForge 源码逐条确认）**：

- `ChunkEvent.Load` 在 `ChunkStatusTasks.full()` 的区块 FULL 任务**内部**触发（主线程）。
- 我们在事件里做 `level.getCapability(...)` → 执行到 Create 传送带的 provider →
  `initializeItemHandler()` → `level.getBlockEntity(controller)`（**别的区块**）→
  `ServerChunkCache.getChunk(..., requireChunk=true)` → `managedBlock` + `join`
  等一个"只能由主线程自己推进"的 future ⇒ 自等自。
- NeoForge 在 `ChunkEvent.Load` javadoc 里已明确警告"不延迟世界交互会死锁"。
- 同区块不卡的原因：原版 `ChunkHolder.currentlyLoading` 旁路只覆盖"正在加载的那个区块本身"。
- 附带的坑：Create 的守卫 `level.isLoaded(controller)` **不充分** —— `hasChunk` 只查 ticket level。

**改动**：

- `ContainerChunkCache.onChunkLoad` → 只登记坐标（唯一 level 调用是 `dimension()`），
  扫描全部推迟到 `flushPendingRescans`（`ServerTickEvent.Pre`）。
- `flushPendingRescans` 新增每 tick 限量 `MAX_RESCANS_PER_TICK = 64`，剩余顺延不丢。
- 新增 `ContainerChunkCacheChunkLoadTest`（4 项），全量 **317 passed / 0 failed / 0 skipped**。

**文档**：infrastructure §3.2 加红线 + 修两处旧口径（`ServerTickEvent.Post`→`Pre`、
`onChunkUnload` 曾写"即时移除"）；decisions `D-core-04`；file-map 测试树；AGENTS 进展 + 基线 317。

**顺带完成文档规约 §4 的归档**（入口已 20,759 > 20,000 且进展达 4 批次）：
09-14 批次迁入 changelog（逐行守恒校验通过），入口 20,759 → 19,653，`doc_check.py` 0 警告。

## 追问：「强制同步加载」的量化（同日）

用户追问这个概念，顺手把三个数字从源码里挖实并写进 §3.2：

- `ChunkPyramid.GENERATION_PYRAMID`：`FULL` 的累积依赖 = **`STRUCTURE_STARTS` 半径 8**
  ⇒ 一次 `getChunk(FULL, true)` 的依赖足迹是 **17×17 = 289 个区块**。
- `TicketType.UNKNOWN` lifespan = **1**，`Ticket.timedOut` = `currentTick - createdTick > 1`，
  `purgeStaleTickets` 每 tick 一次 ⇒ 票据约 2 tick 后失效、区块被卸载
  ⇒ **每 tick 触发 = 每 tick 重新生成**（比"强制加载"更严重的是"反复加载"）。
- `max-tick-time` 默认 1 分钟且 `ServerWatchdog` 只在 `DedicatedServer` 启动
  ⇒ 专用服务器会判崩，单人存档纯卡死（对应用户现象）。
- `ServerTickEvent.Pre` 由 `EventHooks` 从 `MinecraftServer.tickServer` **开头**触发
  （未进 `tickChildren`/区块流水线）⇒ tick 阶段做同步加载合法，只是慢。

**残余风险（未防护，用户未表态）**：`processLevelContainers` 每 tick 对每个 BE 调
`getCapability` —— 若某模组 provider 伸手到未加载区块，就会变成每 tick 强制加载+卸载。
已实测的 Create 传送带有 `isLoaded(controller)` 守卫，不触发。排查触发条件：
spark 里 `getChunkCacheMiss`/`chunkLoad` 异常高。已写进 §3.2。

**顺带修文档缺陷**：`living-item-infrastructure.md` 里 `### 10.1 性能判读…` 被追加在
`## 12. 关键文件索引` 底下、且编号与 §10.1 重复 —— 已移回 §10 并改号为 **§10.3**
（守恒校验通过），同步更新 `docs/README.md` §8 与本文件 MEMORY.md 的引用。

## 追问二：强制加载的入口清单与概率（同日）

用户判断「只有活地图传送主动加载，其余被动」——**不准确**。全量排查后新增 §3.2.1。

**明确主动 `getChunk` 的**：`TeleportHelper`（活地图传送）、`SableIntegration.teleportSubLevel`
（飞艇）、`ExplosionComponent`（3 处，由爆炸区域读方块间接触发）。

**结构性根因（`ChunkLevel` 常量）**：原版 BE 只在 **≤31（ENTITY_TICKING）** 跑 ⇒ 邻居 ≤32
⇒ 必然已加载 ⇒ 读邻居免费。本框架用 `getChunkNow` 拿 **≤33（FULL_CHUNK_LEVEL）** 区
⇒ 容器落在 **33 圈（已加载但不 tick）** 时邻居落在 **34+（未加载）** ⇒ 强制加载。
**危险带 = 最外一圈区块**（视距 12 时 625 中的 96 个）。

**关键事实**：`BlockCapability.getCapability` 内部先 `level.getBlockState(pos)` 再
`getBlockEntity(pos)` ⇒ **能力查询本身就是加载入口**。

**入口清单**（详见 §3.2.1 表）：`ContainerRedstoneData.sampleFaceInput`（getSignal，红石系）、
`CrossContainerTransfer.getNeighborHandler`（活漏斗）、`processContainerAt`（大箱子另一半）、
`StressOutputManager`/`CreateIntegration`（活水车下方一格）、`ExplosionComponent`。
**已守卫**：`LivingEnderChestAccessor`、`ContainerEnergyStorage`（只读自身 pos）、`flushPendingRescans`。

**更正上一轮的说法**：`addTicket` 会 `addOrGet` + `setCreatedTick` **续期** ⇒ 连续每 tick 触发是
**永久钉住该区块**，不是"每 tick 重新生成"。反复重生成只在间歇触发/来回卸载重载时。已在 §3.2 改正。

**概率结论**：小几率但非零，且**移动时概率显著上升**（加载区边缘会扫过基地，逐个容器进入危险带）。
命中后果严重且长期：首次可能真生成（289 区块足迹）+ 永久钉住 + 理论逐圈外扩（未实测）。

**仍未防护**（用户未表态）。若要做，最小方案是在读邻居前统一加 `isLoaded`/`hasChunk` 守卫
（把危险带里的容器降级为"这一 tick 不读邻居"），而不是引入缓存或轮询。

## 追问三：概率更正为 100% + 后果清单（同日）

用户指出「取决于玩家活动半径 ⇒ 百分百」。**同意并更正**：加载区边界随玩家移动扫过世界，
任何需要读邻居的活物品容器迟早被扫进危险带 ⇒ **不是"会不会"而是"多频繁/是否恶化"**。
已把 §3.2.1 里"小几率"的口径改掉。

后果清单已写进 §3.2.1（7 条）：① 单 tick 卡顿（289 足迹，未探索区域是真生成）；
② 移动中周期性卡顿；③ 邻居被**永久钉住**（票据续期）+ 内存/存档/IO/重进变慢；
④ **语义漂移**——活物品在"已加载但不 tick"区块里继续工作（原版 BE 只 ≤31 跑）；
⑤ 逐圈外扩（未实测）；⑥ 诊断难（PerfMetrics 盲区）；⑦ **传染**——同步加载会让其他模组的
Load 处理器在"主线程阻塞于 managedBlock"时运行，若它们也做世界交互就撞同一个死锁
（修复后我们自己的 onChunkLoad 只登记，反而消除了"scan→加载→Load→scan"的递归重入）。

**注意**：④ 其实是个独立的架构问题 —— 本框架把活物品的"工作范围"从原版的 ticking 区（≤31）
扩大到了 loaded 区（≤33）。这条值得单独评估，不只是强制加载的副作用。

## 追问五：越界爆炸的处理逻辑（同日，已写 §3.2.2）

**暴露面比"读邻居"大得多**：`radius = 4.0 × √TNT数` ⇒ 64 TNT 半径 32（5×5 区块）、
128 TNT 半径 45（7×7）、3456 TNT 半径 235（**31×31 = 961 区块**）。
未加载区块被 `getBlockState` 读到 ⇒ 每个 289 足迹 ⇒ 叠加爆炸自身 O(r³) 直接打爆 tick。

**口径定为：爆炸只作用于"当前已加载的世界"，未加载区块整块跳过。** 最有力的论据是
**超级爆炸模式本来就是这么做的**（`tickAll` 里 `if (level.hasChunk(...)) deleteChunkContent(...)`）
⇒ 这不是新增限制，而是**统一三个模式的口径**。另外原版"不越界"靠的是"中心在 ticking 区 +
半径小"，不是靠跳过，所以我们不能照抄"对齐原版"这个说法。

**4 处改动**：① 普通模式收集循环 ② 大当量阶段1 收集循环（各加 chunkPos 判定缓存，
`Long2BooleanOpenHashMap.computeIfAbsent`）③ 阶段2/3 的 `getChunk` → `getChunkNow` 防御性 ④ 跳过量记日志。

**已确认不用改**：`applyExplosionDamage` 的 `level.getEntities(AABB)` —— 1.21 走
`LevelEntityGetter`（已加载实体索引），**不碰区块**（我原本怀疑它会强制加载，验证后否掉了）；
`scheduleSuperExplosion` 纯几何算区块列表；`tickAll` 已有 `hasChunk` 守卫。

**fastutil 坑**：`Long2BooleanOpenHashMap` 默认 `defaultReturnValue(false)` ⇒ 用 `get()` 查
未判定过的 key 会返回 false（误当"未加载"）⇒ 必须 `computeIfAbsent` / `containsKey`。

**顺带发现的独立隐患**：radius 235 时收集循环 `471³ ≈ 1.05 亿次` 迭代，**即使全已加载**也是
主线程巨长操作 ⇒ 建议把"几何算区块列表 + 分帧"范式前移到普通/大当量模式。已记进 §3.2.2。
