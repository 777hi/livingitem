# 2026-09-11

## 卡顿真凶（续 2026-09-10 的 Flux 潜影箱案）：`receive()` 里的 long 溢出 → 零头回收伪死循环

昨天定位到 `ContainerEnergyStorage.receiveEnergy` 占 18968ms/60s，做了「3 遍扫描改 1 遍」
的常数因子优化。**那只是擦伤。真凶是 long 溢出。**

### 链路（用 libs/src/Flux-Networks-1.21 的源码逐层确认）

```
FluxPointHandler.onCycleStart()      ← 报告里 98.81% 挂在「模拟」这一遍
  sendToConsumers(getLimit(), true)
    SideTransfer.send()              每面一次，mTransfers = 6 个方向
      ForgeEnergyConnector.sendTo()
        storage.receiveEnergy((int) Math.min(amount, Integer.MAX_VALUE), simulate)
```

关键两点：
1. `TransferHandler.getLimit()` → **`mDisableLimit ? Long.MAX_VALUE : mLimit`**。
   「绕过限制」开关打开时，每 tick 的模拟调用都是 `receiveEnergy(Integer.MAX_VALUE, true)`
   → `wantMilliFe = 2.147e12`。
2. `onCycleStart` 用的是**满额 limit**，`onCycleEnd` 才用 `min(mBuffer, limit)`。
   所以模拟那一遍永远按最大量跑 —— 这就是 98.81% 全落在 `onCycleStart` 的原因。

### 溢出点

```java
long share = accept * remaining[i] / totalRemaining;   // ← 这里
```
每盏容量 `BULB_UNIT_CAPACITY_MFE = 1e9`（100 万 FE）。空容器 27 槽 × 64 盏时
`totalRemaining = 1.728e12`、`remaining[i] = 6.4e10`，
乘积 **1.1e23 ≫ Long.MAX (9.22e18)**。

**溢出阈值低得离谱：27 槽时铜灯总数超过约 16 盏就会触发**（accept × remaining > 9.22e18）。

后果链：
`share` 变乱值/负数 → `perLamp ≤ 0` → `distributed ≈ 0`
→ `leftover = accept`（巨额）→ 零头回收的 `while` **每轮只扣 count mFE**
→ 退化成 **~10 亿轮 × 27 槽** 的全槽扫描。

| 配置（27 槽，请求 2^31-1 FE） | share | 实充分配 | 循环轮数 |
|---|---|---|---|
| 27 堆 × 1 盏 | 3.17e8 | 8.6e9 / 2.7e10 | 6.8e8 |
| 27 堆 × 2 盏 | **−4.96e7** | **0** / 5.4e10 | 1e9 |
| 27 堆 × 64 盏 | 2.18e6 | 5.9e7 / 1.728e12 | 1e9 |

**定量吻合实测**：27 堆 × 64 盏 + 外部一次请求 50 万 FE ⇒ 7.81e6 次 `getStackInSlot`
× ~150ns ≈ **1.17s**，与 spark 慢 tick 平均 **1094ms**（最大 1362ms，对应 MSPT max 1360）几乎一致。

### 第二个后果（比卡顿更隐蔽）

`receive()` **返回的仍然是 `accept`**（巨额），所以**通量网络以为电已经全额送出了**，
实际上只有涓涓细流进灯。实测退回修复后每盏只充到 **34,338 mFE / 应有的 1e9 mFE = 0.0034%**。
也就是说用户不仅卡，灯还根本没充上电 —— 而外部电网的电量被凭空核销了。

### 修复（`ContainerEnergyStorage.java`）

1. **份额计算防溢出**（核心）：
   ```java
   long share = (long) ((double) accept * remaining[i] / totalRemaining);
   if (share > remaining[i]) share = remaining[i];
   else if (share > 0 && (double) share * totalRemaining > (double) accept * remaining[i]) share--;
   ```
   先转 double 算比例（结果恒 ≤ remaining[i]，不溢出）；量级 < 2^53 时与整数精确一致，
   测试与常规场景无损；末尾回退一步防浮点向上多算 1 mFE（守「宁损勿造」）。
2. **`MAX_LEFTOVER_PASSES = 256` 防御性轮数上限**：合法 leftover = Σ(share mod count)
   ≤ Σ(count−1)，1~2 轮就完；超限说明份额算错，宁可少充也不让服务端卡死（少充仍满足实充 ≤ 记账）。
3. （昨天已做，仍然有效）`isBulb()` 短路顺序反转、`receive()` 单遍收集走 `stacks[]`、
   `getWaxedBulbData()` 结果缓存。

`extract()` 那边是 `Math.min(q * count, remaining)`，`remaining` 被 `wantMilliFe ≤ 2.1e12` 封顶，**无同类溢出**。

### 回归测试（`WaxedCopperStorageTest` 新增第 19 例 + `CountingHandler`）

## 同类第二处：`LivingWaxedCopperFunction.distributeToBulbs`（发电直存，:831）

修完第一处后顺手把电力包所有 `a * b / c` 扫了一遍，发现**同款模式第二处**：

```java
long share = mfe * ref.remaining() / totalRemaining;
```
`mfe` = 全部发电机按锈级累加（`re = factor × period × jumpCount`，单机可到 1e6 RE
⇒ mfe ~ 6e7），`remaining` 可达 6.4e10 ⇒ 乘积越过 Long.MAX。

**后果比第一处更隐蔽，且更危险**：这里没有 leftover 循环所以**不会卡死**，但
- share 变负数 → `perLamp ≤ 0` → **本 tick 发电被静默丢弃**（且 `distributed == 0`
  → 函数返回 false → 不 setChanged）；
- share 变成巨大正数 → `newQ` 被 `Math.min(CAP, ...)` 拉到容量上限 → **凭空造出上百万 FE**。

修法同第一处（double 算比例 + 夹到 remaining）。夹到 remaining 后 `perLamp ≤ 每盏剩余容量`，
两条路都堵死，且 `distributed ≤ Σshare = mfe`，守住了不造电。

回归测试 `distributeToBulbs_hugeGeneration_noOverflow`（第 20 例）：64 盏空灯 + 1e7 RE，
断言每盏充入 `mfe/64 = 9,765,625` mFE。
**已验证能抓 bug**：退回后报 `expected: <9765625> but was: <758425>`（只收到应有的 7.8%）。

## 收口：抽出 `PowerMath.mulDivFloor`（用户批准后执行）

用户决定保留 `LivingWaxedCopperFunction.java` 的修复后，把两处内联的「double 算比例 +
夹上界 + 浮点回退」收敛成一个原语：

```java
public static long mulDivFloor(long a, long b, long c)   // PowerMath
```
契约：`floor(a × b / c)`；`a,b ≥ 0`、`c > 0`；`a > c` 时按 `a = c` 处理（份额不超过 b）。
实现在 `PowerMath.java`（**该文件不在对方的改动集合里**，零冲突），
两个调用点各缩成一行：
- `ContainerEnergyStorage.receive`：`PowerMath.mulDivFloor(accept, remaining[i], totalRemaining)`
- `LivingWaxedCopperFunction.distributeToBulbs`：`PowerMath.mulDivFloor(mfe, ref.remaining(), totalRemaining)`

**收益**：溢出防护从此只有一处定义。下一个写「按比例分配」的人不会再各写一遍错。
副作用是共享文件 `LivingWaxedCopperFunction.java` 的 diff **没有变大**（仍是约 12 行，
只是从内联逻辑变成一行调用）。

## 代码质量评估（用户问「是否盘根错节」，2026-09-11）

### 量化结论：不是整体烂，是**局部沉积**

带日期注释的分布（`grep -rho "20..-..-.." <dir> | wc -l`）：

|---|---|---|

即 v17.5→v18→v19 连续迭代留下的沉积岩，不是全库性问题。

### 最严重的结构问题：**一个概念三份实现，三种口径**

「按剩余容量比例分配」这套算法存在于三处，量化与报账口径**互不相同**：

| 类 | 场景 | 量化 | 报账 |
|---|---|---|---|
| `BulbItemEnergyStorage.receiveEnergy` | 物品栏单堆 | 无 | `min(toReceive, ceil(实充/1000))` |
| `ContainerEnergyStorage.receive` | 容器多堆充电 | `accept -= accept % 1000`（floor） | 声明值 `accept` |
| `LivingWaxedCopperFunction.distributeToBulbs` | 容器多堆直存 | 无 | `boolean` |

**这就是「同一个 long 溢出 bug 修了两次」的物理原因** —— 概念没有单一归属地。
注释里甚至写了「与 ContainerEnergyStorage.receive 同族修复」，说明作者知道是同一族。

### 其他纠缠点

1. **单位只活在名字里**：`mfe`/`re`/`chargeMilliFe`/`accept`/`share` 全是 `long`，类型系统
   无法阻止 RE 加到 mFE。`PowerMath` 集中了常量但没集中运算 → 溢出 bug 的直接土壤。
2. **不变量只活在注释与测试里**：契约「宁损勿造」很真实，但靠 `RoundTripConservationIT`
   偶发守护，不是构造性保证；且三处报账口径不同 ⇒ 该不变量**从未被唯一定义过**。
3. **God class**：`LivingWaxedCopperFunction` 1236 行 = tick 编排 + 相位分析 + 能量记账 +
   分配 + **tooltip 构建/渲染数据**（后两者与 tick 完全无关）；`RecipeBookComponentMixin` 1293 行。
4. **层泄漏**：`ContainerEnergyStorage` 同时管能力解析（含 `DEFER_QUERY` ThreadLocal 重入保护）、
   物品扫描、能量算术、溢出夹取 —— 那个重入保护是「在跟能力系统对抗」的味道。
5. **可观测性盲区比没有工具更危险**：PerfMetrics 只插桩 `processContext`，外部 mod 直调能力接口
   的路径不可见 —— 98.79% 的热路径长期隐身，且自测给出「只占 3%」的**虚假信心**。
