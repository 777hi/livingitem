# 2026-09-20 工作日志

## 容器规则配置：增量语义 + 开发期导出通道 + IronChests 数据勘误

### 起因
用户报「模组打包后没有 container_rules.json」。实际 jar 里**有**该文件；
真问题是 `assets/living_item/container_rules.json` 里 7 条 IronChests 规则**全是错的**。

### 勘误（真值取自 `libs/ironchest-1.21-neoforge-16.0.7.jar` 字节码 `IronChestsTypes.<clinit>`）

- 命名空间是 **`ironchest`**（不带 s，`IronChestsItems.MODID`），旧数据全写成 `ironchests:` ⇒ 7 条规则从未生效。
- 尺寸真值（`size, rowLength`）：IRON 54/9、COPPER 45/9、GOLD 81/9、DIAMOND 108/12、CRYSTAL 108/12、OBSIDIAN 108/12、DIRT 1/1。
  旧数据 45/36/54/63/72 **全部编造**，且 `silver_chest` **该模组不存在**。
- 陷阱箱 `trapped_*` 是独立方块实体，槽位与普通版一致，已补全 7 条。

### 关键洞察：玩家注册反而比手写数据准

`registerTargetContainer` 用 `BuiltInRegistries.BLOCK_ENTITY_TYPE.getKey()` 自动检测 ID，
拿到的是真实注册名 ⇒ 玩家注册的 `ironchest:crystal_chest` 108/12 **三个字段全对**。
**"玩家注册的条目是否是错的"不能靠直觉判断，必须去 jar 字节码核实真值。**

### 机制改动（用户目标：玩家注册的正确条目能随模组打包）

jar 内文件运行时**不可写**（classpath 只读），"自动进包"物理上不存在 ⇒ 建立**开发期导出通道**：

```
/livingitem container register <columns>   ← 对着真容器注册
   ↓ save()
config/living_item/container_rules.json    ← 只含玩家增量（不再全量回写）
   ↓ /livingitem container export
config/living_item/exported_rules.json     ← 与 assets 资源完全同格式
   ↓ 手工合并
src/main/resources/assets/.../container_rules.json → 重新打包
```

- `ContainerRuleConfig`：新增 `BUNDLED_IDS`（加载内置资源时登记）、`isUserRule()`、
  `getUserRules()`、`exportBundledFormat()`、`getExportFile()`；
  **`save()` 改为只写增量**（此前写 `getAllRules()` 全量，导致 config 变成冻结的旧快照——
  那些拷贝永远因"内置优先"而不生效，纯噪声）。
- 导出用 `LinkedHashMap` + 按 ID 排序，保证结果稳定可比对。
- `LivingItemContainerCommand`：新增 `export` 子指令（指令树已补文档）。
- lang 新增 3 键：`export_done` / `export_empty` / `export_failed`（zh + en 各 3 条）。

## 第二轮：覆盖/删除持久化（同日追加）

### 修掉自己上一轮引入的 bug

改成"只写增量"后，**`remove` 内置规则会静默失效**：内置规则从内存移除，但
`load()` 每次都先读内置资源 ⇒ 下次启动**被复活**。这是增量改造的直接副作用。

### 最终模型（三分状态）

| 静态集 | 含义 |
|--------|------|
| `BUNDLED_IDS` | 内置资源里出现过的 ID（与是否被覆盖无关） |
| `USER_RULES` | 玩家注册/覆盖的规则（落盘 + 可导出） |
| `REMOVED_IDS` | 玩家显式删除的内置 ID（落盘，**不可导出**） |

- `load()` 顺序：`resetState()` → 内置资源 → 应用 `removed` → 应用 `rules`（覆盖/新增）。
- **`load()` 必须幂等**：加了 `resetState()`（清 `RULES`/三个静态集）。此前不清空 ⇒
  「先覆盖再删除」这类操作在 reload 后状态错乱。配套 `ContainerCompatibilityConfig.clearAllRules()`。
- `addAndSave` 返回 `boolean overwrote`；`removeAndSave` 对内置 ID 记入 `REMOVED_IDS`。
- `register` **放开为允许覆盖**（此前 `findRule().isPresent()` 直接拒绝 ⇒ 玩家无法修正错误内置数据）。
- `inspect`/`list` 显示来源：内置 / `*`玩家覆盖 / `+`玩家注册。
- `export` **不导出 removed**：删除是本地偏好，不构成对内置资源的修改。

### 踩坑：测试 JVM 静态状态污染（花了 3 轮才定位）

- 现象：新测试 4/7 失败，日志全打 `Loaded 0 container rules from bundled`。
- **第一个假设是错的**（以为测试 classpath 读不到资源）→ 写探针测试实测：
  `getResourceAsStream` 三种方式**全部可读**（2342 字节，`TransformingClassLoader`）。
- 真因：`ContainerCompatibilityConfig.RULES` 是**静态**的，Gradle 同一 JVM 跑完
  `ContainerCompatibilityConfigTest` 后 `minecraft:chest` 已在表里 ⇒ `loadFromResource`
  的 `findRule().isPresent() → continue` ⇒ `loaded=0`。
- **教训：Minecraft 模组测试里凡是静态注册表，测试间必须显式重置**；
  诊断时**先写探针验证假设，别凭直觉改代码**（差点误改 `loadFromResource` 的逻辑）。
- 探针确认后立刻删除 `ResourceProbeTest`，不留在仓库。

## 第三轮：导出改全量快照 + 社区贡献流程（文件级覆盖）

### 用户诉求（关键澄清）

> 「其他玩家手动兼容的其它模组的配置文件，也可以发送给我，我合并进模组的配置文件里并打包。」

用户明确：**要的是「文件」的复制粘贴，不是「条目」的复制粘贴** ⇒ 导出的产物必须能
**直接整文件覆盖** `assets/living_item/container_rules.json`，作者不做逐条摘录、不写合并脚本。

### 机制改动

- **`exportBundledFormat()` 改为导出全量生效规则**（此前只导玩家差异）：
  直接对 `ContainerCompatibilityConfig.getAllRules()` 取快照（内置 + 玩家新增 − 玩家删除），
  按 ID 排序。⇒ 产物**已含作者原有内置条目**，覆盖不会丢数据。这是"文件级粘贴"成立的前提。
  导出 `version=1`（与内置资源一致）、**不含 `removed`**（删除是本地偏好）。
- 新增 `countBundled()` / `countUser()`；启动日志与 `export` 反馈都带来源构成
  （`{} effective ({} bundled + {} community, {} bundled rule(s) removed)`）。
- **冲突检测（先到先得 + WARN）**：`loadFromResource()` 遇同 ID 重复时保留先出现的一条并告警；
  玩家配置文件内部重复也告警。`differs(existing, entry)` **只比 `containerSize`/`columns`** ——
  描述措辞不同**不算**冲突（否则合并多份社区贡献会被假冲突淹没）。
- 用户决策：**直接覆盖单文件**（不做收集目录）、**先到先得 + 警告**、**导出全量生效规则**。

### ⚠️ 修掉一个真 bug：跨平台编码

- 现象：测试 `MalformedInputException: Input length = 1`。
- 真因：`save()`/`export` 用 `FileWriter`/`FileReader`（**平台默认编码**，中文 Windows = **GBK**），
  而测试用 `Files.readString`（严格 UTF-8）⇒ 含中文描述"原版箱子"的文件读不了。
- **后果不止于测试**：玩家（GBK）发给作者（UTF-8）的贡献文件会直接乱码 ⇒ 流程走不通。
- 修复：三处文件 IO 全部显式 `StandardCharsets.UTF_8`
  （`OutputStreamWriter(FileOutputStream, UTF_8)` / `InputStreamReader(FileInputStream, UTF_8)`），
  测试读取也指定 UTF-8。**跨平台交换文件必须锁定编码，不能依赖平台默认。**

## 第四轮：社区闭环可测化（同日追加）

### 动机

前三轮的「文件级覆盖」全靠推理——没有测试守着「玩家导出的快照当真能被当作内置资源加载」。
这是整条链路的关键假设，值得用真实代码验证。

### 改动

- **抽出可测性接缝**：把 `loadFromResource` 的核心解析抽成包级
  **`loadRules(Reader, source, label)`**，原方法降为薄壳。收益：
  ① 作者「覆盖加载」与内置资源加载**共用同一套解析 + 冲突检测**（避免两条路径行为漂移）；
  ② 测试可直接喂 JSON 字符串/Reader，**无需替换 classpath 资源**。
- 新增 2 条闭环守卫：
  - `exportedSnapshot_isLoadableAsBundledResource`：导出 → `resetState()` → 用快照重新加载
    ⇒ 断言规则总数一条不少、内置条目仍在、玩家修正与新增都在。
  - `mergeConflict_keepsFirstAndWarns`：同 ID 两条不同数值 ⇒ 注册数 2（而非 4），保留先出现的一条；
    仅描述不同的两条**不**视为冲突。
