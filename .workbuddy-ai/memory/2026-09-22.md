## 修复：活TNT 爆炸后光照不刷新（用户报告）

### 症状与根因

用户：「**活tnt爆炸后光照没有刷新喵。所有方块都黑黑的喵。**」

根因（读 `libs/src/neoforge-21.1.249-merged` 源码确认，**不是凭记忆**）：
- `NORMAL` 走 `level.setBlock()` → 最终进 `LevelChunk.setBlockState()`，
  **原版把光照更新写在那里**（`LevelChunk.java:258~270`）：
  * section 由非空变空 → `lightEngine.updateSectionStatus(pos, hasOnlyAir)`
  * `LightEngine.hasDifferentLightProperties(...)` 为真 → `lightEngine.checkBlock(pos)`
- `HIGH_YIELD` / `SUPER` 为性能**直接调 `LevelChunkSection.setBlockState()`** ⇒ **绕过**上面那层
  ⇒ 光照引擎完全不知道方块没了：`ChunkSkyLightSources`（天光柱高图）仍认为地下被堵死、
  光数据仍是炸之前的值 ⇒ `ClientboundLevelChunkWithLightPacket` 发出去的是**旧光照**。
- 代码里原本的注释其实已经写明「不触发任何回调/**光照更新**/客户端同步」——
  但没人把"光照更新"这半边补回来。

### 关键：先查源码再动手（本轮的主要方法论）

查清了三件事才写代码，避免又一次"凭推理下结论"：
1. **正确的重算入口**（`LevelLightEngine` 公开方法）：
   `updateSectionStatus` / `propagateLightSources` / `checkBlock`。
   原版 `ThreadedLevelLightEngine.initializeLight()` 与 `lightChunk()` 就是这套组合。
2. **天光柱高图是独立缓存**，不会自动跟随方块变化 ⇒ 必须 `chunk.initializeLightSources()`
   （= `ChunkSkyLightSources.fillFrom(chunk)`）**先重建**。
   `ChunkStatusTasks:163` 在区块加载的 INITIALIZE_LIGHT 阶段调的就是它。
3. **同步给客户端的机制是自动的**：`LayerLightSectionStorage.swapSectionMap`
   → `chunkSource.onLightUpdate` → `ChunkHolder.sectionLightChanged` → `broadcastChanges`
   发 `ClientboundLightUpdatePacket`。所以**不需要**自己造光照包。
   ⚠️ 而且 `ThreadedLevelLightEngine` 上这几个入口是**入队**（`lightTasks`）而非同步执行 ⇒
   我们紧跟着发的 `notifyChunkClients` 里那份光照**当帧仍是旧的**，下一 tick 被覆盖。

### 改动

### 问题一：`affects()` 判据错（**已修，单点根因**）

`ExplosionParams.affects(ChunkPos)` 用的是「**区块中心**到爆心距离 ≤ radius」，
但区块是 **16×16** —— "中心在半径外、边缘却落在球内"的区块大量存在
（区块中心最远可比最近角远约 11 格）。这些区块在 **`schedule()` 建档时就被标记成"已完成"**、
**永不处理** ⇒ **整块地形留着 ⇒ 坑不圆**。

该判据在**三处**生效（建档标记 / `flush` 跳过 / `remainingChunks()`）⇒ 单点根因。

**修法**：改为「**区块 AABB ∩ 球体**」——取区块 AABB 上离爆心最近的点算距离。
只判水平方向即可（区块是贯穿世界高度的柱体）。

⚠️ **它被测试钉住了**：`ExplosionParamsTest.affects_matchesLegacyCriterion` 用例名写着
"与旧 `scheduleSuperExplosion` 同口径"，注释还解释"保持这条判据不动是为了不改变既有行为"。
⇒ **错误行为被测试保护了起来**，这是它长期没被发现的原因。
已改为 `affects_isChunkAabbIntersectingSphere` + 边界回归
`affects_rimChunkWithCenterOutside_isAffected`（**用例内先断言"中心确实在半径外"作为前提**）。
账本侧同步：`ExplosionLedgerTest` 里 `5→9` / `5→9` / `4→8`，并新增
`schedule_marksTrulyOutOfCircleAsDone`（半径 1 → 3×3 里只有中心 1 格，其余 8 格建档即完成）。
`flush_isBudgeted_remainderCarriedOver` 原假设"两轮炸完"不成立（受影响数 49→69），
改为**推进到收敛**（别写死轮数）。

> **教训**：**把"既有行为"当规格钉住之前，先确认既有行为是对的。**

### 机制（已核实源码）

```
notifyChunkClients → ClientboundLevelChunkWithLightPacket
  └─ 客户端 handleLevelChunkWithLight
       ├─ updateLevelChunk → replaceWithPacketData   // 方块**数据**立刻正确
       └─ queueLightUpdate → enableChunkLight
            └─ 对**每个 section** 调 setSectionDirtyWithNeighbors(x, y, z)
                 // 每次 = 标记 3×3×3 = 27 个 section 需重建
```
一次大当量爆炸改动**上万个 section** ⇒ 重建队列要慢慢排，没轮到的仍画旧几何，排完即恢复。
（所以"挖下去是空气、能走进去"——数据是对的。）

**为什么不改用逐方块包**：`ClientboundSectionBlocksUpdatePacket` 只标记改动的那一个 section（无 27 倍放大），
但半径 235 要改几千万个方块，逐方块发包体积不可接受 ⇒ 只能整区块打包，代价就是重建风暴。

## 🔍 调研：活水车的渲染机制（2026-09-22 19:50）

用户问「看看活水车的渲染」。**机制由三部分协作**：

### 1. `GenericLivingItemOverrides.resolve()`（注册在 `LivingIconRegistry:212`）
```java
if (spec.isRotating()) {
    // 读活水车 netStress -> 算 rpm -> 写进 ThreadLocal
    WaterWheelRenderState.setRPM(rpm);
    return getOrCreateRotatingModel(stack);   // ← 提前返回，不走变体路径
}
```
`rpm = signum(netStress) * ModCreate.BASE_RPM`，应力为 0 则 rpm = 0。

### 2. `RotatingWaterWheelModel implements BakedModel`（包装器）
- 构造时**包住 `vanillaModel`**（物品自己的模型）
- 只改写 `applyTransform()`：在 `GUI / GROUND / FIXED` 上下文按 `WaterWheelRenderState.getRpm()` 加 X 轴旋转
- **其余方法全部委托给 baseModel** —— 包括 `isCustomRenderer()`（**这个委托很关键**）

### 3. `ItemRendererWaterWheelMixin`（`@Mixin(ItemRenderer.class)`）
- `@Inject HEAD/RETURN` 捕获当前渲染的 ItemStack + 恢复光照
- `@Redirect` 掉 `ClientHooks.handleCameraTransforms`：
  条件是「Create 已加载 + 物品是 `create:water_wheel` + 是活物品 + GUI/GROUND/FIXED」
  ⇒ `setShaderLights` 设正面光照 → 按 rpm 旋转 Z 轴 → `rotateX(90°)` → 缩放 0.625

### ⭐⭐ 最有价值的发现：变体路径指向的模型**根本不存在**

注册写的是 `.addVariant("base", "item/water_wheel", ...)`，
但 **`models/item/water_wheel.json` 并不存在**（实测 `ls` 报 not found）。
它照样工作 —— 因为 `isRotating()` 分支**提前 return 了包装器**，压根不走变体路径。

⇒ **这证明模组可以在「完全不提供自己的模型/纹理」的前提下工作**：
直接复用物品自身的模型（水车复用的是 Create 的模型）。
**水车没有自己的任何纹理资源。**

### ⇒ 对箱子的方案启示

箱子/末影箱现状（`LivingIconRegistry:81 / :175`）：
```java
register(LivingIconSpec.builder(Items.CHEST)
    .addVariant("base", "item/chest", stack -> true).build());   // → models/item/chest.json
register(LivingIconSpec.builder(Items.ENDER_CHEST)
    .addVariant("base", "item/ender", stack -> true).build());
```
两个模型都是 `parent: minecraft:item/generated` + 自绘图标 ——
**把原版的 `builtin/entity`（3D 方块实体渲染）替换成了平面图标**。

**建议方案**：让箱子/末影箱**不做图标覆盖** ⇒ 恢复原版 `builtin/entity` 的 3D 箱子渲染
⇒ `chest.png` / `ender.png` 可删，且自动跟随材质包。
若要标识「活」状态 ⇒ 用 **decorator 叠加层**（与漏斗箭头 / 雕文箭头 / 地图图标同一套机制）。

**⚠️ 待游戏内验证的未知**：`builtin/entity` 的模型是 `BuiltinModel`，
其 `getOverrides()` 返回 `ItemOverrides.EMPTY` ⇒ **模组的 override 可能根本不会被调用**。
这很可能就是当初改用平面图标的原因。
⇒ 要恢复 3D 箱子，**必须完全不注册 chest / ender_chest 的图标**（而不是让 resolve 返回 vanillaModel）。
**这一步必须游戏内验证，不能静态推断。**

## 🔍 最终审计：剩余 17 张纹理与原版全库交叉比对（2026-09-22 19:50）

**方法**：把剩余 17 张**逐张**与**全部 3070 张**原版纹理比对（不再只比同名纹理）。
判据分三级：① 字节相同 ② 像素相同 ③ alpha 掩码相同 + 色差小（疑似改色）。

**结果**：

|---|---|
