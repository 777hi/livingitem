## 活箱子：配方书材料识别修复（RecipeBookComponentMixin）

**现象**：打开配方书（默认停原版合成标签页）时，活箱子里的材料不被计入，
能合成的配方显示"不可合成"；切一次活箱子标签页再切回来才恢复。

**根因（关键）**：原版 `RecipeBookComponent` 重建 `stackedContents` 有**且仅有两条**路径：
- `initVisuals()` —— 打开配方书 / 切换可见性时调用
- `updateStackedContents()` —— 背包变动计数变化 / 点击槽位时调用

原有 Mixin 只注入了后者（`INVOKE updateCollections(Z)V`），所以"刚打开配方书"
走的是 `initVisuals()`，材料表里没有活箱子物品。所谓"切一下标签页就好了"其实是
任何触发 `updateStackedContents()` 的操作导致的，和活箱子标签页本身无关。

**修复**：
1. 新增 `beforeInitVisualsCollections`，同样注入 `initVisuals` 的 `updateCollections(Z)V`
2. 抽出公共 helper `accountLivingChestItems()` 两条路径复用
3. 新增 `onTickHead`：每 10 tick 用 `ItemContainerContents.hashCode()`（构造时预计算，
   O(1)）采样活箱子指纹；变化则把 `@Shadow timesInventoryChanged` 置为 `Integer.MIN_VALUE`，
   **借原版 tick() 自己的判定**触发刷新 —— 不复制原版清表逻辑，不绕过原版流程。
4. `initVisuals` 时 `chestFingerprintValid = false`，避免重开界面多刷新一次

**其它确认**：
- 服务端 `ServerPlaceRecipe.recipeClicked` 的 `fillStackedContents` 在
  `testClearGrid() || isCreative()` 内无条件执行，Mixin 注入在它 AFTER，无同类隐患。
- 用户选择：默认标签**保持原版行为**（不默认进活箱子页），要**外部改动自动刷新**。

**文档**：`docs/tech/living-chest-tech.md` 第 5 节重写（5.1 双路径注入 / 5.2 自动刷新 /
5.3 服务端 / 5.4 标签页），第 8.3 条新增修复记录与验证清单。

## 活箱子标签页每帧开销：实测结论 = 不需要优化

上一轮我顺口提了"每帧 copy 27 槽可能有开销"，用户追问是否真需要优化。实测后**结论是否定的**，
我那句提醒过度了。记录结论避免重复提议。

**实测方法**：把 `PinyinHelper`（纯字符串逻辑，只依赖 `java.util.Locale`）单独拷出来用 JDK17
跑 micro-benchmark，复刻 `matchesSearchText` 的判定顺序，JIT 预热后取 201 次中位数。
注意 javac 在中文 Windows 默认 GBK，必须加 `-encoding UTF-8`。

**实测数据（60 FPS 帧预算 16.67 ms = 16670 μs）**：
| 物品数 | 每帧开销 | 占帧预算 |
|---|---|---|
| 20 | 1.7–2.9 μs | 0.01% |
| 100 | 8.5–14.8 μs | 0.05–0.09% |
| 300 | 26–35 μs | 0.16–0.21% |
| 972（背包 36 槽全满的理论上限，线性外推）| ≈85 μs | ≈0.5% |

**关键事实（推翻我原先的猜测）**：
- `ItemStack.copy()` 对空槽**直接返回 EMPTY 常量**，零分配。开销正比于**非空槽数**，不是 27。
- `PatchedDataComponentMap.copy()` 是**浅拷贝**（共享 prototype/patch，只置 copyOnWrite），
  所以非空槽的 copy 也只是分配一个对象头。
- `toPinyin` 62 ns/次、`toPinyinInitials` 40 ns/次；`isPinyinMatch` 全路径 121 ns/次 ≈ 2 次转换
  （`hybridMatch` 只在**中英混合**输入时才触发拼音转换，纯拉丁/纯中文都短路）。
- 这些开销**只在活箱子标签页激活时**才发生，默认打开是合成页，根本不触发。

**为什么不该加缓存**：活箱子内容会被服务端异步改写（漏斗、网络包、其他活物品），
缓存 invalidation 时机极难做对 —— 今天刚修的 `initVisuals` vs `updateStackedContents`
就是活生生的例子。用 <1% 的帧预算换一整类"显示不刷新"的 bug，不划算。
**当前代码无状态（每次重读）正是它正确的原因。**

**如果将来真需要优化，正确顺序（前两条无风险、不引入状态）**：
1. 只 copy 当前页需要的 20 个物品（现在收集全部 N 个只为显示 20 个）
2. `hybridMatch` 重复调用 `toPinyin`/`toPinyinInitials`，复用 `isPinyinMatch` 已算好的结果
3. 给 `toPinyin` 加「物品名 → 拼音」小缓存（纯函数，作用域极小，这个才安全）

## 补充：两个标签页的刷新链路（修正我对指纹检测作用的认知）

用户追问"合成标签和活箱子标签是不是都实时变动"。查证后：

| | 活箱子标签页 | 合成标签页 |
|---|---|---|
| 机制 | 每帧渲染时 `collectLivingChestItems()` 重读，无缓存 | 事件驱动，重建材料表 + `updateCollections` |
| 延迟 | 0（当帧生效） | 1–3 tick（原版同步链路）～ ≤10 tick（指纹保底） |

**关键查证：原版同步链路本来就是通的**（不要以为指纹检测是主力）：
- `AbstractContainerMenu.triggerSlotListeners()` 用 `ItemStack.matches(lastStack, stack)` 判定
- `ItemStackMixin` **只改了 `isSameItemSameComponents` 和 `getTooltipImage`，没动 `matches`**
- 所以活箱子 CONTAINER 变化 → `matches` 为 false → `slotChanged` → 发包 →
  客户端 `Slot.set` → `Inventory.setItem` → `timesChanged++` → 客户端 tick 检测到 → 刷新
- 延迟约 1–3 tick，**比我的 10 tick 指纹检测更快**

**结论：指纹检测在主流场景下是冗余的纯保底**，只覆盖"内容变了但背包计数没递增"的非主流路径。
成本 O(1)/10tick，留着无害，但别把它当主力机制 —— 未来排查刷新问题应优先查原版链路。

**边界**：只有在**当前打开菜单的槽位里**的活箱子才会被服务端同步（`broadcastChanges` 只遍历 menu slots）。
活箱子放在地上箱子里、玩家开着背包时不会被同步。但配方书只扫玩家背包，所以不影响合成，
只影响 tooltip 显示旧数据。

## 指纹检测已移除（用户要求：代码还是简单点好）

用户认可"原版链路已覆盖"的论证，要求删掉 10 tick 指纹检测。已移除并编译通过：

- `@Shadow timesInventoryChanged` 字段
- `FINGERPRINT_CHECK_INTERVAL` / `FORCE_REFRESH_SENTINEL` 两个常量
- `lastChestFingerprint` / `chestFingerprintValid` / `fingerprintTickCounter` 三个状态字段
- `onTickHead`（`tick` HEAD 注入）与 `computeLivingChestFingerprint()`
- `onInitVisuals` 里的两行指纹重置、`DataComponents` / `ItemContainerContents` 两个 import

**最终改动净结果：+2 个注入点、+0 个状态字段。**（只保留 `beforeInitVisualsCollections`
和 `accountLivingChestItems`，以及原有的 `beforeUpdateCollections`）

文档同步：`living-chest-tech.md` 的 5.2 从「自动刷新方案」改写为「为什么不需要额外刷新机制」
（含完整原版链路 + 两个前提 + 一条"曾实现过但已移除"的注记），8.3 修复记录删掉第 3 点、
验证清单的 ≈0.5 秒改为 1–3 tick。

应该先查清原版链路是否已经覆盖，再决定动手。
