## LivingWaxedCopperTooltipRenderer 像素对齐审查

把 tooltip 截图下采样到 native 172×112 后逐像素扫描(`classify` 把 BG/黄/青/橙/灰归类,逐坐标打印),发现 4 处像素级未对齐:

### 1. 外圈黄色解锁度弧上下/左右不对称(最严重)

drawArc 把 2x2 块放在 2πr/227 步上,圆心是 `(px+0.5, py+0.5)` 而不是 `(px, py)`。

| 位置 | y | x 范围 | 总宽度 |
|---|---|---|---|
| 12 点正上方 | 4 | 35..48 | 14 |
| 12 点正上方 +1 | 5 | 31..52 | 22 |
| 12 点最远延伸 | 11 | 20..22 + 61..63 | 44 |
| 6 点正下方 | 77 | 36..47 | 12 |
| 6 点正下方 +1 | 76 | 32..51 | 20 |
| 6 点最远延伸 | 72 | 22..26 + 57..61 | 40 |

注意顶部 y=11 延到 x=20..63(总宽 44),底部 y=72 只到 x=22..61(总宽 40)——**顶部比底部每边多出 2 像素**,整体看上去"上宽下窄"。

根因:`drawArc` 的 `dotRadius=1` 实际只画 2×2 块而不是 3×3 块
```java
g.fill(px - dotRadius + 1, py - dotRadius + 1, px + dotRadius + 1, py + dotRadius + 1, color);
```
dotRadius=1 时填 `(px..px+1, py..py+1)`,块中心偏移 +0.5 → 顶部块落在 r-0.5(内圈),底部块落在 r+0.5(外圈)。修复:`g.fill(px - dotRadius, py - dotRadius, px + dotRadius + 1, py + dotRadius + 1, color)`(去掉左边那个 +1)。

### 2. φ=0 标记点在 n==P 时被亮青环截掉下半

代码意图:`fill(cx-1, cy-WHEEL_RING_R-1, cx+2, cy-WHEEL_RING_R+2, LABEL_COLOR)` = 3×3 灰块 (40..42, 8..10)。
实际显示:
- y=8 r=32 全灰 ✓
- y=9 r=31 与 cyan 重叠 → 灰
- y=10 r=30 被 `SPOKE_RING_FULL_COLOR`(亮青)覆盖 → C

视觉上 φ=0 标记只剩 2 行(像贴着内环上半),中心感失衡。当 n<P 时 SPOKE_RING_FILL 不触发,标记完整;触发条件是 `phaseCount >= period`,当前截图正好满足 (n=P=16)。

修复思路(选一):把标记上移一格 (`cy-WHEEL_RING_R` 而不是 `-1`)让它整体落在 r=32;或者把它从 12 点改到外圈(比如 r=37 与黄圈相邻)。

### 3. 下方相位展开条柱间间隙不均(明显)

| 柱 0..3 间距 | 1 px | 5,15,25,35 |
| 柱 3-4 间距 | **2 px** | 44..45,bar4 落在 x=46 |
| 柱 4-15 间距 | 1 px | 56,66,...,157 |
| 柱 11-12 间距 | **2 px** | 125..126,bar12 落在 x=127 |

根因:Java `Math.round(0.5)` 向上取整。`P=16` 时:
- bx(k) = 5 + round(k × 10.125),barW = 9
- k=4: round(40.5)=41 → bx=46(理论上 bx=45 就够了,跳了一格)
- k=12: round(121.5)=122 → bx=127(理论上 bx=126,跳了一格)
- 同时 bx(5)=56 但 bx(4)=46 跳了 10 又跳回来,bar5 跑到 56..65 实际宽度变成 10px

修法选项:
A. 改用 `floor` + 居中:`bx = left + (int)(k * slotW);` 配合 `barW = (int)slotW;`(注意要再减 1 让出间隙)
B. `barW = (int)((slotW-1)*1)` 之类强制 barW 始终比 slotW 小 1
C. 用 `int((k+0.5)*slotW)` 居中放置

### 4. 中心橙色毂上下分布略偏(小)

r=6..10 各半径的橙色像素计数:r6=10, r7=106, r8=177, r9=99, r10=9。
顶部(0°-44°)r=7 通常带橙色,r=9 不带;底部(198°-352°)r=7 通常空(r=8/r=9 带)。
同样是 drawArc dotRadius off-by-one 的副作用,因为中心毂也用 dotRadius=1。修了问题 1 顺手就解。

## 修复实施(同日下午)

写了离线模拟器 `tools/_sim_tooltip.py` 复现全部像素图元(`fill`/`drawRing`/`drawArc`/`drawLine`),
支持 `--old` 复现修复前行为、`--oldpalette` 复现旧配色,改完 Java 先跑它验证再编译。

### 四处修复

1. **drawArc dotRadius off-by-one**:`fill(px-dotRadius+1, ...)` → `fill(px-dotRadius, px+dotRadius+1)`。
   dotRadius=1 从 2×2 变回 3×3,块心回到 (px, py)。
2. **drawArc 步数取偶数**:`ceil(2πr)` → `2*ceil(πr)`。r=36 时 227(奇)→228(偶),
   i=0/57/114/171 精确落在 12/3/6/9 点。这是「上下各差 2px」的真凶,**比 dotRadius 影响更大**。
3. **新增 symRound**:`Math.round` 对 .5 朝 +∞(round(3.5)=4 / round(-3.5)=-3),镜像点会各偏同侧。
   `v>=0 ? round(v) : -round(-v)`。drawArc 与辐条端点都改用它。
4. **展开条整数槽宽**:`slotW=max(1,STEM_W/period)`,`barW=slotW-1`,
   `usedW=min(slotW*period,STEM_W)`,`originX=left+(STEM_W-usedW)/2` 居中。
5. **φ=0 标记移到 renderWheel 末尾画**(原来在辐条之前,底行会被 SPOKE_RING_FULL 回填覆盖)。

### 中心毂调细(用户反馈「橙色毂有些粗」)

## Spark 性能报告分析（docs/problem.md，2026-09-10 晚）

环境：1.21.1 NeoForge + 100+ mod，堆 3.4/3.9 GB（88%），TPS 1m=5.91 / 5m=13.54 / 15m=17.26，
MSPT min 6.34 / med 11.6 / 95%ile 16.2 / max 1370，进程 CPU 5.87%、系统 31%。

### 判读结论（方法论，可复用）
- **med MSPT 11.6ms（满速阈值 50ms）+ 95%ile 16.2 → 常态完全不慢**；
  TPS 5.91 要求平均 tick ≈169ms，与 MSPT 分布不自洽 → 缺失时间**不在** MSPT 分布里。
- 采样 profiler 在 STW GC 期间采样线程一起停 → **GC 停顿在火焰图里完全不可见，但真实吃掉 TPS**。
- 判据组合：低进程 CPU + 高系统 CPU + 堆占用逼近上限 + 极低 med MSPT + 超大 max MSPT ⇒ **GC/内存停顿，不是算法慢**。
- **Spark Mods View 会重复计数**：嵌套调用的样本在父子 mod 名下各算一次。
  living_item 14.93% 与 fluxnetworks 3.63% 有约 3.6% 是同一批样本，不能相加；neoforge 22.91% 里
  也含 living_item 的 10.98%。真实：onServerTick 11.03% + receiveEnergy 3.64% ≈ 14.7%。

### 定位到的代码问题（未修改，仅分析）
1. `ContainerLivingItemHandler:659 scanAndGroupLivingItems`（3.70%）—— 每 tick 全量扫全部槽位；
   `isLivingItem` 被调两次（第 664 行 + `getApplicableFunctions` 内部 `LivingItemManager:264`）；
   每 tick 新建 LinkedHashMap/ArrayList/SlotEntry；`getApplicableFunctions` 返回
   `Collections.unmodifiableList` → 每次迭代分配 `UnmodifiableCollection$1`（报告里 0.18% hasNext）。
2. `syncContentRevision`（0.64%）—— 与 scan 是**同一份数据的第二遍全量遍历**，可合并。
3. `LivingItem:295 processLevelContainers`（self ≈2.25%）—— 第 318 行每 chunk 每 tick
   `new ArrayList<>(chunk.getBlockEntities().values())` 拷贝全部 BE；第 325 行每 BE 每 tick
   `level.getCapability(ItemHandler.BLOCK, pos, null)`；`SimpleContainerContext:107 buildContainerKey`
   每 tick 用 StringBuilder 拼 key 字符串；`ContainerLivingItemHandler:103 cacheKey` 每 tick 每容器
   被调用 5~8 次、每次再拼一次 `dim + "|" + key`。
4. `ContainerEnergyStorage.receive`（3.64%，flux 反向触发）—— **第 205 行 `while (leftover > 0)`
   里嵌 `for (i=0..slots)`，leftover 上限 63 ⇒ 最坏 63 × slots 次 getStackInSlot**，
   即报告里 `SidedInvWrapper.getStackInSlot → NonNullList.get` 的 2.97%。
   另有 `resolveItems` 每次重查能力、`resolveProvider` 每次 new 实例、`getEnergyStored`/`getMaxEnergyStored`
   各全量扫一遍、`isBulb` 对非灯物品也走 DataComponent 查找。
5. `Entity.getCapability`（1.42%）—— `ContainerLivingItemHandler:359` 每玩家每 tick 查 ItemHandler.ENTITY。
6. **Bug：`incrementCleanup()` 在 `processContext` 里调用（:481），CLEANUP_INTERVAL=1200 数的是「容器数」
   不是「tick 数」** ⇒ 每 tick N 个容器时每 1200/N tick 就跑一次三遍全表 `removeIf`。应从 onServerTick 计数。
7. **Bug：`LivingItem:349` `elapsedMs > 10` 就打 PERF 日志** —— TPS 崩时几乎每 tick 一条 + 参数装箱，需节流。

### ⚠️ 重要修正：上一节的 GC 诊断是错的（docs/latest.log 实证）

拿到 `docs/latest.log` 后推翻了基于 problem.md 的判断。**根因是「单人世界 ESC 暂停」，不是 GC。**

证据链：
1. 日志里 `IntegratedServer` + 5 次 `Saving and pausing game`（22:33:39 / 22:34:05 / 22:36:03 / 22:36:07 / 22:42:03）。
   两次巨型 `Can't keep up`（**24689ms、20868ms**）都紧跟在 `Saving and pausing game...` 之后 20ms 内 ——
   **是暂停恢复时的假警报**。21:58:06 的 2216ms 是 JEI 启动（"Starting JEI took 3.053 seconds"）。
2. spark profiler 22:35:59 启动，正好跨越暂停期 → 采样严重失真。
3. 22:41:54 实时读数：**TPS 5s=20.0, 10s=20.0（满速）**，tick 10s = 10.5/14.8/20.0/28.1（健康）；
   只有 1m=2.15 是被暂停污染。1m 窗口 60 秒里约 54 秒游戏是暂停的（2.15×60=129 tick ≈ 5~6 秒运行）。
4. PerfMetrics 精确自测（每个 60s 窗口）：`calls≈98400, avg≈20us, P99≈200us, over5.00ms=0~3`。
   98400/60s ÷ 82 容器每 tick = **1200 tick/60s = 满速 20 TPS**。
   living_item 真实开销 = 98400 × 20us = **1.97s/60s ≈ 3.3%**，不是 spark 说的 14.93%。

**教训（判读 spark 报告前必查）**：
- **先确认是不是 IntegratedServer**，再查日志里有没有 `Saving and pausing game`。
  单人世界的 1m/5m TPS 会被 ESC 暂停严重污染，只有 5s/10s 读数可信。
- `Can't keep up! Running NNNNms` 若紧跟 `Saving and pausing game` 就是假警报，直接忽略。
- **采样占比 ≠ 绝对耗时**：游戏暂停时 tick 少、采样基数小，各 mod 百分比会被同步放大，
  看起来像"某 mod 吃掉 15%"，实际可能只有 3%。
- 有自埋 PerfMetrics 时**优先信自埋数据**（精确的 wall-clock 分段），spark 只用来定位调用路径。

### 四重排除：这 23 秒不是 living_item
1. **GC**：spark 的 GC 监控开着，全程只有 0~26ms（`#489 12ms`、`#509 26ms` 等）。

### 决定性反证：追赶爆发
卡死后 #510(23:08:32) → #783(23:08:35) 跑了 **273 个 tick / 3 秒 = 12.8ms 每 tick**，

### 结论
- spark 的 52.29% 是**归因假象**：wall-clock 采样器在线程「RUNNABLE 但被内核挂起」时，
  抓到的是进入内核前最后一个 Java 栈帧。living_item 在 ServerTickEvent.Pre 里最先跑、
  每 tick 全量扫容器，所以样本集中落在它身上。**第一版的 10.98% 更接近真实。**
- living_item 真实成本（PerfMetrics 自埋，可信）：
  `92316 calls × 18.7us = 1.73s / 60s ≈ 3%`，摊到每 tick **1.4~2.3ms**，
  占服务端真实 tick 工作（11.5ms）的 **13~20%**——值得优化，但不是卡死原因。
- phase 分布（60s）：`container_data 0.88s(51%) > scan 0.39s(22%) > stress 0.28s(16%)
  > func_tick 0.16s(9%) > flush 0.02s`。
- 那 23 秒的疑似方向（无法从这两个文件定论）：阻塞在 I/O 或内存上。
  依据 **CPU(system) 33.13% 是 CPU(process) 7.62% 的 4.3 倍**（内核态主导，

## 第三次定位 + 修复（用户线索：Flux Networks 接入点 → 潜影箱 → 活涂蜡铜灯）—— 破案

用户补了决定性场景：**「只要一传输电力就会明显卡顿，不传输就没问题」**。

### ⚠️ 再次修正：上一节「这 23 秒不是 living_item」是错的

错因：**把「自埋 PerfMetrics 覆盖不到」当成了「不存在」**。
PerfMetrics 只插桩了 `processContext`，而 `ContainerEnergyStorage.receiveEnergy()` 这条路径
是**外部 mod（Flux Networks）在自己的 ServerTickEvent 里直接调的**，完全不在我们的计时区间内。
两条证据并不矛盾，是覆盖盲区。

**教训：交叉验证 spark 时，一定要看节点的绝对毫秒数，不能只看百分比。**
problem.md 第 83 行白纸黑字：

```
com.qiqi.li.living.domain.power.ContainerEnergyStorage.receiveEnergy()  98.79%  18968ms (living_item)
```

60 秒窗口独占 **19 秒**，且 98.79% 挂在 `EventHandler.onServerTick` 下面 = 确实在服务端 tick 内。
分解：`getStackInSlot()` 81.02% + `isBulb()` 14.96% + receive 自身 ~2.8%。

### 根因

`ContainerEnergyStorage.receive()` 对**同一批槽位取了 3 遍** `getStackInSlot`
（第 1 遍收集剩余容量 / 第 2 遍比例分配 / 第 3 遍 leftover 零头回收，且 leftover 是 while 外层套 for）。
每一遍都是 `SidedInvWrapper → RandomizableContainerBlockEntity.getItem → BaseContainerBlockEntity.getItem
→ NonNullList.get` 的**随机内存访问**（cache miss 主导）。
叠加堆 83%、CPU(system) 33% 是 process 7.6% 的 4.3 倍（内核态/缺页主导）→ 每次随机访问被放大到 µs 级。

### 修复（`ContainerEnergyStorage.java`）

1. **`isBulb()` 短路顺序反转**：`isWaxedBulb(Item)`（4 次引用比较，纳秒级、无内存访问）
   前置到 `isLivingItem(stack)`（DataComponentMap → `Reference2ObjectArrayMap` 线性扫描 + cache miss）之前。
   容器里绝大多数槽位不是铜灯 → 省掉几乎全部组件查询。
2. **`receive()` 单遍收集**：新增 `ItemStack[] stacks`（非铜灯槽位留 null），
   比例分配与 leftover 回收两遍改走数组 → `getStackInSlot` 从 3 遍降到 **1 遍**。
   `getCount()` 是 ItemStack 平凡 getter，不必再缓存 `counts[]`。
3. **`getWaxedBulbData()` 结果缓存为局部变量**（原来同一表达式里调了 3 次）。

`extract()` / `getEnergyStored()` / `getMaxEnergyStored()` 因为共用 `isBulb`，自动吃到第 1 条收益。

### 设计取舍（重要，别再改回去）

- **只多分配 `stacks[]` 一个数组**（原实现已有 `remaining[]`），**不引入任何跨调用状态**。
  考虑过 ThreadLocal 暂存池消除分配，但会让 `receive()` 持有跨调用状态、有重入风险 ——
  与配方书 Mixin「保持无状态才正确」的教训一致，故放弃。
- **语义逐条保持不变**：整 FE 量化、完整步进保护（`count > leftover` 跳过）、
  「宁损勿造」记账口径（声明 `accept`、实充 ≤ 记账）全部保留。
- leftover 循环**不是**病态循环：分配阶段每堆最多丢 `count−1` mFE ⇒ leftover ≤ 27×63，
  一轮就能回收完；`!progressed` 兜底 break。
