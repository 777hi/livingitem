## §1 黑曜石循环（岩浆源 + 水 ⇒ 黑曜石）

### 1.1 背景：循环链条与缺口

用户提出的假想场景（C = 接触水的那格，S = 岩浆源，离水 ≥2 格）：

```
1. 岩浆流入 C（每 30t）→ 反应先于焚毁 → C 上圆石 +1（累加）
2. 圆石攒到 64 → 反应判定「放不下」→ 岩浆留在 C → 焚毁接手：
   满组圆石属石头系 → SPAWN_SOURCE → 消耗 64 圆石、C 变成岩浆源
3. 新源 C 邻水 → 【缺口】源格反应 ⇒ 黑曜石，源湮灭
4. 黑曜石被流入 C 的岩浆焚毁（BURN）→ C 空
5. 岩浆从 S 重新流入 C → 回到 1
```

缺口只有第 3 步：**源格与流动格的产物要分开**。原版 `shouldSpreadLiquid` 就是这一个 if 的
两个分支（本格是源 ⇒ 黑曜石；流动 ⇒ 圆石），与「谁撞谁」无关。

### 1.2 定稿值

| # | 定稿 |
|---|---|
| 1 | 契约新增 default 方法 `frontierSourceReaction(FluidType neighbor)`，**默认回退** `frontierReaction(neighbor)`（⇒ 不区分源/流动的流体行为零变化） |
| 2 | 引擎 `reactFrontiers`：本格**是源** ⇒ 问 `frontierSourceReaction`；否则问 `frontierReaction` |
| 3 | 岩浆注册（流体侧）：**源 + 水 ⇒ 黑曜石**；**流动 + 水 ⇒ 圆石**。源格反应 ⇒ 源湮灭（沿用现有 `removeGeneratedSource`） |
| 4 | 黑曜石物品在岩浆格 ⇒ **`BURN`** —— 黑曜石 ∉ 石头系、无 `FIRE_RESISTANT`，走既有默认分支，**不需要特判** |
| 5 | 圆石满 64 转岩浆源（机制一 `SPAWN_SOURCE`）**保留**，作为循环的驱动环节 |
| 6 | 本次**只做蔓延路径**；倒水路径（`pour` ⇒ 黑曜石，§3.5）**另开一轮** |

### 1.3 被否掉的选项及理由

| 选项 | 否掉的理由 |
|---|---|
| B. 改签名 `frontierReaction(neighbor, boolean selfIsSource)` | 破坏性（虽然现在只有一个实现）；且 default 方法无法「默认区分」，将来每个实现都得显式处理 boolean ⇒ 把「不区分」这个最简语义搞没了 |
| C. 上 JSON 反应表（§3.5 提过「两条路径共用一张表」） | 当前只有**一条规则、一个流体对**，表是过度设计（对齐 §6「不为假想需求扩接缝」先例）。**等 `pour` 路径也需要黑曜石时才出现真实需求**，那时再抽表共用 |
| 黑曜石 `SURVIVE` | 会**停摆**：黑曜石占着格 ⇒ 产物放不下 ⇒ 岩浆不再反应 ⇒ 装置产出第一个黑曜石后就不动了（除非玩家取走）。而 `BURN` 让循环闭合 |
| 圆石满 64 停产（不转源） | 循环不成立，圆石堆到 64 就静止 |

### 1.4 待决项

- **D1 黑曜石存活窗口**：黑曜石存活 = 岩浆流入该格的节拍（**30t ≈ 1.5s**）。想拿黑曜石必须
  抢在这 1.5s 内抽走（手快 or 漏斗），否则变回圆石循环。**是否够用属实测项**，不预先调参。
- **D2 DOWN 特例**：原版流动岩浆向下遇水 ⇒ 石头（`LavaFluid.spreadTo`）—— 2D 网格无 DOWN，不映射（不变）。
- **D3 `pushItems` 干扰**：产物格在反应后无流体，理论上不会被推（每 4 tick 的推动只作用于流内格），
  **待实测确认**产物不会被推离接触格导致循环偏移。

### 1.5 测试守卫

| # | 守卫 |
|---|---|
| T1 | 岩浆**源格**邻水 ⇒ 产物为**黑曜石** + 源湮灭 |
| T2 | 岩浆**流动格**邻水 ⇒ 产物为**圆石**（既有 ㉝ 不变，防回归） |
| T3 | 黑曜石物品放在岩浆格 ⇒ 被**焚毁** |
| T4 | 端到端：直接投放 64 圆石到接触格 ⇒ 转岩浆源 ⇒ 黑曜石 ⇒ 焚毁 ⇒ 回到圆石累加（长跑） |
| T5 | 契约默认回退：只覆写 `frontierReaction` 的流体，其源格也返回同一产物（default 语义） |

### 1.6 未来场景预演

- 玩家/漏斗能在 1.5s 内抽走黑曜石 ⇒ 装置退回「圆石累加」阶段；抽不走则自循环。
  ⇒ **黑曜石产线与圆石产线是同一台装置的两个阶段**，交替出现（Gameplay 上是个取舍点）。
- 将来接模组流体（某「液态 X」）：只需覆写这两个方法即可拥有自己的产物对，
  **引擎仍零改动**（1b-2 契约的目的）。

## §2 转化表作用域收窄：取消「非活空桶 → 水桶」

### 2.1 定稿值

| # | 定稿 |
|---|---|
| 1 | 删 `water_empty_bucket` 条目 ⇒ 内置 **16 条**（16 色混凝土粉末→混凝土） |
| 2 | **删除 `consumeSource` 整套机制**：转化表字段 + 解析、`FluidFlowBehavior.consumesSourceOnTransform`、引擎 `transformSourceItems` 的消耗分支 |
| 3 | 口径成文：**转化 = 催化剂语义 —— 非活化物品不得消耗活化资产** |
| 4 | 对称性论证（用户原话归纳）：活流体虽不是物品，定义上**属于活化侧**；一般是**活化影响非活化**，反过来的对称性破缺容易出问题 |
| 5 | **晋升再生不变量独立保留**：三连源中间源被**汲走**（活空桶，活化侧操作）后下一拍补回 —— 不违反对称性 |

### 2.2 被否掉的选项及理由

| 选项 | 否掉的理由 |
|---|---|
| 保留转化、仅改为不消耗源 | 仍是非活化从活化系统**取物**（空桶变水桶 = 活化资产装进非活化物品），且退回「一格水 = 无限水桶」⇒ 否 |
| 保留 `consumeSource` 机制待将来用 | 违反「不为假想需求扩接缝」（§6 `interval` 字段先例）；且与对称性论证冲突 —— 留着等于鼓励违规 ⇒ 否 |
| 连混凝土转化一起取消 | 不符合对称性论证：混凝土是**活化影响非活化**（水把粉末变混凝土，水不受影响）⇒ **保留** |

### 2.3 连带后果（已确认可接受）

- **自动化水桶农场闭环不成立**：三连源 + 漏斗喂非活空桶 ⇒ 不再产水桶。
- **容器内的装桶彻底只能玩家手动**（GUI 汲）：活桶搬不动（活物品隔离）+ 非活桶不转化。
  这是本次取消的直接后果，属已知代价。
- 管道抽取（§10）仍是自动化出口：管道抽源是**活化侧设备**影响活化资产，不违对称。

### 2.4 待决项

- **D4** 混凝土转化（活化影响非活化、不消耗源）保留 —— 待用户确认无异议（默认保留）。
- **D5** 将来若要自动化装桶：正确形态是**先活化**（活空桶走 GUI 汲），或给活桶设计新的联动方式
  （§9 开放问题 1），**而不是开非活化转化的口子**。

### 2.5 测试守卫

| # | 守卫 |
|---|---|
| T6 | 非活空桶放**水源格** ⇒ **不变**（不转化、源不消耗）—— 取代原 ㉕「空桶→水桶」 |
| T7 | 转化不消耗源（催化剂语义）：混凝土粉末转化后源仍在 |
| T8 | 三连源中间源被**移除**（汲走语义）⇒ 下一拍晋升再生 —— 取代原 ㉜「水桶农场」，保住再生不变量 |
| T9 | `FluidTransformTableTest`：内置 17 → **16** 条；`consumeSource` 相关用例随机制删除 |
| — | 原 ㉛「消耗型转化」随机制删除（不再有消耗型条目） |
