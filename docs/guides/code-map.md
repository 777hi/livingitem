# 代码关系图（`tools/gen_code_map.py`）

> **一句话**：从 `src/main/java` **派生**出可交互的代码关系图，回答「**改这个类会牵动谁**」。
>
> ⚠️ **它和文档系统不是一回事，别混**：文档回答「该读哪篇」，本图回答「改动沿哪条链传导」。
> 文档可以手写，图**必须派生** —— 手画的架构图三个月后就是一张撒谎的图。
> 所以**进版本控制的只有生成脚本，图本身不进**。

## 1. 什么时候跑它

| 场景 | 看什么 |
|---|---|
| 改一个核心类**之前** | 它的**上游**（红）= 爆炸半径 |
| 排查「改 A 为什么弄坏 B」 | 沿**下游**（蓝）追传导链 |
| 判断两个模块是否真解耦 | CLI 打印的**双向耦合模块对** |
| 规划框架演进 | **包视图** + CLI 打印的**模块级强连通分量** |

## 2. 命令

```bash
python tools/gen_code_map.py          # → build/code-map.html
python tools/gen_code_map.py --json   # 同时落 build/code-map.json（供二次处理）
```

🔴 **产物只落 `build/`（已 gitignore）—— 提交图等于把「过期风险」一起提交。**

## 3. 交互口径（**代码里推不出来的约定**）

| 元素 | 含义 |
|---|---|
| 实心节点 | 一个本项目 Java 类 |
| **空心节点** | `@Mixin` 注入目标（原版 / 第三方），只作锚点 |
| **红环 = 上游** | **谁依赖我** ⇒ 改我，它们全受影响 |
| **蓝环 = 下游** | **我依赖谁** ⇒ 改它们，我可能坏 |
| 橙线 `inherit` | `extends` / `implements` / `permits` / record 组件 |
| 蓝线 `use` | 文件正文出现该标识符（import / 字段类型 / 方法调用 / 静态引用） |
| 紫线 `mixin` | `@Mixin(X.class)` 或 `@Mixin(targets="…")` |

- 深度滑杆 = 上游 / 下游展开跳数（1~4）
- **高亮口径：线高亮 ⟺ 两端都在高亮集合内**（不会出现「点只亮 1 层、线跑到 2 层」）
- `?view=module` → 包视图（按包聚合，**边粗细 = 耦合强度**）
- `?view=layer` → 层次视图（见 §3.1）
- `?depth=2` → 预设上下游深度
- `code-map.html#ContainerFluidData` → 直达某个类（**三者可组合，链接可分享**）

### 3.1 层次视图与「分层违规」

按脚本顶部的 **`LAYERS` 表**把类排成自下而上的横带：

- **数字越大越靠上层**；上层可以依赖下层，**下层不得依赖上层**
- **红边 = 违规**（下层依赖上层）—— 这是「层次在哪断的」
- 层间直接标出**违规条数**，与 CLI 打印的「分层违规」是同一批

🔴 **`LAYERS` 表是「期望」，不是「现状」。** 改它 = 改你对架构的期望。
别处若要校验分层，应读**同一张表**（别复制第二份）。

> ⚠️ **只统计跨模块的违规**（同模块内部不算）。CLI 打印的合计条数 = 这张图的红边总数
> —— 它同时是**「架构演进」的进度指标**：目标是把违规压到 **0**，
> 并让模块图变成有向无环（最大强连通分量 = 1）。

**注意两个反直觉点**（实测数据）：
1. **领域之间几乎不互相依赖** ⇒ 病**不在水平方向**（子系统互相认识），
   而在**垂直方向**（通用机制 / 基础层伸手去认识具体领域）。
2. **`LivingItemManager` 上游最多不是病** —— 全局注册表被广泛依赖是设计使然。
   判断「该不该改」看的是**跨出**，不是**上游数**。

## 4. 可信边界

⚠️ **读图前必看 —— 它是静态近似，不是调用图。** 以下情况它**看不见**：

| 看不见 | 后果 |
|---|---|
| 反射 / 字符串引用（`Class.forName`、`ResourceLocation("mod:…")`） | 无此边 ⇒ **别据此断言「没人用」** |
| `use` 边的强度 | 「只用到类型」与「真的调用了」**在图上一样** ⇒ 判传导必须回看代码 |
| Mixin 的方法级注入目标（`@Inject` / `@Redirect`） | 只到类级 |
| `src/test` | 测试类**不在图中** |
| 泛型推断出的实参类型 | 调用点靠推断的类型不产生边 |

**判据一句话**：图用来**发现线索**，不用来**下结论**；结论回代码验证。

### 4.1 实测精度（2026-10-06，用 `jdeps` 交叉校验）

本图是**文本解析**（一个文件 = 一个节点），精度实测如下。复算方式：

```bash
jdeps -verbose:class -filter:none build/classes/java/main   # 需先编译（./gradlew classes）
```

| | 条数 | 说明 |
|---|---|---|
| 本图类级边 | 1160 | |
| `jdeps` 类级边（读字节码） | 1189 | |
| **一致** | **1146（占本图 99%）** | |
| 本图独有 | 14 | **全是「未使用的 import」** —— 本图把 import 一律计为使用 |
| `jdeps` 独有 | 43 | **签名级依赖**：`registerFunction(new X())` 这类**方法签名里的类型**（如 `LivingItemFunction`）源码正文不出现、字节码里有 |

⚠️ **另有一条已知结构性局限**：**一个文件 = 一个节点** ⇒
包级私有类 / 嵌套类被折叠进宿主类（实例：`TransferStrategy.java` 里的 `CollectStrategy`、
`DistributeStrategy` 在图上是 `TransferStrategy`）。

⇒ **结论**：对「谁认识谁」可信（99%）；**会漏「通过方法签名间接认识」的边**。
需要判断**编译期耦合**（而不只是源码引用）时，用上面的 `jdeps` 命令交叉验证。

## 5. 给 AI 用：文本查询（`--query` / `--extend`）

> ⭐ **AI 不要用浏览器去看 HTML，也不要自己写脚本解析 `build/code-map.json`** ——
> 直接调下面两个子命令。它们**直接解析源码**（不读产物）
> ⇒ **不存在「读到过期图」的问题**，也**不需要先跑一遍生成**。

```bash
python tools/gen_code_map.py --query ContainerContext   # 类：上下游 + 层 + 传递闭包
python tools/gen_code_map.py --query living/transfer    # 模块：违规明细 + 出入边
python tools/gen_code_map.py --extend                   # 扩展点：多数领域共同依赖的类
```

**三个高频问题的对应关系**：

| AI / 人 常问的问题 | 用哪个 | 看哪一段 |
|---|---|---|
| 「改这个类会牵动谁？」 | `--query <类名>` | **传递闭包**那一行 = 真实爆炸半径 |
| 「这个模块和谁纠缠？该断哪条？」 | `--query <模块名>` | 「向下违规」段 |
| 「新增一个子系统要接哪些口子？」 | `--extend` | 覆盖 N/12 的那张表 |

⚠️ **图只回答「结构」，不回答「意图」。** 「为什么这么设计 / 当初踩过什么坑」
仍然只能读 `docs/`（`tech/*` 与 `system-design/*`）。两者是**互补**的，别互相替代。

## 6. 铁律

🔴 **图是派生的 ⇒ 一定会过期。** 改完代码**必须重新生成**才可信；
**唯一真相永远是 `src/`，不是这张图。**

> 与 `doc_check.py` 的分工：`doc_check` 管**文档**是否与代码一致（可执行断言）；
> 本图管**代码自身**的关系是否可读（可视化）。两者都**不产生新知识**，只暴露已有知识。
