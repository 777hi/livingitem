# 新活物品设计稿模板与检查表

> **受众**：设计新活物品时（人 / AI）。**用法**：把下面的骨架复制进设计稿，逐格填写 ——  
> **填不出来的格子就是「还没想清楚的地方」**，那才是这份模板的价值。
>
> ⚠️ **本文只管「设计阶段特有的检查项」**。`§0 玩法定义` 的六项要求（语义 / 获取 / 核心循环 /  
> 规则 / 能力清单 / 验证入口）见 [docs/README.md](../README.md) §1 —— **不在此重复**。

## 为什么需要它（2026-10-11 立文）

活酿造台开发暴露的两个 bug，**都不是「功能逻辑写错」，而是「设计阶段没覆盖的维度」**：

| bug             | 属于哪类     | 表现                                           |
| --------------- | -------- | -------------------------------------------- |
| 燃料「绑在槽位上」（可刷燃料） | **生命周期** | 数据存在运行时缓存（键 = 容器 + 槽位），物品移走后数据留下 ⇒ 新物品**继承** |
| 活物品被当耗材消耗       | **准入**   | 材料 / 瓶子 / 燃料三处漏了 `isLivingItem` 隔离检查         |

共性：**它们不是「这个功能怎么工作」，而是「它的边界与生命周期」** ——  
写功能流程时天然想不到，写完了也想不起来；而且**单测覆盖不到**（只有破坏性实测才暴露）。  
⇒ 所以固化成本文的两张表 + 两张清单。

## 一、横切检查表（必填）

### 1.1 生命周期表 —— 每个「状态」一行

> 判据：**这个状态在什么事件之后应该失效？** 任何一格填不出来 ⇒ 它没被定义。

| 状态         | 存在哪           | 物品移走时        | 取消活化时 | 换槽位时 | 容器卸载时 |
| ---------- | ------------- | ------------ | ----- | ---- | ----- |
| *（示例）燃料次数* | DataComponent | **保留**（跟物品走） | 保留    | 保留   | 保留    |
| *（示例）冶炼进度* | 运行时缓存         | **作废**       | 作废    | 作废   | 作废    |

⚠️ **「存在哪」决定其余四格**：

- **DataComponent** ⇒ 状态**跟物品走**（移走 / 换槽位都保留）；代价是不同状态值的物品**不能堆叠**。
- **运行时缓存** ⇒ 状态**跟槽位走**（键 = 容器 + 槽位）⇒ **必须显式定义「何时作废」**。  
  框架的作废机制（物品离开槽位 / 换物品 / 容器卸载 ⇒ 作废）见  
  [living-item-infrastructure.md](../system-design/living-item-infrastructure.md) §3.5。

#### 1.1-b 状态粒度 —— 每个「容器级可见物」问一句：per-item 还是 per-container？

> 判据：**同一个容器里有两个该物品时，这个状态该合并还是该各存各的？**
> 写不出答案 ⇒ 先别定数据结构（这一步选错**不可逆**，后面全是返工）。
>
> **纪律：数据层 per-item，视觉聚合放渲染期。** 在**数据层**合并信息 = 不可逆丢失
> （「等级取 max、颜色取胜出者」丢掉了另一枚的全部信息）；要「一个容器只显示一个」，
> 应该在**渲染期**去重/聚合，而不是在存储期合并。
>
> 同理：**副作用按容器键，可视化按物品键** —— 「有活信标就要开盖」是容器级副作用
> （取走一枚不能关盖），「每枚一条光束」是物品级可视化。两者混在一个结构里必写错。

| 维度 | 该按什么键 | 反例（本项目的真实回撤） |
| --- | --- | --- |
| 可见物（光束/模型/面板） | **物品**（容器 + 槽位） | 多枚信标按容器 merge ⇒ 后来改「每枚一条」被迫重构键控 |
| 副作用（开盖/红石/方块事件） | **容器** | 开盖挂在 per-item 宿主上 ⇒ 取走一枚就关盖 |
| 客户端「最近一次」提示状态 | **避免**（改分区/显式键） | 活流体 `chestLikeTarget` 单槽提示被末影箱包翻掉 ⇒ 水渲染到别的箱子界面 |

案例与完整论证：[framework-evolution-plan.md](../buffer/framework-evolution-plan.md) §4。

### 1.2 准入表 —— 每个「槽位」一行

> 判据：**什么东西绝对不能进这个槽？进去了会怎样？**

| 槽位       | 什么能进  | 什么必须挡   | 挡不住会怎样                  |
| -------- | ----- | ------- | ----------------------- |
| *（示例）材料* | 有效材料  | **活物品** | 被 `consumeOne` **吃掉**   |
| *（示例）瓶子* | 可酿的瓶子 | **活物品** | 被 `mix` **原地转化**（丢内部状态） |
| *（示例）燃料* | 烈焰粉   | **活物品** | 被当燃料消耗                  |

⚠️ **活物品一律挡在门外**（隔离规则）—— 它是「设备」不是「耗材 / 载体」。

⚠️ **任何物品都能被活化**（`activation_rules.json` 默认 `default: allow` +  
`options.denyUnclaimed: false`）⇒ 活物品可能出现在**任何**槽位 ——  
**这不是假设场景**，玩家活化的水瓶 / 石头就会出现在槽里。  
（该配置与判定见 `LivingItemActivation` 的 javadoc 与  
[activation-rules.md](activation-rules.md)。）

### 1.3 反馈层三问 —— 做图标 / 音效 / 粒子反馈前先答

> 判据：**这个数据会被玩家用来做决策吗？** —— 会 ⇒ 服务端权威；不会 ⇒ 客户端本地自演。

| 问                              | 答不出来的后果                | 实例                                                                                     |
| ------------------------------ | ---------------------- | -------------------------------------------------------------------------------------- |
| **① 精度需求**：玩家会拿它做决策吗？          | 过度设计（给只看「有没有」的反馈做跨机器时钟对齐） | 白幕宽度：只看「在不在酿」⇒ **本地动画**；tooltip 秒数：据此决定等不等 ⇒ **服务端权威**                                      |
| **② 数据通道**：数据在组件里，还是只发给 viewer？ | 画不出来 / 只在开箱时有         | 装饰器接口只有 `(stack, x, y)`、**拿不到槽位** ⇒ 只能读组件量（燃料 / 能量 / 流体 ✅）；只发 viewer 的瞬态量（酿造倒计时 / 漏斗冷却 ❌） |
| **③ 覆盖场景**：全场景，还是仅开箱可见？        | 选了覆盖面不够的通道            | 全场景（快捷栏 / 背包 / 掉落物）⇒ 组件；仅开箱 ⇒ 运行时同步                                                    |

⭐ **一句话**：**反馈的精度需求决定数据通道** —— 不是「能对齐就对齐」。

⚠️ **立这三问的实例（2026-10-13）**：白幕初版做了「组件存权威时刻 + 客户端与服务端时钟对齐
+ `SetTimePacket` 校正」并分析了三个偏差源，被判定为过度设计；改为**本地动画**后整个时钟链删掉
（新标记 = 新起点 ⇒ 重播是自然结果，不需要额外逻辑）。教训：**锦上添花类反馈应默认本地自演。**

### 1.4 容器能力横切检查表 —— 功能要不要「看见邻居」

> 判据：**这个功能需要访问宿主容器的其它槽位吗？** 需要 ⇒ 它踩在容器适配层上，
> 而那一层有两条**单测与工具都抓不到**的依赖 ⇒ 必须人工核对。

**为什么单独立一节**：§1.1~1.3 全是**域内**视角。2026-10-18/19 的容器兼容性专题
（契约 I-C1~I-C9）修了 6 个 bug，**全部**发生在容器层，而它们在写功能流程时
一个都想不到——与酿造台那两个 bug 同一性质，只是横切方向不同。

| # | 判据 | 要做 | 忘了会怎样（真实案例） |
|---|---|---|---|
| ① | 要读**相邻槽**吗（熔炉燃料 / 漏斗两端 / 信标喂锭）？ | 目标容器须在 `container_rules.json` 且**列数正确**；列数唯一来源是 `ContainerRule.columns` | **列数错 ⇒ 熔炉不烧**（燃料槽 = `slot + width`）。漏斗同病，但「仍在搬」所以更难发现 |
| ② | 有**容器级持久数据**吗（多枚共享的一份状态，如流体 / 电力相位）？ | 附件必须带 `serialize`（= 存档级持久）⇒ 加**物品组件** + 登记 `contentRetaining` | 破坏方块即丢（真机报过「背包变物体形态后活流体没了」）。判据见 I-C9：**不带 `serialize` 的不搬**——运行时数据下一 tick 会自愈，搬它只会放大「磁盘账本说谎」面 |

⚠️ **列数是客户端属性**：`Container` 只有一维 `getContainerSize()`，BE 眼里没有行列；
布局只以 `Slot.x/y` 坐标存在于 GUI 层，服务端探测不到 ⇒ **新容器只能靠人录规则**
（`docs/TODO.md` 的「客户端列数探测」就是想解决它，未做）。

⚠️ **已有工具兜底、本表不用管的**（2026-10-20 复核过一遍）：
依赖方向与域耦合（`check_layers.py` R1/R3 + 棘轮基线）· Mixin 位置（R2）·
注册入口唯一（R4）· 文档一致性（`doc_check.py` 11 项）· 改动传导（`gen_code_map.py --query`）·
写回 ≠ 插入、模拟与真实同源（`ContainerBoundaryContractTest`）· 规则表 vs 类型表一致（单测）。
⇒ **第一段接入完成后立刻跑 `python tools/check_layers.py`**（见 §4）。

## 二、两张清单

### 2.1 原版对齐清单

> 用户原则：**能对齐的就对齐，实在无法对齐的再讨论**。  
> 但「对齐」要落成**逐条清单**，不能只写一句原则 —— 否则必然漏项。

| 原版的检查 / 行为          | 本实现   | 处置                             |
| ------------------- | ----- | ------------------------------ |
| *（示例）输入槽放活物品 ⇒ 不工作* | 同     | ✅ 对齐                           |
| *（示例）燃料存在方块实体字段*    | 运行时缓存 | ⚠️ **偏离**（原因：活物品无坐标；影响：见生命周期表） |

⭐ **关键**：把原版的**每一处检查**都列出来逐条对照。  
（实例：活熔炉有 **2 处**隔离检查〔输入槽、燃料槽〕⇒ 酿造台对应有 **3 处**〔材料、瓶子、燃料〕，  
少对照一处就是漏项。）  
**偏离是有意识的**（能写进文档），**漏项是无意识的**（变成 bug）。

### 2.2 规则 → 验证入口 对应表（§0 必填）

> **每条规则都必须指向一个守卫**（测试类 or 游戏内验证项）。  
> **指不出来的那条** = 它没有验证手段 ⇒ 要么补测试，要么进「游戏内验证清单」。

| 规则                 | 守卫                           |
| ------------------ | ---------------------------- |
| *（示例）活物品不作材料 / 瓶子* | `BrewingSlotEligibilityTest` |
| *（示例）堆叠只加速过程、消耗不变* | `BrewingBatchLogicTest`      |
| *（示例）活漏斗投料取货*      | 游戏内验证清单                      |

⚠️ **立这条的实例（2026-10-11）**：隔离规则**写进了规则表、但代码里没实现** ——  
从文档上完全看不出来（写了 11 条、实现了 10 条，文档不会告诉你少了哪条）。  
⇒ 把「**写没写**」变成「**能不能被验证**」：前者靠记性，后者可机械检查。

⚠️ **改动后的机械自检：改语义 / 改几何 ⇒ `grep` 相关词**，覆盖三类落点：
**Java 注释 · 文档 · 测试消息**。  
实例（2026-10-13）：白幕语义从「起始时刻」降级为「批次标记」，旧措辞扩散到 4 处
（Data javadoc ×2 / Function 注释 ×2 / 测试断言消息）—— `grep 起始时刻` 一次扫清。  
同族既有红线：**删纹理前 grep Java 字符串 + 模型 JSON 两类引用**（见 icon-system.md）。

## 三、要不要抽框架？（框架化时机）

> 判据：**已知有多个接入方 + 接入成本是「配置」而非「逻辑」⇒ 值得先抽框架。**

| 情形                    | 判断           | 实例                                                                                |
| --------------------- | ------------ | --------------------------------------------------------------------------------- |
| 只有一个用户、逻辑各不相同         | **不抽**（过度设计） | 白幕初版（做成通用机制 = 多余；简化后反而更短）                                                         |
| 已知多个用户、接入 = 填配置       | **抽**        | `ProgressBarDecorator`（注册「栈 → (比例, 颜色, 朝向)」；燃料条是第一个用户，活水源液位 / 活发电机能量各加一行） |

⭐ 反例同样重要：**抽早了就是过度设计** —— 判据里「已知多个接入方」这一条不能省。

## 四、落地顺序（沿用项目惯例）

| 段             | 内容                           | 验证                    |
| ------------- | ---------------------------- | --------------------- |
| **第一段：纯框架接入** | 域包骨架 + 槽位方向 + 注册（**不含业务逻辑**）<br>+ `python tools/check_layers.py` 通过 | **全量回归** + **层纪律** —— 证明没改坏别的东西、也没引入跨层/跨域依赖 |
| **第二段：特有逻辑**  | 状态机 / 消耗 / 配方 / tooltip      | **新增单测** + 游戏内实测      |

⭐ 第一段「无新逻辑 ⇒ 无新测试」可接受（回归即证据）；**第二段必须补单测**。

---

## 五、交付时的「游戏内验证点」

**必须显式区分**：单测覆盖了什么 / **只能靠游戏内实测的**（UI · 破坏性操作 · 跨容器搬运 · 重进存档）。

⚠️ 实测要**主动做破坏性尝试**：移走 · 换槽 · 取消活化 · 混入活物品 · 中途改槽内容。  
2026-10-11 的两个 bug 都是这样发现的，**单测碰不到**。
