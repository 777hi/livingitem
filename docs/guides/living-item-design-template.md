## 零、玩法原点（先填，再找复用接口）

### 对应物速查（定义玩法后使用）

> 本表只缩短查证路径，不替代原点五问，也不按已有接口反推玩法。只参考相同语义的部分，不继承先例的全部规则。

| 已明确的需求 | 先查对应物 | 重点判据 |
|---|---|---|
| 触发物品离场后状态仍存在 | [活流体 §1](../tech/living-fluid-tech.md#1-子系统关系红电类比) | 状态属于容器还是物品；触发器不等于状态宿主 |
| 多件物品通过布局产生整体行为 | [活地狱门](../tech/living-nether-portal-tech.md)、[活红石](../tech/living-redstone-tech.md) | 构件、结构与状态归属分开；不先给每件构件认主 |
| 空槽中存在可点击/可显示的状态 | [活流体](../tech/living-fluid-tech.md)、[GUI交互](../system-design/gui-interaction-system.md) | 槽位状态不等于槽内物品；交互和绘制使用同一权威对象 |
| 物品容器内的功能需要世界位置 | [容器七问·第4问](../system-design/container-overview.md)、[活背包 §5.5](../tech/living-backpack-tech.md#55-宿主锚点的玩法开关2026-10-24) | 自身位置、配置允许的真实宿主借位、未知位置分开，不借查看者兜底 |
| 对原版实体/世界执行动作 | [活工具](../tech/living-tool-tech.md)、[活地狱门 §3](../tech/living-nether-portal-tech.md#3-货物与玩家传送边界) | 先追官方公开入口与事件；复用执行不代表库存已结算 |
| 槽内数量变化或向外交付资产 | [槽位操作](slot-ops.md)、[API契约 §1.7/§1.8](../system-design/api-contract.md) | 真实宿主确认量、提交与失败结算；同步/修改副本不等于交付 |
| 容器身份、几何、查看者或跨形态保存 | [容器七问](../system-design/container-overview.md) | 先定位是哪一问，再使用该问唯一入口，不另建扫描/身份/回填链 |
| GUI反馈、图标或显示层级 | [图标系统](../system-design/icon-system.md)、[Tooltip系统](../system-design/tooltip-system.md) | 决策量服务端权威、装饰本地；先选现有通道和叠加层族 |

### 原点五问

> **实现便利不能作为玩法依据。** 本节只检查设计是否明确，不承诺机械判断玩法对错。

| 问题 | 必须写明 |
|---|---|
| 作用对象 | 槽位 / 容器 / 玩家 / 实体 / 世界位置；边界外和无关对象是否参与 |
| 输入或变化粒度 | 类型 / 数量 / 公开状态 / 实际事件；同 tick 多次变化只看最终状态，还是逐事件处理 |
| 方向含义 | 输入 / 输出 / 观察 / 位移；多种方向之间的关系 |
| 首次出现 | 活化、首次运行、移入时建立基线、执行还是反馈；分别说明 |
| 忙碌窗口 | 丢弃 / 合并 / 排队 / 覆盖；何时恢复受理，是否补发 |

不适用的格子写原因；至少提供一幅正例和一幅负例布局，并标出输入、对象与输出。**语义定清楚后**才判断现有抽象能否表达；找不到对应物再按入口的设计铁律讨论新机制，不新增审批流程。

**样例（活侦测器，现行规则见 [红石 §0](../tech/living-redstone-tech.md)）**：

```text
正例：[被观察槽] [活侦测器 →] [输出线路]
      目标公开状态变化 ⇒ 延迟后向右脉冲
负例：[无关槽变化] …… [活侦测器 →]
      正面目标未变 ⇒ 无脉冲
```

作用对象仅输出反侧相邻槽；同拍只看结算结果；首次放入只建基线；忙碌期追平基线但丢弃变化，不恢复补发。

## 一、横切检查表（必填）

### 1.1 生命周期表 —— 每个「状态」一行

> 判据：**这个状态在什么事件之后应该失效？** 任何一格填不出来 ⇒ 它没被定义。

| 状态 | 存在哪 | 物品移走时 | 取消活化时 | 换槽 / 同拍机械移动 | 拆分 / 合并 | 暂时卸载 | 缓存回收 / 重建后的首次行为 |
|---|---|---|---|---|---|---|---|
| *燃料次数* | DataComponent | 跟物品保留 | 由本功能规定 | 跟物品保留 | 明确每枚账本的拆合规则 | 持久值保留 | 按组件恢复，不继承其他机器 |
| *冶炼进度* | 槽位运行态 | 作废 | 作废 | 旧槽作废，新槽重新开始 | 规定数量变化是否复位 | 按宿主停止 tick，不把暂停等同回收 | 允许丢弃；明确重新开始的业务行为 |

⚠️ **先定生命周期语义，再选择存储**：

- DataComponent 的持久值跟随物品，组件差异会影响堆叠比较；不能因此推断所有状态都该跨迁移保留。
- 槽位运行态必须定义旧设备何时作废，以及缺缓存后的首次动作；**暂时卸载、真正回收、重新建基线是不同事件**。
- 同拍机械移动要说明后续读数是否失效；拆合要分别说明存量守恒与计时是否继续，不套用其他活物品的例外。

框架现有回收边界见 [living-item-infrastructure.md](../system-design/living-item-infrastructure.md) §3.5；需要跨卸载 / 重启保留的业务值不得只放可丢弃缓存。

#### 1.1-b 状态粒度 —— 每个「容器级可见物」问一句：per-item 还是 per-container？

> 判据：**同一个容器里有两个该物品时，这个状态该合并还是该各存各的？**
> 写不出答案 ⇒ 先别定数据结构（这一步选错**不可逆**，后面全是返工）。
>
> **纪律：数据层 per-item，视觉聚合放渲染期。** 副作用按容器键，可视化按物品键；在数据层合并信息 = 不可逆丢失。

| 维度 | 该按什么键 |
| --- | --- |
| 可见物（光束/模型/面板） | **物品**（容器 + 槽位） |
| 副作用（开盖/红石/方块事件） | **容器** |
| 客户端「最近一次」提示状态 | **避免**（改分区/显式键） |

案例与完整论证：[framework-evolution-plan.md](../buffer/framework-evolution-plan.md) §4。

### 1.2 准入表 —— 每个「槽位」一行

> 判据：**什么东西绝对不能进这个槽？进去了会怎样？**

| 槽位       | 什么能进  | 什么必须挡   | 挡不住会怎样                  |
| -------- | ----- | ------- | ----------------------- |
| *（示例）材料* | 有效材料  | **活物品** | 被 `consumeOne` **吃掉**   |
| *（示例）瓶子* | 可酿的瓶子 | **活物品** | 被 `mix` **原地转化**（丢内部状态） |
| *（示例）燃料* | 烈焰粉   | **活物品** | 被当燃料消耗                  |

⚠️ **活物品一律挡在门外**（隔离规则）—— 它是「设备」不是「耗材 / 载体」。

⚠️ **任何物品都能被活化**（`activation_rules.json` 默认 `default: allow` + `options.denyUnclaimed: false`）⇒ 活物品可能出现在**任何**槽位。配置与判定见 [activation-rules.md](activation-rules.md)。

#### 1.2-b 交互表 —— 每个「动作」一行

> 判据：**改谁、改什么、影响哪里；拒绝时哪些状态必须不变？**
> 有玩家交互时填写；无交互写「不适用」。本表与物品准入表分开：点击槽只是定位入口，空槽也可能承载容器状态。事故与契约见 [GUI交互 §1.1](../system-design/gui-interaction-system.md#11-身份访问能力与玩法条件)（`D-gui-01`）。

| 动作 | 实际对象 | 修改内容 / 外部效果 | 作用范围 | 消耗及结算时机 | 拒绝时必须保持 |
|---|---|---|---|---|---|
| *门点火* | 容器门面 | 建立点燃区域 | 候选整门；边框仅读取 | 成功后扣打火石耐久 | 门数据、光标、槽内货物 |
| *拉杆切换* | 槽内活拉杆 | 改开关状态 | 目标物品 | 无 | 物品状态、数量 |
| *桶倒水* | 容器源格 | 更新流体账本 | 目标格 | 源操作成功后按模式结算桶内容 | 源状态、光标桶 |

**填完再选接口，不由存取接口反推动作语义**：

- **身份与授权**：如何证明当前菜单、真实目标及作用范围？玩家的访问约束由谁提供，未知或明确拒绝时怎样止步？规则匹配、能取物或能放某物品不能代答状态权限。
- **能力与玩法**：宿主能否执行并确认修改？领域还须重验哪些玩法条件？区域动作不能只验点击格，也不把无关格或只读边框扩大为授权范围。
- **查询与提交**：哪些调用发生在授权前？候选计算必须只读，不懒建附件、热条目、位置索引或回收计时，不改光标、扣量或触发后置维护。查询现有值、加载运行态、提交修改分别注明允许的副作用；不能靠 `peek/get` 名字或「返回值没变」证明只读。

拒绝分清**未受理**与**已受理后的玩法失败**，后者逐项定义已发生的效果与结算，不默认存在全局回滚。自动 tick 的宿主运行规则另列，不绑定当前查看者权限；本表不要求新建权限框架或逐模组白名单。

### 1.3 反馈层三问 —— 做图标 / 音效 / 粒子反馈前先答

> 判据：**这个数据会被玩家用来做决策吗？** —— 会 ⇒ 服务端权威；不会 ⇒ 客户端本地自演。

| 问 | 答不出来的后果 |
| --- | --- |
| **① 精度需求**：玩家会拿它做决策吗？ | 过度设计（给只看「有没有」的反馈做跨机器时钟对齐） |
| **② 数据通道**：数据在组件里，还是只发给 viewer？ | 画不出来 / 只在开箱时有（装饰器拿不到槽位，只能读组件量） |
| **③ 覆盖场景**：全场景，还是仅开箱可见？ | 选了覆盖面不够的通道（全场景 ⇒ 组件；仅开箱 ⇒ 运行时同步） |
| **④ 画在哪族**：GUI 自绘叠加层的层级归属？ | 手选绝对 Z ⇒ 换界面被深度剔除或挡光标（`D-render-02` 禁手选绝对 Z） |

⭐ **反馈的精度需求决定数据通道** —— 不是「能对齐就对齐」；锦上添花类反馈默认本地自演。
通道与叠加层族选型见 [图标系统](../system-design/icon-system.md) / [Tooltip系统](../system-design/tooltip-system.md)（`GuiOverlays`）。

### 1.4 容器能力横切检查表 —— 邻居访问、真实宿主与对外报账

> 判据：**需要访问宿主槽位，或返回会让另一个系统收付资源的“成功/数量”吗？**
> 任一成立 ⇒ 必须明确宿主写入责任与支持边界；接口行为可用替身守卫，具体模组行为以源码/实机证据核对。

| # | 判据 | 要做 |
|---|---|---|
| ① | 要读**相邻槽**吗（熔炉燃料 / 漏斗两端 / 信标喂锭）？ | 列数走 `ContainerLayoutResolver` **统一链**（见下方 ⚠️）；需**指定**列数时录 `container_rules.json` 且必须正确 |
| ② | 有**容器级持久数据**吗（多枚共享的一份状态，如流体 / 电力相位）？ | 附件带 `serialize`（存档级持久）⇒ 加**物品组件** + 登记 `contentRetaining`（I-C9：不带 `serialize` 的不搬） |
| ③ | 返回的“成功/数量”会让另一端**实际收付资源**吗（抽灌 / 充放 / 存取）？ | 逐项填明资产真实宿主、提交入口、成功判据与失败结算；**先确认提交，再按领域取整规则报账** |
| ④ | 本次拿到的物品由谁负责写回？ | 区分独立/自有物品栈与 `getItem/getStackInSlot` 的槽位读取结果；后者不可假定能原地修改。纯组件提交走 §1.5，标脏/同步不能代替提交 |
| ⑤ | 目标宿主是否必须有**允许使用的写入口**？ | 分开定义玩法支持与写入能力；无可靠写入口可安全返回0/失败，不抽插绕过只读，不默认增加模组专用适配 |

**范围边界**：不要求所有容器运行活物品；“安全不工作”和“虚报成功制造资源”必须分开。
普通内部计时/RuntimeCache 不因上述检查自动变成库存交易；旧功能仅因写法相似不自动排迁移，须有实际玩法需求或结算风险证据。
事故与用户定界见 [海绵 §12.3](../tech/living-sponge-tech.md)；铜灯失败结算见 [红电 §4.2](../tech/living-power-tech.md)。

⚠️ **列数/布局从统一链解析，别自己算**：生效列数由 `ContainerLayoutResolver` 统一链解析 ——
Tier 0 活对象来源 → Tier 1 注册规则（`ContainerRule.columns`）→ Tier 1.5 自动学习
（准入四判据见 [infrastructure.md §6.2](../system-design/living-item-infrastructure.md)）→ Tier 2 内建约定 → Tier 3 启发式兜底。
**要指定列数才录规则表**；`SlotItemHandler` 包装的共享空容器学不了 ⇒ 那类才需要人录。

⚠️ **已有工具承担的检查**（不在本表复制实现细节）：
依赖方向与域耦合（`check_layers.py` R1/R3 + 棘轮基线）· Mixin 位置（R2）· 注册入口唯一（R4）·
文档一致性（`doc_check.py`）· 改动传导（`gen_code_map.py --query`）· 写回与数量原语契约（`ContainerBoundaryContractTest` / `ContainerSlotOpsTest`）。
**工具守住入口，不保证新增业务已经调用入口**；对外资源结算必须在 §2.2 补自己的验证。
⇒ **第一段接入完成后立刻跑 `python tools/check_layers.py`**（见 §四）。

### 1.5 槽位操作选型表 —— 数量原语与组件提交分开

> 判据：**修改的是槽内物品的数量/身份，还是仅组件？**
> 数量增减走四原语；同 Item、同 count 的槽内组件更新走明确提交。
> 选型见 [slot-ops.md](slot-ops.md) §2/§2.1；契约见 [api-contract](../system-design/api-contract.md) §1.7/§1.8。

| # | 判据 | 要做 |
|---|---|---|
| ① | 玩法语言是哪种：「搬 A 到 B」/「吃掉 n 件」/「生成 n 件放入」/「原地变身」？ | 分别用 `move` / `consume` / `produce` / `transform`；非 1:1 替换 = consume+produce（**consume 先行**，丢 ≤ 复制） |
| ② | 一次操作吃几件（变换单元 U，I-C13）？ | 声明为功能常量（熔炉按配方 / 酿造一槽一瓶 / 耕地整份）；不可拆的写 `transform`，可拆的只扣实际量 |
| ③ | 活物品 count 怎么参与产量/速率？ | **先 long 算预算、再按预算消费**（I-C14②）；容量问 `simulateInsertItem`，**不自算** `min(slotLimit, 64)`（NeoForge getSlotLimit=99 不是真容量） |
| ④ | 搬运在玩法上是「物理力」还是「容器同意的转移」？ | 默认 `STANDARD`（查准入+抽取权限）；只有物理力（水流推动一类）才显式选 `PHYSICAL`（A3 特例，不照抄流体） |
| ⑤ | 同 Item、同 count，只改槽内组件吗？ | 选 `commitItemComponents(slot, before, after)`，按 [slot-ops §2.1](slot-ops.md) 在副本上计算、通过正式写回确认；不新造提交机制 |
| ⑥ | 模拟、提交失败或多堆部分成功时，返回什么量？ | 模拟不写宿主/不通知；无写入口返回0；失效/no-op写入器不能靠模拟证明可写。定义确认量→返回量的取整、前缀结算与失败留痕（[API §1.8](../system-design/api-contract.md)） |

### 1.6 横切门槛爆炸半径 —— 新增准入 / 解析 / 生命周期 / 提交门时必填

> 判据：**这个新判断位于哪些旧行为之前？原来能通过的对象，现在是否都能继续通过？**
> 只验证新功能不够；已支持目标落到 UNKNOWN / fallback / no-op 也是回归。

| 新门槛 | 旧入口 / 既有行为 | 实现者全集如何复算 | 每个既有支持者继续通过的证据 | 未知新目标的安全默认 |
|---|---|---|---|---|
| *（示例）GUI动作访问* | *槽内物品动作、空槽流体、容器门面* | *查注册表、接口实现及 `gen_code_map.py --query`，不手写名单* | *原版槽、物品容器、实体容器各有接缝守卫；第三方真实行为列实机项* | *权限不明拒绝且可诊断* |

填写约束：

- **全集从代码复算**：沿注册入口、接口实现者、调用方或代码地图枚举；不要凭本次需求列“想到的几个”，也不在文档复制一份会漂的成员清单。
- **逐个证明继续通过**：每个既有支持族至少指向自动守卫或游戏内验收；共同 helper 通过不能替代真实入口。关键修复须验证旧门槛能使守卫失败。
- **区分未知与断线**：全新目标权限不明可安全拒绝；已被项目认领、过去可运行/交互的目标突然变成 UNKNOWN，默认按回归排查，不能用安全退化解释。
- **相关不等于授权**：身份来源、布局来源、viewer、读写能力与动作权限仍各自负责；可让同一联动对象提供多类事实，但不得从一个接口自动推出另一个接口的结论。

## 二、两张清单

### 2.1 原版对齐清单

> 用户原则：**能对齐的就对齐，实在无法对齐的再讨论**。  
> 但「对齐」要落成**逐条清单**，不能只写一句原则 —— 否则必然漏项。

| 原版的检查 / 行为 | 源码入口 / 判据 | 容器玩法选择 | 处置 |
|---|---|---|---|
| *侦测器忙碌期不受理更新* | `ObserverBlock.updateShape/startSignal`：POWERED 与已排定 tick 的受理门 | 忙碌期丢弃，不恢复后补发 | 精确对齐 |
| *侦测正面方块更新* | `ObserverBlock.updateShape`：只接收 FACING 方向更新 | 输出反侧相邻槽的公开状态变化 | 容器映射（不是逐世界更新事件） |
| *燃料存在方块实体字段* | 对应原版 BE 的保存 / 移除入口，设计时查证 | 物品组件或槽位运行态按生命周期表选择 | 有意偏离，写明理由 |

**精确对齐 / 容器映射 / 有意偏离必须分开标注**；未查证的项写「待查证」，不得用记忆、类名或相似实现充当源码事实。判据应能让后续开发者重新找到受理门、调用方与状态变化路径；数值和步骤放具体设计稿，不在此维护原版机制快照。

⭐ **关键**：把原版的**每一处检查**都列出来逐条对照。**偏离是有意识的**（能写进文档），**漏项是无意识的**（变成 bug）。

### 2.2 规则 → 验证入口 对应表（§0 必填）

> **每条规则都必须指向一个守卫**（测试类 or 游戏内验证项）。  
> **指不出来的那条** = 它没有验证手段 ⇒ 要么补测试，要么进「游戏内验证清单」。

| 规则                 | 守卫                           |
| ------------------ | ---------------------------- |
| *（示例）活物品不作材料 / 瓶子* | `BrewingSlotEligibilityTest` |
| *（示例）堆叠只加速过程、消耗不变* | `BrewingBatchLogicTest`      |
| *（示例）活漏斗投料取货*      | 游戏内验证清单                      |

**有玩家交互的功能，将 §1.2-b 每个动作补成以下接缝验证**：

| 场景 | 必须验证 |
|---|---|
| 正常动作；合法空槽状态 / 非空物品状态 | 驱动真实分发或公开交互入口，断言实际对象、范围与消耗，不只测匹配 helper |
| 旧菜单 / 同号异库存 / 禁用或只读 / 权限未知 | 请求不落到另一对象；不改光标、数据、数量，不执行后置维护或世界动作 |
| 区域内另一格受限 / 无关格受限 | 前者不能由允许点击格绕过；后者不误伤当前区域；仅读边框不额外授权 |
| 冷状态下的授权前查询 | 使用真实上下文与附件路径，断言热条目、索引、回收计时和附件均未新增；拒绝后消耗及状态不变 |

优先使用真实原版 / NeoForge 菜单与槽；只替换必要的外部边界，不让替身绕开被测的解析、授权或提交路径。第三方真实行为留实机验收，不复制其实现造假单测；关键回归须确认旧错误能使守卫失败。测试做法见 [unit-testing.md](unit-testing.md)。

**会对外承诺资源收付的新接口，至少填写以下接缝验证**（不据此要求全部内部计时迁移）：

| 场景 | 必须验证 |
|---|---|
| 正常全成功，读取返回原引用 / 副本 | 两者后端实际库存都按确认量改变；原定容量、分配/聚合玩法不变 |
| 无写入口 / 声明可写但setter无动作或拒写 | 不虚报成功，不抽插绕过限制；允许安全不工作 |
| 首槽成功、后槽失败 | 依据确认部分结算，返回量不冒充全量；取整损耗不能变成交付；恢复失败按契约留痕 |
| SIMULATE / 零请求 / 无变化 | 不写库存、不触发宿主保存或同步；拒写后端不要求模拟能够预测执行成功 |
| 超大堆叠 / 无关组件 | 改存量不截断物品数量，不丢无关数据；预算与返回值不回绕 |

**断言对象必须是后端实际槽值**，不是预先拿到、可能已被替换的旧栈引用；同时核对另一端的收付量与容器内容回调。共同入口测试通过，不能替代功能接口自身的这组验证。参考现有 `ContainerComponentCommitTest`、`SpongeContainerCapabilityTest`、`ContainerEnergyCapabilityTest`；复用脚手架，不新建通用测试框架。

⚠️ **改动后的机械自检：改语义 / 改几何 ⇒ `grep` 相关词**，覆盖三类落点：**Java 注释 · 文档 · 测试消息**。  
同族既有红线：**删纹理前 grep Java 字符串 + 模型 JSON 两类引用**（见 icon-system.md）。

### 2.4 新增机制的文档同步清单

**新增机制 / 原语 / 物品 / 动作时：§2.3 管「设计定案归位」，本表管「既有文档不被落下」。**

| 检查 | 问什么 |
|---|---|
| **既有支持者** | 是否新增了准入 / 解析 / 生命周期 / 提交门？按§1.6从代码复算受影响实现者，每个族的继续通过证据落在哪？ |
| **枚举类清单** | 哪些文档枚举了这一类？新成员补了吗？计数对吗？ |
| **对外契约** | 是公开 API（第三方拿得到）吗？api-contract 收了吗？ |
| **主域 tech** | §0 + 实现节更新？跨域机制只写主域，其它域留结论+指针 |
| **术语 / 决策** | glossary 新术语？decisions 新决策（含取代旧口径）？ |
| **不变量** | 涉守恒/容量/写回？container-boundary / power-invariants 补条目？ |
| **changelog** | 改口径 / 能力边界 ⇒ 记一行（纯实现重构不记） |

⚠️ **枚举类清单是重灾区**：手维护的「N 原语 / N 动作 / N 规则」随新增必漂（铁律3）。
能改「以代码注册为准 + 查命令」的就改（如 interaction-rules 动作表）；必须列的，新增时同步并核对计数。
**机械自检**：新增后 `grep` 该类别枚举词（「原语」「动作」等），扫所有落点（tech / 契约 / 指南 / javadoc）。

## 三、要不要抽框架？（框架化时机）

> 判据：**已知有多个接入方 + 接入成本是「配置」而非「逻辑」⇒ 值得先抽框架。**

| 情形                    | 判断           |
| --------------------- | ------------ |
| 只有一个用户、逻辑各不相同         | **不抽**（过度设计） |
| 已知多个用户、接入 = 填配置       | **抽**        |

⭐ **抽早了就是过度设计** —— 判据里「已知多个接入方」这一条不能省。
