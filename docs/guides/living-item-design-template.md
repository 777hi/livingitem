# 新活物品设计稿模板与检查表

> **受众**：设计新活物品时（人 / AI）。**用法**：把下面的骨架复制进设计稿，逐格填写 ——  
> **填不出来的格子就是「还没想清楚的地方」**，那才是这份模板的价值。
>
> ⚠️ **本文只管「设计阶段特有的检查项」**。`§0 玩法定义` 的六项要求（语义 / 获取 / 核心循环 /  
> 规则 / 能力清单 / 验证入口）见 [docs/README.md](../README.md) §1 —— **不在此重复**。

## 为什么需要它（2026-10-11 立文）

活酿造台开发暴露的两个 bug，**都不是「功能逻辑写错」，而是「设计阶段没覆盖的维度」**：

| bug             | 属于哪类     | 表现                                           |
| --------------- | -------- | -------------------------------------------- |
| 燃料「绑在槽位上」（可刷燃料） | **生命周期** | 数据存在运行时缓存（键 = 容器 + 槽位），物品移走后数据留下 ⇒ 新物品**继承** |
| 活物品被当耗材消耗       | **准入**   | 材料 / 瓶子 / 燃料三处漏了 `isLivingItem` 隔离检查         |

共性：**它们不是「这个功能怎么工作」，而是「它的边界与生命周期」** ——  
写功能流程时天然想不到，写完了也想不起来；而且**单测覆盖不到**（只有破坏性实测才暴露）。  
⇒ 所以固化成本文的两张表 + 两张清单。

## 零、玩法原点（先填，再找复用接口）

> 2026-11-11 活侦测器复盘：先看到整容器签名能复用，再反推观察整个容器，造成局部布线、红石状态与忙碌窗口三处返工。**实现便利不能作为玩法依据。** 本节只检查设计是否明确，不承诺机械判断玩法对错。

| 问题 | 必须写明 |
|---|---|
| 作用对象 | 槽位 / 容器 / 玩家 / 实体 / 世界位置；边界外和无关对象是否参与 |
| 输入或变化粒度 | 类型 / 数量 / 公开状态 / 实际事件；同 tick 多次变化只看最终状态，还是逐事件处理 |
| 方向含义 | 输入 / 输出 / 观察 / 位移；多种方向之间的关系 |
| 首次出现 | 活化、首次运行、移入时建立基线、执行还是反馈；分别说明 |
| 忙碌窗口 | 丢弃 / 合并 / 排队 / 覆盖；何时恢复受理，是否补发 |

不适用的格子写原因；至少提供一幅正例和一幅负例布局，并标出输入、对象与输出。**语义定清楚后**才判断现有抽象能否表达；找不到对应物再按入口的设计铁律讨论新机制，不新增审批流程。

**样例（活侦测器，现行规则见 [红石 §0](../tech/living-redstone-tech.md)）**：

```text
正例：[被观察槽] [活侦测器 →] [输出线路]
      目标公开状态变化 ⇒ 延迟后向右脉冲
负例：[无关槽变化] …… [活侦测器 →]
      正面目标未变 ⇒ 无脉冲
```

作用对象仅输出反侧相邻槽；基础粒度是类型、数量与活化身份，功能可显式追加公开状态，同拍只看结算结果；方向表示输出；首次放入只建基线；忙碌期追平基线但丢弃变化，不恢复补发。旧「整容器签名易复用」不能回答上述负例，因而不应成为实现起点。

## 一、横切检查表（必填）

### 1.1 生命周期表 —— 每个「状态」一行

> 判据：**这个状态在什么事件之后应该失效？** 任何一格填不出来 ⇒ 它没被定义。

| 状态 | 存在哪 | 物品移走时 | 取消活化时 | 换槽 / 同拍机械移动 | 拆分 / 合并 | 暂时卸载 | 缓存回收 / 重建后的首次行为 |
|---|---|---|---|---|---|---|---|
| *燃料次数* | DataComponent | 跟物品保留 | 由本功能规定 | 跟物品保留 | 明确每枚账本的拆合规则 | 持久值保留 | 按组件恢复，不继承其他机器 |
| *冶炼进度* | 槽位运行态 | 作废 | 作废 | 旧槽作废，新槽重新开始 | 规定数量变化是否复位 | 按宿主停止 tick，不把暂停等同回收 | 允许丢弃；明确重新开始的业务行为 |

⚠️ **先定生命周期语义，再选择存储**：

- DataComponent 的持久值跟随物品，组件差异会影响堆叠比较；不能因此推断所有状态都该跨迁移保留。
- 槽位运行态必须定义旧设备何时作废，以及缺缓存后的首次动作；**暂时卸载、真正回收、重新建基线是不同事件**。
- 同拍机械移动要说明后续读数是否失效；拆合要分别说明存量守恒与计时是否继续，不套用其他活物品的例外。

框架现有回收边界见 [living-item-infrastructure.md](../system-design/living-item-infrastructure.md) §3.5；需要跨卸载 / 重启保留的业务值不得只放可丢弃缓存。

#### 1.1-b 状态粒度 —— 每个「容器级可见物」问一句：per-item 还是 per-container？

> 判据：**同一个容器里有两个该物品时，这个状态该合并还是该各存各的？**
> 写不出答案 ⇒ 先别定数据结构（这一步选错**不可逆**，后面全是返工）。
>
> **纪律：数据层 per-item，视觉聚合放渲染期。** 在**数据层**合并信息 = 不可逆丢失
> （「等级取 max、颜色取胜出者」丢掉了另一枚的全部信息）；要「一个容器只显示一个」，
> 应该在**渲染期**去重/聚合，而不是在存储期合并。
>
> 同理：**副作用按容器键，可视化按物品键** —— 「有活信标就要开盖」是容器级副作用
> （取走一枚不能关盖），「每枚一条光束」是物品级可视化。两者混在一个结构里必写错。

| 维度 | 该按什么键 | 反例（本项目的真实回撤） |
| --- | --- | --- |
| 可见物（光束/模型/面板） | **物品**（容器 + 槽位） | 多枚信标按容器 merge ⇒ 后来改「每枚一条」被迫重构键控 |
| 副作用（开盖/红石/方块事件） | **容器** | 开盖挂在 per-item 宿主上 ⇒ 取走一枚就关盖 |
| 客户端「最近一次」提示状态 | **避免**（改分区/显式键） | 活流体 `chestLikeTarget` 单槽提示被末影箱包翻掉 ⇒ 水渲染到别的箱子界面 |

案例与完整论证：[framework-evolution-plan.md](../buffer/framework-evolution-plan.md) §4。

### 1.2 准入表 —— 每个「槽位」一行

> 判据：**什么东西绝对不能进这个槽？进去了会怎样？**

| 槽位       | 什么能进  | 什么必须挡   | 挡不住会怎样                  |
| -------- | ----- | ------- | ----------------------- |
| *（示例）材料* | 有效材料  | **活物品** | 被 `consumeOne` **吃掉**   |
| *（示例）瓶子* | 可酿的瓶子 | **活物品** | 被 `mix` **原地转化**（丢内部状态） |
| *（示例）燃料* | 烈焰粉   | **活物品** | 被当燃料消耗                  |

⚠️ **活物品一律挡在门外**（隔离规则）—— 它是「设备」不是「耗材 / 载体」。

⚠️ **任何物品都能被活化**（`activation_rules.json` 默认 `default: allow` +  
`options.denyUnclaimed: false`）⇒ 活物品可能出现在**任何**槽位 ——  
**这不是假设场景**，玩家活化的水瓶 / 石头就会出现在槽里。  
（该配置与判定见 `LivingItemActivation` 的 javadoc 与  
[activation-rules.md](activation-rules.md)。）

### 1.3 反馈层三问 —— 做图标 / 音效 / 粒子反馈前先答

> 判据：**这个数据会被玩家用来做决策吗？** —— 会 ⇒ 服务端权威；不会 ⇒ 客户端本地自演。

| 问                              | 答不出来的后果                | 实例                                                                                     |
| ------------------------------ | ---------------------- | -------------------------------------------------------------------------------------- |
| **① 精度需求**：玩家会拿它做决策吗？          | 过度设计（给只看「有没有」的反馈做跨机器时钟对齐） | 白幕宽度：只看「在不在酿」⇒ **本地动画**；tooltip 秒数：据此决定等不等 ⇒ **服务端权威**                                      |
| **② 数据通道**：数据在组件里，还是只发给 viewer？ | 画不出来 / 只在开箱时有         | 装饰器接口只有 `(stack, x, y)`、**拿不到槽位** ⇒ 只能读组件量（燃料 / 能量 / 流体 ✅）；只发 viewer 的瞬态量（酿造倒计时 / 漏斗冷却 ❌） |
| **③ 覆盖场景**：全场景，还是仅开箱可见？        | 选了覆盖面不够的通道            | 全场景（快捷栏 / 背包 / 掉落物）⇒ 组件；仅开箱 ⇒ 运行时同步                                                    |

⭐ **一句话**：**反馈的精度需求决定数据通道** —— 不是「能对齐就对齐」。

⚠️ **立这三问的实例（2026-10-13）**：白幕初版做了「组件存权威时刻 + 客户端与服务端时钟对齐
+ `SetTimePacket` 校正」并分析了三个偏差源，被判定为过度设计；改为**本地动画**后整个时钟链删掉
（新标记 = 新起点 ⇒ 重播是自然结果，不需要额外逻辑）。教训：**锦上添花类反馈应默认本地自演。**

### 1.4 容器能力横切检查表 —— 邻居访问、真实宿主与对外报账

> 判据：**需要访问宿主槽位，或返回会让另一个系统收付资源的“成功/数量”吗？**
> 任一成立 ⇒ 必须明确宿主写入责任与支持边界；接口行为可用替身守卫，具体模组行为以源码/实机证据核对。

**为什么单独立一节**：§1.1~1.3 全是**域内**视角。2026-10-18/19 的容器兼容性专题
（契约 I-C1~I-C9）修了 6 个 bug，**全部**发生在容器层，而它们在写功能流程时
一个都想不到——与酿造台那两个 bug 同一性质，只是横切方向不同。

| # | 判据 | 要做 | 忘了会怎样（真实案例） |
|---|---|---|---|
| ① | 要读**相邻槽**吗（熔炉燃料 / 漏斗两端 / 信标喂锭）？ | 相邻槽换算用的列数走 `ContainerLayoutResolver` **统一链**（见下方 ⚠️）；需**指定**列数时录 `container_rules.json` 且必须正确 | **列数错 ⇒ 熔炉不烧**（燃料槽 = `slot + width`）。漏斗同病，但「仍在搬」所以更难发现 |
| ② | 有**容器级持久数据**吗（多枚共享的一份状态，如流体 / 电力相位）？ | 附件必须带 `serialize`（= 存档级持久）⇒ 加**物品组件** + 登记 `contentRetaining` | 破坏方块即丢（真机报过「背包变物体形态后活流体没了」）。判据见 I-C9：**不带 `serialize` 的不搬**——运行时数据下一 tick 会自愈，搬它只会放大「磁盘账本说谎」面 |
| ③ | 返回的“成功/数量”会让另一端**实际收付资源**吗（抽灌 / 充放 / 存取）？ | 逐项填明资产真实宿主、提交入口、成功判据与失败结算；**先确认提交，再按领域取整规则报账** | 海绵/铜灯只改读取副本就报成功，库存未变却已对外交付；计算量正确也挡不住复制 |
| ④ | 本次拿到的物品由谁负责写回？ | 区分独立/自有物品栈与 `getItem/getStackInSlot` 的槽位读取结果；后者不可假定能原地修改。纯组件提交走 §1.5，保存标脏/客户端同步不能代替提交 | 组件属于物品≠修改已经落到宿主；即使返回原引用，也可能绕过宿主内容回调 |
| ⑤ | 目标宿主是否必须支持这套玩法，且是否有**允许使用的写入口**？ | 分开定义玩法支持与写入能力；无可靠写入口可安全返回0/失败，不抽插绕过只读，不默认增加模组专用适配 | 把“不工作”误当必须兼容，或把可读/有setter误当已写成；特殊库存只读/no-op不能假报成功 |

上述检查自动变成库存交易；旧功能仅因写法相似不自动排迁移，须有实际玩法需求或结算风险证据。
事故与用户定界见 [海绵 §12.3](../tech/living-sponge-tech.md)；铜灯失败结算见
[红电 §4.2](../tech/living-power-tech.md)。

⚠️ **列数/布局从统一链解析，别自己算**（2026-10-31 更正：原「列数是客户端属性、服务端探测不到、

### 1.5 槽位操作选型表 —— 数量原语与组件提交分开

> 判据：**修改的是槽内物品的数量/身份，还是仅组件？**
> 数量增减走四原语；同 Item、同 count 的槽内组件更新走明确提交。
> 选型见 [slot-ops.md](slot-ops.md) §2/§2.1；契约见 [api-contract](../system-design/api-contract.md) §1.7/§1.8。

| # | 判据 | 要做 | 忘了会怎样（真实案例） |
|---|---|---|---|
| ① | 玩法语言是哪种：「搬 A 到 B」/「吃掉 n 件」/「生成 n 件放入」/「原地变身」？ | 分别用 `move` / `consume` / `produce` / `transform`；非 1:1 替换 = consume+produce（**consume 先行**——丢 ≤ 复制） | 裸 `setItem` 拼「先写再扣源」＝ A1 丢 436 / R-13 复制那一代 bug；现在门禁（`check_stack_ops.py`）直接拦红 |

| ⑤ | 同 Item、同 count，只改槽内组件吗？ | 选 `commitItemComponents(slot, before, after)`，按 [slot-ops §2.1](slot-ops.md) 在副本上计算、通过正式写回确认；不新造提交机制 | 改副本后未写回，或直接改原引用绕过容器通知；不能靠补 `setChanged` 解决 |

## 二、两张清单

### 2.1 原版对齐清单

> 用户原则：**能对齐的就对齐，实在无法对齐的再讨论**。  
> 但「对齐」要落成**逐条清单**，不能只写一句原则 —— 否则必然漏项。

| 原版的检查 / 行为 | 源码入口 / 判据 | 容器玩法选择 | 处置 |
|---|---|---|---|
| *侦测器忙碌期不受理更新* | `ObserverBlock.updateShape/startSignal`：POWERED 与已排定 tick 的受理门 | 忙碌期丢弃，不恢复后补发 | 精确对齐 |
| *侦测正面方块更新* | `ObserverBlock.updateShape`：只接收 FACING 方向更新 | 输出反侧相邻槽的公开状态变化 | 容器映射（不是逐世界更新事件） |
| *燃料存在方块实体字段* | 对应原版 BE 的保存 / 移除入口，设计时查证 | 物品组件或槽位运行态按生命周期表选择 | 有意偏离，写明理由 |

**精确对齐 / 容器映射 / 有意偏离必须分开标注**；未查证的项写「待查证」，不得用记忆、类名或相似实现充当源码事实。判据应能让后续开发者重新找到受理门、调用方与状态变化路径；数值和步骤放具体设计稿，不在此维护原版机制快照。

⭐ **关键**：把原版的**每一处检查**都列出来逐条对照。  
（实例：活熔炉有 **2 处**隔离检查〔输入槽、燃料槽〕⇒ 酿造台对应有 **3 处**〔材料、瓶子、燃料〕，  
少对照一处就是漏项。）  
**偏离是有意识的**（能写进文档），**漏项是无意识的**（变成 bug）。

### 2.2 规则 → 验证入口 对应表（§0 必填）

> **每条规则都必须指向一个守卫**（测试类 or 游戏内验证项）。  
> **指不出来的那条** = 它没有验证手段 ⇒ 要么补测试，要么进「游戏内验证清单」。

| 规则                 | 守卫                           |
| ------------------ | ---------------------------- |
| *（示例）活物品不作材料 / 瓶子* | `BrewingSlotEligibilityTest` |
| *（示例）堆叠只加速过程、消耗不变* | `BrewingBatchLogicTest`      |
| *（示例）活漏斗投料取货*      | 游戏内验证清单                      |

**会对外承诺资源收付的新接口，至少填写以下接缝验证**（不据此要求全部内部计时迁移）：

| 场景 | 必须验证 |
|---|---|
| 正常全成功，读取返回原引用 / 副本 | 两者后端实际库存都按确认量改变；原定容量、分配/聚合玩法不变 |
| 无写入口 / 声明可写但setter无动作或拒写 | 不虚报成功，不抽插绕过限制；允许安全不工作 |
| 首槽成功、后槽失败 | 依据确认部分结算，返回量不冒充全量；取整损耗不能变成交付；恢复失败按契约留痕 |
| SIMULATE / 零请求 / 无变化 | 不写库存、不触发宿主保存或同步；拒写后端不要求模拟能够预测执行成功 |
| 超大堆叠 / 无关组件 | 改存量不截断物品数量，不丢无关数据；预算与返回值不回绕 |

**断言对象必须是后端实际槽值**，不是预先拿到、可能已被替换的旧栈引用；同时核对另一端的收付量
与容器内容回调。共同入口测试通过，不能替代功能接口自身的这组验证。
参考现有 `ContainerComponentCommitTest`、`SpongeContainerCapabilityTest`、`ContainerEnergyCapabilityTest`；
复用脚手架，不新建通用测试框架。接口级验证与具体模组实机结果分别记录；实机按各功能已定的验收方式，
不把“支持安全拒绝”记成“支持该容器完整玩法”。

⚠️ **立这条的实例（2026-10-11）**：隔离规则**写进了规则表、但代码里没实现** ——  
从文档上完全看不出来（写了 11 条、实现了 10 条，文档不会告诉你少了哪条）。  
⇒ 把「**写没写**」变成「**能不能被验证**」：前者靠记性，后者可机械检查。

⚠️ **改动后的机械自检：改语义 / 改几何 ⇒ `grep` 相关词**，覆盖三类落点：
**Java 注释 · 文档 · 测试消息**。  
实例（2026-10-13）：白幕语义从「起始时刻」降级为「批次标记」，旧措辞扩散到 4 处
（Data javadoc ×2 / Function 注释 ×2 / 测试断言消息）—— `grep 起始时刻` 一次扫清。  
同族既有红线：**删纹理前 grep Java 字符串 + 模型 JSON 两类引用**（见 icon-system.md）。

## 三、要不要抽框架？（框架化时机）

> 判据：**已知有多个接入方 + 接入成本是「配置」而非「逻辑」⇒ 值得先抽框架。**

| 情形                    | 判断           | 实例                                                                                |
| --------------------- | ------------ | --------------------------------------------------------------------------------- |
| 只有一个用户、逻辑各不相同         | **不抽**（过度设计） | 白幕初版（做成通用机制 = 多余；简化后反而更短）                                                         |
| 已知多个用户、接入 = 填配置       | **抽**        | `ProgressBarDecorator`（注册「栈 → (比例, 颜色, 朝向)」；燃料条是第一个用户，活水源液位 / 活发电机能量各加一行） |

⭐ 反例同样重要：**抽早了就是过度设计** —— 判据里「已知多个接入方」这一条不能省。

## 四、落地顺序（沿用项目惯例）

| 段             | 内容                           | 验证                    |
| ------------- | ---------------------------- | --------------------- |
| **第一段：纯框架接入** | 域包骨架 + 槽位方向 + 注册（**不含业务逻辑**）<br>+ `python tools/check_layers.py` 通过 | **全量回归** + **层纪律** —— 证明没改坏别的东西、也没引入跨层/跨域依赖 |
| **第二段：特有逻辑**  | 状态机 / 消耗 / 配方 / tooltip      | **新增单测** + 游戏内实测      |

⭐ 第一段「无新逻辑 ⇒ 无新测试」可接受（回归即证据）；**第二段必须补单测**。

## 五、交付时的「游戏内验证点」
