# 活魂符与女仆背包联动

> **实现状态**：首版及无槽裁剪、四向身体、有限头部追光标均获用户实测确认；2026-11-10 模型层精确栈握手获用户确认，原先不显示的容器现可显示女仆，未逐项覆盖组合见§4。
> **范围**：Minecraft 1.21.1、NeoForge 21.1.219，编译对接TLM 1.5.3-neoforge+mc1.21.1。
> **定案与否决**：§2.2；后续工作统一见[需求池](../TODO.md)。

## §0 玩法定义

**语义**：活魂符是存有具体女仆的魂符的活物品形态，在容器内自行换槽，在容器界面显示所存女仆。
女仆实体背包兼容是独立的宿主接入：允许放入的活物品在该库存里运行，不要求背包接纳每一种活物品。

**获取**：空魂符收存已有女仆得到`smart_slab_has_maid`，再经活按钮活化。
初始赠送的INIT魂符尚无具体女仆快照，本功能不把它当已有女仆；可先释放、再收存。

**核心循环**：活化后I=7；每个服务端整秒边界以`1/I`概率发起一次尝试 → 命中后先随机四向 →
实际成功`I−1`、玩法失败`I+1`（范围1～49）。开关GUI不参与服务端判断。

**规则**（违反即bug）：
1. I表示平均多少秒发起一次尝试，初始7；成功`I=max(1,I−1)`，玩法失败`I=min(49,I+1)`。
2. 仅在服务端整秒边界以`1/I`概率判定；未命中不写组件，也不抽方向。I=1时每秒必定尝试。
3. 命中后必须先在上/下/左/右中等概率选一个方向，再判断能否移动；不预过滤、不因别处有空格重掷。
4. 成功仅指实际`move`完成，或确认消耗随机目标槽一份合格供品并写回好感账；越界、目标占用、准入/容量/抽取拒绝属于玩法失败。
   物品已被拿走/过期条目、Unsupported/BackendViolation属于技术中性，不改变I；下一整秒正常再判，不每tick狂试。
5. 命中的目标槽若为TLM居家餐规则允许的**非活化食物**，魂符不移动，整件消耗一份，待兑现好感+1，按成功`I−1`。
   活化食物、居家餐黑名单、满好感容量或不可抽取均不吃并按失败`I+1`；碗/瓶/食用转化物不返还，不执行食物效果、进食事件或经验奖励。
6. 每枚每tick至多一步或一份供品；不合并、不交换、不跨容器、不进入非存储槽，异常多件魂符不拆分。
   更早功能若本拍已搬动魂符，旧扫描条目按框架契约失效，本拍不补到新槽执行；连续机械搬动可以持续压制自主走位，
   这是接受的互动，不增加挣脱保底、公平轮换或错过次数补偿。
7. 组件只保存I并随物品换槽；缺失或非法时写7且本拍不抽签，之后从下一个整秒边界参与概率判定。
   换槽、换箱、跨维度或重启不需要恢复截止时间；结果组件提交被特殊后端拒绝时，移动事实保留、I暂时保持原值。
8. 基础走位不读取饱食度或背包容量，不运行女仆任务或快照背包。投喂只在`maid_info`写我方`living_item:pending_favor`账，
   取消活化只清clock、保留已赚取好感；主人成功释放且实体确认入世后，以TLM原生好感管理器一次性兑现并从快照移除账本。
9. 女仆实体背包按当前装备类型开放的范围运行，普通区六列；隐藏、装备、饰品、机器等区域不冒领。
   原准入/黑名单/拾取/穿脱/死亡处理不改，活魂符仍可能被原背包规则拒收。
9. 模型/简单待机音仅在容器界面演出，临时预览女仆不入世界、不完整tick。
   每枚独立，移槽匹配只排除clock与pending好感账；同数据有歧义重置演出，不共享实体。
10. 模型准备失败保留原图；模型绘制失败只补回原底图，不重复数量/耐久/高亮。
    只有Background登记的真实槽栈引用在同帧、同槽位GUI矩阵中可被透明化；复制栈/复制槽、假槽、冷却、carried、HUD、配方列表、世界与手持渲染保持原样。
    若第三方界面不发容器事件、复制栈、绕过物品模型override/GUI transform、改变槽位渲染矩阵，或同一物理槽存在多个显示别名，则安全退化为原图，不按内容签名猜测。
    关闭界面、物品离开、重载或换世界明确停声并释放实例。

11. 槽位只作为模型的站立锚点，不按槽位矩形裁剪；模型可伸到邻槽，不扩大点击区域或增加实际占槽。
12. 身体初始正面，随最后迈步方向转向：上背面、下正面、左朝左、右朝右；停步不自动回正。
    头部在相对身体的范围内追踪光标，不让身体跟着光标转，不在背面强行扭头180度。
    朝向只在存续的客户端预览中保持；关界面或取起后预览重建回正是已接受的展示边界，不要求物品持久化朝向。

13. 图片表情气泡只在界面可见预览中生成，使用原Emoji数据/背景/寿命/资源，遵守原全局、个人显示与图片权重设置。
    不生成服务端颜文字、台词或历史聊天；不新增同步/物品组件，关闭/重建预览即清理。

14. 活魂符tooltip显示当前I对应的**每秒行动尝试概率**`1/I`与一位小数百分比；这不是实际移动成功率。
    待兑现好感大于0时另显示`+N（释放后生效）`，零值隐藏；缺失/非法I只读按初始7展示，不修改物品。

**已接入能力**：女仆背包宿主选择/范围与反馈过滤；活魂符自适应随机走位、居家餐供品与待兑现好感；槽位图标替换、
原模型预览/步行动画与待机语音，四向身体、有限光标追踪、投喂脉冲/吃声，以及原图片气泡接线。
**明确不做**：放宽女仆背包准入、INIT原地生成、完整进食/食物效果、饱食度消费、经验奖励、任务回放、槽位物品寻路、
手持食物吸引/光标方向偏置、状态文字/颜文字/聊天内容、手持女仆模型或另造库存操作协议。
**验证入口**：§3的我方守卫与§4的实机清单，不以构建绿灯代替实际模型/库存行为。

## §1 自适应概率状态

`maid_info`仍是收存时的女仆快照，可供未来互动读取；**基础走位不再读取其好感、经验、饱食度或背包容量**。
能读取这些字段不构成增加好感、消费饱食度或运行任务的授权，需要新增互动时另定玩法。

- `LivingSoulSlabClock`为本功能自有持久/同步组件，**只保存I**；没有维度、deadline或分数余量。
- 无组件或非法I时写初始7，本拍不抽签；有效I仅在服务端整秒边界以`1/I`概率判断。
- 未命中零写入；命中后随机原四向。Success提交`I−1`，玩法失败提交`I+1`，技术中性不写。
- 组件随物品换槽并由owned在取消活化时清理；重启/跨维度无需恢复时间基准。
- `canApply`按Item与活标记认领，逐枚执行时才确认确有模型快照；框架缓存按Item不缓存动态状态。

### 1.1 被动位移与机械压制

活魂符的自主走位与其它功能造成的被动位移共用容器移动原语，但二者不做动作所有权仲裁。
容器在本拍开始时扫描功能条目；更早执行的功能若移动魂符，源槽与目标槽进入`movedSlots`，
魂符原扫描条目随即失效，目标槽不会在同拍补扫成一条新魂符条目。因而本拍不进入整秒门、`1/I`抽签或方向抽取，
I保持不变；错过的机会不累计、不在下一秒补做。框架原因与不可绕开的安全边界见
[API契约 §1.3.1](../system-design/api-contract.md#131-同拍位移旧扫描失效不提供公平调度)。

功能跨槽执行序由各功能在槽位扫描中**首次出现的位置**决定，不是固定写死“活塞永远优先”。典型布局中，
朝魂符施力的活塞位于更小槽位，活塞组先执行：高电平把魂符从A推到B，下一次低电平再从B拉回A，
两拍都使随后魂符条目失效。只要这种成功位移持续发生（甚至只在每秒边界稳定发生），魂符就可以一直没有自主抽签机会。
持续通电的活塞只推一次并保持，后续无新位移时魂符恢复正常尝试；推拉失败的拍也不会凭空压制。

这不是物品复制、覆盖或随机坏运气，而是安全失效机制与确定执行序形成的机械控制玩法：
活塞可以困住活魂符。**不增加**公平轮换、连续受迫后的优先权、挣脱概率或 missed-attempt 补偿；
也不得删除`movedSlots`检查来制造挣脱，否则会让魂符按旧扫描操作空槽、替代物品或错误运行时。
活塞侧只记录本域结论，见[living-piston-tech.md §5](living-piston-tech.md#5-生命周期)。

### 1.2 居家餐供品与待兑现好感

随机方向确定后才检查目标，不预搜索食物、不重掷。空槽仍走移动；非空目标只有同时满足“非活物品、
TLM `DefaultMaidHomeMeal`允许、待兑现容量未满、目标可抽取一份”时才作为供品。成功供品不移动魂符，
在源魂符同一次组件提交中写`pending_favor+1`与`I−1`，再用`consume(target,1)`整件扣一；扣除失败则按
验证式补偿恢复源组件并技术中性。食物自身效果、使用事件、碗瓶和转化物均不执行/返还。

`living_item:pending_favor`是`maid_info`顶层我方命名空间整数；只接受合法`MaidFavorability`与TAG_Int账本，
用long饱和保证当前好感+pending不超过384。修改只复制该快照并改我方键，未知TLM/附属字段保留。
取消活化不删除已赚取账本；TLM `ToMaid`事件以最低优先级把账本从root移入待加载快照的`NeoForgeData`交接标记，
服务器Post tick确认同一`EntityMaid`真实入世且主人一致后，先删实体标记再调用`FavorabilityManager.add`。因此跨64/192/384时仍由TLM更新属性、
成就、饰品回调、等级事件与爱心；未入世或主人不符不兑现，也不擅自回滚TLM自身的魂符释放事务。

客户端把pending初值当基线，只在同一预览后续观察到增长且模型实际claim时，播放约6 tick轻微缩放脉冲
与一次本地吃声；pending从视觉身份副本中剥除，投喂不会导致预览重建、回正、停声或气泡清空。

## §2 宿主与客户端接缝

**实体宿主**：`EntityContainers.Provider`收敛认领、构造和菜单物理槽判据。
TLM提供者复用可写范围库存与EntityContainerContext，六列从`getLiveColumns()`进入共同布局链。
菜单级实体身份不等于该菜单全部槽归此实体；GUI反查、脏槽同步、tooltip与流体映射核对真实存储handler。
原实体白名单/能力面双闸仍保留；新入口不把所有生物装备栏升级成运行宿主。

**概率判定**：组件只属于物品，不依赖runtime槽缓存；每秒门控来自世界gameTime，但不保存时间。
命中后随机四向，只有实际结果改变I；技术错误保持I，下一秒重新按概率判定。

**客户端图标握手**：容器Background遍历active、非fake且显示位置唯一的真实菜单槽，先准备预览，
再按`ItemStack`对象引用与原版槽位GUI矩阵登记本帧允许透明化的位置。`smart_slab_has_maid`的inventory模型在烘焙后包装：
保留TLM原override解析（含`null`缺失模型语义），只有同帧引用与矩阵同时命中时，才在
`ItemDisplayContext.GUI`变换中记录claim并返回NeoForge `EmptyModel.BAKED`。Foreground只画实际消费到claim且仍是原槽栈的女仆，
随后无条件关闭token；数量/耐久/高亮仍由原槽位链绘制，模型异常只补底图，避免装饰重复。
复制品、官方复制槽、carried、HUD、配方/搜索项、同引用异位置和非GUI context不命中；第三方绕过上述链路时保留原图。
原渲染器直接分派模型，不改变dispatcher阴影或玩家选项，不full load/tick所存女仆。
多枚实例按宿主/物理槽独立；物理槽多显示别名不猜位置而退化原图。保存的槽位矩阵含原版Z100层级，模型与失败补图不落到界面后方；只有稳定快照唯一一对一时插值，计时组件不参与视觉身份比较。

### 2.1 展示朝向与光标（2026-11-08）

首版固定Y旋转且身体默认0，用户实测背对玩家；原生摆臂、尾巴、迈步和语音实际正常，
不需要启动完整女仆AI补动画。现去掉固定Y角，身体以原渲染器读取的角度表示：
初始/下180°、上0°、左270°、右90°，最短角度平滑转向，停步保留。

光标位置由Foreground现成事件传入，头部参考点以当前插值位置和保存的绘制矩阵变换到GUI坐标。
`SoulSlabPreviewFacing`分别维护身体与相对头角，左右限45°、俯仰限20°；
侧向略向观察者倾头、背向反转左右投影，不解算必须盯住鼠标的完整3D目标。
原renderer读body/head/pitch前后值插值，骨骼动作仍由模型决定，独立眼球响应不作跨模型承诺。

取消额外槽矩形scissor，保留界面原有scissor及异常恢复；模型仍以槽底为锚点。
原数量/耐久预留、冷却反馈回原图和真实点击链不变。不增加跳跃或舞蹈；图片气泡后续接线见§2.3。

### 2.2 定案与否决留痕

以下是设计阶段的用户取舍，不能仅由现行代码反推；原设计稿退役后以本节为正文。

| 定调 | 否决方案 / 不能重新推导的边界 | 理由与出处 |
|---|---|---|
| 基础走位采用概率自适应 | ~~确定等待I秒后必定尝试~~（中间实现）及更早的H/C均匀排期 | 用户选择I表示平均等待秒数：每秒`1/I`概率；简化组件并增加随性节奏，成功/失败反馈仍保留 |
| 命中后先随机原方向 | 不先过滤出可移动邻槽，也不失败后重掷 | 用户要“随机方向尝试移动”；否则只要有一格空位就必成功，自适应失败反馈失去意义 |
| 宿主运行兼容不改原准入 | 不为活魂符在女仆背包增加局部放行、接管拾取或全局解除嵌套限制 | 原始三条玩法是背包中的活物品运行、魂符显示女仆、魂符走位；用户明确它们不是“让魂符能进入女仆背包”。改原模组机制必须有独立用户需求，不能从“联动兼容”自行推出 |
| 功能不由viewer驱动 | 不因无人查看/GUI关闭停止迈步 | 用户明确走位是活魂符功能，问题是如何走而非何时准许工作 |
| 外部参数路线已否决 | 不用昼夜/天气等世界量驱动基础走位 | 用户要求基础走位由活魂符自身机制表达；当前概率自适应只读近期尝试结果，换宿主不改外部输入 |
| 迈步均匀、方向随机 | 不回到每tick概率迈步或再加自由基础速度倍率 | 用户用“饱食度20、背包6格，6分钟20次、间隔平均”确定比例；只有目标方向掷随机 |
| 槽位是站立锚点 | 不加槽矩形裁剪、视觉碰撞或额外占槽 | 用户认为尾巴/翅膀/大模型越槽更像女仆站在格上，而非被关在框里；实际点击仍属原物品槽 |
| 原模型显示状态，不执行实体行为 | 不为动画调用完整实体tick，不因能读好感/饥饿就顺便更新第三方快照 | 原生动画/语音用户已确认正常；本体目标是物品栏演出，不是放出女仆或重建任务AI |
| 预览临时状态可重建 | 不为关闭界面、取起放下后回正新增持久朝向/共享UUID缓存 | 用户理解并接受预览内存生命周期；服务端迈步计时另由物品组件保存 |

INIT并未存有具体女仆，原地活化生成属于另一个玩法，不是首版遗漏；状态台词、颜文字、寻路及其他未来互动
统一在需求池登记，不能为保留设想而继续维护整份已兑现实施计划。

### 2.3 最小图片气泡（2026-11-09）

复用原`EmojiChatBubbleData`、`ChatBubbleManager`的集合和`EntityMaidRenderer`自带气泡绘制，
不造气泡框架、不调用完整实体tick。原气泡是运行时数据，不从魂符还原历史说话内容。

预览逻辑tick清除原集合的过期项；只有可见且`GlobalMaidShowChatBubble`、个人`ChatBubbleShow`、
`EnableEmoji`允许、集合为空时，按原`EmojiCheckRate`和图片/颜文字权重抽取图片分支。
未选图片就跳过，不进入服务端数据包颜文字链；图片权重为0或总权重非法安全不生成。
图片来自原客户端资源（含PNG/GIF），寿命/背景用原值；不绑定待机声音生成假字幕。
