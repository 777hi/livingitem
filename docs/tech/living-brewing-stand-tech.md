## §0 玩法定义

> **实现入口**：`living/domain/brewing/` —— 关键类：`LivingBrewingStandFunction`（功能入口）·
> `BrewingStandRegistration`（域注册）· `BrewingBatchLogic`（批次状态机·纯逻辑）·
> `BrewingRecipes`（`PotionBrewing` 适配层）· `BrewingStandSegment`（runtime 遥测片段）

> **性质**：本节「规则」是**契约**（违反即 bug），不是实现细节 —— 它是本子系统
> **功能需求的来源**与**行为对错的判据**。⚠️ **只写规则与语义**；数值与操作步骤归实现层。

**语义**：**活酿造台 = 容器内的虚拟酿造台**。它把原版酿造台的酿造功能**虚拟化**进容器槽位 ——
从 3 个瓶子槽取瓶子、烧燃料槽的烈焰粉、把材料槽的材料转化成药水。

**获取**：原版酿造台 + 活化。

**核心循环**：`瓶子 ×3 + 材料 + 燃料` →（400 tick 批次）→ **最多 3 瓶原地转化 + 材料 −1**；
槽位方向可配（见 §6）。

## 1. 架构概览

### 1.1 什么是活酿造台？

活酿造台是一种特殊的活物品（Living Item），它将普通酿造台的酿造功能**虚拟化**到容器内。
活酿造台放置在容器（如箱子）的某个槽位中，从 3 个瓶子槽取瓶子、消耗材料槽的材料与燃料槽的
烈焰粉，把结果**原地写回瓶子槽**，实现容器内的自动化酿造。

宿主物品是 `minecraft:brewing_stand`（酿造台），必须同时具备活物品标记。

### 1.2 数据流总览图

```
                     ┌─────────────────────── 服务端 tick ───────────────────────┐
容器槽位（5 个方向槽）  │                                                            │
  bottle1/2/3 ────────┼─► ① 补燃料（fuel<=0 且燃料槽是烈焰粉 ⇒ fuel=20）           │
  material ───────────┼─► ② 实时判定 canBrew（材料有效 + 至少 1 瓶 hasMix）        │
  fuel ───────────────┼─► ③ BrewingBatchLogic.advance(...)  ──► Step（纯逻辑）     │
                     │         │                                                  │
                     │         ├─ Start    ⇒ fuel--、brewTime=400、记录材料 Item   │
                     │         ├─ Continue ⇒ brewTime -= step                     │
                     │         ├─ Complete ⇒ doBrew（转化 3 瓶 + 材料 -1）        │
                     │         ├─ Abort    ⇒ brewTime=0（不退不扣）                │
                     │         └─ Idle     ⇒ 无动作                                │
                     │         │                                                  │
                     │         ├─► ④ 运行时缓存（brewTime + 本批次材料 Item）      │
                     │         └─► ⑤ dirty ⇒ 写 DataComponent（fuel / 首次方向）  │
                     └────────────────────────────────────────────────────────────┘
                                              │ 运行时缓存（RuntimeSegment）同步
                                              ▼
                                     客户端 tooltip 读缓存 → 显示实时进度
```

### 1.3 关键类和职责

| 类 | 职责 |
|---|---|
| `LivingBrewingStandFunction` | **世界侧**：`tick` 解析 5 个方向槽、读实时槽内容、把 `Step` 落到槽位与组件；`HasDirection` 实现；tooltip |
| `BrewingBatchLogic` | **纯逻辑状态机**：只回答「这一 tick 该发生什么」（`Idle`/`Continue`/`Abort`/`Complete`/`Start`）—— 不碰世界 ⇒ 可单测 |
| `BrewingRecipes` | `PotionBrewing` 薄适配层：把形参名陷阱包成自解释签名 + 统一「从 `Level` 取酿造表」入口 |
| `BrewingStandSegment` | runtime 遥测片段（档 2）：批次倒计时 + 本批次材料 `Item`（瞬态 ⇒ 不影响堆叠） |
| `LivingBrewingStandData` | 数据组件：`direction`（持久）+ `fuel`（持久 + 同步） |
| `BrewingDirectionData` | 槽位名 → 方向 的映射 + 默认布局声明 |
| `BrewingStandComponents` | 组件注册（`LIVING_BREWING_STAND_DATA`） |
| `BrewingStandRegistration` | 域注册入口：注册功能 + 运行时片段 |

**职责切分**：`tick` 只负责「读槽位、把 `Step` 落地」，所有判断都在 `BrewingBatchLogic` 里
—— 所以 13 条单测能覆盖全部规则，**不依赖游戏环境**。

### 1.4 数据归属（持久 vs 瞬态）

| 状态 | 归属 | 理由 |
|---|---|---|
| 5 个槽位方向 | **DataComponent**（持久） | 玩家配置，需跨容器保留 |
| **燃料次数 `fuel`** | **DataComponent**（持久 + 同步） | 次数型、变化极慢（400t 一次）⇒ 可落盘（§9.1） |
| 批次倒计时 `brewTime` | **运行时缓存**（瞬态） | 每 tick 变，不能影响堆叠 |
| 本批次材料 `Item` | **运行时缓存**（瞬态） | 仅用于「中途换材料」检测 |
| ~~配方缓存~~ | **不做** | `hasMix` 只是几次列表扫描；做缓存反而要处理失效 |
| ~~「酿造中」标志~~ | **不需要** | 不做图标 ⇒ 谓词无消费者 |

> ⚠️ **燃料值不能进 `getIgnoredComponentTypes()`**：那是**派生数据**才能忽略的；燃料是真实数据，
> 忽略会导致堆叠合并时静默丢数据。

## 2. 核心流程（tick 主循环）

`LivingBrewingStandFunction.tick` 对每个「活酿造台所在槽位」执行：

1. **解析 5 个方向槽** —— `SlotResolver.resolve(本体槽, 方向, size, width)` 得到
   `bottle1/2/3` / `fuel` / `material` 的槽位索引（越界返回 -1 ⇒ 后续跳过）。
2. **补燃料**（对齐原版）：`fuel <= 0` 且燃料槽是烈焰粉 ⇒ `fuel = 20`、吃掉 1 个烈焰粉。
   ⚠️ **与是否在酿造无关** —— 原版 `serverTick` 开头无条件执行。
3. **实时判定 `canBrew`** —— 材料槽非空 + `isIngredient(材料)` + **至少 1 瓶 `hasMix(瓶, 材料)`**。
4. **推进状态机** —— `BrewingBatchLogic.advance(brewTime, batchIngredient, canBrew,
   currentIngredient, fuel, step)` 返回一个 `Step`，世界侧按类型落地（见 §3.1）。
5. **写回** —— 运行时缓存（瞬态）每 tick 都写；DataComponent **仅当持久数据变化时**才写
   （燃料变化 / 首次落盘默认布局）⇒ **稳态零写入**，不影响堆叠。

**关键常量**（`BrewingBatchLogic`）：

| 常量 | 值 | 说明 |
|---|---|---|
| `BREW_TIME` | `400` | 一个批次的倒计时长度（= 20 秒，对齐原版） |
| `FUEL_USES` | `20` | 1 个烈焰粉的可用次数（对齐原版 `FUEL_USES`） |

## 3. 批次机制

> 原版是**离散批次**（非连续进度）：`brewTime` 倒计时，材料失效即中止。
> 活酿造台**结构与判据顺序完全照抄**原版 `BrewingStandBlockEntity.serverTick`，只把「−1」换成「−step」。

### 3.1 状态机（`BrewingBatchLogic.advance`）

```
brewTime > 0（酿造中）：
    next = brewTime - step
    ① next <= 0 && canBrew      → Complete（转化 + 扣材料）
    ② !canBrew || 材料 Item 变了 → Abort（brewTime=0，不退不扣）
    ③ 否则                       → Continue(next)

brewTime == 0（待机）：
    canBrew && fuel > 0         → Start（fuel--、brewTime=400、记录材料 Item）
    否则                         → Idle
```

⚠️ **一个照抄原版的细节**：① 是 `if`、② 是 `else if` ⇒ **完成那一 tick 不再检查材料变化**
（命中完成分支就不会再判材料）。`BrewingBatchLogicTest#completingTick_ignoresIngredientChange` 守这条。

### 3.2 消耗点（对齐原版，D7）

> ⚠️ **燃料与材料在批次的两个端点扣，不是同一时刻** —— 这是最容易混的地方。

| 动作 | 时机 | 说明 |
|---|---|---|
| **补燃料**：`fuel = 20` + 吃掉 1 个烈焰粉 | `fuel <= 0` 且燃料槽是烈焰粉时**随时**（与是否在酿造无关） | `fuel` 只在归零时补 ⇒ 0..20 的计数器 |
| **扣 1 次燃料**：`fuel--` | **批次启动那一刻**（`brewTime` 0 → 400） | `Step.Start` 分支 |
| **扣 1 份材料**：`shrink(1)` | **批次完成那一刻**（`doBrew` 内） | 转化 1 瓶还是 3 瓶都只扣 1 |

⇒ **作废时都不退 / 不扣**（原版只有 `doBrew` 才 `shrink`，作废路径根本没走到）。

### 3.3 作废条件（对齐原版，D8）

原版就一行：`else if (!flag || !itemstack1.is(ingredient)) brewTime = 0;` —— 两个条件**任一成立**即归零：

1. **不可酿造**（`!canBrew`）：材料槽空 / 材料不是有效材料 / **3 瓶里没有任何一个能配**
2. **材料的「物品类型」变了** —— ⚠️ 只比 `Item`，**不比数量 / 内容**

| 场景 | 行为 |
|---|---|
| 1 个地狱疣 → 2 个地狱疣 | **不算换**，继续酿造 |
| 地狱疣 → 萤石粉 | **算换** ⇒ 整批作废（燃料不退、材料不扣） |
| 3 瓶全被拿走 | 命中第 1 条 ⇒ 同样作废 |

### 3.4 酿造中改动槽位的语义（对齐原版）

> 每 tick 用**实时槽内容**重算 `canBrew` ⇒ 下面的行为全部**即时生效**。
> ⚠️ **作废判据只有两条**（§3.3）：**瓶子完全不参与判据**。

| 酿造中你做了什么 | 结果 |
|---|---|
| **拿走 1 个瓶子**，剩下的仍有能配的 | **继续**；完成时只转化**剩下的那些** |
| 拿走**所有**能配的瓶子 | **整批作废**（`canBrew` = false） |
| 往**空瓶槽**塞入**可配**的瓶子 | **会被一起酿**（"中途加瓶子"生效） |
| 往瓶槽塞入**无关物品**（石头） | **无害**：`hasMix(石头, 材料)` = false ⇒ 该槽被忽略；`mix` 原样返回 ⇒ 石头不变 |
| **换掉**瓶槽里的瓶子 | ⚠️ **不作废**（原版**不记录瓶子**）⇒ 继续，产出按**当前**瓶子算 |
| **材料槽换另一种材料** | **整批作废** |
| 材料槽换成非材料 / 清空 | **整批作废** |
| **燃料槽**放别的 / 清空 | **不影响当前批次** —— 燃料在启动时已扣，`fuel > 0` 就继续 |

**两条安全保证（读源码核实）**：

- `mix(材料, 瓶子)` 对**空瓶子**直接返回空 ⇒ 空槽安全（`doBrew` 不会往空槽塞东西）。
- `mix(材料, 无关物品)`：该物品没有 `POTION_CONTENTS` ⇒ **原样返回** ⇒ 石头等不会被改动。
  ⚠️ 但**有 `POTION_CONTENTS` 的活物品**（如「活药水」）**会被改动** ⇒ 见 §3.5。

### 3.5 槽位准入（隔离规则，规则 7）

活物品是「**设备**」不是「耗材 / 载体」⇒ **三个槽位的准入都挡活物品**（与活熔炉 / 活漏斗同族）：

| 槽位 | 判据 | 不挡会怎样 |
|---|---|---|
| **材料** | 非空 + **非活物品** + `isIngredient` | 被 `consumeOne` **吃掉** |
| **瓶子** | 非空 + **非活物品** | 被 `mix` **原地转化** —— 丢掉活标记与内部状态 |
| **燃料** | 烈焰粉 + **非活物品** | 被当燃料消耗 |

⚠️ **瓶子槽也必须挡**：原版 `hasMix` 只看 `POTION_CONTENTS`、**不看活标记** ⇒
「活药水」会被判为可酿并被 `mix` **替换掉**。
⭐ **这是真实可达的场景、不是防御**：**任何物品都能被活化**（`activation_rules.json` 的
`default: allow` + `options.denyUnclaimed: false` ⇒ 连「无功能认领」的物品也能活化，
见 `LivingItemActivation` 的 javadoc）⇒ 玩家活化的**水瓶 / 药水**会真实出现在瓶子槽里。

**实现点**：`LivingBrewingStandFunction#isEligibleIngredient`（材料）· `#isEligibleBottle`（瓶子）·
`#isBlazePowder`（燃料，包级可见供测试）。**验证**：`BrewingSlotEligibilityTest`（6 项）。
⚠️ 2026-10-12 补：燃料侧判据 2026-10-11 就在，唯独漏了测试守卫（材料/瓶子两侧都补了）——
「规则表每一条都必须有验证入口」的又一次实证（§10.5 的教训当时只覆盖到实现，没覆盖到测试）。

## 4. 燃料机制

### 4.1 次数型燃料 + 落盘（D2）

- 燃料 = 烈焰粉，**1 个 = 20 次**（`FUEL_USES`）。
- `fuel` 存 `LivingBrewingStandData` 的 DataComponent（**持久 + 同步**）。
- ⚠️ **与活熔炉的燃料不同**：熔炉是**时间型**（`burnTime` 每 tick −1）⇒ 落盘会每秒写 20 次 +
  破坏堆叠 ⇒ 只能走运行时缓存；酿造台是**次数型**（每次酿造才 −1，400 tick 一次）⇒ 变化频率极低 ⇒ 落盘可行。
  **不能照抄熔炉的燃料方案。**

**代价**：`fuel=20` 与 `fuel=19` 的堆叠**不能互相合并**（未使用过的 `fuel=0` 仍可堆叠）。
⚠️ 但**不影响单个堆叠内部**（堆叠内共享同一份组件）⇒「堆叠加速」照常成立。

### 4.2 补燃料时机

照抄原版：`fuel <= 0` 且燃料槽是烈焰粉 ⇒ **立刻**补满 20、吃掉 1 个烈焰粉（与是否在酿造无关）。

⚠️ UX 含义：玩家看到的是「烈焰粉进燃料槽 → 消失 → 物品 tooltip 变成 `燃料: 20 次`」。

### 4.3 拆堆复制燃料 = 当特性保留（D2 补充）

已核实 `ItemStack.split` → `copyWithCount` → `copy()` ⇒ **组件被复制**
（`DataComponentMap` 是不可变共享）⇒ `fuel=20` 的一叠拆出 1 个，两个都是 `fuel=20` ⇒ **凭空多 20 次**。

- 框架**没有拆堆钩子**（活箱子是靠「`count > 1` 时不工作」回避的，但 D3 要堆叠加速 ⇒ 不能这么回避）。
- **用户拍板：当特性保留**（原话「如果有玩家乐意不停的堆叠拆分，那他值得这份所谓的奖赏」）。
- 📌 若日后要修：需新增框架级拆堆钩子（按比例分摊燃料），成本高、且「按比例」语义模糊。

## 5. 堆叠加速（D3 / D11）

**公式**：`step = 堆叠数`（`BrewingBatchLogic.stepFor(count) = max(1, count)`）
—— 每 tick 推进 `count` tick。

| count | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|
| 每批 | 400t（20s） | 200t | 100t | 50t | 25t | 13t | **7t** |
| 速度 | 1× | 2× | 4× | 8× | 16× | 32× | **64×** |

**为什么是 `step = count`**：唯一「过原点、斜率 1」的线性 ——
✅ 单个 = 原版 400t；✅ 低端平缓（2 个 = 2 倍，无「多堆 1 个快 7 倍」的跳跃）；
✅ **公式就是 `count`** ⇒ **不需要 `maxStack`、不需要除零保护、不需要封顶**
（每 tick 只检查一次「是否完成」⇒ 速度天然封在 ≈1 批/tick，超大堆叠也不失控）。

**成本映射 = 每批固定**（1 燃料 + 1 材料，与堆叠数无关）—— 这是**定义**，不是取舍（见 §9.2）。

⚠️ **当前实现照原版：每批有 1 tick「启动开销」** —— 完成那一 tick 只归零（`nextBrewTime = 0`），
**下一 tick 才重新启动** ⇒ `step=64` 时实际是 **8t/批** 而非 7t。
（设计稿曾计划做 **overshoot 结转** 消除这 1 tick，但**当前代码未实现**；差异仅 1 tick = 0.05 秒。）

⚠️ **上限是 7t 而非 1t —— 且这是好事**：1t/批 = 20 批/秒 = 1200 材料/分、一颗烈焰粉只够 1 秒（失控）；
7t/批 ≈ 171 材料/分（≈514 瓶/分），屏幕上已是「瞬间」。

## 6. 方向配置系统

### 6.1 槽位模型

5 个方向槽位：`bottle1` / `bottle2` / `bottle3` / `fuel` / `material`。
默认布局（相对活酿造台，`BrewingDirectionData.DEFAULT_BREWING`）：

```
瓶子1(↖)   瓶子2(↑)   瓶子3(↗)
燃料(←)    活酿造台    材料(→)
```

⚠️ 该布局需要 **2 个对角方向**（`↖` `↗`）⇒ 依赖框架的**九宫格方向输入**
（键位 `QWE/ASD/ZC`，见 [gui-interaction-system.md](../system-design/gui-interaction-system.md) §6）。

### 6.2 槽位解析

`SlotResolver.resolve(本体槽位, 方向, 容器 size, 容器 width)` —— 与活熔炉共用同一套解析
（`living/transfer/SlotResolver`）。越界返回 -1 ⇒ 该槽位被跳过。

### 6.3 斜向能力（`supportsDiagonal`）

`LivingBrewingStandFunction#supportsDiagonal()` 返回 `true` ——
这是**九宫格对角键（`Q/E/Z/C`）在框架里「按能力放行」的唯一声明点**。
未声明对角的功能（如活熔炉 / 活漏斗）上，对角键**直接忽略**、`Q`/`E` 保持原版行为（丢弃 / 关界面）。

### 6.4 未配置时的行为

- `BrewingDirectionData.getDirection(未配置槽位)` 返回 `Pos2D.NONE`（显示为「·」）。
- 但 `LivingBrewingStandData.of()` 在组件缺失时返回 `DEFAULT`（**已含完整默认布局**）
  ⇒ 未配置的活酿造台**直接按默认布局工作**（首次 tick 会落盘默认布局）。
- `updateSlotDirection` 首次配置时以默认布局为底（其余槽位保持默认）。

## 7. 与活漏斗的交互（D6）

**基本机制（与熔炉一致，天然支持）**：活酿造台的 5 个槽位 = **周围的普通容器槽位**（方向配置指向）。
活漏斗只认「槽位」不认「酿造台」⇒ **投料 / 取货天然可用，零额外代码**。

**4 个具体问题**：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **无槽位准入** | 石头能放进「材料槽」（与熔炉一致：不工作但不报错）。要准入需框架新能力（**不做**） |
| 2 | **取货会中断酿造** | 漏斗取走瓶子 ⇒ 若「还有能配的瓶子」则继续、否则作废（精确语义见 §3.4） |
| 3 | **空瓶干扰** | 空瓶会被一并取走 ⇒ 需漏斗自己的黑白名单过滤 |
| 4 | **跨容器** | 邻居侧只认裸 `IItemHandler`；普通槽位投料 / 取货正常 |

## 8. 酿造反馈（白幕 + 燃料条 + 完成音效，2026-10-12 立 / 10-13 修订）

活酿造台是**物品**：没有专属 GUI、没有方块形态、不开箱时甚至看不见槽位。原版的酿造反馈
（进度箭头 / 燃料格 / 冒泡循环 / 完成音）全部长在方块与 GUI 上，直接照搬不了。本节的取舍 =
**把反馈搬到「物品图标 + 声音」上**：白幕管「在不在酿」、燃料条管「还能烧几次」、音效管「这批完了」。

> 📜 **2026-10-13 修订**：白幕从「组件存权威起始时刻 + 客户端与服务端时钟对齐」简化为
> **纯客户端本地动画**（用户判定：锦上添花不必精确）—— 删掉 SetTimePacket 校正链路与
> 两个偏差源；堆叠加速改为「时长按堆叠数折算」（零新数据）。同时新增燃料条，
> 并把进度条做成框架级 `ProgressBarDecorator`。

### 8.1 白幕：复刻原版物品冷却语言（本地动画）

- **形态**：批次进行中，图标底部往上消退的**纯白覆盖层**——几何、颜色、方向全部照抄原版
  物品冷却（`GuiGraphics.renderItem`：底部对齐、高度 = 16 × 剩余比例、
  `Integer.MAX_VALUE` = `0x7FFFFFFF` ⇒ **约 50% 半透明白** —— 原版冷却下能隐约看到物品图标）。
  玩家对「末影珍珠 / 盾牌的那个白幕」已有条件反射，零学习成本；
- **数据流**：组件 `brewStartTick` 是**批次标记**（`BrewingBatchLogic.batchMarkAfter`）——
  **只在批次进行中有效**：`Start` 写 `level.getGameTime()`、`Continue` 保持，
  `Complete` / `Abort` / **`Idle` 一律收起**（`-1`）；稳态零写入（只在「有↔无」翻转时写）。
  客户端第一次见到某个标记时记下**本地**时刻作为动画起点，之后每帧
  `f = 1 − (本地now − 起点) / 时长`；
- **⭐ 为什么不需要校正**：起点与 now **同为客户端时钟** ⇒ 不漂，不需要 `ClientboundSetTimePacket`
  校正、不存在跨机器偏差（原版末影珍珠冷却同款做法：`ItemCooldowns` 用客户端自己的 tickCount）。
  初版的「堆叠偏慢 / 校正滞后 / 接缝闪断」三个偏差源随之消失两个、第三个本就是「重播」语义；
- **堆叠加速（零新数据）**：时长 = `BREW_TIME / 堆叠数`，与服务端 `BrewingBatchLogic.stepFor(count)`
  严格同源；堆叠数就在栈上（`stack.getCount()`）⇒ **不需要任何新组件字段**。堆叠 4 个 = 动画 1/4 时长；
- **重播语义**：新批次 ⇒ 新标记 ⇒ 新起点 ⇒ 白幕自动重新满格（哪怕上一段还没播完）——
  不是额外逻辑，是「新 key 新起点」的自然结果；
- **播完不删**：条目留在 map 里当「这个批次播过了」的戳 ⇒ 避免「播完被重建、反复重播」的竞态；
  map 只增（一次游戏几十个 long 条目），跨存档清理时统一清空；
- **tooltip 互补**：悬浮仍有数字版（百分比 + 剩余秒数，服务端权威）。白幕管「扫一眼」，
  tooltip 管精确值；
- **边界**：批次不跨存档（`brewTime` 在运行时缓存，服务端重启即清）。
  ⭐ **「没有进度却还在播」已由 `Idle` 自愈覆盖**（2026-10-13 修，用户实测发现）：
  物品被移出容器后运行时缓存按方案 A 作废（`brewTime` 归零）⇒ 状态机走不到
  `Complete`/`Abort`（那两支要求 `brewTime > 0`）⇒ 组件标记残留 ⇒ 客户端拿它当
  「批次在跑」的凭据 ⇒ 白幕空播完一轮。⇒ `Idle` 也收起标记
  （`batchMarkAfter` 的 `default -> -1L`），顺带把旧边界「重启后材料不足」一并修好
  （当时判定「接受空播、不写守卫」，现在零成本解决）。
  **唯一剩余**：物品**被拿在手上**（不在任何容器槽 ⇒ 不被 tick）时，最多播完当前这一轮
  （≤ 20 秒，且玩家通常会很快放回容器）。

### 8.2 燃料条：原版耐久条同款几何

- **为什么是耐久条形态**：耐久条是 MC 里唯一长在图标上的进度语言（快捷栏 / 背包 / 任何容器
  全覆盖），玩家已有条件反射。几何照抄原版（`GuiGraphics.renderItemDecorations` 源码）：
  左下角 13×2 黑底 + 13×1 彩条，从左往右长；
- **颜色**：取烈焰棒纹理（`blaze_rod.png`）的色相并提亮 ⇒ `#F8A820`。理由：细条画在浅灰槽位上，
  忠实平均色 `#C4861A` 偏暗会糊；原版耐久条用的也是高亮全饱和色；
- **画条口径**：`fuel > 0` 才画（满条 = 满燃料是正反馈），与耐久条「有损才画」互补；
  燃料 0 时不画（tooltip 里说「无燃料」）；
- **数据来源约束（框架级，决定了「条能画什么」）**：装饰器接口只有 `(stack, x, y)`、
  **拿不到槽位索引** ⇒ 只能读「跟着物品走」的数据。燃料次数是落盘组件 ✅；
  运行时缓存里只发给 viewer 的瞬态量（酿造倒计时、漏斗冷却）❌ —— 那些归 tooltip 与白幕。
  这同时是进度条**天生全场景新鲜**的原因；
- **框架**：`ProgressBarDecorator`（通用；横 = 左下从左往右长、竖 = 左缘从底往上长；
  几何为纯函数可单测）+ 每种活物品注册一个「栈 → (比例, 颜色, 朝向)」函数。
  酿造台是第一个接入方；下一个（活水源液位、活发电机能量）只需加一行注册；
- **z 层次**：条 190 < 白幕 200 ⇒ 白幕播放时盖在条上（白幕是「进行中」横幅）；
- **多装饰器**：NeoForge 原生支持一个物品多个装饰器（`RegisterItemDecorationsEvent` 内部
  就是 `Map<Item, List<IItemDecorator>>`）⇒ 项目侧 `LivingIconSpec.decorator(...)` 改为可多次调用。

### 8.3 ⭐ 为什么不直接驱动原版冷却（addCooldown）

服务端 `player.getCooldowns().addCooldown(Items.BREWING_STAND, ticks)` 能**零代码**蹭到
原版渲染与同步（`ServerItemCooldowns` 自动发 `ClientboundCooldownPacket`），评估后**否决**，
三条语义债（全部源码实证）：

| 债 | 说明 |
|---|---|
| 按**物品类型 × 玩家**，不按实例 | 玩家眼前所有酿造台物品一起糊；两个错峰批次只显示最后一次 |
| 冷却期内该物品类型**右键使用被丢包** | `MultiPlayerGameMode#useItem` 的 `!isOnCooldown(item)` 门槛 ⇒ 手里拿着酿造台放不出方块 |
| 只有「见证开始」的批次才显示 | 关着的箱子里开批没有冷却可加；需在开容器 / 切维度时补发 |

⇒ **自绘同款视觉、数据按实例走**：`LivingBrewingStandDecorator`（约 90 行）+ 组件一个字段。

### 8.4 完成音效（项目第一个活物品音效）

- **素材**：原版 `SoundEvents.BREWING_STAND_BREW`（对齐原版 `levelEvent 1035`，原汁原味）；
- **发给谁**：`playBrewSound` 只发**正在照看这台机器的人**——世界容器 ⇒ 开着这个容器
  GUI 的玩家（`ContainerContexts#isViewing`）；背包 / 末影箱容器 ⇒ 主人本人（不管开没开
  GUI，自己的酿造完成自己听见）；
- **为什么不半径广播**：原版玩家站在方块旁 ⇒ 等价于「开着 GUI」；活酿造台可能在背包 /
  远处箱子里，按位置广播要么听不到（人走远了）、要么扰民（路人无故听响）；
- **位置**：容器方块中心；背包容器取玩家自身位置。客户端按距离衰减（位置音）⇒ 离箱子远
  就轻，符合直觉；
- **假玩家守卫**：`FakePlayer`（活工具回放）没有真实 connection，发包前判 `connection != null`。

### 8.5 反馈层的验证入口

- 组件 codec（旧数据可解码 / 新字段真在 codec 里）→ `LivingBrewingStandDataTest`（4 项）；
- 白幕（守卫 / 时长堆叠折算 / 比例时间线 / 动画起点与重播 / 播完不删 / 跨存档清理）→
  `LivingBrewingStandDecoratorTest`（8 项）；
- 进度条（守卫 / 横竖几何 / 燃料刻度 / 越界 clamp）→ `ProgressBarDecoratorTest`（6 项）；
- 批次标记生命周期（`Start` 写当下 / `Continue` 保持 / `Complete`·`Abort`·**`Idle` 自愈**收起）→
  `BrewingBatchLogicTest`（14 项，含 2026-10-13 的 `Idle` 自愈回归）；
- 画面与声音本身 → 游戏内（附录·验证清单·酿造反馈）。

## 9. 关键设计决策（理由留档）

> 以下理由**代码里读不出来** ⇒ 必须留档（铁律 3）。**决策正文即本节** ——
> 按 [decisions.md](../decisions.md) §6「逐子系统的实现细节决策不收录」，本子系统不进决策索引。

### 9.1 D2 · 为什么燃料能落盘、熔炉的不能

熔炉燃料是**时间型**（`burnTime` 每 tick −1）⇒ 落盘会每秒写 20 次 + 破坏堆叠 ⇒ 只能走运行时缓存；
酿造台燃料是**次数型**（每次酿造才 −1，400 tick 一次）⇒ 变化频率极低 ⇒ 落盘可行。
⚠️ **不能照抄熔炉的燃料方案。**

### 9.2 D3 / D11 · 堆叠语义 = 「N 台并行酿造台」，成本映射只能是「每批固定」

- ⚠️ 已核实熔炉的堆叠**不是**「单位成本不变」，而是**亏本加速**：速度 `1+count/8`、燃料**每 tick ×count**
  ⇒ 每单位产出的燃料成本 = `count/(1+count/8)`（count=2 → 2.0×、8 → 4.0×、64 → 7.1×）。
  ⇒ **熔炉是「用燃料换时间」**；「照抄熔炉」只能照抄**曲线**，成本映射必须另定。
- **成本映射必须「每批固定」—— 这是定义，不是取舍**：只有它能维持「N 堆叠 ≡ N 台独立机器」：

  | 400 tick 内 | N 台独立 | **N 堆叠 + 每批固定** | N 堆叠 + ×count |
  |---|---|---|---|
  | 材料 / 燃料 | N / N | **N / N** ✓ | **N² / N²** ✗ |
  | 产出药水 | 3N | **3N** ✓ | 3N |
  | 每瓶的材料成本 | 1/3 | **1/3** ✓ | **N/3** ✗ |

  ⇒ 「×count」会让成本变成 **N²**（堆 64 个 → 400t 内消耗 4096 份材料）⇒ 荒诞。
  ⇒ 由此得出清晰的设计意图：**堆叠的唯一收益 = 槽位压缩**（1 个槽位 = N 台机器的产能）；
  玩家**不堆叠、分开摆效果完全相同**（只多占槽位 + 多配 N−1 次方向）⇒ **中性设计**（不惩罚也不奖励）。

**设计原则（本子系统沉淀）**：**不替玩家做决定 —— 实现简单不是砍掉玩家选择的理由**。
反面教材：曾以「堆叠与燃料落盘有矛盾」为由建议「不做堆叠加速」，既误判技术、也越界替玩家做了决定。

### 9.3 D9 · 残留物为什么「放回槽位」而不是「掉落」

原版靠 `Containers.dropItemStack(level, 方块坐标…)` 掉落，而活物品**没有坐标** ——
`SimpleContainerContext.associatedBlockPositions` 是**私有字段**（只用于生成容器 key），
`ContainerContext` 接口**没有** `getPosition()`；且**玩家背包 / 末影箱这类容器坐标为空的**
⇒ 「掉落」对背包场景**无解**。⇒ 改照**本框架既有先例**：活熔炉 `consumeFuel` 把残留物**放回槽位**。

⚠️ 影响面 ≈ 0：原版全部酿造材料（地狱疣 / 萤石粉 / 红石 / 火药 / 龙息 / 发酵蜘蛛眼 / 糖 / 兔子脚 /
闪烁的西瓜 / 河豚 / 岩浆膏 / 金胡萝卜 / 海龟壳…）**都不带合成残留物**。

### 9.4 模组兼容 = 零工作量

`level.potionBrewing()` 返回的实例**已在 bootstrap 聚合所有来源**
（原版三张表 + `RegisterBrewingRecipesEvent` 注册的全部模组配方）。
⇒ 活酿造台**只调这一个入口**，自动兼容所有模组的药水配方，**不需要任何兼容代码**。
（同族先例：活熔炉共用 `RecipeType.SMELTING`。）

### 9.5 D7~D10 · 一律对齐原版

用户原则：**能对齐的就对齐，实在无法对齐的再讨论**。
D7（消耗时机）/ D8（作废条件）/ D10（搬运丢进度留燃料）全部对齐原版；
唯一**无法对齐**的是 **D9（残留物）**（见 §9.3）。

## 10. 实现踩坑与注意点

### 10.1 ⚠️ `PotionBrewing` 的形参名是误导的

`hasMix` / `mix` 的形参名（`reagent` / `potionItem`）**与实际语义不符** ——
原版自己在 `mix` 里注释了 `"Parameters are swapped compared to what vanilla passes!"`。
⇒ **一律以调用点为准**：`hasMix(瓶子, 材料)`、`mix(材料, 瓶子)`。

本项目的解法：`BrewingRecipes` 薄适配层把签名固定成自解释的 `hasMix(brewing, bottle, ingredient)` /
`brew(brewing, ingredient, bottle)`，**把坑收在这一处**。

### 10.2 旧数据可解码（`optionalFieldOf`）

`fuel` 用 `Codec.INT.optionalFieldOf("fuel", 0)` ⇒ **只有 `direction` 字段的旧数据仍可解码**
（第一段落地过、可能已写进存档）。⚠️ 虽然项目规约「不做旧存档兼容」（铁律 6），
但这里用的是**增量字段的优雅降级**（缺失即默认），代价为零 ⇒ 顺手做掉。

### 10.3 「完成那一 tick 不再检查材料变化」

`BrewingBatchLogic.advance` 里 ① 是 `if`、② 是 `else if` ⇒ 命中完成分支就不会再判材料。
这是**照抄原版**（`else if`）的行为，不是疏漏。改动前先读 `BrewingBatchLogicTest`。

### 10.4 只写必要数据（稳态零写入）

`tick` 里 DataComponent **仅当 `dirty`**（燃料变化 / 首次落盘默认布局）时才 `set` + `syncSlotToClients`
⇒ 稳态零写入，避免每 tick 无谓同步。

### 10.5 ⚠️ 隔离规则「文档写了、实现漏了」（2026-10-11 修复）

首版实现**漏了 `LivingItemManager.isLivingItem` 检查**（材料 / 燃料 / 瓶子三处都没有），
用户实测发现「**活红石被当材料消耗**」—— 而 §0 规则 7 与设计稿 §2 都写了「活物品不作材料 / 燃料」。
（同族对照：活熔炉的输入槽 / 燃料槽**都有**该检查。）

⇒ **教训**：**§0 规则表里每一条都必须有对应的实现点与验证入口** ——
只写在规则表里不构成实现，规则表反而会让人以为已经做了。
本次补了 `isEligibleIngredient` / `isEligibleBottle` / `isBlazePowder` 三个准入判据 + 4 项单测。
⚠️ **2026-10-12 复查发现**：4 项单测只覆盖了材料与瓶子两侧，**燃料侧的判据当时漏了测试守卫**
（判据 `isBlazePowder` 是 private，测试够不着）⇒ 补 2 项（活烈焰粉 / 普通烈焰粉 + 空槽），
共 6 项。教训升级为：**「规则 → 实现点 → 验证入口」三件套，当初复盘时也只核对到前两件**。

## 11. 调试指南

### 11.1 查看状态

- **物品 tooltip**：`燃料: N 次` / `酿造中: P%（剩余 S 秒）` / 5 个槽位方向。
- **容器界面 HUD**：手持活酿造台悬停活按钮 → 显示方向配置（`QWE/ASD/ZC` 输入）。

### 11.2 常见问题

| 现象 | 排查 |
|---|---|
| 不开始酿造 | ① 材料槽是否有有效材料 ② 至少 1 瓶 `hasMix(瓶, 材料)` ③ `fuel > 0`（或燃料槽有烈焰粉） |
| 酿到一半停了 | 材料被换 / 瓶子全被拿走 / 材料槽清空 ⇒ 整批作废（§3.3） |
| 堆叠不加速 | 确认是**同一堆叠**（`count > 1`）；`step = count`，8 个 = 8 倍速 |
| tooltip 进度不动 | 进度在**运行时缓存** ⇒ 需服务端在跑；客户端缓存靠 `RuntimeSegment` 同步 |
| 方向配不上对角 | 该功能是否声明 `supportsDiagonal()`；键位是 `QWE/ASD/ZC`（`X` 弃用） |
