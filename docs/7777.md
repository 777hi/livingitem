## 建议 1：`processContainerAt` 双重扫描合并

**现状**：`processContainerAt` 先扫描一遍检查有没有活物品，再在 `processContext` 里扫描第二遍按功能分组。两次全量扫描。

```java
// 第一次扫描（processContainerAt）
for (int i = 0; i < context.getSize(); i++) {
    if (LivingItemManager.isLivingItem(context.getItem(i))) {
        hasLivingItem = true;
        break;
    }
}
if (!hasLivingItem) return false;

// 第二次扫描（processContext）
for (int i = 0; i < context.getSize(); i++) {
    ItemStack stack = context.getItem(i);
    if (LivingItemManager.isLivingItem(stack)) {
        // 分组...
    }
}
```

**建议**：把惰性检查合并到 `processContext` 内部，一次扫描同时完成"检查有没有"和"分组"，没有活物品直接 return。省掉一次全容器扫描。

## 建议 2：`ContainerSnapshot` 缓存

**现状**：每 tick 都重建 `ContainerSnapshot`，包括遍历所有槽位、解析所有活漏斗的 source/target、递归构建过滤链。

**问题**：大部分容器在大部分 tick 里没有任何变化，但 snapshot 仍然全量重建。

**建议**：给 `ContainerSnapshot` 加一个版本号或脏标记。只有当容器内容发生变化（`setItem` 被调用）时才重建。可以在 `SimpleContainerContext.setItem` 里递增一个 `version` 字段，`TickContext.reset` 里比较版本号决定是否重建。

```
改动前：每 tick 无条件重建 snapshot
改动后：仅当 container.version != lastVersion 时重建
```

这对"大部分容器闲置"的服务器场景收益明显。

---

## 建议 3：`syncWorldContainer` 的反向索引

**现状**：同步世界容器时，遍历所有在线玩家，检查每个人的 `containerMenu` 是否匹配：

```java
for (ServerPlayer serverPlayer : level.getServer().getPlayerList().getPlayers()) {
    AbstractContainerMenu menu = serverPlayer.containerMenu;
    // 检查 menu 是否匹配...
}
```

**问题**：每次同步一个槽位，O(所有在线玩家)。大型服务器上可能几十上百人。

**建议**：维护一个 `Map<BlockPos, Set<ServerPlayer>>` 反向索引，记录哪些玩家正在查看哪个容器。玩家打开容器时注册，关闭时注销。同步时直接查索引，O(查看者) 而非 O(所有玩家)。

---

## 建议 4：`ContainerChunkCache` 定期校验

**现状**：缓存完全依赖事件驱动（chunk load/unload, block place/break）。如果某个事件被吞掉或遗漏，缓存就会永久错误。

**建议**：加一个低频率的校验（比如每 600 tick = 30 秒），随机抽查几个缓存中的区块，验证它们确实还有容器。如果发现不一致，重新扫描。成本极低（每 30 秒只抽查几个），但能防止缓存漂移。

---

## 建议 5：`getItem` 返回副本的安全性

**现状**：`SimpleContainerContext.getItem` 直接返回 `handler.getStackInSlot(logicalSlot)`——原始引用。

```java
public ItemStack getItem(int logicalSlot) {
    return handler.getStackInSlot(logicalSlot);
}
```

**风险**：调用方如果意外修改了返回的 ItemStack（比如 `setCount`），会直接污染容器数据。IItemHandler 的实现通常返回内部引用，不是副本。

**建议**：返回 `copy()`。代价是每 tick 多几次 copy，但避免了一类极难排查的 bug。如果担心性能，可以只在"已知会修改"的调用路径上 copy，其他地方加 `@NotNull` 文档说明。

---

## 建议 6：过滤链深度限制

**现状**：`ContainerSnapshot.buildFilterForSlot` 递归构建过滤链，用 `visited` 集合防循环，但没有深度限制。

**建议**：加一个 `maxDepth`（比如 16），超过深度直接返回 `FilterData.EMPTY`。防止恶意或错误配置的活漏斗链导致栈溢出。
