## 项目架构全面审查

经过对整个代码库的深入审查，我从**架构合理性**、**原版/NeoForge 模式利用**、**未来扩展性**三个维度提出以下分析和建议。

---

### 一、当前架构的亮点（做得好的地方）

1. **组件化 + 编排器模式**：`ILivingComponent` + `LivingOrchestrator` 的分层很清晰，新增活物品只需声明配置，几乎零代码
2. **SlotAccessor 统一抽象**：传输引擎与存储后端完全解耦，新增活箱子/活末影箱等存储类型无需改传输逻辑
3. **DataComponent 直存架构**：利用 1.21 的 DataComponent 系统替代 NBT，类型安全 + 自动同步
4. **ContainerChunkCache 事件驱动缓存**：避免全量扫描区块，性能优化到位
5. **S2C 同步包模式**（刚完成的重构）：`EnderChannelClientCache` + `EnderChannelSyncPacket` 是 Minecraft 标准的客户端-服务端数据分离模式

---

### 二、架构问题与改进建议

#### 🔴 P0：ComponentState 基于 CompoundTag —— 应迁移到 DataComponent

**现状**：[ComponentState.java](file:///g:/777hi/mc/mymods/livingitem-template-1.21.1/src/main/java/com/qiqi/li/living/core/ComponentState.java) 本质是 `CompoundTag` 的包装器，通过字符串 key（如 `"_us"`、`"progress"`）读写数据。

**问题**：
- **类型不安全**：`state.getInt("progress", 0)` — 拼错 key 不会编译报错，运行时静默返回默认值
- **与 DataComponent 系统不一致**：项目已用 `IS_LIVING` 和 `LIVING_FUNCTION_DATA` 两个 DataComponent，但组件状态仍走 CompoundTag 路线
- **序列化开销大**：每次 tick 都要 `CompoundTag → NBT → CompoundTag` 往返
- **无法利用原版同步机制**：DataComponent 自带网络同步，CompoundTag 需要手动 `syncSlotToClients`

**建议**：将每个组件的状态定义为一个 record，注册为独立的 DataComponentType。例如：

```java
// 旧：ComponentState (CompoundTag wrapper)
state.setInt("progress", 50);
state.setInt("total", 200);

// 新：强类型 record + DataComponent
public record ProgressData(int current, int total, boolean paused) {
    public static final Codec<ProgressData> CODEC = RecordCodecBuilder.create(...)
    public static final StreamCodec<RegistryFriendlyByteBuf, ProgressData> STREAM_CODEC = ...
}
```

**好处**：
- 编译时类型检查
- 自动网络同步（不再需要 `syncSlotToClients`）
- 与原版 `ItemStack` 体系一致（`stack.get(PROGRESS_DATA)` / `stack.set(PROGRESS_DATA, newData)`）
- 原版配方系统、附魔系统等可以直接感知组件状态

**迁移路径**：渐进式 — 先保留 `ComponentState` 作为过渡层，新组件用 DataComponent，旧组件逐步迁移。

#### 🔴 P0：LivingFunctionData 是"CompoundTag 大杂烩" —— 应拆分为独立 DataComponent

**现状**：[LivingFunctionData.java](file:///g:/777hi/mc/mymods/livingitem-template-1.21.1/src/main/java/com/qiqi/li/living/LivingFunctionData.java) 将所有活物品功能的数据塞进一个 `CompoundTag`，键名为 functionId。

**问题**：
- 一个组件的修改导致整个 `LivingFunctionData` 重新序列化
- 不可变设计下，每次修改创建新实例，但数据量大时开销高
- 无法利用 DataComponent 的增量同步（1.21 的 DataComponent 系统只同步变化的组件）

**建议**：将 `LIVING_FUNCTION_DATA` 拆分为每个功能独立的 DataComponentType：

```java
// 旧：一个大数据块
LIVING_FUNCTION_DATA → { "living_furnace": {...}, "living_hopper": {...} }

// 新：每个功能独立组件
LIVING_FURNACE_DATA → ProgressData + FuelData + TransformData
LIVING_HOPPER_DATA  → DirectionData + TransferData + FilterData
LIVING_CHEST_DATA   → InternalStorageData
```

**好处**：增量同步（只同步变化的组件）、类型安全、与原版堆叠比较逻辑一致。

#### 🟡 P1：FunctionExecutor 是单例 + 反射创建组件 —— 应改为注册表模式

**现状**：[FunctionExecutor.java](file:///g:/777hi/mc/mymods/livingitem-template-1.21.1/src/main/java/com/qiqi/li/living/core/FunctionExecutor.java) 通过 `componentCache.computeIfAbsent(clazz, c -> c.getDeclaredConstructor().newInstance())` 反射创建组件。

**问题**：
- 反射创建绕过编译时检查
- 单例 `FunctionExecutor.INSTANCE` 持有全局缓存，无法支持不同配置的同类组件
- `LivingFunctionConfig` 的 `ComponentEntry` 既有 `componentClass` 又有 `preconfiguredInstance`，两套创建路径

**建议**：采用 NeoForge 的 `DeferredRegister` 模式注册组件：

```java
public static final DeferredRegister<LivingComponentType<?>> COMPONENT_TYPES =
    DeferredRegister.create(LIVING_COMPONENT_REGISTRY_KEY, MOD_ID);

public static final Holder<LivingComponentType<?>> PROGRESS =
    COMPONENT_TYPES.register("progress", () -> LivingComponentType.builder()
        .componentClass(ProgressComponent.class)
        .factory(ProgressComponent::new)
        .defaultState(ProgressState::new)
        .build());
```

#### 🟡 P1：ContainerContext 接口过于庞大 —— 应拆分关注点

**现状**：[ContainerContext.java](file:///g:/777hi/mc/mymods/livingitem-template-1.21.1/src/main/java/com/qiqi/li/living/container/ContainerContext.java) 承担了太多职责：物品读写、槽位限制、同步、快照、流体数据、占用标记、传输标记...

**问题**：
- 违反接口隔离原则（ISP）：活TNT不需要 `getTransferredTargetSlots()`，活漏斗不需要 `getBlockPos()`
- 每新增一个容器级功能（如红石信号），就要往 `ContainerContext` 加方法

**建议**：拆分为能力接口，按需组合：

```java
interface ItemContainer {    // 基础：物品读写
    int getSize();
    ItemStack getItem(int slot);
    void setItem(int slot, ItemStack stack);
}

interface SyncableContainer { // 同步能力
    void syncSlotToClients(int slot, ItemStack stack);
}

interface WorldContainer {    // 世界关联能力
    Level getLevel();
    BlockPos getBlockPos();
}

interface SnapshotContainer { // 快照能力
    ContainerSnapshot getSnapshot();
}
```

#### 🟡 P1：ContainerFluidData 是全局静态 Map —— 应绑定到 BlockEntity 或 Capability

**现状**：[ContainerLivingItemHandler.java](file:///g:/777hi/mc/mymods/livingitem-template-1.21.1/src/main/java/com/qiqi/li/living/container/ContainerLivingItemHandler.java) 中 `FLUID_DATA_CACHE` 是一个 `LinkedHashMap<String, ContainerFluidData>`，用 containerKey 做索引，手动管理过期清理。

**问题**：
- 全局静态 Map 无法随世界卸载自动清理
- containerKey 的生成逻辑分散在 `SimpleContainerContext` 中，容易不一致
- 无法利用 NeoForge 的 Capability 系统

**建议**：利用 NeoForge Capability 将流体数据绑定到 BlockEntity：

```java
// 注册 Capability
public static final Capability<ContainerFluidData> CONTAINER_FLUID =
    CapabilityManager.get(new CapabilityToken<>(){});

// BlockEntity 初始化时自动创建
level.getCapability(CONTAINER_FLUID, pos);  // 自动生命周期管理
```

**好处**：随 BlockEntity 自动创建/销毁、无需手动清理、支持模组容器。

#### 🟡 P1：活物品 Tick 调度是"拉取模型" —— 应考虑 NeoForge TickEvent 改造

**现状**：`LivingItem.onServerTick` → 遍历所有容器 → 遍历所有活物品 → tick。这是典型的**拉取模型**。

**问题**：
- 每个 tick 都要遍历所有容器位置（即使没有活物品）
- `ContainerChunkCache` 的"有容器的区块"缓存缓解了问题，但仍需扫描所有方块实体
- 无法按优先级调度（如活TNT引信应比活漏斗优先）

**建议**：改为**注册模型** — 活物品激活时注册到全局调度器，移除时注销：

```java
public class LivingItemScheduler {
    // 按 tick 优先级分组
    private final List<ActiveLivingItem> highPriority = new ArrayList<>();  // TNT, 爆炸
    private final List<ActiveLivingItem> normalPriority = new ArrayList<>(); // 漏斗, 熔炉
    private final List<ActiveLivingItem> lowPriority = new ArrayList<>();   // 箱子, 末影箱

    public void register(ItemStack stack, ContainerContext ctx, int slot) { ... }
    public void unregister(ItemStack stack) { ... }
    public void tick() { ... }
}
```

**好处**：O(活物品数) 而非 O(容器数)、支持优先级调度、活物品移除后零开销。

#### 🟢 P2：ComponentConfig 是弱类型 Map —— 应改为 Record

**现状**：[ComponentConfig.java](file:///g:/777hi/mc/mymods/livingitem-template-1.21.1/src/main/java/com/qiqi/li/living/core/ComponentConfig.java) 用 `Map<String, Object>` 存储配置，通过 `config.get("recipe_type", RecipeType.class, SMELTING)` 读取。

**建议**：每个组件定义自己的配置 Record：

```java
public record ProgressConfig(int totalTicks, boolean canPause) {
    public static final ProgressConfig DEFAULT = new ProgressConfig(200, true);
}

public record TransformConfig(RecipeType<?> recipeType, boolean consumeContainer) {
    public static final TransformConfig SMELTING = new TransformConfig(RecipeType.SMELTING, false);
}
```

#### 🟢 P2：活箱子存储仍用 ItemContainerContents —— 应考虑自定义 DataComponent

**现状**：活箱子用原版 `ItemContainerContents`（即 `CONTAINER` 组件）存储物品，但有 16384 字节限制。

**问题**：
- `ItemContainerContents` 是为潜影盒设计的，不适合大量物品存储
- 16384 字节限制导致活箱子容量受限
- 每次读写都要序列化/反序列化整个容器

**建议**：自定义 `LivingChestStorage` DataComponent，使用增量序列化：

```java
public record LivingChestStorage(List<NonNullList<ItemStack>> chests) {
    // 只序列化非空槽位
    // 支持按箱子索引增量读写
    // 压缩存储：空槽位用位图标记
}
```

---

#### 🟢 P2：交互系统应利用原版 UseOnContext 模式

**现状**：GUI 交互通过 Mixin 拦截 `mouseClicked` → `GuiInteractionPacket` → `InteractionRegistry`。

**建议**：对于"2D物品栏 ↔ 3D方块世界"的交互，可以参照原版 `UseOnContext` / `InteractionResult` 模式，定义统一的 `LivingInteractionContext`：

```java
public class LivingInteractionContext {
    private final ItemStack trigger;     // 触发物品
    private final ItemStack target;      // 目标物品
    private final ContainerContext container; // 容器上下文
    private final int targetSlot;        // 目标槽位
    @Nullable private final Level level; // 世界（可能为空，如背包中）
    @Nullable private final BlockPos pos;// 方块位置（可能为空）
}
```

这样未来"活物品右键方块"和"方块右键活物品"可以复用同一套交互逻辑。

### 三、未来扩展性建议

#### 1. 活物品 ↔ 方块世界双向通道

当前活物品只能"在容器内运行"，无法主动影响方块世界（除了爆炸）。建议：

```
活物品 → 方块世界：
  - 活漏斗 → 向相邻方块容器推拉物品（已有 CrossContainerTransfer）
  - 活活塞 → 推拉方块（新组件：BlockManipulateComponent）
  - 活红石 → 发射红石信号（新组件：RedstoneSignalComponent）

方块世界 → 活物品：
  - 方块被破坏 → 物品掉落进活箱子（新事件：BlockBreakComponent）
  - 红石信号 → 激活/停用活物品（新组件：RedstoneReceiverComponent）
  - 实体碰撞 → 触发活TNT（新组件：EntityProximityComponent）
```

#### 2. 利用 NeoForge Capability 打通物品栏与方块

NeoForge 的 Capability 系统天然支持"同一个接口，不同实现"：

```java
// 统一接口：无论物品栏还是方块，都是 IItemHandler
IItemHandler handler = level.getCapability(Capabilities.ItemHandler.BLOCK, pos, dir);
IItemHandler handler = livingChest.getCapability(Capabilities.ItemHandler.ITEM);

// 活物品可以同时是 IItemHandler 的提供者
// 这样原版漏斗、模组管道等可以直接与活箱子交互
```

**建议**：让活箱子实现 `ICapabilityProvider`，暴露 `IItemHandler` Capability。这样原版漏斗可以直接向活箱子推拉物品，无需特殊处理。

#### 3. 容器级"场景"概念

`ContainerFluidData` 已经开了先河 — 容器级数据独立于活物品。建议抽象为"容器场景"：

```java
interface ContainerScene {
    void tick(ContainerContext ctx);
    void onItemAdded(int slot, ItemStack stack);
    void onItemRemoved(int slot, ItemStack stack);
}

// 水流场景
class FluidScene implements ContainerScene { ... }
// 红石场景
class RedstoneScene implements ContainerScene { ... }
// 温度场景（活熔炉加热周围）
class TemperatureScene implements ContainerScene { ... }
```

### 四、优先级排序

| 优先级 | 改进项 | 影响范围 | 工作量 |
|--------|--------|---------|--------|
| 🔴 P0 | ComponentState → DataComponent | 全部组件 | 大（但收益最大） |
| 🔴 P0 | LivingFunctionData 拆分 | 全部功能 | 大 |
| 🟡 P1 | ContainerContext 拆分 | 全部容器 | 中 |
| 🟡 P1 | ContainerFluidData → Capability | 活水桶 | 小 |
| 🟡 P1 | Tick 调度改为注册模型 | 核心调度 | 中 |
| 🟢 P2 | ComponentConfig → Record | 全部配置 | 小 |
| 🟢 P2 | 活箱子自定义存储组件 | 活箱子 | 中 |
| 🟢 P2 | 交互系统统一化 | GUI交互 | 中 |

**建议实施顺序**：先做 P1 的 Capability 改造（活水桶 → 活箱子 Capability 暴露），验证效果后再做 P0 的 DataComponent 迁移。P2 可以随新功能逐步推进。

---

这些是我对整个项目架构的系统性审查。核心观点是：**当前架构的组件化思路是正确的，但数据层（ComponentState/LivingFunctionData）仍停留在 NBT 时代，没有充分利用 1.21 的 DataComponent 系统和 NeoForge 的 Capability 系统**。打通这两层后，"2D物品栏 ↔ 3D方块世界"的壁垒自然就消解了 — 因为活物品本身就是 Capability 提供者，原版和模组的方块系统可以直接与之交互。

好的喵。允许架构大改。不用考虑旧数据旧存档。只往最好的方向优化。为以后天马行空的活物品实现奠定基础。
