## 全部 Mixin 审查报告

### 1. 🔴 `KineticBlockEntityMixin` — 与断连最相关，需要重点优化

**问题 A：`sendData()` 在 `tick` HEAD 中调用，可能触发客户端反序列化链式崩溃**

```java
// tick HEAD 中：
self.attachKinetics();
self.setChanged();
self.sendData();  // ← 触发客户端 read() → spawnParticles() → 空栈崩溃！
```

当 `livingItem$pendingReattach` 为 true 时，`tick` 方法开头就调用了 `sendData()`。这会向客户端发送方块实体数据包，客户端在 `readClient()` → `read()` 时可能触发 Create 的 `PressingBehaviour.spawnParticles()`，如果此时压制槽位为空栈就会崩溃。

**优化建议**：在 `sendData()` 前添加延迟或条件检查，避免在 tick HEAD 中立即同步：

```java
if (livingItem$pendingReattach) {
    livingItem$pendingReattach = false;
    try {
        self.attachKinetics();
        self.setChanged();
        // 不在这里 sendData()，改为在 tick TAIL 统一同步
        livingItem$needsSync = true;
    } catch (Exception e) { ... }
}
```

**问题 B：`livingItem$setGeneratedRPM` 中的 `sendData()` 也有同样风险**

每次 RPM 变化都立即 `sendData()`，如果此时方块实体处于不一致状态（比如 MechanicalPress 正在压榨），客户端可能收到不完整的数据。

**问题 C：`livingItem$isSafeForStressInjection()` 使用 `className.startsWith()` 字符串匹配**

```java
if (className.startsWith("com.simibubi.create.content.kinetics.simpleRelays.SimpleKineticBlockEntity")) {
    return true;
}
```

字符串匹配在运行时每次调用都做 `startsWith`，而且如果 Create 重构包名就会失效。

**优化建议**：改用 `instanceof` 检查：

```java
@Override
public boolean livingItem$isSafeForStressInjection() {
    KineticBlockEntity self = (KineticBlockEntity) (Object) this;
    return self instanceof GeneratingKineticBlockEntity
        || self.getClass() == KineticBlockEntity.class;
}
```

**问题 D：异常处理过于宽泛**

多处 `catch (Exception e)` 捕获了所有异常，可能掩盖真正的 Bug。建议至少区分 `NullPointerException`、`ConcurrentModificationException` 和其他异常。

### 2. 🟡 `ItemStackMixin` — 有性能隐患

**问题 A：`onIsSameItemSameComponents` 每次堆叠比较都遍历所有功能**

```java
for (LivingItemFunction func : LivingItemManager.getApplicableFunctions(stack1)) {
    ignoredTypes.addAll(func.getIgnoredComponentTypes());
}
```

堆叠比较在容器操作中会被**极其频繁地调用**（拖动物品、合并槽位等），每次都遍历功能列表并创建 `HashSet` 开销不小。

**优化建议**：缓存忽略的组件类型集合：

```java
// 在 LivingItemManager 中缓存
private static final Map<Item, Set<DataComponentType<?>>> IGNORED_TYPES_CACHE = new WeakHashMap<>();

public static Set<DataComponentType<?>> getIgnoredComponentTypes(ItemStack stack) {
    return IGNORED_TYPES_CACHE.computeIfAbsent(stack.getItem(), item -> {
        Set<DataComponentType<?>> types = new HashSet<>();
        for (LivingItemFunction func : getApplicableFunctions(stack)) {
            types.addAll(func.getIgnoredComponentTypes());
        }
        return Collections.unmodifiableSet(types);
    });
}
```

**问题 B：组件比较逻辑可能不完整**

当前只检查 `types1` 中的组件是否在 `types2` 中存在且相等，但没有检查 `types2` 中是否有 `types1` 没有的非忽略组件。如果 `types2` 多了一个非忽略组件，当前代码会错误地返回 `true`。

### 3. 🟡 `AbstractContainerScreenMixin`（水流渲染）— 有渲染性能问题

**问题 A：每帧都遍历所有槽位并解析 flow 字符串**

```java
@Inject(method = "render", at = @At("TAIL"))
private void onRender(...) {
    List<WaterBucketRender> buckets = collectWaterBuckets(self);
    // ...
}
```

`render` 每帧调用，`collectWaterBuckets` 每次都遍历所有槽位 + `parseFlowData` 解析字符串。

**优化建议**：缓存水流数据，只在数据变化时重新解析：

```java
private int lastFlowHash = 0;
private List<WaterBucketRender> cachedBuckets = null;

// 在 onRender 中：
int flowHash = computeFlowHash(self);
if (flowHash != lastFlowHash) {
    cachedBuckets = collectWaterBuckets(self);
    lastFlowHash = flowHash;
}
```

**问题 B：`resolveSlotWrapperTarget` 使用反射遍历字段**

```java
for (java.lang.reflect.Field f : clazz.getDeclaredFields()) {
    if (Slot.class.isAssignableFrom(f.getType())) {
        f.setAccessible(true);
```

反射在每帧每个 SlotWrapper 上执行，性能很差。

**优化建议**：缓存反射结果（`Field` 对象只需查找一次）：

```java
private static final Map<Class<?>, Field> SLOT_WRAPPER_FIELD_CACHE = new ConcurrentHashMap<>();
```

### 4. 🟡 `ItemRendererWaterWheelMixin` — ThreadLocal 使用不当

**问题**：使用 `ThreadLocal<ItemStack>` 在 HEAD 捕获、Redirect 中使用、RETURN 中清除：

```java
private static final ThreadLocal<ItemStack> RENDERING_ITEM = new ThreadLocal<>();
```

虽然渲染是单线程的，但 `ThreadLocal` 有内存泄漏风险（如果 `remove()` 被跳过），而且 `RETURN` 注入点在异常时可能不执行。

```java
private BakedModel redirectHandleCameraTransforms(
    PoseStack poseStack, BakedModel model, ItemDisplayContext context, 
    boolean applyLeftHandTransform,
    @Local(argsOnly = true) ItemStack itemStack  // ← 直接捕获参数
```

## 与断连 Bug 的关联总结

```
断连根因：Create 的 PressingBehaviour.makeCompactingParticleEffect() 用空栈创建 ItemParticleOption

我们的 KineticBlockEntityMixin 可能的间接影响：
  1. tick HEAD 中 sendData() → 客户端在 read() 时触发 spawnParticles()
  2. setGeneratedRPM 中 sendData() → 同上
  3. detachKinetics/attachKinetics 可能导致方块实体状态不一致
     → MechanicalPress 的压制槽位在同步时为空
```

**最关键的优化**：在 `KineticBlockEntityMixin` 中，将 `tick` HEAD 里的 `sendData()` 延迟到 tick TAIL 执行，确保方块实体状态完全更新后再同步到客户端。这样可以避免客户端收到不一致的数据包。
