# 容器槽位解析（列数）收编与自动化

> **状态：方向已认可（2026-10-25 用户），§6 四项待拍板，拍板前不动代码。**
> **起因**：用户实测「物品形态下储罐插件导致的槽位变化能正确解析，放置态错误」
> （`D-container-17` 已修）。修完复盘时发现这不是孤例，而是**同一个问题的第七种答案**。
> 用户原话：「感觉又多又乱」「是否存在更合理的槽位解析方式呢」。
>
> **用户已定的两条**：① 玩家优先级最高（“它是玩家可配置的”）；② 内置表仍要有，
> 但**不参与解析**，只用来生成配置表。

---

## §0 一句话结论

**「这个容器多宽」现在有 7 种答案来源**（4 个 `getWidth()` 实现 × 6 种取值 + 1 个死默认），
每层都是为一次真实事故打的补丁。收编方案：**收敛成一条按 provenance 排序的链**，
并把链上最易过期的那一环（手写表）改造成**玩家可配置 + 开门时自动习得**。

**不改任何玩法语义，只改「我们怎么知道容器的形状」。**

---

## §1 容器三问：这是第三问

| 问题 | 收编前 | 收编后 | 决策 |
|---|---|---|---|
| 谁在看这个容器 | 两条数据轨各一份 if-chain（漏一条静默失效） | `ContainerViewers.of(...)` | `D-container-14` |
| 容器在世界里哪 | 4 份各写一遍的解析 | `ContainerAnchor`（参考物，不是坐标） | `D-container-15` |
| **容器是什么形状** | **7 种答案来源，无统一优先级** | **本文提案** | 待拍板 |

前两问的共同教训：**散落的多个答案 ⇒ 加新形态时漏改一处就静默失效**。
第三问今天更严重——它不只是“散落”，还有**两份要手工同步的数据**和一个**会过期且无征兆**的静态表。

## §2 普查：7 种答案来源

### 2.1 清单

| # | 来源 | 位置 | 判定 |
|---|---|---|---|
| 0 | 接口默认 9 | `SlotInfoProvider#getWidth()` | **死默认** —— 3 个真实 ctx 全覆写，生产无人使用；且 9 是“看着对”的值，未来忘覆写会**静默答错** |
| 1 | 玩家背包特判 | `SimpleContainerContext` `inventory != null` | 硬事实 |
| 2 | 联动来源权威值 | Tier 0 / `ItemFormContainerContext#columns` | 活对象现算（`槽数 ÷ 行数`） |
| 3 | 规则表 | Tier 1 `findRule(id, size)` | 28 条静态数据（`container_rules.json` + 玩家 register） |
| 4 | 原版类型表 | Tier 2 `resolveColumnsFromContainer` | 9 种 BE 硬编码 |
| 5 | 加权启发式 | Tier 3 `resolveColumns(size)` | 13 个候选宽度找第一个能整除的，纯猜 |
| 6 | 原版 API | `EntityContainerContext` | `AbstractHorse#getInventoryColumns()` |

### 2.2 每层的来历（没有一层是“为了将来”铺的）

| 层 | 对应事故 |
|---|---|
| Tier 2 原版表 | 熔炉 / 漏斗列数错 |
| Tier 1 规则表 | 模组容器（炼金箱子 13 列、铁箱大箱 18 列） |
| Tier 3 启发式 | 规则表没收录的容器 |
| Tier 0 来源 | 背包升级占列（30 槽被猜成 10 列，`D-container-17`） |

### 2.3 两处已知腐化点

1. **Tier 1 与 Tier 2 是同一个机制的两个家**（都按 `id + size` 查静态列数），
   得有个测试 `typeTable_agreesWithRegisteredRules` 专门守它们一致 —— “两份数据”的气味。
2. **手写表对模组改版过期，且无征兆**。今天所有槽位 bug 都是这一条：

   ```
   54 格背包装 2 个占列升级 ⇒ 30 存储槽
     内置表无此键 ⇒ 启发式选 10 列（真值 5）
     ⇒ 邻居判定 / 流体渲染 / 漏斗传输全线错位，玩家看到的是「搬错格子但仍在搬」
   ```

## §3 目标形态

### 3.1 优先级链（按“这个答案是谁说的”排，不按“它存在哪张表里”排）

| 顺位 | 答案来源 | 理由 |
|---|---|---|
| 1 | **玩家显式写 / 覆盖的条目** | 玩家主权（2026-10-25 用户定） |
| 2 | **联动来源（活对象）** | 对“眼前这个对象”的陈述，不会过期 |
| 3 | **机器填进配置表的**（内置播种 + 自动学） | 会过期，但自动学让它自愈；内部再排：**自动学 > 内置播种** |
| 4 | 猜（启发式） | 最后一道 |

**为什么“活对象”必须高于“机器填的表”**：表是**对一类容器的断言**，会过期；
来源是**对眼前这个对象的陈述**，不过期。让会过期的断言否决不会过期的事实，
出事时没有任何征兆。实证：

```
铜背包（45 格，无升级）        ：45 槽 ÷ 5 行 = 9 列
金背包（81 格，装 2 个占列升级）：81 − 9×4 = 45 槽 ÷ 9 行 = 5 列
⇒ 同一个键 (sophisticatedbackpacks:backpack, 45) 有两个正确答案
```

内置表里恰好写着 `{backpack, 45} → 9`。若配置表绝对首要（机器填的也压过来源），
放置态的金背包 + 2 升级会被解析成 9 列（真值 5）—— `D-container-17` 的 bug 原样复活。

### 3.2 配置表是唯一的“表”，三条填充路径

```
                  ┌─ 内置表播种（降格：不再被解析路径读取，只做种子）
   配置表（唯一） ─┼─ 自动学（开门时读菜单现算，落盘，标 auto）
                  └─ 玩家手写（指令 register，最高权威）
```

- 内置表**不再参与解析**，只负责在配置表里缺键时播种
- **有来源的容器，内置表不为它播种**（今天内置表里 6 条精妙背包条目本就是死的，删掉）
  —— 这条与 provenance 优先级互为双保险，任一条都能防住 3.1 的碰撞
- 玩家对配置表的显式修改压过一切，包括来源

## §4 自动学机制

### 4.1 五步

1. **触发**：`PlayerContainerEvent.Open`（NeoForge 现成事件，`ServerPlayer#openMenu` /
   `openHorseInventory` 都会 post，**只在服务端**，一次开门一次，不碰热路径）。
   玩家按 E 看自己背包不走这条路（客户端本地界面）。
2. **取材**：从 `menu.slots` 里挑出属于容器的槽（`slot.container != player.getInventory()`，
   与 `syncWorldContainer` 同判据 ⇒ 玩家背包 / 盔甲 / 副手全排除），收集 `(x, y)`。
   `Slot.x/y` 是 `public final`，**双端各自构造同一套菜单 ⇒ 坐标天然一致，不走网络**
   （TODO §4 已论证：列数不是客户端属性，是服务端就有的信息）。
3. **安全阀：只收“干净矩形”** —— 按 `y` 分组，要求每行格数相同、每行内 `x` 等间距、
   总数 = 行 × 列；任一条不满足 ⇒ **不学**。
   熔炉反例：input `(56,17)` / fuel `(56,53)` / output `(116,35)` ⇒ 分组行数不等 ⇒ 拒绝，
   继续用手写表的 1 列（我们真正需要的“每槽独占一列”语义）。
   ⇒ **自学习只在网格语义成立的地方生效，非矩形容器永远落在原有层上。**
4. **键与冲突**：`(容器 id, 槽数)`，与手写表同键。容器 id 复用现成机制：
   `slot.container` 是 BE 直接取 type key；大箱那种 `CompoundContainer` 走
   `MenuSlotOwners.resolve` 拿位置再取 BE。**同键先后学到两个不同值 ⇒ 标记歧义、不写表**。
5. **落盘**：写进同一张配置表，标 `auto`。**必须落盘**：只存内存的话，重启后自学条目丢失、
   掉回内置播种值，万一播种值已过期，那个容器又开始静默错，而玩家以为配置表是对的。

### 4.2 覆盖面实证（28 条规则逐个查上游 GUI 源码）

| 容器 | 能学 | 依据 |
|---|---|---|
| 箱子 / 大箱 / 木桶 / 潜影盒 | ✅ | 干净 9 列矩形，row-major |
| 漏斗 | ✅ | 单行 5 格等间距 |
| 发射器 / 投掷器 | ✅ | 3×3 |
| **铁箱子全部 14 个 id** | ✅ | `new Slot(inv, col + row*rowLength, 12+col*18, 18+row*18)` —— 等距矩形 + row-major |
| 无尽箱子（300 格） | ✅ | `new SlotInfinity(tile.chest, i + y*25, 8+i*18, 18+y*18)` |
| **精妙背包 6 档** | ❌ | 升级槽与存储槽在同一个菜单、不同面板 ⇒ 行分组不等长 / x 不等距 ⇒ 安全阀拒绝 |
| （表外）熔炉族 / 酿造台 | ❌ | 非网格 ⇒ 拒绝（正好，它们需要 1 列） |
| （表外）驴 / 船 / 矿车 | ❌ | 实体容器，走原版 API |

**22 / 28 条可学；唯一学不到的精妙背包恰好有 Tier 0 来源兜着。**
这正是分层该有的样子：**每层各救一类，没有一层是通用的。**

### 4.3 残留风险：GUI 矩形 ≠ 编号方向

安全阀验的是 **GUI 几何**，无法验证槽位编号方向。若某模组“GUI 排成矩形但编号列优先”
（column-major），几何检查会通过、列数学得对、但 `slot/width` 映射全错。

- 表内 22 条：已逐个查上游源码确认 row-major，**无此风险**
- 表外陌生容器：今天它们是纯猜（多数也错），学了最坏是“猜对的地方变错”。
  严格说存在一种回退场景：猜巧了对、学到的是错的方向

⇒ 这条风险无法用机制消除，只能靠** provenance 优先级 + 对账工具**显形。

### 4.4 附带能力：对账

学到的值可以和内置播种值对账，**任何一条不一致就是内置表过期的信号**——
相当于给手写表装了个自动审计。

## §5 对现有机制的处置

| 现状 | 处置 |
|---|---|
| Tier 2 原版表（9 种硬编码） | 并入配置表种子，`resolveColumnsFromContainer` 删除，一致性测试删除 |
| Tier 1 规则表（`container_rules.json`） | 降格为种子，**不再被解析路径读取** |
| Tier 0 来源 | 保留，位置在“玩家显式”之下、“机器填”之上 |
| `SlotInfoProvider#getWidth()` 默认 9 | 删除 default 或改抛异常（死默认，留着只会制造静默错） |
| 内置表里 6 条精妙背包条目 | 删除（有来源，不播种） |
| `/livingitem container register` | 保留，成为“玩家显式”的唯一入口 |

## §6 未定案（拍板前不动代码）

1. **provenance 优先级的实现方式**：是否引入显式的“权威度”概念
   （`player > live > auto > bundled`），还是在查表时按条目来源分支判断。
2. **自动学落盘的格式**：`auto` 条目长什么样、玩家如何 review / 锁定 / 删掉它。
3. **“查不到就不工作”（方向 D）是否本次一起做**：配置表查无 ⇒ 该容器的活物品不 tick
   + tooltip 明说“布局未知”。它不再等同于 `D-container-05` 否掉的白名单
   （表是玩家可见可改的），但默认行为仍然变了，属玩法决策。
4. 🔮 **槽位变来变去的容器（用户 2026-10-25 点名：“需要慢慢讨论”）**：
   同一 `(id, size)` 对应多个布局（3.1 的背包 45 槽碰撞就是最小实例）。
   歧义检测（同键异值 ⇒ 不学）只是“不劣化”，不是“解决”。
   真正的解法可能是让来源返回**完整 `Layout`**（rows/cols + slot→(r,c) 映射）而不是一个 int，
   但那今天是过度设计（只有矩形 + 一种前缀偏移两种形状）⇒ **单独议题，不埋进本方案**。

## §7 实施顺序（每步可独立验证）

| 步 | 内容 | 性质 |
|---|---|---|
| S1a | 删死默认（`SlotInfoProvider#getWidth()` 改抽象） | **零行为变化**，先做 |
| S1b | Tier 2 并入配置表种子（两张表合成一张） | ⚠️ 有行为差异，见下 |
| S2 | provenance 优先级 + 内置表降格为种子 + 删 6 条背包条目 | 行为不变（今天 Tier 0 已在表前） |
| S3 | 自动学（事件 + 安全阀 + 落盘 + 冲突检测） | 新增能力 |
| S4 | 对账工具（自学 vs 播种，不一致时告警） | 可观测性 |

**S1a 已实施（2026-10-25）**，并且当场证明它不是理论风险：删掉默认值时编译期
立刻抓出 `ItemEntityContainerContext`（掉落物形态，单槽）一直在白嫖那个 `9` ——
9 对 1 槽是错答案，只因单槽让行列退化才没造成可见问题。现已显式答 1，
并由 `ContainerBoundaryContractTest` 的 I-C11 用例钉住（四种形态都 ≥ 1）。

⚠️ **S1b 不是"零行为变化"（2026-10-25 查证，推翻本文此前的说法）**：
Tier 2 是 `instanceof` 判据，**对第三方继承原版容器 BE 的子类也生效**；规则表只认
精确 id。删掉 Tier 2 后这类子类会掉到启发式。已找到真实实例：
`twilightforest:cinder_furnace`（暮色森林灰炉，`extends FurnaceBlockEntity`、3 槽、
用原版熔炉菜单）今天靠 instanceof 拿到正确的 1 列，删后会拿到 3 列（错，且静默）。
⇒ S1b 动手前要先定：**家族兜底要不要保留**（保留则"两张表"仍有两个家，
不保留则需为已知子类补规则，且未知子类静默劣化）。
