## 0. 背景：三种病与三个方向

红电系统的本质是**离散事件仿真**（信号变化 → 传播 → 元件响应），但实现是「每 tick 全量重算 + 帧间 diff」的轮询系统。这个模型差异产生的翻译损耗，在本会话的修复史中反复出现：

| 病 | 症状 | 关联修复 |
|---|---|---|
| prev 双缓冲的维护分散 | 稳态跳过不同步、v15 prev 语义、`!hasAny` 分支 zero 时机——电力层跳变检测静默失效 | 稳态跳过整体移除 |
| 消费者直读 edgeGrid 实现细节 | v15 出边模型变更同时波及电力层采样、漏斗锁定、TNT 点燃，漏了两个 | **SensorPort（本文 §1，已完成）** |
| 元件语义分支散落在 phase 方法里 | 切制被强充能破坏方向性、格栅被穿透、加新元件改 4-5 处 | 规划③（本文 §3） |

三个演进方向的共同本质：**把隐式契约（edgeGrid 语义、prev 责任、mask 类型判定）显式化到接口签名**。

**建议顺序**：②（已完成）→ ①（下次电力层功能迭代时顺路）→ ③（铜门等新信号元件立项时）。

## 1. 已完成：SensorPort 感知端口（②）

**`RedstoneSensor`**（**`living/api/`** —— 2026-10-08 从 `domain/redstone/` **上移到契约层**）
——电力层与跨层消费者读取信号层的唯一接口：

```java
public interface RedstoneSensor {
    int DIRECTIONS = 4;
    int EDGE_UP = 0; int EDGE_DOWN = 1; int EDGE_LEFT = 2; int EDGE_RIGHT = 3;  // 唯一定义点
    int sensedSignal(int slot, int dir);       // dir 方向邻居朝本槽发出的出边值
    int prevSensedSignal(int slot, int dir);   // 上一 tick 同方向值
    int maxSensedSignal(int slot);             // 四方向最大值（漏斗锁定/TNT 点燃语义）
}
```

> ⚠️ **为什么必须上移**：接口原先住在 `domain/redstone/` ⇒ 消费者（`power` / `hopper` / `tnt`）
> **用端口仍要 import 领域**，模块级依赖并未真正切断。上移后 `power` / `hopper` 已**完全不引用** redstone 域
> ⇒ **R3 领域互依赖 28 → 25**（顺带 `container → redstone` 也少一条 ⇒ R1 94 → 93）。

- `ContainerRedstoneData implements RedstoneSensor`；`TickContext.getSensor(ctx)` 提供实例；
- 感知语义：**dir 方向邻居朝本槽发出的出边**；边界（邻居越界）返回 0——涂蜡元件不感应容器外信号（设计决策）；
- **消费者**：电力层 BFS 采样（`runBfs`）、活漏斗锁定（`maxSensedSignal`）、活 TNT 点燃。信号层内部传播**不经过**本端口。

**收益**：edgeGrid 边模型后续重构只改端口实现；v15 类重构的波及面从三个消费者缩到一个实现类。

**注意**：`getSignal(slot)` 保留为 `maxSensedSignal` 的便捷别名（既有测试与跨层读取方使用）。

## 2. 规划①：跳变检测前移到写入点（事件流）

### 2.1 现状与问题

电力层的一切能量事件来自 `cur vs prevEdgeGrid` 的帧间对比。这个 diff 的正确性依赖 prev 的绝对正确，而 prev 的维护分散在多处（reset 的 swap、`!hasAny` 分支 zero、稳态跳过同步、注入时序）——**任何一处遗漏都是静默错误**。本会话的修复史：稳态跳过 tick 不同步 prev → 重复假上升沿压碎周期估计。

### 2.2 重构后的形态

**信号层在写入点直接产生事件**——`edgeGrid.set` 的调用点天然知道旧值（`propagateDir` 里 `signal <= currentEdge` 的提前返回证明），值变化时发 `EdgeChanged(slot, dir, old, new, tick)`。电力层订阅事件流，不再 diff。

### 2.3 优点

1. **消灭整类 prev 维护 bug**——不是修某一个，是让这一类 bug 不可能存在；
2. 「跳变即能量事件」从设计口号变成字面实现——记账直接吃事件；
3. 稳态 = 无事件 = 天然零成本，**预测器（SteadyState 惨剧）在结构上不需要存在**；
4. 事件流自带调试可观测性；
5. 派生相位注册表的活性判断吃同一条流，实现统一。

### 2.4 缺点与实施难点

1. **最大的隐藏成本：必须先统一边写入口径**。`edgeGrid.set` 的调用点分散在 phase1/2/4 多处且语义混杂——有的写「自己出边」、有的写「对方入边」（powerConductiveNeighbor）、dust 分支内联 set。事件发射若只挂在 set 上，语义混杂会原样转移进事件层。**收口写入口径本身是一次中型重构**；
2. 同 tick 多事件的处理需要定义（tracker 按 slot+dir 独立，事件无序不伤语义，但要有文档）；
3. 振荡高峰的事件对象分配（对象池可解，加复杂度）；
4. phase5 的显示状态更新仍是轮询（显示是场不是事件）——事件化只覆盖电力层；
5. 迁移期双轨：场快照仍需要（tooltip 显示、当前值查询），事件流与场要一致。

### 2.5 净评价与时机

优明显大于缺，但**关键前置（写入口径统一）容易低估**。建议时机：下次电力层要加新功能（如用电侧元件）时顺路实施——有新消费者驱动事件流设计，避免纯重构。

## 3. 规划③：信号层元件接口化

### 3.1 现状与问题

phase1-5 每个方法内部 per-类型分支（`BIT_DUST` 一支、`BIT_COPPER` 里再分 `CHISELED`/`CUT`/base……）——加新元件类型要同时动 4-5 个 phase 方法。历史上「切制被强充能破坏方向性」「格栅被穿透」的根源就是语义分支跨 phase 重复、phase3/phase4 判定不一致。

### 3.2 重构后的形态

元件协议接口，引擎保留位图快筛与 BFS 骨架：

```java
interface RedstoneComponent {
    void collectSources(SourceCollector out);   // phase1：我是不是源
    void propagate(PropagationContext ctx);     // phase2：我怎么传播
    void recheck(RecheckContext ctx);           // phase3：级联输入
    void updateDisplay(DisplayContext ctx);     // phase5：显示状态
}
// 注册表：bit → component
```

### 3.3 优点

1. **新元件只加类**——规划中的铜门（信号闸门）、活塞有了基建；这是三个方向里唯一有「新功能开发效率」收益的；
2. **语义内聚**：二极管方向过滤、切制双轴、格栅求和——一个元件的全部行为一处可见；
3. **与电力层对称**：电力层已经是「引擎统一、形态只管解读」（interpretShifter/Splitter/Adder），信号层对齐后两层风格统一；
4. per-元件单测：不需要整个容器场景。

### 3.4 缺点与风险

1. **工程量与回归风险最大**：phase1-5 每一处分支搬家都要行为等价性证明——回归风险集中且无增量收益；
2. **性能张力真实存在**：位图 + 数组的 4.9μs 靠「引擎无虚调用」换来，元件接口的虚调用会退化——54 槽规模退化到几十 μs 仍可接受，但大规模部署的倍数要有数；
3. **边界难划**：chiseled 的方向过滤是元件语义还是引擎语义？dust 只入队 dust/copper 是谁的责任？接口边界划错会比现状更乱；
4. **纯重构无行为收益**：玩家看不到任何差异——动力完全来自未来；
5. **元件集合可能已收敛**：8 种红石 + 5 种铜家族 = 13 种，铜门还在「暂不设计」状态——短期不加新元件的话，现状够用。

### 3.5 净评价与时机

**等铜门/新信号元件真的立项再做**——那时有明确的新消费者驱动接口设计，现在是提前还债。

## 4. 不建议动的部分

**六阶段的全局时序**（phase0 倒计时 → 1 收源 → 2 传播 → 4 充能 → 3 重检 → 5 显示）看起来乱，但每个顺序都有物理理由——先推进定时器再收源、先传播再充能再重检级联、显示最后。这个时序是 **vanilla 红石行为的近似模型**，它的「乱」是领域复杂度，不是架构债——重排的风险远大于可读性收益。

**值得保留、重来也不会改的部分**：跳变门控记账 + 显示/记账分离（物理语义与表现语义已解耦）；相位解读三元件的镜像设计（信号层拓扑 → 电力层行为可推断）；锈级共振的构造性防膨胀（R ≤ 4 靠锈级数封顶，不靠数值调平）；slotMask 位图（4.9μs 满载传播是所有宽松设计的安全垫）；processContext 级测试。

## 5. 元观察：隐式契约的显式化

三个方向的共同本质是**把隐式契约显式化**——edgeGrid 的语义、prev 的维护责任、mask 的类型判定，目前都是「读代码才知道」的约定。这几轮的坑（涂蜡采样、漏斗/TNT、稳态跳过、方向引用比较）全部是隐式契约被无意破坏。

显式化有三个层级，成本递增、效果递增：

1. **文档级**：坑清单沉淀（tooltip-system.md §7 是范例）——缓解，不根治；
2. **接口级**：SensorPort（已完成）——把「怎么读」变成类型承诺；
3. **类型级**：值对象的引用比较审计（`pos2dToEdgeDir` 的 `==` 坑教训）、事件类型——让编译器挡住语义错用。

**领域复杂度（多相/共振/锈级隔离的数值体系）是游戏设计决定的，换任何架构都要实现**——架构演进消除的是翻译损耗与防御性补丁，消不掉领域复杂度本身。红电系统的领域设计（相位代数、镜像语义、构造性防刷）是这套代码最有价值的资产——演进的方向是保护它，不是简化它。

### 6.2 活避雷针（原 §3.14，红电波频道）

活避雷针是电力系统从**局域**走向**全局**的关键。
涂蜡铜块管容器内发电，活避雷针管跨容器输电。

```
局域：活红石振荡 → 铜块信号网络 → 涂蜡铜块发电 → totalPower → IEnergyStorage
全局：totalPower → 活避雷针 → 红电波频道 → 活避雷针 → 其它容器
```

#### 物品

活避雷针只有一种，没有氧化/涂蜡变体。
堆叠数 = 频道，64个独立频道。

#### 方向性 I/O

活避雷针一头大（输入端）一头小（输出端），参考活漏斗的方向性设计。
4 个朝向（上下左右）+ 输入/输出分离，在 2D 网格中实现灵活拓扑：

```
        输入端(大头)
          ↑
    ┌─────┴─────┐
    │ 活避雷针   │  ← 朝向 = 上（输入在上，输出在下）
    └─────┬─────┘
          ↓
        输出端(小头)

4 种朝向：
  上：输入=上邻居，输出=下邻居
  下：输入=下邻居，输出=上邻居
  左：输入=左邻居，输出=右邻居
  右：输入=右邻居，输出=左邻居
```

右键旋转朝向。

#### 供需分配模型（能量守恒）

活避雷针按朝向区分**输入端**（供给）和**输出端**（需求），
采用标准电网供需模型，保证能量守恒。

```
channelSupply[频道] = Σ(所有输入端贡献的功率)
channelDemand[频道] = Σ(所有输出端请求的功率)

每个输出端实际获得 = request × min(1, supply / demand)
```

```
频道 5：
  容器A：铜块总线(100 FE/t) → 避雷针输入端 → supply += 100
  容器B：铜块总线(50 FE/t)  → 避雷针输入端 → supply += 50
  supply = 150

  容器C：避雷针输出端 → request 200 → demand += 200
  容器D：避雷针输出端 → request 100 → demand += 100
  demand = 300

  分配比例 = min(1, 150/300) = 0.5
  容器C 获得 200 × 0.5 = 100
  容器D 获得 100 × 0.5 = 50
  总输出 150 = 总输入 150   ✅ 守恒
```

> ⚠️ **为什么不用「共振 + 净值扣除」**
>
> 早期方案是「频道共振总和广播给每个避雷针，扣除自身贡献」。
> 该模型能挡住单容器自环，但**两个容器可以互相刷**：
>
> ```
> 容器A 贡献 100，容器B 贡献 100，共振 = 200
> 容器A 获得 200 - 100 = 100（拿到 B 的）
> 容器B 获得 200 - 100 = 100（拿到 A 的）
> 总输入 200 → 总输出 400，能量翻倍
> ```
>
> N 个容器互联时按 N×(N-1) 放大，10 个容器就是 90 倍。
> 「共振」概念上很浪漫，但**能量守恒是硬约束**。
> 现改为供需分配，保留跨维度无衰减的特性，玩家感知不到区别。
>
> 该思路与 `EnderChannelRegistry` 的轮询公平调度一致——
> 同样是多对多的资源分配问题。

#### 四种拓扑模式

| 模式       | 输入接铜块 | 输出接铜块 | 效果                |
| -------- | ----- | ----- | ----------------- |
| **纯供给**  | ✅     | ✗     | 只向频道供电（发电站）       |
| **纯需求**  | ✗     | ✅     | 只从频道取电（用电端）       |
| **双向桥接** | ✅     | ✅     | 同时供给与需求，可用于频道间转运  |
| **空闲**   | ✗     | ✗     | 不参与分配             |

#### 与容器电力的关系

避雷针不绑定锈蚀档位——它的输入端从**容器的 `totalPower`** 取电注入红电波频道，
输出端从频道取电补充**容器的池与铜灯**：

```
容器A: 涂蜡铜块发电 → totalPower → 避雷针(输入) → 红电波频道 5
                                                      ↓
容器B: 铜灯 ← 避雷针(输出) ←──────────────────┘
```

避雷针的频道由**堆叠数**决定（1~64 共 64 个独立频道），与锈蚀无关。
一个避雷针可以是纯供给、纯需求，或两端都接以实现频道间转运。

> 早期设计里避雷针在「4 条电力总线」之间桥接。
> 现在电力就地产生并汇总为单一 `totalPower`，容器内已无总线可桥，
> 避雷针的唯一职责就是**跨容器输电**。这比原设计更简单，玩家也更好理解：
> 「容器内不需要电线，容器间用避雷针」。

#### 跨维度无衰减

红电波是概念频道，不分维度。主世界的频道 5 和下界的频道 5 是同一个频道，状态完全同步。

#### 全局注册表

```java
public class RedElectricWaveRegistry {
    /** 频道 → 本 tick 的供给总量(FE/t) */
    Int2IntMap channelSupply;

    /** 频道 → 本 tick 的需求总量(FE/t) */
    Int2IntMap channelDemand;
}
```

> ⚠️ **必须在** **`ServerStoppedEvent`** **中清空**。
> 这是进程级静态表，单人游戏「退出存档 → 进入另一个存档」不会重启 JVM，
> 不清理会把上一个世界的频道状态带入新世界。
> 参考 [LivingItem.onServerStopped](../../src/main/java/com/qiqi/li/LivingItem.java) 的现有处理。

#### 每 tick 流程

```
1. 清零 channelSupply[1..64] 和 channelDemand[1..64]

2. 收集阶段：遍历所有容器中所有活避雷针
   → 输入端有铜块？ channelSupply[频道] += 该铜块所属总线功率
   → 输出端有铜块？ channelDemand[频道] += 该铜块所属总线的需求量

3. 分配阶段：遍历所有容器中所有活避雷针
   → 输出端有铜块？
   → ratio = min(1.0, channelSupply[频道] / channelDemand[频道])
   → 注入功率 = 该端 request × ratio

4. 扣减供给侧：各输入端按同一 ratio 实际输出，未被消耗的功率留在本地总线
```

**复杂度**：O(全局避雷针数)，通常 < 100，每 tick 两趟遍历。

#### 典型应用

```
1. 跨容器输电：
   容器A：活红石振荡 → 铜块A → 避雷针(stack=8, 朝右) → 频道8
   容器B：频道8 → 避雷针(stack=8, 朝左) → 铜块A → IEnergyStorage

2. 跨维度供电：
   主世界：发电机 → 铜块A → 避雷针(stack=1) → 频道1
   地狱：频道1 → 避雷针(stack=1) → 铜块A → 用电

3. 多频道分工：
   频道1：低功率控制信号
   频道8：主电源
   频道16：辅助电源

4. 跨频道桥接：
   铜块(未锈蚀) → 避雷针(输入) → 红电波频道 → 避雷针(输出) → 铜块(斑驳)
   实现未锈蚀总线和斑驳总线的功率互通
```

### 6.3 信息时代（原 §4，计算 + 电力）

> 封装维度（原「+ 封装」）随活潜影箱剥离至独立文档：
> [活潜影箱实现细节.md](活潜影箱实现细节.md)。红电系统的信息时代愿景
> 依赖活潜影箱作为外部基础设施（CPU 封装、寄存器封装），协同关系见该文档。

#### 冯·诺依曼架构映射

| 计算机组件   | 活物品实现                      |
| ------- | -------------------------- |
| **CPU** | 活潜影箱封装的 ALU + 控制器          |
| **RAM** | 活铜灯阵列（T 触发器，原版自带记忆语义）      |
| **ROM** | 活拉杆阵列（只读）                  |
| **总线**  | 活铜块（4 条锈蚀频道隔离）             |
| **I/O** | 铜块信号网络（局域）+ 活避雷针（全局，红电波频道） |
| **时钟**  | 活红石中继器环形振荡器                |
| **电源**  | 振荡信号 → 涂蜡铜块发电 → totalPower  |

> **活铜灯是 RAM 的关键**：原版铜灯本身就是 T 触发器，
> 比用活红石火把交叉搭 RS 锁存器省得多（1 格 vs 4+ 格）。

#### 时序逻辑

| 电路     | 实现             | 用途             |
| ------ | -------------- | -------------- |
| T 触发器  | **活铜灯（原生支持）**  | 1 bit 存储 / 计数器 |
| RS 锁存器 | 活红石火把交叉连接      | 1 bit 存储（备选方案） |
| D 触发器  | 活铜灯 + 时钟门控     | 同步 1 bit 存储    |
| 寄存器    | 活铜灯阵列 + 活潜影箱封装 | 多 bit 存储       |

#### 通信协议栈

```
Layer 4：应用层 —— 活物品间协作协议
Layer 3：传输层 —— 红电波频道（活避雷针，跨容器/跨维度，供需分配）
Layer 2：链路层 —— 锈蚀频道（4 条互不干扰的信号线路）
Layer 1：网络层 —— 铜块信号网络（5 种拓扑：电缆/二极管/立交桥/分频器/触发器）
Layer 0：物理层 —— 涂蜡铜块发电（铜块网络传播）+ 涂蜡铜灯储能
```

#### 杀手级应用

1. **自动化工厂**：活红石逻辑 → 涂蜡铜块发电 → 驱动活水车
2. **容器内信号网络**：4 条锈蚀频道隔离布线，涂蜡铜灯做 UPS
3. **跨容器电力网**：活避雷针供需分配，跨维度无衰减输电
4. **分布式计算**：多 CPU 各自就地发电，活避雷针跨容器协调
5. **精密电厂**：三相 120° + 共振调谐 + 铜块网络规模化，用最少槽位榨取最高功率

#### 实施步骤

```
Step 1：时序逻辑（活铜灯 T 触发器 → D 触发器）
Step 2：基本计算单元（ALU、寄存器）封装为芯片
Step 3：电力驱动逻辑（信号→电力→信号闭环）
Step 4：可编程控制器（简化 CPU + 铜块供电）
Step 5：多电路协调（4 条电路分工：电源/信号/时钟/备用）
```
