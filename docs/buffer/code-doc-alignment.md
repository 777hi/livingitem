## 2. 逐项口径与建议

**用户已明确的规则直接记为定案；询问意见的条目保留为建议。本轮不改代码。** 不再把内部实现状态包装成玩家必须理解的新玩法。

### A1. 已定：活TNT没有锚点就不炸

- **规则**：没有爆炸锚点，不执行爆炸；不增加“待爆”“储存爆炸”等独立玩法状态。
- 文档只需说明这个执行条件，不再把实现中的引信值解释成一套额外状态机，也不能把“没有爆炸”写成“已熄灭”。
- 本项不额外改变既有引信规则；无锚点时不应以爆炸为由消耗TNT。

### A2. 已定：活熔炉不保留这些运行过程数据

- **规则**：活熔炉使用容器运行时快照，进度、剩余燃烧时间、配方缓存不随物品搬运保存；不增加续作、余热补偿或资源返还机制。
- 更新 [活熔炉 §1.4、附录](../tech/living-furnace-tech.md) 的旧保留承诺即可，方向等配置与运行过程数据仍按现有结构区分。
- 酿造台是另一种活物品，有它自己的逻辑；保留其现行规则，不再拿两者互相要求一致。

### A3. 已定：活地图指哪就传哪，不替玩家选安全地点

- **规则**：按选定位置传送，不因墙体、岩浆、虚空或下界基岩顶层而拒绝、改点或搜索附近安全落脚处。
- 玩家可能主动借助抗火、飞行等能力使用危险目的地；没有空间可以卡墙，这不是必须由模组干预的问题。
- 已有坐标换算与地图定位方式照常使用；“传到目标”与“替玩家避险”分开。旧天花板扫描／避岩浆方案不恢复。
- 无效输入、目标维度不存在、服务器事件取消等执行失败，不属于地形危险，不因本规则变成成功传送。

### A4. 已定并实施：普通坐骑落载具，飞艇艇底落目标高度

- 普通坐骑保持原版式口径：坐骑实体到目标坐标，乘客重新回到马、船、矿车或骆驼的座位；不为让玩家脚落地而把坐骑埋进地面。
- Sable飞艇使用自身口径：X/Z保持操作者在艇内的相对位置，使操作者对齐地图目标；Y将飞艇当前世界投影包围盒的底面移到目标高度。
- 公式：`飞艇新原点Y = 旧原点Y + 目标Y − 当前艇底Y`。只做平移，保留姿态、玩家局部位置和乘坐关系；不自动扶正、不找安全地形、不保留旧高度。
- 已在 `SableIntegration.teleportSubLevel` 接入，纯函数回归见 `SableTeleportMathTest`。地图仍按既有方式确定目标Y，本项不增加任意三维选点能力。

### A5. 已定并实施：停机后重新计时，不补发停机期间的电

- **规则**：停跳不发电；上升沿间隔超过失活窗口（`aliveWindow(P)=max(32,2P)` 夹 [32,1200]）时旧周期作废，恢复沿只当新起点，第二个沿重新得出周期再照常发电。
- 已实施于 `SignalTracker.onRisingEdge`（阈值复用失活判据，不新增第二套计时）；回归 `SignalTrackerRestartTest` 4 项（正常运行 / 停机恢复 / 正常改频平滑跟随 / 快照回填不受误伤）。
- 语义说明见 [红电 tech](../tech/living-power-tech.md) §6.5 末段「停机重启语义」。

### A6. 已定并实施：双箱拆半 ⇒ 物品照原版分家，容器级状态重新开始

- **规则**：拆半只掉被拆半内容（原版行为），余箱物品保留；流体源与红电相位**不分摊不复制**——拆半时清空存活半的流体附件与相位快照，按新布局重新开始（重新倒水、重新锁相）。物品自身状态（种植物、储电灯中的电等）不清除。
- 已实施：拆半判定下沉 `ContainerDrops.otherChestHalf`（L1）；`ContainerDataMigration.clearFluidOnChestSplit` 与 `PhaseDataMigration.clearPhaseOnChestSplit` 各清自己领域的存活半附件（被破坏半随 BE 移除，无需处理）。红石缓存随旧 cacheKey 失效自然重建，无需额外代码。
- 回归：`ContainerDataMigrationChestSplitTest` 3 项 + `PhaseDataMigrationChestSplitTest` 2 项。PhaseDataMigration javadoc 的「两半各得一份」未解决项随之消解。

### A7. 红石规则：已定部分与火把说明

- **活铜**：用户明确它传的是红电信号，不能直接当世界红石信号输出；只有红石信号走这条对外输出链。收回“铜是否输出仍待拍板”的问题，按该区别改文档。
- **活中继器**：用户明确逻辑对齐原版，延迟、短脉冲、锁定都以当前MC版本原版行为为准，不另设计一套过滤策略。
- **火把“烧毁”**：这是原版红石火把快速反复亮灭后暂时熄灭的现象，不是物品被烧掉；本模组当前并没有因此获批新增过热／冷却机制。建议文档去掉未实现的“烧毁检测”承诺，继续保留活火把反相逻辑与原有持续振荡能力。

### A8. 其余玩法：核对后的作者视角建议

- **活武器保持逐把辅助**：`LivingWeaponAssist` 逐把回放合格武器，实际出手后写回其耐久变化；目标先死亡、武器冷却等仍按已有规则处理。挖掘速度只取最高是另一条玩法规则，不据此把攻击限成最高一把。
- **活珍珠保留普通投掷**：它仍是 `Items.ENDER_PEARL` 加活化能力，地图传送是附加用途，不是剥夺原版用途。没有实际冲突证据，不新增投掷禁令；两种用途共用物品冷却照现有逻辑。
- **水车源格不产生力矩是正常逻辑**：`ContainerStressData.calculate` 对 `fromSlot < 0` 跳过，力矩由邻格位置与水流方向的叉积计算。静止源格没有流向，流过轮边才转；径向流动也可能力矩为零，反向流动互相抵消，不补“源格也要出力”的机制。
- **双箱产能与接点分开**：当前 `ContainerStressWriteback` 对两个BE各调用 `StressOutputManager.apply`，每次都注入完整净应力，不是共享总量。如果两接点接到同一Create网络，就有重复贡献同一份产能的路径。
- **建议双箱只按一个容器提供一份产能**：最简单采用一个固定输出接点（复用容器主位置／首宿主约定）；不为了“双箱更大”默默翻倍。若要保留两处输出，就需要分配总量，反而增加机制。此项只是建议，尚未改玩法。

## 6. 原审查摘要的纠错清单

1. **完成范围**：原目标为16个主题；漏斗独立审查多次因并发限制失败，不能用“16/16完成”表示已经收到全部独立报告。其他域读过传输源码不等于完成漏斗专项。
2. **计数**：“22个真bug全修”没有逐项编号与可复算清单，且仍有隔离、回滚等代码问题挂起。保留提交记录，不把宣传式数量当验收门。
3. **误归域**：装饰精确匹配、源位置粒子属于地图，不属于TNT；流体pour/scoop不属于熔炉／酿造。
4. **已修仍列未修**：红石私有死方法、TNT点燃标脏、未知流体加载WARN、骨粉handler、幅度下行测试、配方缓存测试，应标“代码或测试已修改，仍需看对应文档／游戏验证”。
5. **错误宣布同步**：`884772d`修改了地图代码与测试，并未修改地图tech正文；Y、装饰匹配与源粒子不能写“文档已随修同步”。
6. **验证层级**：预检查出一致、mock用例通过、全量测试通过、真机反馈通过分别记，不统一叫“确认没有问题”。
