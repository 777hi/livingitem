## §0 原始需求（用户原话）

> 「开始探讨新活物品：活信标。我想让信标的光束能够从玩家脑袋上射出。」
>
> 「还有在箱子这种有开盖动画的容器里时，能不能保持盖子一直打开的样子，然后光束从里面射出来。
> 其它没有开盖动画的容器就不管。」

**⇒ 目标**：一个**移动信标**，**两种宿主形态**：

- **带在身上** ⇒ 光束从你**头顶**射出、方向随**视线**走；
- **放进箱子** ⇒ **盖子保持打开**、光束从**箱口垂直向上**射出。

两种情况都：被方块挡住就**截断**、联机**所有人都能看到**、给**周围玩家加信标 buff**。

**⚠️ 与其它活物品的根本差异（核心设计约束）**：活信标**只在两种宿主下生效** ——
**玩家本人（背包 / 手持）** 或 **箱子（含陷阱箱）**。
掉进其它容器（漏斗 / 木桶 / 潜影箱 / 末影箱…）或变成掉落物 ⇒ **不发光**。
（其它活物品在任意容器里都跑；这是活信标唯一的"宿主限定"。）

## §1 目标玩法定义（草案 —— 六项）

> ⚠️ 本节是**草案**，用于定稿后搬进 tech 文档的 `§0 玩法定义`。
> 判据同 [docs/README.md](../README.md)：**只写规则与语义，不写数值与操作步骤**。

**语义**：**活信标 = 移动信标**。活化后的信标**带在身上**时在**玩家头顶**生成一条**信标光束**
（跟随视线、被方块截断）；**放进箱子**时让**箱子盖子保持打开**、光束从**箱口垂直向上**射出。
两种形态都对周围玩家施加信标效果。它把原版"固定方块 + 金字塔"的信标，变成了"跟着人走 /
藏进箱子"的信标。

**获取**：原版信标 + 活化。

**核心循环**：活化信标 → 放进背包 / 手持（或箱子）→ 出现光束（头顶跟视线 / 箱口向上）→
**在相邻槽位摆材料堆 ⇒ 金字塔层数上升 ⇒ buff 档位与范围随之提升** →
移出有效宿主 / 取消活化 ⇒ 光束消失（箱盖恢复）+ buff 停止。

**规则**（违反即 bug）：

| # | 规则 | 为什么 / 后果 |
|---|---|---|
| 1 | 宿主必须是**玩家本人**（背包 / 手持）或**箱子（含陷阱箱）**才生效 | 其它宿主没有"发光形态"（用户 2026-10-14 定） |
| 2 | **玩家宿主**：光束起点 = **头顶上方**，方向 = 宿主**完整视线**（含俯仰） | 玩法定义 |
| 3 | **箱子宿主**：光束起点 = **箱子顶部中心**，方向 = **垂直向上** | 玩法定义（箱内无视线，故固定） |
| 4 | **箱子宿主：盖子保持打开** | 视觉语义（"从里面射出来"）；机制见 §2.3 |
| 5 | 光束**被不透明方块截断** | 还原原版手感 |
| 6 | 光束**所有玩家可见**（联机） | 玩法定义 |
| 7 | 对**周围玩家**施加信标 buff；**范围 / 时长随等级**（照原版公式） | 核心功能（照 `BeaconBlockEntity.applyEffects` 公式**等价自写**——原版该方法为 `private`，不可直调） |
| 8 | **取消活化 / 移出有效宿主** ⇒ 光束消失 + 箱盖恢复 + buff 停止 | 生命周期（见 §3.1） |
| 9 | 活信标是**设备**，不被其它活物品当**耗材**消耗 | 通用隔离规则（同活熔炉 / 活酿造台） |
| 10 | **激活/等级 = 下方一行 9 列「1D 金字塔」柱高**（以信标列为中心 ±4，越界视为 0；每列 ≥ 目标、取满足的最高 N；见 §2.4）；未激活 = 完全死物 | 玩法定义（用户 2026-10-15 晚定，见 §2.4） |
| 11 | **buff 数量 = `min(信标堆叠数, 当前等级可用矿石池大小)` + (等级==4 且未因「满配+加倍」消耗免费再生 ? 1 : 0)**；矿石池按等级门控（仿原版，见 §2.5）；等级 4 再叠加**免费生命恢复**（等级 / 有无见 §2.5「4 级特权」） | 玩法定义（用户定，见 §2.5） |
| 12 | **效果配置存 DataComponent**（固定 5 个矿石槽）；右键 + 矿石锭**消耗写入**；**取消活化清空**。⚠️ **生命恢复 II 不在此列**——它是等级 4 的免费赠品（满级专属，不占槽、不存组件、不花锭） | 玩法定义（用户定，见 §2.5） |

**能力清单**（目标；实现后逐项打勾）：

- ✅ 玩家宿主光束（跟随视线 + 被方块截断 + 本地判级门控）
- ✅ 箱子宿主光束（垂直向上 + 盖子保持打开 + S2C 同步，见 §2.3）

- 🟡 tooltip（**运行时**等级/范围/金字塔账本已落地；**静态**配置账本属 Phase 3，见 §2.6）
- ⬜ 联机可见（其它玩家能看到）

## §2 技术方案

### 2.1 三条关键发现（决定省力程度）

**① 渲染零代码 —— 复用原版函数。**
`BeaconRenderer.renderBeaconBeam(...)` 是 `public static`（`net.minecraft.client.renderer.blockentity`），
原版信标自己就调它。它画的是**沿局部 `+Y` 的柱体** + 流动闪烁 + 纹理 ⇒
只要把 PoseStack 平移到起点、旋转到目标方向，即可直接调用。

```java
public static void renderBeaconBeam(
    PoseStack poseStack, MultiBufferSource bufferSource, ResourceLocation beamLocation,
    float partialTick, float textureScale, long gameTime,
    int yOffset, int height, int color, float beamRadius, float glowRadius)
```

> ⚠️ **已知坑**：函数内部写死 `translate(0.5, 0, 0.5)`（给方块坐标补到方块中心用）
> ⇒ 平移起点时需在**局部 XZ 各减 0.5 预补偿**，否则光束轴线偏离起点。
> （箱子宿主起点恰好是方块中心，天然对齐；玩家宿主需补偿。）

**② 挂载点现成。**
`RenderLevelStageEvent`（`AFTER_ENTITIES` 阶段）—— `LivingItemClient.onRenderLevelStage`
已转发给 `LivingToolRayRenderer` / `LivingToolModelRenderer`
⇒ 活信标光束挂**同一事件**，是第 3 个消费者，**零新增基础设施**。

**③ 方向对齐写法可复用。**
玩家宿主（视线方向）用 `LivingToolModelRenderer.drawModel` 的
`Axis.YP.rotation(yaw)` + `Axis.XP.rotation(pitch)`；箱子宿主方向恒为 `(0,1,0)`，无需旋转。

### 2.2 职责分工

| 层 | 做什么 |
|---|---|
| **服务端** | ① 容器 tick 检测宿主类型（玩家 / 箱子）② 加 buff（照 `BeaconBlockEntity.applyEffects` 公式**等价自写**——原版 `private` 不可直调）③ 箱子宿主：发 `blockEvent` 保持盖子打开 ④ S2C 广播「谁 / 哪个箱子有活信标 + 颜色」 |
| **客户端** | ① 玩家宿主：读玩家位置 / 视线（**原版已自动同步**）② 箱子宿主：读 S2C 缓存的箱子位置 ③ 沿方向 raycast 找截断点（同活工具 `level.clip`）④ 调 `renderBeaconBeam` 画光束 |

**⭐ 同步最小化**：玩家宿主的位置与朝向**原版已自动同步**；箱子宿主只需广播**位置集合 + 颜色**。
参考项目现成实现：`LivingToolHostSync`（按 32 格定向 + 内容去重）+ `LivingToolHostClientCache`（整表替换 + 维度校验）。

### 2.3 容器宿主（箱子）—— 机制调研与做法

**为什么难**：客户端**看不到方块容器内容**（不开 GUI）⇒「这个箱子该不该开着 / 发光」必须**服务端同步**。

**⚠️ 三类容器的开盖机制不统一**（2026-10-14 核源码）：

| 容器 | 机制 | 保持打开要动哪 |
|---|---|---|
| **箱子 / 陷阱箱 / 末影箱** | `LidBlockEntity` + `ChestLidController`；服务端 `level.blockEvent(pos, block, 1, count)` → 客户端 `triggerEvent` → `shouldBeOpen` → `tickLid` **平滑过渡** | 发 `blockEvent(1, 1)` |
| 木桶 | ⚠️ **不是 LidBlockEntity** —— 开盖 = **方块状态** `BarrelBlock.OPEN`（服务端 `setBlock`），**离散无平滑** | 服务端 `setBlock` |
| 潜影箱 | 自有 `AnimationStatus` + `progress`；⚠️ **碰撞箱与 progress 耦合**（`ShulkerBoxBlock.getShape` → `getBoundingBox` → `getProgressAabb`）⇒ 只改客户端会穿模 | 两端一致改 |

**本版只做箱子 / 陷阱箱**（用户 2026-10-14 定：其它容器不考虑）。

**做法**：
- **服务端**：容器 tick 检测箱内有活信标 ⇒ 发 `level.blockEvent(pos, block, 1, 1)`
  ⇒ 客户端盖子**平滑打开并保持**；活信标取走 ⇒ 发 `blockEvent(1, 0)` 恢复。
- **客户端**：**无需 Mixin**（复用原版 `blockEvent` 通道）；仅需 S2C 缓存定位箱子以画光束。

**⚠️ 三个已查明的坑**：

1. **陷阱箱红石**：`TrappedChestBlock.getSignal` = `Mth.clamp(ChestBlockEntity.getOpenCount(...), 0, 15)`，
   而 `getOpenCount` 读的是**服务端 `openersCounter`**。我们的 `blockEvent` **只影响客户端渲染**、
   不动 `openersCounter` ⇒ **不会误触发红石** ✅。
   🔴 **反面**：将来若改成直接改 `openersCounter`，**就会误触发陷阱箱** —— 别那样做。
2. **与真玩家开关的竞争**：真玩家关箱子 ⇒ 服务端发 `blockEvent(1, 0)`，我们下 tick 补 `blockEvent(1, 1)`
   ⇒ 最多 **1 tick 抖动**（盖子闪一下）。可接受。
3. **新玩家进入 / 区块重载**：`blockEvent` 只发给**当时跟踪该区块的玩家** ⇒ 后到的玩家看不到开盖。
   ⇒ 需**周期性重发**（倾向每 20 tick）或客户端本地兜底（见 §5 U11）。

### 2.4 金字塔层数 —— 下方一行 9 列的「1D 金字塔」（用户 2026-10-15 晚定）

**层槽定义**：活信标所在槽位**正下方整整一行**的 9 个槽位，**以信标所在列为中心**
（偏移 −4…+4 共 9 列；越出容器边界的列视为 0）。

⭐ **这不是随手切几个槽 —— 它是原版 4 层方锥的 1D 投影**：每列的矿物块堆叠数 = **该列的方块柱高**
= 覆盖该列的各层边宽之和。中心列在 L4 有 4 层叠加 ⇒ 9+7+5+3 = **24**；边列只有最宽那层的一半 ⇒ **9**。
俯视即"信标被这座底座**承托**在中央"，保留原版金字塔的**形状语义**。

| 等级 | 目标柱高（左半 → 中心） | 覆盖列数 | 合计 | 对应原版 |
|---|---|---|---|---|
| 1 | 3-3-3 | 3（±1） | 9 | 铺满底 3×3 层 |
| 2 | 5-8-8-8-5 | 5（±2） | 34 | + 5×5 层 |
| 3 | 7-12-15-15-15-12-7 | 7（±3） | 83 | + 7×7 层 |
| 4 | 9-16-21-24-24-24-21-16-9 | 9（±4） | 164 | + 9×9 层（满级） |

**激活 / 等级判定**（口径 = **每列 ≥ 目标，取满足的最高 N**；用户 2026-10-15 晚定）：
- 材料 = **底座矿物块**（`BEACON_BASE_BLOCKS`：铁/金/钻石/绿宝石/下界合金块），**混材质按列合计**
  （对齐原版 `updateBase` 只看形状、不看材质）。
- 逐级判定：该级中心 (2N+1) 列的**每列柱高 ≥ 目标值** ⇒ 达 N 级；从 4 往 1 试，取第一个满足的。
- ⇒ **少一块自动掉档、多堆不亏**；四级图案**嵌套单调**（L4⟹L3⟹L2⟹L1），判定自洽。
- 无一满足 ⇒ **0 级**：未激活 = 完全死物（用户定）——光束不亮、buff 不施加，就是个普通信标
  ⇒ 判定结果直接映射"亮不亮 / 加不加"，**零歧义、零额外状态**。

**成本与原版对齐**：4 级合计 **164 = 原版满层成本**（全铁块 ≈ 1476 铁锭 ≈ 23 组）；
活化**不减材料成本**，减的是**操作复杂度**：在容器里填 9 槽 vs 在世界里堆一座四层金字塔。
代价从"建造成本"转成"携带成本"——而这正是"移动信标"该有的样子。

**居中要求（以信标列为中心的必然推论）**：信标必须放在**中列**才铺得满 9 列；
偏 1 列 ⇒ 越界 1 列 ⇒ 最高只能到 L3，依此类推 ⇒ 玩家自然会把信标往中列放。

**物理上限**：9 槽 × 每组 64 = **576** ⇒ 164 档轻松可达（平均每列约 19 个）。

### 2.5 效果配置 —— 消耗制 + 组件存储（用户 2026-10-15 定）

**⭐ 三层分离（三个规则互不冲突，因为它们不在同一层）**：

| 输入 | 层 | 存储 |
|---|---|---|
| 底座矿物块**数量** | **容器层** | **不存** —— 每 tick 读下方一行 9 槽（柱高） |
| 信标**堆叠数** | **物品栈层** | **不存** —— 读 `getCount()` |
| 矿石锭**种类** | **组件层** | **存** DataComponent（固定 5 个效果槽） |

⇒ 关键认知：**MC 堆叠的本质是「组件相同就能叠」，不是"每个物品独立配置"。**
一摞信标**共享同一套配置**；「buff 数量 = 堆叠数」只是「激活这套配置的前 N 个槽」——
改 count **不需要改组件**。这就是三层能共存的根本原因。

**配置操作（消耗制）**：
- 光标拿矿石锭 → **右键活信标**（走 `InteractionRegistry`，与「活打火石点活TNT」同款，
  复用 `GuiInteractionPacket` → `InteractionHandler` 链路）
- 该锭对应效果**不在**配置里 ⇒ 消耗 **1 个锭**，追加一个 **I 级**槽
- 该锭对应效果**已在**配置里 ⇒ **仅当 等级==4** 时消耗 **1 个同种锭**升 **II 级**（2 锭 = II 级）；**低等级右键同种已配锭 ⇒ 拒绝（不消耗）**，因为 II 只在满级解锁（仿原版 `主效果==次级效果` 需 `beaconLevel>=4`）
- 写入对**整摞**生效（同一 `ItemStack` 的 `set`）⇒ 整摞组件始终相同 ⇒ **永远可堆叠**

**槽位与激活**：
- **固定 5 个矿石效果槽**（同种锭升级占**同一个**槽，不新增）
- 配置**按写入顺序**排列
- 生效矿石效果数 = `min(信标堆叠数, 已配置且档位 ≤ 当前等级的槽数)`（等级门控见下方「等级门控矿石池」）；按配置顺序取前 N 个
- 总 buff 数 = 矿石效果数 + (等级==4 且未因「满配+加倍」消耗免费再生 ? 1 : 0 个免费再生)；满级 5 堆叠且未加倍 ⇒ 5 + 1 = **6 种 = 原版完整池**（再生等级 / 有无见下方「4 级特权」）

**4 级特权（满级白送再生，不占槽）**：等级达到 4（满级）时，**自动免费赠送「生命恢复」**——
**不占任何矿石槽、不花锭、不存组件**。

⭐ **再生的等级 / 有无（关键，案例 2 才暴露的完整规则 —— 三档，不是两档）**：
- **有空的「种类槽」⇒ 再生 II 级**（默认上限）
- **无空槽、且所有已配效果都是 I 级 ⇒ 再生 I 级**
- **无空槽、且至少有一个效果被加倍到 II 级 ⇒ 再生【不授予】**（免费再生被"加倍"消耗掉）

⭐ **这正是"仿原版"的核心**：原版 `BEACON_EFFECTS[3] = REGENERATION`，**再生只在第 4 档（满级）才解锁**；
而原版想让某效果到 II 级必须 `主效果==次级效果`（`applyEffects` 放大器 `i=1`），这会**吃掉次级槽** ⇒
原版里"II 级效果"和"再生"互斥。活信标把"免费再生"当作那个次级槽：
**你把某个效果加倍到 II、又没有空槽兜底时，免费再生就被消耗掉**——和原版"加倍即占次 slot"完全同构。
（有空槽时再生照给 II，因为还有余力。）

**验证（与全部测试用例逐字一致，含案例 2 不写再生）**：

| 案例 | 堆叠 | 喂锭 | 占用槽 | 空槽 | 免费再生 |
|---|---|---|---|---|---|
| 1 | 1 | 1 钻石 | 力量 I | 0 | I |
| 2 | 1 | 2 钻石（力量 II） | 力量 II | 0 | **无**（满配且已加倍 → 消耗） |
| 3 | 2 | 1 绿宝石 | 跳跃 I | 1 | II |
| 4 | 2 | 2 绿宝石（跳跃 II） | 跳跃 II | 1 | II |
| 5 | 2 | 1 绿宝石 + 1 钻石 | 跳跃 I + 力量 I | 0 | I |

⚠️ **我之前的错误（两处）**：① 以为"2 个同种锭 = 占了 2 个槽"，案例 4 看似满配；
其实 2 同种锭升级同槽到 II、不新增槽 ⇒ 案例 4 仍余 1 空槽 ⇒ 再生 II。
② 顺着错把案例 2 也写成"再生 I（推断）"——其实案例 2 是 **1 堆叠、力量加倍到 II、0 空槽**，
正落在"满配+加倍 → 再生不授予"那一档，所以你原话只写"2 级力量"、没提再生是对的。
这两点想通后，5 个案例（含案例 2 的省略）全部自洽。

**等级门控矿石池（仿原版 `BEACON_EFFECTS` 分档，用户 2026-10-15 定「参考原版」）**：

等级这一轴**不仅**管范围/时长，**也管能选哪些效果**——和原版逐档解锁池一致。
各矿石按原版 index 分档解锁；低于当前档位的矿石锭**喂了会被拒（不消耗）**，
已配置的高阶效果在等级下降时**休眠（不施加）、回升后自动恢复**（配置留在组件里）。

| 信标等级 | 可用矿石池（仿原版分档） | 最多矿石效果数 | 免费再生 |
|---|---|---|---|
| 1 | 铁/金 → 速度/急迫（index 0） | 2 | 无 |
| 2 | + 下界合金/绿宝石 → 抗性/跳跃（index 1） | 4 | 无 |
| 3 | + 钻石 → 力量（index 2） | 5 | 无 |
| 4 | 同 3（全 5 矿石） | 5 | 有（3 档规则，见上） |

⭐ 这就让 1/2/3 级各有**不同的可用效果**（不是只差范围/时长）：
1 级拿不到力量、3 级才解锁，和原版 tier 进度一致；堆叠仍管"同种效果的数量"。

**矿石锭 → 效果映射**（一一对应原版 6 效果池里除再生外的 5 个；再生由满级白送接管；每矿石标注解锁档位）：

| 矿石锭 | 效果（原版 `BEACON_EFFECTS`） | 解锁档位 | 占用 |
|---|---|---|---|
| 铁锭 | 速度（index 0） | 1 | 矿石槽 1 |
| 金锭 | 急迫（index 0） | 1 | 矿石槽 2 |
| 下界合金锭 | 抗性提升（index 1） | 2 | 矿石槽 3 |
| 绿宝石 | **跳跃提升**（index 1） | 2 | 矿石槽 4 |
| 钻石 | 力量（index 2） | 3 | 矿石槽 5 |
| （满级白送，不入槽） | **生命恢复**（index 3，仅满级；**II 当有余槽 / I 当满配且全 I / 无 当满配且已加倍**） | 4 | 免费，不占槽 |

⭐ **为什么绿宝石→跳跃提升（而不是再生）**：再生被"满级白送"接管后，绿宝石槽就**空出来**了。
把它映射到原版池里**唯一还没被分配的「跳跃提升」(JUMP)**，于是
**5 种矿石 + 满级白送再生 = 原版完整 6 效果池**，一个不少。
（之前我误把绿宝石=再生、砍掉跳跃提升，是错的——根因是没看原版 `BEACON_EFFECTS` 的 index 3 专属再生。）

✅ **仿原版：等级门控矿石池**（用户 2026-10-15 定「参考原版」）：原版按档位**层层解锁**效果池
（1 档 index0、2 档加 index1…），本实现**同样按等级门控矿石效果**——
铁/金 1 级可用，下界合金/绿宝石 2 级，钻石 3 级，再生满级白送。
范围 / 时长仍随等级缩放（照原版 `level×10+10` / `(9+level×2)×20`）。
⇒ 1/2/3 级各有不同可用效果，和原版 tier 进度对齐；堆叠只管"同种效果数量"，不重复门控。

**等级 1~3 场景示例（仿原版门控，堆叠仍管数量）**：

| 场景 | 等级 | 堆叠 | 喂锭 | 生效效果 | 范围/时长 |
|---|---|---|---|---|---|
| 1 级拿速度 | 1 | 1 | 1 铁 | 速度 I | 20 / 11s |
| 1 级满配（仅 2 矿石） | 1 | 5 | 铁+金 | 速度 I + 急迫 I（其余 3 槽因门控空着） | 20 / 11s |
| 2 级拿 4 效果 | 2 | 5 | 铁+金+下界合金+绿宝石 | 速度 I+急迫 I+抗性 I+跳跃 I | 30 / 13s |
| 3 级满池 | 3 | 5 | 全 5 矿石 | 速度 I+急迫 I+抗性 I+跳跃 I+力量 I | 40 / 15s |
| 3 级力量（II 未解锁） | 3 | 1 | 2 钻石（第 2 个被拒，不消耗） | 力量 I | 40 / 15s |
| 4 级满池+再生 | 4 | 5 | 全 5 矿石 | 5 效果 + 再生（3 档） | 50 / 17s |

⭐ **与原版对比焦点**：原版 1~3 级只能选 **1 个**效果、4 级最多 **2 个**；活信标靠堆叠给到 **1~5 个 + 满级再生**，
每个等级都超原版数量——但**可用效果的种类**现在和原版一样按档解锁（1 级拿不到力量）。
范围/时长两列与原版逐档对齐。

**⭐ 拆堆 = 策略（规则自己长出来的，未额外设计）**：
- 一摞 N 个 ⇒ 激活前 N 槽 ⇒ **N 种 buff 集中在一个范围圈**
- 拆成单个分开放 ⇒ 每个只激活**第 1 槽** ⇒ **同一个 buff 铺开到多个位置**
- ⚠️ 推论：想铺开 5 种 buff ⇒ 配 5 摞、每摞只配 1 种（各自要下方 9 槽底座 ⇒ 每摞约 10 格、5 摞约 50 格）

**生命周期**：
- 效果配置存 DataComponent ⇒ **跟物品走**（移出 / 换槽 / 容器卸载都保留）
- **取消活化 ⇒ 清空配置**（项目铁律：取消活化清理自有组件；
  `getOwnedComponentTypes()` 必须声明，漏列即孤儿数据）
- 物品拆堆 ⇒ 组件**复制**到子栈 ⇒ 每摞都带同一套配置（激活数不同）

**⭐ 为什么不需要"令牌位"**：消耗制下令牌不占格 ⇒ 信标只需**下方一行 9 槽底座**，
含信标本体共 **10 格**即可满配。
（常驻制才需要 5 个令牌位、共 9 格 —— 已否决。）

**⚠️ 坑**：

1. **信标要放在"下方有整整一行、且自身居中列"的位置**：信标在**最底行** ⇒ 下方无行 ⇒
   **无法激活**；信标不在中列 ⇒ 9 列被容器边界钳制 ⇒ **到不了满级**（§2.4）。
   接受（玩家会往中列放）；列入游戏内验证点。
2. **混材质按合计**：同槽混铁块 + 钻石块正常累加（原版也不看材质，见 §4）。
3. **材料被拿走** ⇒ 等级下降甚至失活 ⇒ 自然行为，无副作用。
4. **堆叠**：活信标自身若可堆叠，层槽判定要以"单个信标所在槽位"为基准（见 §5 U16）。

### 2.6 图标与 tooltip（用户 2026-10-16 定）

**图标：极简 —— 无专属 spec，原版外观 + 默认活标记**：
- **不注册 `LivingIconSpec`** ⇒ 全形态（掉落物 / 手持 / GUI）都是**原版信标外观**，
  由 `LivingDefaultDecorator` 自动叠 `living.png` 活标识（排除法默认挂标记；先例：活箱子 /
  末影箱的"活标识一直在"）。
- **不画光束、不做变体**（用户定：简单点）——活化与否 / 等级 / 宿主全是**运行时数据**，
  本就上不了图标层（图标只能读 DataComponent，见 [icon-system.md](../system-design/icon-system.md)）。
- ∴ 图标**零新增成本**：无模型 JSON、无新 Java 类。实现第一步先 grep `LivingDefaultDecorator`
  的排除法注册逻辑，确认无 spec 物品确实吃得到默认标记。

**tooltip：文本层两路 —— 「静态（组件）+ 运行时（遥测）」**（用户 2026-10-16 定，可后改）：

*静态层*（`addToTooltip` 直读 DataComponent —— 任何 GUI、关着的容器都能显示）：
- 未配置 ⇒ 一行提示：「右键喂矿石锭配置效果（1 锭 = I；2 锭 = II，**仅满级**）」；
- 已配置 ⇒ **槽位账本 5 行**：`① 速度 I` / `② 力量 II（L3 解锁）` …未配槽标空；
  每种矿石旁标注**解锁档位**（门控信息来自档位表，静态可推）。

*运行时层*（新增 `BeaconSegment` 遥测段，照抄 `FurnaceSegment` / `HopperSegment` 范式）：
- 等级 / 范围 / 柱高**每 tick 现算且在变** ⇒ ⚠️ **严禁写 DataComponent**（遥测铁律，见
  [tooltip-system.md](../system-design/tooltip-system.md) §7-1），必须走
  `ContainerRuntimeCache` + `LivingItemSyncPacket`；**背包悬停走 `player_` 直发通道**（§3.2）。
- 显示行：
  - `激活等级 N / 范围 XX 格`（未激活 ⇒ 一行"未激活"）；
  - **金字塔账本**（本物品最有用的行）：`距 L(N+1) 还差 X 块 —— 缺列：中心差 3、C2 差 5`；
  - 满级 ⇒ `免费再生 II / I / 无`（三档规则的实时输出，见 §2.5）。

*BeaconSegment 字段草案*：`level`(int 0–4) · `rangeBlocks`(double) ·
`columnHeights`(long[9]，以信标列为中心的排列) · `freeRegenTier`(enum NONE/I/II)。

*二期（U22，可后补）*：F3+H 仪器面板「**小金字塔**」——9 根柱 = 当前柱高 +
目标高度刻度线（当前等级目标或满级目标），相位圆盘同思路：**图上就是你搭的金字塔本体，
缺哪根柱一眼可见**。纯客户端渲染，数据与文本层共用同一个 `BeaconSegment`。

### 2.7 实现复用图谱（2026-10-16 核实代码后整理）

**结论：活信标是新活物品里最省的一类**——框架 tick / 交互 / 遥测 / 同步 / 渲染挂载全是现成的；
真正新写的核心 = **「金字塔判定 + 配置组件 + buff 计算」三个纯逻辑件 + 一个客户端渲染器**。

**可直接复用（已核实存在）**：

| 实现需求 | 用什么 | 先例 / 说明 |
|---|---|---|
| 功能挂载 + 每 tick 扫描 | `LivingItemFunction` + `LivingItemManager.registerFunction` | 照 `domain/tnt/TntRegistration` 范式写 `BeaconRegistration`；信标是 vanilla BEACON 活化，**无新物品注册** |
| 右键喂锭（消耗制） | `living/interaction/InteractionRegistry`（JSON 规则 + `registerHandler`）+ `InteractionHandler` | 活打火石 / 活耕地骨粉同链路，零新传输 |
| 下方 9 列底座读写 | `living/transfer/SlotResolver`（9 列网格 + `Pos2D` 偏移 + 越界返 −1） | **天然命中设计**：±4 批量解析，越界 −1 即柱高 0 = "越界钳制" |
| tooltip 运行时数据 | `living/runtime/`：`RuntimeSegmentType/Registry` + `ContainerRuntimeCache` + `LivingItemRuntimeSync` + `LivingItemClientCache` | 照 `FurnaceSegment` / `HopperSegment` 写一个段；背包悬停的 `player_` 直发通道已有 |
| tooltip 静态文本 | `LivingItemFunction.addToTooltip` 钩子 + `client/render/LivingItemTooltip` | 组件直读 |
| 箱子宿主同步（位置 + 颜色） | `LivingToolHostSync` / `LivingToolHostClientCache` 模式（32 格定向 + 内容去重 + 整表替换） | 信标内容更简单（只要位置），照抄 |
| 客户端渲染挂载 | `RenderLevelStageEvent`（`LivingItemClient.onRenderLevelStage` 已转发）+ **原版 `BeaconRenderer.renderBeamBeam` 是 `public static` 可直调** | 光束纹理 / 流动白拿；方向算法抄 `LivingToolModelRenderer`；截断用 `level.clip` |
| 箱盖保持打开 | 原版 `blockEvent` 通道 | 不动 `openersCounter` ⇒ 不误触发陷阱箱（§2.3） |
| 图标 | `LivingDefaultDecorator` 排除法自动活标记 | **零成本**，什么都不写（§2.6） |
| 数据持久化 / 清理 | DataComponent record + `withXxx()` + `getOwnedComponentTypes()` | 项目通用模式；取消活化清空 |
| 单测 | `SimpleContainerContext`（640 测底座） | 金字塔判定 / buff 逻辑可 100% 纯逻辑测 |

**必须自己写（均有先例可抄）**：

| 新件 | 量级 | 抄谁 |
|---|---|---|
| `BeaconFunction` 本体（宿主检测 / tick 节奏 / buff 施加） | 中 | 任一功能类 + 自写 `applyEffects` 等价 |
| **`BeaconPyramid` 判定器**（9 列柱高 → 0~4 级 + 距下一级差额） | 小，**纯逻辑** | 无先例但零依赖，单测全覆盖 |
| 矿石配置组件（5 槽 record + codec） | 小 | 任意 DataComponent record |
| `BeaconSegment`（level / range / 柱高 / 再生档） | 小 | FurnaceSegment 拷贝改造 |
| 喂锭 handler（门控 / 满 II 门槛 / 消耗 / 写组件） | 小 | InteractionHandler |
| 客户端光束渲染器（玩家射线 + 箱子垂直） | 中（唯一有几何量的件） | LivingTool 渲染器 + renderBeamBeam |
| buff 数量 + 再生三档计算器 | 小，纯逻辑 | — |
| （二期）F3+H 金字塔面板 | 中 | 相位圆盘渲染器 |

**⚠️ 三个钩子**：
1. 原版 `applyEffects` 是 `private` ⇒ 等价自写（公式已在 §1 / §2.5 备齐）；
2. `InteractionRegistry` 两趟匹配（精确 vs 通配）——喂锭 triggerItem = 矿石锭属精确趟，天然优先；
3. 遥测段 `id` 是**线格式契约**，发布后不可改名——`beacon` 想好再定。
