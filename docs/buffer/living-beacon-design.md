## §0 原始需求（用户原话）

> 「开始探讨新活物品：活信标。我想让信标的光束能够从玩家脑袋上射出。」
>
> 「还有在箱子这种有开盖动画的容器里时，能不能保持盖子一直打开的样子，然后光束从里面射出来。
> 其它没有开盖动画的容器就不管。」

**⇒ 目标**：一个**移动信标**，**两种宿主形态**：

- **带在身上** ⇒ 光束从你**头颅顶面**射出（**像帽子一样贴在头顶、随头转动**）、方向 = **头颅顶面法线**；
- **放进箱子** ⇒ **盖子保持打开**、光束从**箱口垂直向上**射出。

两种情况都：被方块挡住就**截断**、联机**所有人都能看到**、给**周围玩家加信标 buff**。

**⚠️ 与其它活物品的根本差异（核心设计约束）**：活信标**只在两种宿主下生效** ——
**玩家本人（背包 / 手持）** 或 **箱子（含陷阱箱）**。
掉进其它容器（漏斗 / 木桶 / 潜影箱 / 末影箱…）或变成掉落物 ⇒ **不发光**。
（其它活物品在任意容器里都跑；这是活信标唯一的"宿主限定"。）

## §1 目标玩法定义（草案 —— 六项）

> ⚠️ 本节是**草案**，用于定稿后搬进 tech 文档的 `§0 玩法定义`。
> 判据同 [docs/README.md](../README.md)：**只写规则与语义，不写数值与操作步骤**。

**语义**：**活信标 = 移动信标**。活化后的信标**带在身上**时从**玩家头颅顶面**射出一条**信标光束**
（沿顶面法线、被方块截断）；**放进箱子**时让**箱子盖子保持打开**、光束从**箱口垂直向上**射出。
两种形态都对周围玩家施加信标效果。它把原版"固定方块 + 金字塔"的信标，变成了"跟着人走 /
藏进箱子"的信标。

**获取**：原版信标 + 活化。

**核心循环**：活化信标 → 放进背包 / 手持（或箱子）→ 出现光束（头颅顶面法线 / 箱口向上）→
**在相邻槽位摆材料堆 ⇒ 金字塔层数上升 ⇒ buff 档位与范围随之提升** →
移出有效宿主 / 取消活化 ⇒ 光束消失（箱盖恢复）+ buff 停止。

**规则**（违反即 bug）：

| # | 规则 | 为什么 / 后果 |
|---|---|---|
| 1 | 宿主必须是**玩家本人**（背包 / 手持）或**箱子（含陷阱箱）**才生效 | 其它宿主没有"发光形态"（用户 2026-10-14 定） |
| 2 | **玩家宿主**：光束**像帽子一样贴在头顶**（起点 = **头颅顶面中心**、方向 = **头颅顶面法线**，两者**都随头俯仰转动**）—— 平视 = 竖直向上；低头 = 朝前上方且起点往前下移；抬头 = 朝后上方。⚠️ 顶面法线与**视线垂直**（相差 90°），不是视线；起点早先取过**眼睛位置**、也曾固定高度不随头转，均已被取代 | 玩法定义（用户 2026-10-16 在「所有读法」中选定） |
| 3 | **箱子宿主**：光束起点 = **箱子顶部中心**，方向 = **垂直向上** | 玩法定义（箱内无视线，故固定） |
| 4 | **箱子宿主：盖子保持打开** | 视觉语义（"从里面射出来"）；机制见 §2.3 |
| 5 | 光束**被遮光方块截断**（透明方块穿过：玻璃 / 树叶 / 铁栏 / 台阶 / **基岩**…，判据**逐字对齐原版** `getLightBlock ≥ 15 && !bedrock`） | 还原原版手感；⚠️ 曾用直接 `level.clip` ⇒ 玻璃也挡光（用户实测 2026-10-16 修）；⚠️ 判据曾用 `canOcclude()` ⇒ 基岩被挡/遮光边缘不一致（用户要求对齐，2026-10-16 改原版口径）。⚠️ **「通天失效」明确不对齐**（用户 2026-10-16 拍板）：原版被盖住时光束/buff/等级重算三重停，我们只截断到盖底露一截、buff 与等级不受影响——理由：活信标在密闭箱子/地下室里也生效是玩法增强，不强制玩家搭通天柱 |
| 6 | 光束**所有玩家可见**（联机） | 玩法定义 |
| 7 | 对**周围玩家**施加信标 buff；**范围 / 时长随等级**（照原版公式） | 核心功能（照 `BeaconBlockEntity.applyEffects` 公式**等价自写**——原版该方法为 `private`，不可直调） |
| 8 | **取消活化 / 移出有效宿主** ⇒ 光束消失 + 箱盖恢复 + buff 停止 | 生命周期（见 §3.1） |
| 9 | 活信标是**设备**，不被其它活物品当**耗材**消耗 | 通用隔离规则（同活熔炉 / 活酿造台） |
| 10 | **激活/等级 = 下方一行 9 列「1D 金字塔」柱高**（以信标列为中心 ±4，越界视为 0；每列 ≥ 目标、取满足的最高 N；见 §2.4）；未激活 = 完全死物 | 玩法定义（用户 2026-10-15 晚定，见 §2.4） |
| 11 | **buff 数量 = `min(信标堆叠数, 当前等级可用矿石池大小)` + (等级==4 且未因「满配+加倍」消耗满级再生 ? 1 : 0)**；矿石池按等级门控（仿原版，见 §2.5）；等级 4 再叠加**满级再生**（等级 / 有无见 §2.5「4 级特权」） | 玩法定义（用户定，见 §2.5） |
| 12 | **效果配置存 DataComponent**（固定 5 个矿石槽）；右键 + 矿石锭**消耗写入**；**取消活化清空**。⚠️ **生命恢复 II 不在此列**——它是等级 4 的满级专属项（不占槽、不存组件、不花锭） | 玩法定义（用户定，见 §2.5） |

## §2 技术方案

### 2.1 三条关键发现（决定省力程度）

**① 渲染零代码 —— 复用原版函数。**
`BeaconRenderer.renderBeaconBeam(...)` 是 `public static`（`net.minecraft.client.renderer.blockentity`），
原版信标自己就调它。它画的是**沿局部 `+Y` 的柱体** + 流动闪烁 + 纹理 ⇒
只要把 PoseStack 平移到起点、旋转到目标方向，即可直接调用。

```java
public static void renderBeaconBeam(
    PoseStack poseStack, MultiBufferSource bufferSource, ResourceLocation beamLocation,
    float partialTick, float textureScale, long gameTime,
    int yOffset, int height, int color, float beamRadius, float glowRadius)
```

> ⚠️ **已知坑**：函数内部写死 `translate(0.5, 0, 0.5)`（给方块坐标补到方块中心用）
> ⇒ 平移起点时需在**局部 XZ 各减 0.5 预补偿**，否则光束轴线偏离起点。
> （箱子宿主起点恰好是方块中心，天然对齐；玩家宿主需补偿。）

**② 挂载点现成。**
`RenderLevelStageEvent`（**`AFTER_BLOCK_ENTITIES` 阶段**——2026-10-16 用户实测「开光影原版亮我们暗」
后从 `AFTER_ENTITIES` 改：必须与原版信标（BlockEntityRenderer）同段，光影才把我们当同一类发光体
送进 bloom；深度双保险不变）—— `LivingItemClient.onRenderLevelStage`
已转发给 `LivingToolRayRenderer` / `LivingToolModelRenderer`
⇒ 活信标光束挂**同一事件**，是第 3 个消费者，**零新增基础设施**。
⚠️ 直调 `renderBeaconBeam` 后必须**两趟 flush**（beam 不透明 + glow 半透明是两个 RenderType）——
漏 glow 那趟 ⇒ 光晕被推迟提交 ⇒ 暗淡（不开光影也在）。

**③ 方向对齐写法可复用。**
玩家宿主（顶面法线方向）用 `LivingToolModelRenderer.drawModel` 的
`Axis.YP.rotation(yaw)` + `Axis.XP.rotation(pitch)`；箱子宿主方向恒为 `(0,1,0)`，无需旋转。

### 2.2 职责分工

| 层 | 做什么 |
|---|---|
| **服务端** | ① 容器 tick 检测宿主类型（玩家 / 箱子）② 加 buff（照 `BeaconBlockEntity.applyEffects` 公式**等价自写**——原版 `private` 不可直调）③ 箱子宿主：发 `blockEvent` 保持盖子打开 ④ S2C 广播「谁 / 哪个箱子有活信标」（**不带颜色**——U3-A 下颜色由客户端读世界方块现算） |
| **客户端** | ① 玩家宿主：读玩家位置 / 朝向（**原版已自动同步**）⇒ 起点 = 头颅顶面、方向 = 顶面法线 ② 箱子宿主：读 S2C 缓存的箱子位置 ③ 沿方向 raycast 找截断点（`level.clip` + **跳过非遮光方块**，判据 `blocksBeam` = 原版 `getLightBlock ≥ 15 && !bedrock`，见 §4 规则 5）④ 调 `renderBeaconBeam` 画光束 |

**⭐ 同步最小化**：玩家宿主的位置与朝向**原版已自动同步**；箱子宿主只需广播**位置集合**。
参考项目现成实现：`LivingToolHostSync`（按 32 格定向 + 内容去重）+ `LivingToolHostClientCache`（整表替换 + 维度校验）。

**⭐⭐ 可见距离的口径（2026-10-16 定「和原版差不多」）**：
原版光束"很远都能看见"来自**方块身份 + 三个免剔除开关**（核源码）：
① `shouldRenderOffScreen() = true` ⇒ 进"全局方块实体"名单，**跳过视锥剔除**（背对着信标也能看见光束）；
② `getViewDistance() = 256`，且判据**只算水平距离**（`multiply(1,0,1)`，Y 清零）；
③ `getRenderBoundingBox()` 从基座包到 `y + MAX_RENDER_Y(1024)`；光束自身高度上限也是 1024。
实际可见上限 = `min(渲染距离, 256)`。

⚠️ **活信标是物品（在背包 / 箱子里）⇒ 客户端看不见，做不到"零同步"** ⇒ **可见性完全由我们的广播半径决定**。
因此半径取 **256 + 水平判据**（对齐原版 `getViewDistance`），长度取 **1024**（对齐 `MAX_RENDER_Y`）；
代价可忽略（条目十几字节 + 只在变化时发，稳态零流量）。另有天然天花板：玩家宿主要对方**实体**同步给你
（玩家实体 `clientTrackingRange = 32` 区块，实际受视距限制）⇒ 256 已足够"看得见他就看得见光束"。
⚠️ 客户端对箱子宿主加 **`hasChunkAt` 守卫**（未加载区块不画），否则半径超出视距时会出现悬空光束
（原版是方块、没这问题）。

**⭐⭐ 光束颜色的口径（U3 方案 A，2026-10-16 用户定）**：
原版机制（核源码）：从信标往上扫，每格取 `BlockState#getBeaconColorMultiplier`（NeoForge 扩展点，
染色玻璃 / 玻璃板 / **信标自身**都实现 `BeaconBeamBlock`）——
① 第 1 个有色块是**信标自身**（色=白）⇒ 白底段；
② **第 2 个**（紧邻的第一块玻璃）⇒ 仍是**纯色**新段 ⇒ 所以"直接放一块玻璃"拿到玻璃本色；
③ **第 3 个起**：同色加高、**异色 ⇒ 新段 = 前段与新色的平均**（`FastColor.ARGB32.average`）；
④ 非染色方块加高当前段、**不透明方块**（原版 `lightBlock ≥ 15 且非基岩`）停止扫描；
⑤ 渲染端"最后一段画到顶"（写死 1024）⇒ 感知上"第一块玻璃决定整根颜色"。

我们的对应（**方案 A：颜色一律取自世界方块，贴合原版**）：
- **玩家宿主**：客户端扫**头颅顶面上方**的世界方块（上限 32 格，避免每帧长扫；超出部分由最后
  一段兜住）⇒ 走进染色玻璃走廊会变色，与原版同源。
- **箱子宿主**：客户端扫**箱口上方**世界方块（同上限）。
- ⭐ **颜色不需要任何同步**：世界方块本来就同步给所有客户端 ⇒ 别人的光束颜色也本地算得出来
  （这是方案 A 相对方案 B 的主要好处；`BeaconPlayerHostPacket` 因此**只带 UUID + 等级**）。
- 算法落在 `client/render/BeamColorSections`（纯逻辑，9 项单测）；取色走 NeoForge 同一入口
  `BlockState#getBeaconColorMultiplier` ⇒ 兼容第三方彩色玻璃。
- ⚠️ 分段高度是**竖直格数**，玩家光束沿**顶面法线** ⇒ 两者不严格对应；因"最后一段画到顶"，观感仍是
  "第一块玻璃决定整根颜色"。
- 无染色玻璃 ⇒ 原版白光（原版此情形无光束；我们的光束本就常亮，故保留白色）。

⚠️ **两个实测修复的坑（2026-10-16）**：① **白底段高度必须 ≥ 1**（模拟原版「信标自身那一格」）——曾设为 0，叠加渲染循环「0 高段 break」⇒ **第一格就是染色玻璃时整条光束不画**（贴箱口/贴头顶放玻璃消失，隔一格正常）；渲染循环已改为「0 高段跳过、高度用尽才停」。② 时间差哨兵值**不能用 `Long.MIN_VALUE`**（`gameTime - MIN_VALUE` 溢出成负 ⇒ 开盖重发永假，见 §2.3）。

### 2.3 容器宿主（箱子）—— 机制调研与做法

**为什么难**：客户端**看不到方块容器内容**（不开 GUI）⇒「这个箱子该不该开着 / 发光」必须**服务端同步**。

**⚠️ 三类容器的开盖机制不统一**（2026-10-14 核源码）：

| 容器 | 机制 | 保持打开要动哪 |
|---|---|---|
| **箱子 / 陷阱箱 / 末影箱** | `LidBlockEntity` + `ChestLidController`；服务端 `level.blockEvent(pos, block, 1, count)` → 客户端 `triggerEvent` → `shouldBeOpen` → `tickLid` **平滑过渡** | 发 `blockEvent(1, 1)` |
| 木桶 | ⚠️ **不是 LidBlockEntity** —— 开盖 = **方块状态** `BarrelBlock.OPEN`（服务端 `setBlock`），**离散无平滑** | 服务端 `setBlock` |
| 潜影箱 | 自有 `AnimationStatus` + `progress`；⚠️ **碰撞箱与 progress 耦合**（`ShulkerBoxBlock.getShape` → `getBoundingBox` → `getProgressAabb`）⇒ 只改客户端会穿模 | 两端一致改 |

**本版只做箱子 / 陷阱箱**（用户 2026-10-14 定：其它容器不考虑）。

**做法**：
- **服务端**：容器 tick 检测箱内有活信标 ⇒ 发 `level.blockEvent(pos, block, 1, 1)`
  ⇒ 客户端盖子**平滑打开并保持**；活信标取走 ⇒ 发 `blockEvent(1, 0)` 恢复。
- **客户端**：**无需 Mixin**（复用原版 `blockEvent` 通道）；仅需 S2C 缓存定位箱子以画光束。

**⚠️ 三个已查明的坑**：

1. **陷阱箱红石**：`TrappedChestBlock.getSignal` = `Mth.clamp(ChestBlockEntity.getOpenCount(...), 0, 15)`，
   而 `getOpenCount` 读的是**服务端 `openersCounter`**。我们的 `blockEvent` **只影响客户端渲染**、
   不动 `openersCounter` ⇒ **不会误触发红石** ✅。
   🔴 **反面**：将来若改成直接改 `openersCounter`，**就会误触发陷阱箱** —— 别那样做。
2. **与真玩家开关的竞争**：真玩家关箱子 ⇒ 服务端发 `blockEvent(1, 0)`，我们下 tick 补 `blockEvent(1, 1)`
   ⇒ 最多 **1 tick 抖动**（盖子闪一下）。可接受。
3. **新玩家进入 / 区块重载**：`blockEvent` 只发给**当时跟踪该区块的玩家** ⇒ 后到的玩家看不到开盖。
   ⇒ 需**周期性重发**（倾向每 20 tick）或客户端本地兜底（见 §5 U11）。

### 2.4 金字塔层数 —— 下方一行 9 列的「1D 金字塔」（用户 2026-10-15 晚定）

**层槽定义**：活信标所在槽位**正下方整整一行**的 9 个槽位，**以信标所在列为中心**
（偏移 −4…+4 共 9 列；越出容器边界的列视为 0）。

⭐ **这不是随手切几个槽 —— 它是原版 4 层方锥的 1D 投影**：每列的矿物块堆叠数 = **该列的方块柱高**
= 覆盖该列的各层边宽之和。中心列在 L4 有 4 层叠加 ⇒ 9+7+5+3 = **24**；边列只有最宽那层的一半 ⇒ **9**。
俯视即"信标被这座底座**承托**在中央"，保留原版金字塔的**形状语义**。

| 等级 | 目标柱高（左半 → 中心） | 覆盖列数 | 合计 | 对应原版 |
|---|---|---|---|---|
| 1 | 3-3-3 | 3（±1） | 9 | 铺满底 3×3 层 |
| 2 | 5-8-8-8-5 | 5（±2） | 34 | + 5×5 层 |
| 3 | 7-12-15-15-15-12-7 | 7（±3） | 83 | + 7×7 层 |
| 4 | 9-16-21-24-24-24-21-16-9 | 9（±4） | 164 | + 9×9 层（满级） |

**激活 / 等级判定**（口径 = **每列 ≥ 目标，取满足的最高 N**；用户 2026-10-15 晚定）：
- 材料 = **底座矿物块**（`BEACON_BASE_BLOCKS`：铁/金/钻石/绿宝石/下界合金块），**混材质按列合计**
  （对齐原版 `updateBase` 只看形状、不看材质）。
- 逐级判定：该级中心 (2N+1) 列的**每列柱高 ≥ 目标值** ⇒ 达 N 级；从 4 往 1 试，取第一个满足的。
- ⇒ **少一块自动掉档、多堆不亏**；四级图案**嵌套单调**（L4⟹L3⟹L2⟹L1），判定自洽。
- 无一满足 ⇒ **0 级**：未激活 = 完全死物（用户定）——光束不亮、buff 不施加，就是个普通信标
  ⇒ 判定结果直接映射"亮不亮 / 加不加"，**零歧义、零额外状态**。

**成本与原版对齐**：4 级合计 **164 = 原版满层成本**（全铁块 ≈ 1476 铁锭 ≈ 23 组）；
活化**不减材料成本**，减的是**操作复杂度**：在容器里填 9 槽 vs 在世界里堆一座四层金字塔。
代价从"建造成本"转成"携带成本"——而这正是"移动信标"该有的样子。

**居中要求（以信标列为中心的必然推论）**：信标必须放在**中列**才铺得满 9 列；
偏 1 列 ⇒ 越界 1 列 ⇒ 最高只能到 L3，依此类推 ⇒ 玩家自然会把信标往中列放。

**物理上限**：9 槽 × 每组 64 = **576** ⇒ 164 档轻松可达（平均每列约 19 个）。

### 2.5 效果配置 —— 消耗制 + 组件存储（用户 2026-10-15 定）

**⭐ 三层分离（三个规则互不冲突，因为它们不在同一层）**：

| 输入 | 层 | 存储 |
|---|---|---|
| 底座矿物块**数量** | **容器层** | **不存** —— 每 tick 读下方一行 9 槽（柱高） |
| 信标**堆叠数** | **物品栈层** | **不存** —— 读 `getCount()` |
| 矿石锭**种类** | **组件层** | **存** DataComponent（固定 5 个效果槽） |

⇒ 关键认知：**MC 堆叠的本质是「组件相同就能叠」，不是"每个物品独立配置"。**
一摞信标**共享同一套配置**；「buff 数量 = 堆叠数」只是「激活这套配置的前 N 个槽」——
改 count **不需要改组件**。这就是三层能共存的根本原因。

**配置操作（消耗制）**：
- 光标拿矿石锭 → **右键活信标**（走 `InteractionRegistry`，与「活打火石点活TNT」同款，
  复用 `GuiInteractionPacket` → `InteractionHandler` 链路）
- 该锭对应效果**不在**配置里 ⇒ 消耗 **1 个锭**，追加一个 **I 级**槽
- 该锭对应效果**已在**配置里 ⇒ **仅当 等级==4** 时消耗 **1 个同种锭**升 **II 级**（2 锭 = II 级）；**低等级右键同种已配锭 ⇒ 拒绝（不消耗）**，因为 II 只在满级解锁（仿原版 `主效果==次级效果` 需 `beaconLevel>=4`）
- 写入对**整摞**生效（同一 `ItemStack` 的 `set`）⇒ 整摞组件始终相同 ⇒ **永远可堆叠**

**槽位与激活**：
- **固定 5 个矿石效果槽**（同种锭升级占**同一个**槽，不新增）
- 配置**按写入顺序**排列
- 生效矿石效果数 = `min(信标堆叠数, 已配置且档位 ≤ 当前等级的槽数)`（等级门控见下方「等级门控矿石池」）；按配置顺序取前 N 个
- 总 buff 数 = 矿石效果数 + (等级==4 且未因「满配+加倍」消耗满级再生 ? 1 : 0 个满级再生)；满级 5 堆叠且未加倍 ⇒ 5 + 1 = **6 种 = 原版完整池**（再生等级 / 有无见下方「4 级特权」）

**4 级特权（满级授予再生，不占槽）**：等级达到 4（满级）时，**自动授予「生命恢复」**——
**不占任何矿石槽、不花锭、不存组件**。

⭐ **再生的等级 / 有无（关键，案例 2 才暴露的完整规则 —— 三档，不是两档）**：
- **有空的「种类槽」⇒ 再生 II 级**（默认上限）
- **无空槽、且所有已配效果都是 I 级 ⇒ 再生 I 级**
- **无空槽、且至少有一个效果被加倍到 II 级 ⇒ 再生【不授予】**（满级再生被"加倍"消耗掉）

⭐ **这正是"仿原版"的核心**：原版 `BEACON_EFFECTS[3] = REGENERATION`，**再生只在第 4 档（满级）才解锁**；
而原版想让某效果到 II 级必须 `主效果==次级效果`（`applyEffects` 放大器 `i=1`），这会**吃掉次级槽** ⇒
原版里"II 级效果"和"再生"互斥。活信标把"满级再生"当作那个次级槽：
**你把某个效果加倍到 II、又没有空槽兜底时，满级再生就被消耗掉**——和原版"加倍即占次 slot"完全同构。
（有空槽时再生照给 II，因为还有余力。）

**验证（与全部测试用例逐字一致，含案例 2 不写再生）**：

| 案例 | 堆叠 | 喂锭 | 占用槽 | 空槽 | 满级再生 |
|---|---|---|---|---|---|
| 1 | 1 | 1 钻石 | 力量 I | 0 | I |
| 2 | 1 | 2 钻石（力量 II） | 力量 II | 0 | **无**（满配且已加倍 → 消耗） |
| 3 | 2 | 1 绿宝石 | 跳跃 I | 1 | II |
| 4 | 2 | 2 绿宝石（跳跃 II） | 跳跃 II | 1 | II |
| 5 | 2 | 1 绿宝石 + 1 钻石 | 跳跃 I + 力量 I | 0 | I |

⚠️ **我之前的错误（两处）**：① 以为"2 个同种锭 = 占了 2 个槽"，案例 4 看似满配；
其实 2 同种锭升级同槽到 II、不新增槽 ⇒ 案例 4 仍余 1 空槽 ⇒ 再生 II。
② 顺着错把案例 2 也写成"再生 I（推断）"——其实案例 2 是 **1 堆叠、力量加倍到 II、0 空槽**，
正落在"满配+加倍 → 再生不授予"那一档，所以你原话只写"2 级力量"、没提再生是对的。
这两点想通后，5 个案例（含案例 2 的省略）全部自洽。

**等级门控矿石池（仿原版 `BEACON_EFFECTS` 分档，用户 2026-10-15 定「参考原版」）**：

等级这一轴**不仅**管范围/时长，**也管能选哪些效果**——和原版逐档解锁池一致。
各矿石按原版 index 分档解锁；低于当前档位的矿石锭**喂了会被拒（不消耗）**，
已配置的高阶效果在等级下降时**休眠（不施加）、回升后自动恢复**（配置留在组件里）。

| 信标等级 | 可用矿石池（仿原版分档） | 最多矿石效果数 | 满级再生 |
|---|---|---|---|
| 1 | 铁/金 → 速度/急迫（index 0） | 2 | 无 |
| 2 | + 下界合金/绿宝石 → 抗性/跳跃（index 1） | 4 | 无 |
| 3 | + 钻石 → 力量（index 2） | 5 | 无 |
| 4 | 同 3（全 5 矿石） | 5 | 有（3 档规则，见上） |

⭐ 这就让 1/2/3 级各有**不同的可用效果**（不是只差范围/时长）：
1 级拿不到力量、3 级才解锁，和原版 tier 进度一致；堆叠仍管"同种效果的数量"。

**矿石锭 → 效果映射**（一一对应原版 6 效果池里除再生外的 5 个；再生由满级授予接管；每矿石标注解锁档位）：

| 矿石锭 | 效果（原版 `BEACON_EFFECTS`） | 解锁档位 | 占用 |
|---|---|---|---|
| 铁锭 | 速度（index 0） | 1 | 矿石槽 1 |
| 金锭 | 急迫（index 0） | 1 | 矿石槽 2 |
| 下界合金锭 | 抗性提升（index 1） | 2 | 矿石槽 3 |
| 绿宝石 | **跳跃提升**（index 1） | 2 | 矿石槽 4 |
| 钻石 | 力量（index 2） | 3 | 矿石槽 5 |
| （满级授予，不入槽） | **生命恢复**（index 3，仅满级；**II 当有余槽 / I 当满配且全 I / 无 当满配且已加倍**） | 4 | 满级授予，不占槽 |

⭐ **为什么绿宝石→跳跃提升（而不是再生）**：再生被"满级授予"接管后，绿宝石槽就**空出来**了。
把它映射到原版池里**唯一还没被分配的「跳跃提升」(JUMP)**，于是
**5 种矿石 + 满级授予再生 = 原版完整 6 效果池**，一个不少。
（之前我误把绿宝石=再生、砍掉跳跃提升，是错的——根因是没看原版 `BEACON_EFFECTS` 的 index 3 专属再生。）

✅ **仿原版：等级门控矿石池**（用户 2026-10-15 定「参考原版」）：原版按档位**层层解锁**效果池
（1 档 index0、2 档加 index1…），本实现**同样按等级门控矿石效果**——
铁/金 1 级可用，下界合金/绿宝石 2 级，钻石 3 级，再生满级授予。
范围 / 时长仍随等级缩放（照原版 `level×10+10` / `(9+level×2)×20`）。
⇒ 1/2/3 级各有不同可用效果，和原版 tier 进度对齐；堆叠只管"同种效果数量"，不重复门控。

**等级 1~3 场景示例（仿原版门控，堆叠仍管数量）**：

| 场景 | 等级 | 堆叠 | 喂锭 | 生效效果 | 范围/时长 |
|---|---|---|---|---|---|
| 1 级拿速度 | 1 | 1 | 1 铁 | 速度 I | 20 / 11s |
| 1 级满配（仅 2 矿石） | 1 | 5 | 铁+金 | 速度 I + 急迫 I（其余 3 槽因门控空着） | 20 / 11s |
| 2 级拿 4 效果 | 2 | 5 | 铁+金+下界合金+绿宝石 | 速度 I+急迫 I+抗性 I+跳跃 I | 30 / 13s |
| 3 级满池 | 3 | 5 | 全 5 矿石 | 速度 I+急迫 I+抗性 I+跳跃 I+力量 I | 40 / 15s |
| 3 级力量（II 未解锁） | 3 | 1 | 2 钻石（第 2 个被拒，不消耗） | 力量 I | 40 / 15s |
| 4 级满池+再生 | 4 | 5 | 全 5 矿石 | 5 效果 + 再生（3 档） | 50 / 17s |

⭐ **与原版对比焦点**：原版 1~3 级只能选 **1 个**效果、4 级最多 **2 个**；活信标靠堆叠给到 **1~5 个 + 满级再生**，
每个等级都超原版数量——但**可用效果的种类**现在和原版一样按档解锁（1 级拿不到力量）。
范围/时长两列与原版逐档对齐。

**⭐ 拆堆 = 策略（规则自己长出来的，未额外设计）**：
- 一摞 N 个 ⇒ 激活前 N 槽 ⇒ **N 种 buff 集中在一个范围圈**
- 拆成单个分开放 ⇒ 每个只激活**第 1 槽** ⇒ **同一个 buff 铺开到多个位置**
- ⚠️ 推论：想铺开 5 种 buff ⇒ 配 5 摞、每摞只配 1 种（各自要下方 9 槽底座 ⇒ 每摞约 10 格、5 摞约 50 格）

**生命周期**：
- 效果配置存 DataComponent ⇒ **跟物品走**（移出 / 换槽 / 容器卸载都保留）
- **取消活化 ⇒ 清空配置**（项目铁律：取消活化清理自有组件；
  `getOwnedComponentTypes()` 必须声明，漏列即孤儿数据）
- 物品拆堆 ⇒ 组件**复制**到子栈 ⇒ 每摞都带同一套配置（激活数不同）

**⭐ 为什么不需要"令牌位"**：消耗制下令牌不占格 ⇒ 信标只需**下方一行 9 槽底座**，
含信标本体共 **10 格**即可满配。
（常驻制才需要 5 个令牌位、共 9 格 —— 已否决。）

**⚠️ 坑**：

1. **信标要放在"下方有整整一行、且自身居中列"的位置**：信标在**最底行** ⇒ 下方无行 ⇒
   **无法激活**；信标不在中列 ⇒ 9 列被容器边界钳制 ⇒ **到不了满级**（§2.4）。
   接受（玩家会往中列放）；列入游戏内验证点。
2. **混材质按合计**：同槽混铁块 + 钻石块正常累加（原版也不看材质，见 §4）。
3. **材料被拿走** ⇒ 等级下降甚至失活 ⇒ 自然行为，无副作用。
4. **堆叠**：活信标自身若可堆叠，层槽判定要以"单个信标所在槽位"为基准（见 §5 U16）。

3. **删未激活独立行**（`beacon.inactive`）——折叠行已含该语义；
4. **休眠三因**（旧只有「等级不足」一种，两种完全不同的休眠被压成一句话）：`需 L%d`（升级底座）/ `信标不足（需 %d 个）`（补货）。

**生效数口径**：`min(堆叠数, 档内可用槽数)`，**客户端本地算**（`getCount()` + 组件配置 + 遥测等级），调 `BeaconEffects.activeEntries` 同一纯函数 ⇒ tooltip 与实际 buff **单一事实源**；遥测缺失 ⇒ 不猜（等级是其输入，缺输入只显示静态层）。

**lang key 变更清单**（zh/en 两份同步）：

| key | 动作 | 内容 |
|---|---|---|
| `beacon.level` | 改 | `等级 %d · 生效 %d/%d 槽`（去范围） |

| `beacon.inactive` | **删** | 未激活独立行删 |
| `beacon.config_locked` | **删** | 由 `sleep_level` 取代 |
| `beacon.sleep_level` | 新 | `休眠：需 L%d` |
| `beacon.sleep_ingot` | 新 | `休眠：信标不足（需 %d 个）` |
| `beacon.config_inactive` | 新 | `效果配置 %d 槽（未激活，全部休眠）` |
| `beacon.config_empty` | 改 | 补规则：`…右键喂入：1 锭 = I，2 锭 = II（仅满级）` |

#### 2.6.2 图形层：9 柱小金字塔（160×76）

**几何常数**（拟建 `BeaconPanelGeometry` 纯函数，供单测；渲染器 `LivingBeaconTooltipRenderer` 照抄）：

| 项 | 值 |
|---|---|
| 面板 | 160 × 76（深空蓝底 + 靛紫描边，配色沿用发电机体系） |
| 柱位 | 9 列，槽宽 16 / 柱宽 13，x 起点 8 ⇒ 柱区 8..152 |
| 柱区 | y=15..55（高 40），基线 `BASE_Y=55` |
| 柱高映射 | **0~24 块 → 0~40px 线性，且每列钳到该列自己的目标**（柱高 = `min(堆叠, 目标)`）⇒ 实心柱即「金字塔的填充版」，任何时刻都是在建中的金字塔；超额不伸高，改贴该列刻度线 3px 金帽（**不标数字**） |
| 刻度线 y | `55 − round(target×40/24)` ⇒ L1=50 / L2=42 / L3=30 / L4=15 |
| 数字位 | 未达标列：目标值贴刻度线上方 9px（**面板唯一数字语义：这列没到位、要堆到这么多**） |
| 底部读数 | y=57：左 deficit / no room，右 已投/总需求 或 满级 `需 164 块` |

**元素编码**（每列独立，**无水平目标线**——9 列目标高度各异，实际是 9 段阶梯刻度）：

| 元素 | 编码 |
|---|---|
| 实心柱 | 现状，**柱高钳到该列目标**（中心列 = 信标列，亮青 `4CD9E8`；其余列暗青 `2E7A88`）；非参与列（target=0）不画柱（「该列当前未启用」，其材料仍计入底部已投读数） |
| 阶梯刻度线 | 该列自己的目标高度（琥珀 `FFB454`；满级档金色 `FFE17A`），仅未达标列 |
| 横纹缺口 | 待填区：柱顶 → 刻度，3px 一条 1px 线（暗青 `1E4A56`） |
| 金帽（无数字） | 该列超额（堆叠 > 目标），贴**该列**刻度线上方 3px——超额无决策价值（「多堆不亏」），金帽单独表意 |
| 1px 竖虚线 | 越界列（被容器边界钳制，**别填了**）；与「空槽 = 什么都不画」严格区分 |
| 底部左读数 | `to L3: 48 more` / `no room for L1 - move beacon` / `L4 full` |
| 底部右读数 | `51/83`（已投/本级总需求；**含放错列的料** ⇒ 多投不动进度，玩家自己发现）/ 满级 `164 stacked` |

**提示逻辑四转变**（「下一级怎么摆」是行动指令，不是状态描述）：

1. **数字从差额改目标值**——`15` 而非 `−7`（玩家不心算加法）；数字贴着刻度线，「目标标记」是线 + 数的整体；
2. **缺口从实心改横纹**——「待填的格子」与「已有的柱子」纹理可分；达标列虚实重合，自然只剩实心；
3. **底部双读数**——左「还要干多少活」右「投的料有没有走空」；`51/83` 比百分比信息多（能反算差额）且能暴露放错列；
4. **不可达兜底**——下一级参与列存在越界列 ⇒ 该级永不可达（信标贴容器边缘、宽度不足）⇒ 左读数改 `no room for L{n} - move beacon`，**绝不显示 deficit**（「补 9 块就能亮」在不可达时是谎言）。判定：`下一级所有 target>0 的列都存在`。

**状态行为**：

| 状态 | 面板 |
|---|---|
| `level≥1` | 全画（刻度 = 下一级目标行） |
| `level=0` | **照画**，刻度 = L1 行——未激活是它最该出力的时刻（不像发电机 `empty→0 高度`） |
| 满级全达标 | 刻度金色 L4 行、**零目标数字**（「没问题」本身就是信息） |
| 遥测缺失（掉落物/未被 tick） | **不挂载**（`GatherComponents` 里 `runtimeData == null` 直接 return） |

**数据层改动（必做）**：`BeaconRuntime` 新增 `boolean[9] columnExists`（codec 加 1 个 varint 位图；`equals/hashCode` 纳入防稳态恒脏）——`readColumnHeights` 已产出 `targets`（−1 = 越界），顺手产出位图；`BeaconColumnSlotsTest` 扩测。

**挂载实现要点**：`RenderTooltipEvent.GatherComponents` + `RegisterClientTooltipComponentFactoriesEvent` 注册 `BeaconTooltipComponent`（record + `from(BeaconRuntime)`）；⚠️ ThreadLocal 在 GatherComponents 前已被 finally 清空 ⇒ 悬停定位**照抄 `generatorDataFor` 模式**（含 `player_` 背包通道 + 创造模式物品栏引用兜底），不可读 `getCurrentTooltipData()`。

**边界前提（必须遵守）**：删差额行的前提是**面板始终可见**。若将来改回 F3+H 门控，`beacon.pyramid` 差额行必须同步恢复，否则非高级模式下底座信息全裸。

**测试清单**：`columnExists` 位图数学（扩 `BeaconColumnSlotsTest`）/ `reachable` 判定（纯布尔，参数化）/ `BeaconPanelGeometry` 纯函数（刻度 y、缺口高度、数字取舍、溢出帽）/ `BeaconTooltipComponent` 构建与往返 / tooltip 口径两条（堆叠数 < 配置槽数 ⇒ 生效数 = 堆叠数；等级不足槽位不计入生效数——tooltip 与 buff 一致性守卫）。

⚠️ **`fill` 坐标语义坑（2026-10-16 用户实测修复）**：`GuiGraphics.fill` 是
`(x1,y1,x2,y2)` **坐标语义**（右下排他），**不是** `(x,y,宽,高)`。柱区 5 处（刻度 / 横纹 /
柱体 / 帽 / 越界虚线）曾按宽高误传 ⇒ `x2 < x1`，每列画出从面板左上蔓延到柱位的巨大矩形
（黄色刻度/帽 = 「溢出一大块」，深色叠加 = 「铺满屏幕」；用户两条反馈同源）。
**纪律：新写绘制代码的 fill 一律写成 `px .. px + BAR_W` 形式，禁止传裸宽高**；背景/边框
照抄发电机渲染器未错 ⇒ 错的全是新写部分。几何纯函数单测拦得住算错的 y、拦不住传错的 fill
参数 ⇒ 新渲染器的游戏内实测（§6.1）不可省。

### 2.7 实现复用图谱（2026-10-16 核实代码后整理）

必须**主动做破坏性尝试**：

- [ ] **玩家宿主**：光束像帽子一样贴在头顶 —— 起点随头移动、方向随头转（平视 = 竖直向上 / 低头 = 朝前上方 / 抬头 = 朝后上方）

- [ ] **联机**：另一个玩家能看到你的光束 / 箱子光束
- [ ] buff 对**周围玩家**生效
- [ ] **激活等级**：下方一行 9 列按目标柱高图案填充 ⇒ 逐档上升；抽走某列材料 ⇒ 自动掉档；信标不放中列 ⇒ 被容器边界钳制、到不了满级
