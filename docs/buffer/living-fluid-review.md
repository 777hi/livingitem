## A. 数据安全

### A1 推动写入目标失败时仍清源槽 ⇒ 物品消失

**现状**（`pushFluidItems` 空目标分支）：

```java
ctx.setItem(targetSlot, item.copy());
ctx.setItem(slot, ItemStack.EMPTY);   // 无条件的
```

`ContainerContext.setItem` 返回 `void` —— 写失败**不可知**。`SimpleContainerContext.setItem`
的兜底路径 `writeBackViaExtractInsert` 失败时**只记 WARN** 不抛（`extract` 不完整 / `insertItem`
返回剩余 / 写后校验不符）。

**触发面**：第三方 `IItemHandler` —— 不支持 `setStackInSlot`、且 `insertItem` 有输出过滤或整库重定向。
原版 / 常规容器走 `writeBackDirectly` 不会触发。

**待拍板**：
1. 推动侧**写后校验**：`ctx.setItem(target, x)` 后读回比较，不符则不清源槽（改一行，代价 = 一次读 + 一次比较）；
2. 或给 `setItem` 加布尔返回值 / 新增 `trySetItem`（跨全部功能类，改动大）。

**判据**：写入失败 ⇒ 源槽保留原物品，宁可不动也不丢。

---

### A2 合并按「物品堆叠上限」算容量 ⇒ 多出的数量被 clamp 掉

**现状**：

```java
} else if (ItemStack.isSameItemSameComponents(item, targetItem)
           && targetItem.getCount() < targetItem.getMaxStackSize()) {
    int space = targetItem.getMaxStackSize() - targetItem.getCount();
```

判据用的是 `ItemStack#getMaxStackSize`（通常 64），**不是** `ctx.getSlotLimit(targetSlot)`。
而 `ctx.setItem` 写回时会 `clampToSlotLimit`。

**两个方向的错**：
- 槽位上限 **< 64**（单格槽 / 展示槽 / 某些机器的输出槽）：`toAdd` 算多 ⇒ 目标被 clamp ⇒
  **源槽已扣、目标没加 = 丢数量**；
- 槽位上限 **> 64**（抽屉 / 堆叠升级）：合不满（只是效率损失，不丢）。

**待拍板**：改用 `Math.min(ctx.getSlotLimit(target), item.getMaxStackSize())` 作为容量基线上限。

**判据**：合并前后 `来源数量 + 目标数量` 守恒。

---

### A3 推动完全不校验 `isItemValid`

**现状**：推动的准入判据只有「空 / 同类 / 不是活物品 / 不是源格」，与漏斗那条链
（模拟插入 + 槽位上限 + 准入）不同。`setItem` 是**覆盖槽位**语义，也不校验。

**触发面**：只出不进的槽（输出槽、展示槽、某些模组的专用槽）—— 物品会被塞进去且再也拿不出来。

**待拍板**：是否接 `SlotInfoProvider#isItemValid`。⚠️ 接入后行为会变（水流不再往那些槽推），
需要确认这是期望。

## B. 推动语义

### B1 分叉回退序「右→下→左→上」没有机制依据

**现状**（2026-10-30 新增的 `orderChildren` / `childRank`）：分叉时**直行优先**，
直行不可用按 **右 → 下 → 左 → 上**。

**问题**：这个顺序是纯 GUI 阅读习惯，不是从水流 / 原版推出来的；而且是**绝对方向序**，
来向为「下」时先试左、来向为「上」时先试右，语义会翻转。
**触发点不是罕见分支**：物品走到容器边缘（直行方向没水）时必然用到它。

**候选口径**：
1. **slot 升序**（左/上优先）—— 与 `spread` 的同到达时间、`pushFluidItems` 的同 level 完全同一条规则，一句话可解释；
2. 保留顺时针（右优先）；
3. 相对来向的「右转优先 → 左转 → 掉头」（需要新定义坐标系语义）。

**待拍板**：选一条。现状 = 2。

---

### B2 `level` 允许非单调 ⇒ 「上游先」的遍历假设不总成立

**现状**：`advanceGrowth` 里 `newLevel = min(target.level, bestFeeder)`，当目标 BFS 距离更近时
`newLevel < 父 level + 1`，此时「level 升序遍历 = 上游先」不成立。

**实际影响**：`moved` 集合仍能保证**每个物品每拍最多走一格**（被推入的格在 `moved` 里，
后续循环跳过）⇒ 不会连跳。剩下的影响只是**同拍抢位的先后**。

**待验证**：是否会产出可观察的异常（两物品抢同意格时路线跳变）。若无，本条可关闭并写进 §3.3.1 边界。

---

### B3 同拍上游被下游占位挡住时白等一拍

**现状**：`sorted` 升序 + 不重试。上游物品先试，下游还占着 ⇒ 不动；随后下游被推走，
但上游本拍不再重试 ⇒ 队列过窄口时整体速度仍是「一拍一格」，只是多抖一拍。

**待拍板**：是否改成**降序处理**（下游先走、腾出位置）或加一轮重试。
⚠️ 降序会改变「同拍抢占」的语义，需要同时确认 B2。

---

### B4 多源鞍部：物品停在水流相遇点

**现状**：推动方向 = BFS 流树父→子。两个源的水在前沿相遇时，相遇格没有下游 ⇒ 物品停在那里。

**待拍板**：这是「水流末端」的忠实语义，还是需要「物品优先被推到容器出口/边缘」的额外规则？
（若后者，需要先定义「出口」，属于新玩法。）

---

### B5 源格上的物品永不推动

**现状**：`pushFluidItems` 开头 `if (fe.isSource) continue;`（§3.3 文档明写「源格只接受显式投放」）。
物品若被玩家直接丢进源格：
- 转化表命中 ⇒ 当拍转化（机制三）；
- **转化表无条目 ⇒ 永久停住**，水把它冲不走。

**待拍板**：是否给「未被转化的源格物品」一个兜底（如推到相邻下游格）。
⚠️ 与「机制三依赖物品停留浸泡」冲突，需要明确优先级。

---

### B6 每 5t 一格 + GUI 瞬移的观感

**现状**：水推动 = 该流体推进拍（水 5t / 岩浆 30t）**每拍移动一格**，GUI 里是跳格。
`setItem` 清源 + 写目标 ⇒ 客户端看到的是瞬移，没有中间帧。

**待验证**：真机观感是否可接受（用户此前未单独反馈速度问题，本次只报了分叉随机）。

## C. 与其它子系统的交互

### C1 推动不参与 `TickContext` 互斥：漏斗刚放入同拍被冲走

**现状**：容器 tick 顺序 = **功能 tick 先**（漏斗/熔炉）→ **容器级数据后**（流体 prio 0）。
流体推动完全绕开 `TickContext.occupiedSlots` / `transferredTargetSlots`。

**后果**：漏斗本拍放进某槽的物品，**同一 tick 就被水推走**。玩家看到的是「物品刚进箱子就被冲走」，
且漏斗本拍的其它判断基于旧位置。

**待拍板**：是否给「本拍新写入的槽」加 1 tick 保护（与 `transferredTargetSlots` 打通）。
