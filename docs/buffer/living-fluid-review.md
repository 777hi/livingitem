## A. 数据安全

### A1 推动写入目标失败时仍清源槽 ⇒ 物品消失

**现状**（`pushFluidItems` 空目标分支）：

```java
ctx.setItem(targetSlot, item.copy());
ctx.setItem(slot, ItemStack.EMPTY);   // 无条件的
```

`ContainerContext.setItem` 返回 `void` —— 写失败**不可知**。`SimpleContainerContext.setItem`
的兜底路径 `writeBackViaExtractInsert` 失败时**只记 WARN** 不抛（`extract` 不完整 / `insertItem`
返回剩余 / 写后校验不符）。

**触发面**：第三方 `IItemHandler` —— 不支持 `setStackInSlot`、且 `insertItem` 有输出过滤或整库重定向。
原版 / 常规容器走 `writeBackDirectly` 不会触发。

**2026-10-31 用户拍板：移交框架侧**（`TODO.md`「物品传输（跨子系统）」节）——
本池只负责**发现问题**；A1/A2 的修法（写后回读校验 / 事务式移动原语）由框架侧统一处理，
不在流体侧单独打补丁。

**判据**（框架侧实施时用）：写入失败 ⇒ 源槽保留原物品，宁可不动也不丢。

---

### A2 合并按「物品堆叠上限」算容量 ⇒ 多出的数量被 clamp 掉

**现状**：

```java
} else if (ItemStack.isSameItemSameComponents(item, targetItem)
           && targetItem.getCount() < targetItem.getMaxStackSize()) {
    int space = targetItem.getMaxStackSize() - targetItem.getCount();
```

判据用的是 `ItemStack#getMaxStackSize`（通常 64），**不是** `ctx.getSlotLimit(targetSlot)`。
而 `ctx.setItem` 写回时会 `clampToSlotLimit`。

**两个方向的错**：
- 槽位上限 **< 64**（单格槽 / 展示槽 / 某些机器的输出槽）：`toAdd` 算多 ⇒ 目标被 clamp ⇒
  **源槽已扣、目标没加 = 丢数量**；
- 槽位上限 **> 64**（抽屉 / 堆叠升级）：合不满（只是效率损失，不丢）。

**2026-10-31 用户拍板：移交框架侧**（同 A1）。

**判据**（框架侧实施时用）：合并前后 `来源数量 + 目标数量` 守恒。

---

### A3 推动完全不校验 `isItemValid`

**现状**：推动的准入判据只有「空 / 同类 / 不是活物品 / 不是源格」，与漏斗那条链
（模拟插入 + 槽位上限 + 准入）不同。`setItem` 是**覆盖槽位**语义，也不校验。

**触发面**：只出不进的槽（输出槽、展示槽、某些模组的专用槽）—— 物品会被塞进去且再也拿不出来。

**2026-10-31 用户拍板：保持现状**（不接 `isItemValid` 准入）。
推动的定位是「水流搬运」而不是「漏斗插入」，不承担准入职责 ⇒ 水流把物品推进只出不进的槽，
是接受的边界，不作为缺陷处理。

## B. 推动语义

### B1 分叉回退序（✅ 已解决，2026-10-31）

**原问题**：`orderChildren` / `childRank` 按「右 → 下 → 左 → 上」排 children ——
纯 GUI 阅读习惯，且是**绝对方向序**（来向为「下」时先试左、为「上」时先试右，语义翻转）。

**解决**：力场模型 —— 方向由**四邻 level 差**决定，候选最多 2 个（主分量 + 次分量），
不再从「树的所有子节点」里挑；绝对回退序连同 `orderChildren` / `childRank` 一并删除。
45° 平局改为「**容器主轴**」（宽 ⇒ 横；竖 / 正方 ⇒ 纵，用户定兜底取上下）。
落点：`FluidFlowVector#candidates`，tech §3.3.1。

---

### B2 `level` 非单调 ⇒ 力场方向不稳（✅ 关闭，2026-10-31）

**原担忧**：`advanceGrowth` 的 `newLevel = min(target.level, bestFeeder)` 会让实际层 `level`
不严格递增；树模型下「level 升序 = 上游先」的假设会失效。

**力场模型下不成立**：方向不再依赖「上游先」的遍历序，而是四邻差矢量和：

```
fx = Σ (邻居 level − 本格 level) × 方向
```

每个邻居的贡献都是「远离更高水位、趋向更低水位」，线性叠加，对非单调是**稳健的**。
唯一的「异常」是**局部极值**（四邻都更小）⇒ 分量互相抵消 ⇒ `flow = 0` ⇒ 停 ——
这与原版「四周水位都更高，推力抵消」一致，是正确行为。

⇒ 本条关闭，不需要真机验证。

---

### B3 同拍上游被下游占位挡住时白等一拍（✅ 关闭，2026-10-31）

**原现状**：`sorted` 升序 + 不重试。上游先试、下游还占着 ⇒ 上游不动；下游被推走后不回头重试。

**力场模型下前提消失**：不再按「父 → 子」遍历，而是按 level 升序**独立处理每一格**
（`moved` 保证每物品每拍最多一格）。上游被挡时下游同拍也在被处理，不存在「等下游让位」的队列。
⇒ 本条关闭。

---

### B4 多源鞍部：物品停在水流相遇点

**2026-10-31 力场模型**：鞍部两侧的差分量**互相抵消** ⇒ `flow = 0` ⇒ 物品停住
（与「无下游」等效，但依据从「树」变成「力场」；原版也是两侧推力抵消）。

**边界**：瞬时流体（`flowSpeed = 0`）**不存在鞍部** —— `perCellCost = 0` ⇒ 所有格
`arrival` 相同 ⇒ BFS 退化成 slot 升序 ⇒ 左边的源吞掉右半边（实测见 tech §3.3.1）。

---

### B5 源格上的物品永不推动（✅ 已定案：保持，2026-10-31）

**现状**：`pushFluidItems` 开头 `if (fe.isSource) continue;`（§3.3 文档明写「源格只接受显式投放」）。
物品若被玩家直接丢进源格：
- 转化表命中 ⇒ 当拍转化（机制三）；
- 转化表无条目 ⇒ **停住**，水把它冲不走。

**2026-10-31 用户拍板：保持**。源格是「转化台」语义，**优先于推力**——
不为了「水里都该被推」的一致性去削掉机制三的浸泡玩法。
未命中转化的物品停在源格是接受的代价，不再作为缺陷处理。

### B6 每 5t 一格 + GUI 瞬移的观感

**现状**：水推动 = 该流体推进拍（水 5t / 岩浆 30t）**每拍移动一格**，GUI 里是跳格。
`setItem` 清源 + 写目标 ⇒ 客户端看到的是瞬移，没有中间帧。

**待验证**：真机观感是否可接受（用户此前未单独反馈速度问题，本次只报了分叉随机）。

### B7 直角弯一个弯都过不去（✅ 已修，2026-10-31 真机）

**现象**：用活物品摆弯道，物品在弯口停住，一个弯都过不去。
**根因**：力场只取了主分量，主分量正好撞在活物品上 ⇒ 直接停。
而原版的力是**两个分量同时作用**，碰撞只挡一个轴、另一个轴照常位移 ⇒ 物品会「斜着擦过障碍、
挪回直道」。
**修**：主分量不可用时试次分量（`FluidFlowVector#candidates` 返回最多 2 个）；两个都不可用才停。
**测试**：53（直角弯兜底）。

---

### B8 水车力矩不判流体类型（✅ 结案：不是缺陷，2026-10-31）

**曾被误判为缺陷**：`ContainerStressData` 读任意流体的 `FlowEntry`，我一度改成「只认 `Fluids.WATER`」。
**用户口径**：Create 的水车本来就可以由岩浆驱动 ⇒ **不按流体类型过滤才是对的**，过滤已撤回。
**保留的部分**：力矩算法抽成纯函数 `wheelTorque`（`ContainerStressDataTest` 四项覆盖：
直流水无力矩 / 侧向 CCW / 堆叠放大 / 无水为 0），不再受「测试环境无 Create」的限制；
每个邻居按**它自己的流体**建力场表，水与岩浆同容器时互不污染。

---

### F1 物品停在水流末端（✅ 已修，2026-10-31 力场模型）

**原行为**：物品被推到水流末端（没有下游水格）就停住，永远停在水的边缘。
**用户口径**：「物品在水流里相当于受到一股推力，推出水流才对，和原版对齐」。

**现行为**：**没有「末端」分支** —— 物品沿力场走一格，目标可以是水格、也可以是无水格；
目标无水即离开水流（之后不在 `flows` 里，自然失去推力）。

**落点**：tech §3.3 / §3.3.1；测试 ㊽（推出）/ ㊾（挡）/ ㊿（越界）/ 51（力场函数）/ 52（鞍部）。
**顺带回答了「推动的目的是什么」**：目的地 = **离开水流的那一格**（岸边）。

## C. 与其它子系统的交互

### C1 推动不参与 `TickContext` 互斥：漏斗刚放入同拍被冲走

**现状**：容器 tick 顺序 = **功能 tick 先**（漏斗/熔炉）→ **容器级数据后**（流体 prio 0）。
流体推动完全绕开 `TickContext.occupiedSlots` / `transferredTargetSlots`。

**后果**：漏斗本拍放进某槽的物品，**同一 tick 就被水推走**。玩家看到的是「物品刚进箱子就被冲走」，
且漏斗本拍的其它判断基于旧位置。

**2026-10-31 现状核实**：
- `transferredTargetSlots` 由漏斗 `markTransferred()` 写入，**唯一消费者是漏斗自己**
  （`TransferPipeline` 跳过「本 tick 已被写入过」的来源槽，防 A→B→C 同 tick 级联）——
  它不是通用槽保护；
- `TickContext.occupiedSlots` 全项目**零引用**（死字段）。

**已定方案（暂不实施，记 [TODO.md](../TODO.md) 活流体第 10 条）**：
`ContainerFluidData.tick` 增加 `Set<Integer> frozenSlots`，`LivingFluidFunction` 传
`tick.transferredTargetSlots`；`pushFluidItems` 循环跳过这些槽。
已知边界：该集合是「本 tick 被写入过」⇒ 漏斗**连续供料**的槽会永远被跳过（物品堆着不动）；
若要「只保护第一拍」需按槽记录上次写入 tick。

### C2 推动排在焚毁/转化之前 ⇒ 物品抢跑逃过反应（✅ 已修，2026-10-30）

**问题**：末端推出落地时暴露的顺序缺陷 —— `pushItems` 原先排在
`transformSourceItems` / `reactFrontiers` / `incinerateFlowItems` **之前** ⇒ 物品在熔岩末端
先被推出水流，焚毁 / 满组石头生源 / 防火存活三条语义**全部被绕过**（实测 3 项既有测试同时红）。

**修**：`pushItems` 移到反应类之后；契约写进 tech §3.6「反应类先于推动」。
副作用是好的：推动读到的是「反应后的水流」（焚毁生源格变源 ⇒ 自然不被推）。
