## 1. 调研结论（已核实，非探讨）

### 1.1 原版酿造台机制

| 项 | 值 | 出处 |
|---|---|---|
| 槽位 | 5 个：0/1/2 = 瓶子，3 = 材料，4 = 燃料 | `BrewingStandBlockEntity` |
| 燃料 | 烈焰粉，1 个 = **20 次**（`FUEL_USES = 20`） | 同上 |
| 酿造时间 | **400 tick**（20 秒） | 同上 |
| 一次酿造 | **同时转化最多 3 个瓶子**，消耗 1 份材料 | 同上 |
| 材料残留 | 有 crafting remainder 语义 | 同上 |
| 可酿造判定 | 材料槽非空 + 是有效材料 + 3 瓶中至少 1 个 `hasMix` | 同上 |
| 状态机 | **离散批次**（非连续进度）：`brewTime` 倒计时，材料失效即中止 | 同上 |

### 1.2 配方系统 = 三张内置表 + 一张模组注册表

`PotionBrewing` 聚合 4 个来源：

| 来源 | 类型 | 内容 | 例 |
|---|---|---|---|
| `containers` | `List<Ingredient>` | 可作为「输入瓶」的物品 | 药水 / 喷溅 / 滞留药水 |
| `potionMixes` | `Mix<Potion>` | 药水效果转化 | 粗制 + 金胡萝卜 → 夜视 |
| `containerMixes` | `Mix<Item>` | 容器形态转化 | 药水 + 火药 → 喷溅；喷溅 + 龙息 → 滞留 |
| NeoForge `registry` | `List<IBrewingRecipe>` | **模组注册的自定义配方** | Create / 农夫乐事等 |

原版配方（`addVanillaMixes`）四类：

- **基础**：水瓶 + 地狱疣 → 粗制；+ 萤石粉 → 浓稠；+ 红石 → 浑浊
- **效果**：粗制 / 水 + 材料 → 效果药水（夜视 / 抗火 / 跳跃 / 迅捷 / 治疗 / 再生 / 力量 / 中毒 / 水下呼吸 / 缓降…）
- **修饰**：+ 红石 = 延长；+ 萤石粉 = 强化；+ 发酵蜘蛛眼 = 腐化 / 反转
- **形态**：+ 火药 = 喷溅；+ 龙息 = 滞留

### 1.3 ⭐ 模组兼容 = 零工作量

`level.potionBrewing()` 返回的实例**已在 bootstrap 聚合所有来源**
（原版三表 + `RegisterBrewingRecipesEvent` 注册的全部模组配方）。

⇒ 活酿造台**只调这一个入口**，自动兼容所有模组的药水配方，**不需要任何兼容代码**。
（同族先例：活熔炉共用 `RecipeType.SMELTING`。）

### 1.4 官方接口

| 接口 | 用途 | 我们要不要 |
|---|---|---|
| `PotionBrewing`（`level.potionBrewing()`） | 查询：`isIngredient` / `isInput` / `hasMix` / `mix` | ✅ **唯一入口** |
| `IBrewingRecipe` | 模组自定义配方 | ❌ 我们是消费者，不是注册者 |
| `RegisterBrewingRecipesEvent` | 模组注册配方的事件 | ❌ 同上 |
| `BrewingRecipe` | 简单配方实现 | ❌ 同上 |

⚠️ **调用约定易错**（原版自己注释了「参数顺序反直觉」）：

- `hasMix(potionStack, ingredientStack)` —— 瓶子在前、材料在后
- `mix(ingredientStack, potionStack)` —— 材料在前、瓶子在后
- `ClientLevel` / `ServerLevel` **两端都能拿到**酿造表。

### 1.5 框架能提供的便利

| 框架能力 | 对活酿造台 |
|---|---|
| `LivingItemFunction` | 直接实现 `canApply`（`Items.BREWING_STAND` + 活标记）+ `tick` |
| `HasDirection` | **5 槽位方向** —— `DirectionSlotsData` 用 `Map<String, Pos2D>`，天然支持任意槽位数（熔炉只是用了 3 个） |
| 运行时缓存（`RuntimeSegmentRegistry`） | 瞬态数据**不写物品组件**，不影响堆叠 |
| 活化钩子 / 活物品隔离 / `SlotAccessor` | 直接复用 |
| 图标 | **D5 决定不做**（原版图标 + 默认活标记，零文件） |

**不需要**：`HasContainerData`（无容器级计算）。

### 1.6 ⭐ 原版批次的精确时序（读源码核实，2026-10-11）

> 出处：`BrewingStandBlockEntity`（`serverTick` / `isBrewable` / `doBrew`）。
> ⚠️ **燃料与材料在批次的两个端点扣，不是同一时刻** —— 这是最容易混的地方。

| 动作 | 时机 | 代码位置 |
|---|---|---|
| **补燃料**：`fuel = 20` + 吃掉 1 个烈焰粉 | `fuel <= 0` 且燃料槽是烈焰粉时**随时**（**与是否在酿造无关**） | `serverTick` 开头 |
| **扣 1 次燃料**：`fuel--` | **批次启动那一刻**（`brewTime` 由 0 → 400） | `else if (flag && fuel > 0)` |
| **扣 1 份材料**：`shrink(1)` | **批次完成那一刻**（`doBrew` 内）—— 转化 1 瓶还是 3 瓶都只扣 1 | `doBrew` |

**作废条件**（原版就一行：`else if (!flag || !itemstack1.is(ingredient)) brewTime = 0;`）：

1. **不可酿造**（`!flag` = `!isBrewable`）：材料槽空 / 材料不是有效材料 /
   **3 瓶里没有任何一个 `hasMix(瓶, 材料)`**
2. **材料的「物品类型」变了** —— ⚠️ 只比 `Item`，**不比数量 / 内容**：
   - 1 个地狱疣 → 2 个地狱疣 = **不算换**（继续酿造）
   - 地狱疣 → 萤石粉 = **算换** ⇒ 整批作废（**燃料不退、材料不扣**）
   - 3 瓶被全部拿走 ⇒ 命中第 1 条 ⇒ 同样作废

**其他要点**：

- `fuel` 是 **`BlockEntity` 的字段**（`tag.putByte("Fuel", ...)`），**不是物品字段**。
- `fuel` **只在归零时补** ⇒ 是 0..20 的计数器，不是「每用一次补一次」。
- 材料带合成残留物时：原版 `shrink(1)` 后若槽空则放残留物、否则**掉落到方块坐标**
  （活物品没有坐标 ⇒ 见 D9）。

## 2. 玩法定义（已定案）

> ⚠️ 本节是**功能需求的来源**与**行为对错的判据**。定案后迁 `docs/tech/living-brewing-stand-tech.md` §0。

**语义**：**活酿造台 = 容器内的虚拟酿造台** —— 把原版酿造台的功能虚拟化进容器槽位
（3 个瓶子槽 + 1 个材料槽 + 1 个燃料槽）。

**获取**：原版酿造台 + 活化。

**核心循环**：`瓶子 ×3 + 材料 + 燃料` →（400 tick 批次）→ **3 瓶原地转化 + 材料 −1**。

**规则**（违反即 bug）：

| # | 规则 | 来源 |
|---|---|---|
| 1 | **五槽语义**：3 瓶 + 材料 + 燃料，各司其职，方向可配 | D1 |
| 2 | **燃料对齐原版**：烈焰粉 = 20 次；燃料值**落盘** | D2 |
| 3 | **堆叠只加速酿造过程**：`step = count`（每 tick 推进 `count` tick）；**每批仍只扣 1 燃料 + 1 材料** | D3 · D11 |
| 4 | **中途换材料 = 整批作废**（`brewTime` 归零；燃料不退、材料不扣） | D4 · D8 |
| 5 | **不做自定义图标**（原版图标 + 默认活标记） | D5 |
| 6 | **活漏斗走「普通槽位」模型**（槽位即周围容器槽位） | D6 |
| 7 | 活物品**不作材料 / 燃料**（隔离规则，与熔炉同族） | 框架 |
| 8 | **消耗时机对齐原版**：燃料在**批次启动**扣 1 次、材料在**批次完成**扣 1 份 | D7 |
| 9 | **作废条件对齐原版**：不可酿造 / 材料的**物品类型**变化（数量变不算） | D8 |
| 10 | **材料的合成残留物放回材料槽**（照活熔炉先例，不掉落） | D9 |
| 11 | **搬运丢进度、留燃料**（进度在运行时缓存 ⇒ 清零；燃料落盘 ⇒ 保留） | D10 |

**能力清单**（规划）：酿造（配方查询）· 燃料（次数制）· 批次进度 · 3 瓶并行转化 · 堆叠加速 · 方向可配

| D10 | 酿造中搬运 | **丢进度、留燃料**（进度在运行时缓存 ⇒ 清零；燃料落盘 ⇒ 保留）—— 用户确认合理 | 2026-10-11 |
| D11 | 堆叠加速公式 | **`step = count`**（每 tick 推进 `count` tick）+ **成本每批固定** | 2026-10-11 |

### 3.1 关键决策的理由留档

**D2 · 为什么燃料能落盘、熔炉的不能**：
熔炉燃料是**时间型**（`burnTime` 每 tick −1）⇒ 落盘会每秒写 20 次 + 破坏堆叠 ⇒ 只能走运行时缓存；
酿造台燃料是**次数型**（每次酿造才 −1，400 tick 一次）⇒ 变化频率极低 ⇒ 落盘可行。
⚠️ **不能照抄熔炉的燃料方案。**

**D2 · 代价**：燃料值进组件 ⇒ **不同燃料值的两个堆叠不能互相合并**（未使用过的 `fuel=0` 仍可堆叠）。
⚠️ 但**不影响单个堆叠内部**（堆叠内共享同一份组件）⇒「堆叠加速」照常成立。
⚠️ **不可**把燃料值放进 `getIgnoredComponentTypes()`（那是**派生数据**才能忽略的；燃料是真实数据，忽略会静默丢数据）。

**D3 · 为什么「燃料消耗不变」对次数型是必要的**：
若照抄熔炉的「倍耗」（燃料 ×count），20 次燃料在堆叠 20 时**一次酿造就烧掉 20 次** ⇒ 语义崩坏。

**D5 · 连带效果**：取消「酿造中」轻量标志组件（它只为图标谓词服务，图标不做了就没有消费者）。
代价：图标上看不出「正在酿造」（原版靠气泡粒子，物品图标没有）⇒ 只能靠 tooltip。

**设计原则（本轮沉淀）**：**不替玩家做决定 —— 实现简单不是砍掉玩家选择的理由**。
反面教材：曾以「堆叠与燃料落盘有矛盾」为由建议「不做堆叠加速」，既误判技术、也越界替玩家做了决定。

**D2 补充（2026-10-11）· 拆堆会复制燃料 ⇒ 当特性保留**：
已核实 `ItemStack.split` → `copyWithCount` → `copy()` ⇒ **组件被复制**（`DataComponentMap` 是不可变共享）
⇒ `fuel=20` 的一叠拆出 1 个，两个都是 `fuel=20` ⇒ **凭空多 20 次**。
框架**没有拆堆钩子**（活箱子是靠「`count > 1` 时不工作」回避的，但 D3 要堆叠加速 ⇒ 不能这么回避）。
**用户拍板：当特性保留**（原话「如果有玩家乐意不停的堆叠拆分，那他值得这份所谓的奖赏」）。
📌 若日后要修：需新增框架级拆堆钩子（按比例分摊燃料），成本高、且「按比例」语义模糊。

**D3 / D11 · 堆叠语义 = 「N 台并行酿造台」，成本映射只能是「每批固定」**：

- ⚠️ 已核实熔炉的堆叠**不是**「单位成本不变」，而是**亏本加速**：速度 `1+count/8`、燃料**每 tick ×count**
  ⇒ 每单位产出的燃料成本 = `count/(1+count/8)`（count=2 → 2.0×、8 → 4.0×、64 → 7.1×）。
  ⇒ **熔炉是「用燃料换时间」**；「照抄熔炉」只能照抄**曲线**，成本映射必须另定。
- 本设计选 **`step = count`**（唯一「过原点、斜率 1」的线性，无任何缩放系数）：

  | count | 1 | 2 | 8 | 16 | 32 | 64 |
  |---|---|---|---|---|---|---|
  | 每批 | 400t | 200t | 50t | 25t | 13t | **7t** |

  - ✅ 单个 = 原版 400t；✅ 低端平缓（2 个 = 2 倍，无「多堆 1 个快 7 倍」的跳跃）；
    ✅ **公式就是 `count`** ⇒ **不需要 `maxStack`、不需要除零保护、不需要封顶**
    （每 tick 只检查一次「是否完成」⇒ **速度天然封在 ≈1 批/tick**，超大堆叠也不失控）。
  - ⚠️ 上限是 **7t（0.35s）而非 1t** —— 且这是**好事**：1t/批 = 20 批/秒 = 1200 材料/分、
    一颗烈焰粉只够 1 秒（失控）；7t/批 ≈ 171 材料/分（≈514 瓶/分），屏幕上已是「瞬间」。
- **成本映射必须「每批固定」—— 这是定义，不是取舍**：只有它能维持「N 堆叠 ≡ N 台独立机器」：

  | 400 tick 内 | N 台独立 | **N 堆叠 + 每批固定** | N 堆叠 + ×count |
  |---|---|---|---|
  | 材料 / 燃料 | N / N | **N / N** ✓ | **N² / N²** ✗ |
  | 产出药水 | 3N | **3N** ✓ | 3N |
  | 每瓶的材料成本 | 1/3 | **1/3** ✓ | **N/3** ✗ |

  ⇒ 「×count」会让成本变成 **N²**（堆 64 个 → 400t 内消耗 4096 份材料）⇒ 荒诞。
  ⇒ 由此得出清晰的设计意图：**堆叠的唯一收益 = 槽位压缩**（1 个槽位 = N 台机器的产能）；
  玩家**不堆叠、分开摆效果完全相同**（只多占槽位 + 多配 N−1 次方向）⇒ **中性设计**（不惩罚也不奖励），
  与上面那条「不替玩家做决定」的设计原则一脉相承。

**D7~D10 · 一律对齐原版**（精确时序见 §1.6）—— 用户原则：**能对齐的就对齐，实在无法对齐的再讨论**。
唯一**无法对齐**的是 **D9（残留物）**：原版靠 `Containers.dropItemStack(level, 方块坐标…)` 掉落，
而活物品**没有坐标** —— `SimpleContainerContext.associatedBlockPositions` 是**私有字段**（只用于生成容器 key），
`ContainerContext` 接口**没有** `getPosition()`；且**玩家背包 / 末影箱这类容器坐标为空的**
⇒ 「掉落」对背包场景**无解**。⇒ 改照**本框架既有先例**：活熔炉 `consumeFuel` 把残留物**放回槽位**。
⚠️ 影响面 ≈ 0：原版全部酿造材料（地狱疣 / 萤石粉 / 红石 / 火药 / 龙息 / 发酵蜘蛛眼 / 糖 / 兔子脚 /
闪烁的西瓜 / 河豚 / 岩浆膏 / 金胡萝卜 / 海龟壳…）**都不带合成残留物**。

## 4. 状态设计

### 4.1 槽位模型

5 个方向槽位：`bottle1` / `bottle2` / `bottle3` / `ingredient` / `fuel`。
默认布局（相对活酿造台）：

```
瓶子1(↖)   瓶子2(↑)   瓶子3(↗)
燃料(←)    活酿造台    材料(→)
```

⚠️ 该布局需要 **2 个对角方向** ⇒ 依赖框架扩展（见配套文档）。

### 4.2 数据归属

| 状态 | 归属 | 理由 |
|---|---|---|
| 5 个槽位方向 | **DataComponent（持久）** | 玩家配置，需跨容器保留 |
| ~~配方缓存~~ | **不做**（2026-10-11 修订） | 原计划放组件；但 `PotionBrewing.hasMix` 只是几次列表扫描 ⇒ 先不做缓存（缓存反而要处理失效）；若实测有性能问题再加**运行时**缓存 |
| **燃料次数 fuel** | **DataComponent（持久 + 同步）** | 次数型、变化极慢 ⇒ 可落盘（见 §3.1） |
| 酿造进度 brewTime | **运行时缓存（瞬态）** | 每 tick 变，不能影响堆叠 |
| 当前材料 ingredient | **运行时缓存（瞬态）** | 仅用于「中途换材料」检测 |
| ~~酿造中标志~~ | **不需要** | D5 不做图标 ⇒ 谓词消失 ⇒ 无消费者 |

### 4.3 状态机

```
IDLE（材料 + 瓶子就绪）
  │ 有配方 + 燃料 > 0
  ↓
BREWING（倒计时 400 → 0）
  │ 倒计时归零
  ↓
转化 3 瓶、材料 −1 → 回 IDLE
BREWING 中「不可酿造」或「材料的 Item 变了」→ 整批作废 → 回 IDLE
（精确条件与每 tick 顺序见 §4.5）
```

### 4.4 与活熔炉的语义差异（决定了不能照抄）

| | 活熔炉 | 活酿造台 |
|---|---|---|
| 进度 | 连续，可暂停 / 回退 / 余热 | **离散批次**，启动即锁定，失效即作废 |
| 燃料 | 时间型（烧 N tick），走运行时缓存 | **次数型（N 次）**，落盘 |
| 一次产出 | 1 → 1 | 1 材料 → **同时 3 瓶**，瓶子原地变 |
| 配方 | `RecipeType.SMELTING` | `PotionBrewing` |

### 4.5 批次时序与边界（实现依据）

**每 tick 的顺序**（对齐原版 `serverTick`）：

1. **补燃料**：`fuel <= 0` 且燃料槽是烈焰粉 ⇒ `fuel = 20`、吃掉 1 个烈焰粉
2. 算 `canBrew`（= `isBrewable`：材料槽非空 + `isIngredient(材料)` + **至少 1 瓶 `hasMix(瓶, 材料)`**）
3. **若 `brewTime > 0`**（酿造中）：
   - `brewTime -= step`（`step = count`，D11）
   - 若 `brewTime <= 0` 且 `canBrew` ⇒ **完成**：扣 1 份材料（D7）+ 转化最多 3 瓶
   - 否则若 `!canBrew` **或** 材料的 `Item` 变了 ⇒ `brewTime = 0`（**作废**，燃料不退、材料不扣，D8）
4. **否则**（`brewTime == 0`）：若 `canBrew` 且 `fuel > 0` ⇒ `fuel--`、`brewTime = 400`、记录本批次材料 `Item`

**两个实现细节**：

- **overshoot 结转**：原版每批有 1 tick「启动开销」（完成那 tick 只归零、下一 tick 才重启）
  ⇒ `step = 64` 时实际是 8t/批。拟在完成时把**超出的部分带到下一批**，做到「7t 就是 7t」
  （纯优化，不改任何语义、不影响作废与消耗规则）。
- **「本批次材料」的记录**：原版用 BE 字段 `ingredient` 存**材料的 `Item`**（不是 ItemStack）；
  活物品的对应物 = **运行时缓存**（与 `brewTime` 同生命周期；不进组件 ⇒ 不影响堆叠）。

## 5. 与活漏斗的交互（D6）

**基本机制（与熔炉一致，天然支持）**：活酿造台的 5 个槽位 = **周围的普通容器槽位**（方向配置指向）。
活漏斗只认「槽位」不认「酿造台」⇒ **投料 / 取货天然可用，零额外代码**。

**4 个具体问题**：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **无槽位准入** | 石头能放进「材料槽」（与熔炉一致：不工作但不报错）。要准入需框架新能力（**不做**） |
| 2 | **取货会中断酿造** | 漏斗取走瓶子槽的药水 ⇒ 批次作废（D4） |
| 3 | **空瓶干扰** | 空瓶会被一并取走 ⇒ 需漏斗自己的黑白名单过滤 |
| 4 | **跨容器** | 邻居侧只认裸 `IItemHandler`；普通槽位投料 / 取货正常 |
