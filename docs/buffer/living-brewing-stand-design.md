## 1. 调研结论（已核实，非探讨）

### 1.1 原版酿造台机制

| 项 | 值 | 出处 |
|---|---|---|
| 槽位 | 5 个：0/1/2 = 瓶子，3 = 材料，4 = 燃料 | `BrewingStandBlockEntity` |
| 燃料 | 烈焰粉，1 个 = **20 次**（`FUEL_USES = 20`） | 同上 |
| 酿造时间 | **400 tick**（20 秒） | 同上 |
| 一次酿造 | **同时转化最多 3 个瓶子**，消耗 1 份材料 | 同上 |
| 材料残留 | 有 crafting remainder 语义 | 同上 |
| 可酿造判定 | 材料槽非空 + 是有效材料 + 3 瓶中至少 1 个 `hasMix` | 同上 |
| 状态机 | **离散批次**（非连续进度）：`brewTime` 倒计时，材料失效即中止 | 同上 |

### 1.2 配方系统 = 三张内置表 + 一张模组注册表

`PotionBrewing` 聚合 4 个来源：

| 来源 | 类型 | 内容 | 例 |
|---|---|---|---|
| `containers` | `List<Ingredient>` | 可作为「输入瓶」的物品 | 药水 / 喷溅 / 滞留药水 |
| `potionMixes` | `Mix<Potion>` | 药水效果转化 | 粗制 + 金胡萝卜 → 夜视 |
| `containerMixes` | `Mix<Item>` | 容器形态转化 | 药水 + 火药 → 喷溅；喷溅 + 龙息 → 滞留 |
| NeoForge `registry` | `List<IBrewingRecipe>` | **模组注册的自定义配方** | Create / 农夫乐事等 |

原版配方（`addVanillaMixes`）四类：

- **基础**：水瓶 + 地狱疣 → 粗制；+ 萤石粉 → 浓稠；+ 红石 → 浑浊
- **效果**：粗制 / 水 + 材料 → 效果药水（夜视 / 抗火 / 跳跃 / 迅捷 / 治疗 / 再生 / 力量 / 中毒 / 水下呼吸 / 缓降…）
- **修饰**：+ 红石 = 延长；+ 萤石粉 = 强化；+ 发酵蜘蛛眼 = 腐化 / 反转
- **形态**：+ 火药 = 喷溅；+ 龙息 = 滞留

### 1.3 ⭐ 模组兼容 = 零工作量

`level.potionBrewing()` 返回的实例**已在 bootstrap 聚合所有来源**
（原版三表 + `RegisterBrewingRecipesEvent` 注册的全部模组配方）。

⇒ 活酿造台**只调这一个入口**，自动兼容所有模组的药水配方，**不需要任何兼容代码**。
（同族先例：活熔炉共用 `RecipeType.SMELTING`。）

### 1.4 官方接口

| 接口 | 用途 | 我们要不要 |
|---|---|---|
| `PotionBrewing`（`level.potionBrewing()`） | 查询：`isIngredient` / `isInput` / `hasMix` / `mix` | ✅ **唯一入口** |
| `IBrewingRecipe` | 模组自定义配方 | ❌ 我们是消费者，不是注册者 |
| `RegisterBrewingRecipesEvent` | 模组注册配方的事件 | ❌ 同上 |
| `BrewingRecipe` | 简单配方实现 | ❌ 同上 |

⚠️ **调用约定易错**（原版自己注释了「参数顺序反直觉」）：

- `hasMix(potionStack, ingredientStack)` —— 瓶子在前、材料在后
- `mix(ingredientStack, potionStack)` —— 材料在前、瓶子在后
- `ClientLevel` / `ServerLevel` **两端都能拿到**酿造表。

### 1.5 框架能提供的便利

| 框架能力 | 对活酿造台 |
|---|---|
| `LivingItemFunction` | 直接实现 `canApply`（`Items.BREWING_STAND` + 活标记）+ `tick` |
| `HasDirection` | **5 槽位方向** —— `DirectionSlotsData` 用 `Map<String, Pos2D>`，天然支持任意槽位数（熔炉只是用了 3 个） |
| 运行时缓存（`RuntimeSegmentRegistry`） | 瞬态数据**不写物品组件**，不影响堆叠 |
| 活化钩子 / 活物品隔离 / `SlotAccessor` | 直接复用 |
| 图标 | **D5 决定不做**（原版图标 + 默认活标记，零文件） |

**不需要**：`HasContainerData`（无容器级计算）。

## 2. 玩法定义（待确认）

> ⚠️ 本节是**功能需求的来源**与**行为对错的判据**。定案后迁 `docs/tech/living-brewing-stand-tech.md` §0。

**语义**：**活酿造台 = 容器内的虚拟酿造台** —— 把原版酿造台的功能虚拟化进容器槽位
（3 个瓶子槽 + 1 个材料槽 + 1 个燃料槽）。

**获取**：原版酿造台 + 活化。

**核心循环**：`瓶子 ×3 + 材料 + 燃料` →（400 tick 批次）→ **3 瓶原地转化 + 材料 −1**。

**规则**（违反即 bug）：

| # | 规则 | 来源 |
|---|---|---|
| 1 | **五槽语义**：3 瓶 + 材料 + 燃料，各司其职，方向可配 | D1 |
| 2 | **燃料对齐原版**：烈焰粉 = 20 次；燃料值**落盘** | D2 |
| 3 | **堆叠只加速酿造过程**（`brewTime` 递减加快），燃料 / 材料消耗**不变** | D3 |
| 4 | **中途换材料 = 整批作废**（`brewTime` 归零，材料不返还） | D4 |
| 5 | **不做自定义图标**（原版图标 + 默认活标记） | D5 |
| 6 | **活漏斗走「普通槽位」模型**（槽位即周围容器槽位） | D6 |
| 7 | 活物品**不作材料 / 燃料**（隔离规则，与熔炉同族） | 框架 |

**能力清单**（规划）：酿造（配方查询）· 燃料（次数制）· 批次进度 · 3 瓶并行转化 · 堆叠加速 · 方向可配

## 3. 决策池（D1~D6，全部已定）

| # | 问题 | 结论 | 日期 |
|---|---|---|---|
| D1 | 瓶子槽定义 | **固定 5 个方向槽位**（3 瓶 + 材料 + 燃料），默认布局「瓶-瓶-瓶 / 烈焰粉-台-材料」，方向可自定义 | 2026-10-10 |
| D2 | 燃料语义 | **对齐原版**（烈焰粉 = 20 次）；燃料值**写 DataComponent**（持久 + 同步） | 2026-10-10 |
| D3 | 堆叠加速 | **保留**，规则 = 只加速酿造过程，燃料 / 材料消耗不变 | 2026-10-10 |
| D4 | 中途换材料 | **同原版**（整批作废） | 2026-10-10 |
| D5 | 图标 | **不做自定义图标** —— 原版图标 + 保留活标记（零文件） | 2026-10-10 |
| D6 | 活漏斗投料 | **模型 A「普通槽位」** —— 与熔炉一致、零代码 | 2026-10-10 |

### 3.1 关键决策的理由留档

**D2 · 为什么燃料能落盘、熔炉的不能**：
熔炉燃料是**时间型**（`burnTime` 每 tick −1）⇒ 落盘会每秒写 20 次 + 破坏堆叠 ⇒ 只能走运行时缓存；
酿造台燃料是**次数型**（每次酿造才 −1，400 tick 一次）⇒ 变化频率极低 ⇒ 落盘可行。
⚠️ **不能照抄熔炉的燃料方案。**

**D2 · 代价**：燃料值进组件 ⇒ **不同燃料值的两个堆叠不能互相合并**（未使用过的 `fuel=0` 仍可堆叠）。
⚠️ 但**不影响单个堆叠内部**（堆叠内共享同一份组件）⇒「堆叠加速」照常成立。
⚠️ **不可**把燃料值放进 `getIgnoredComponentTypes()`（那是**派生数据**才能忽略的；燃料是真实数据，忽略会静默丢数据）。

**D3 · 为什么「燃料消耗不变」对次数型是必要的**：
若照抄熔炉的「倍耗」（燃料 ×count），20 次燃料在堆叠 20 时**一次酿造就烧掉 20 次** ⇒ 语义崩坏。

**D5 · 连带效果**：取消「酿造中」轻量标志组件（它只为图标谓词服务，图标不做了就没有消费者）。
代价：图标上看不出「正在酿造」（原版靠气泡粒子，物品图标没有）⇒ 只能靠 tooltip。

**设计原则（本轮沉淀）**：**不替玩家做决定 —— 实现简单不是砍掉玩家选择的理由**。
反面教材：曾以「堆叠与燃料落盘有矛盾」为由建议「不做堆叠加速」，既误判技术、也越界替玩家做了决定。

## 4. 状态设计

### 4.1 槽位模型

5 个方向槽位：`bottle1` / `bottle2` / `bottle3` / `ingredient` / `fuel`。
默认布局（相对活酿造台）：

```
瓶子1(↖)   瓶子2(↑)   瓶子3(↗)
燃料(←)    活酿造台    材料(→)
```

⚠️ 该布局需要 **2 个对角方向** ⇒ 依赖框架扩展（见配套文档）。

### 4.2 数据归属

| 状态 | 归属 | 理由 |
|---|---|---|
| 5 个槽位方向 | **DataComponent（持久）** | 玩家配置，需跨容器保留 |
| 配方缓存 | **DataComponent（持久）** | 减少每 tick 查询 |
| **燃料次数 fuel** | **DataComponent（持久 + 同步）** | 次数型、变化极慢 ⇒ 可落盘（见 §3.1） |
| 酿造进度 brewTime | **运行时缓存（瞬态）** | 每 tick 变，不能影响堆叠 |
| 当前材料 ingredient | **运行时缓存（瞬态）** | 仅用于「中途换材料」检测 |
| ~~酿造中标志~~ | **不需要** | D5 不做图标 ⇒ 谓词消失 ⇒ 无消费者 |

### 4.3 状态机

```
IDLE（材料 + 瓶子就绪）
  │ 有配方 + 燃料 > 0
  ↓
BREWING（倒计时 400 → 0）
  │ 倒计时归零
  ↓
转化 3 瓶、材料 −1 → 回 IDLE
BREWING 中材料失效 → 整批作废 → 回 IDLE
```

### 4.4 与活熔炉的语义差异（决定了不能照抄）

| | 活熔炉 | 活酿造台 |
|---|---|---|
| 进度 | 连续，可暂停 / 回退 / 余热 | **离散批次**，启动即锁定，失效即作废 |
| 燃料 | 时间型（烧 N tick），走运行时缓存 | **次数型（N 次）**，落盘 |
| 一次产出 | 1 → 1 | 1 材料 → **同时 3 瓶**，瓶子原地变 |
| 配方 | `RecipeType.SMELTING` | `PotionBrewing` |

## 5. 与活漏斗的交互（D6）

**基本机制（与熔炉一致，天然支持）**：活酿造台的 5 个槽位 = **周围的普通容器槽位**（方向配置指向）。
活漏斗只认「槽位」不认「酿造台」⇒ **投料 / 取货天然可用，零额外代码**。

**4 个具体问题**：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **无槽位准入** | 石头能放进「材料槽」（与熔炉一致：不工作但不报错）。要准入需框架新能力（**不做**） |
| 2 | **取货会中断酿造** | 漏斗取走瓶子槽的药水 ⇒ 批次作废（D4） |
| 3 | **空瓶干扰** | 空瓶会被一并取走 ⇒ 需漏斗自己的黑白名单过滤 |
| 4 | **跨容器** | 邻居侧只认裸 `IItemHandler`；普通槽位投料 / 取货正常 |
