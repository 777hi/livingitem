# 活地狱门设计稿 —— 容器级组合结构玩法

> 状态：设计探讨稿 —— 已明确的玩法与建议分列，未实现，不是代码实施授权。
> 本稿按[设计模板](../guides/living-item-design-template.md)组织。需求入口见 [TODO](../TODO.md)；现有子系统口径仍以各自 tech 文档为准。

## 1. 定位与分类

**建议名称：活地狱门。设计类别：容器级组合结构玩法。构件：活黑曜石。**

“组合结构”指多件活物品在同一容器逻辑网格中形成空间关系，经交互产生独立状态并由结构整体执行行为。活黑曜石提供边界，活打火石提供点火触发，门面属于容器；门不是某块黑曜石携带的传送属性。

能力从“单件物品携带”扩展到“活物品摆放产生”，但作用空间仍是容器、构件仍是活物品、移动构件仍会改变结构。扩展的是表达单位，不是另造世界机械系统。

不为每块黑曜石写“所属门”、框体 UUID 或点燃状态。共享边界建议允许，不必认主。一容器多扇门分别保留状态，不把容器级归属误解为只能有一扇门。

**不提前抽通用组合框架**：围闭点火型结构目前只有这个明确需求。[活潜影箱组合虚拟布局提案](活潜影箱实现细节.md)尚未定案，解决的是槽空间与库存，不是门框维护的公共契约。后续确有多个主要通过配置表达的接入方时，再讨论共同机制。

## 2. 玩法原点与已明确需求

### 2.1 已明确的核心

未列出的实现建议不得当成用户已拍板。

| 编号 | 已明确需求 |
|---|---|
| C1 | 活地狱门是活物品摆放产生的组合玩法，不是单件活黑曜石功能 |
| C2 | 用活黑曜石围出内部槽位；不限八块矩形环，四块位于中心槽上下左右也成立 |
| C3 | 光标活打火石右键内部空槽点燃，内部槽位呈现传送门门面 |
| C4 | 玩家空光标右键门面进行主世界↔下界传送 |
| C5 | 物品进入门面槽会被传送到另一侧；具体交付与失败语义见 §6/§9 |
| C6 | 门面由围住它的活黑曜石维持；状态归属参考活流体，不给框材认主 |
| C7 | 必要边界破坏后门灭，补回材料不自动复燃 |
| C8 | 自由围闭是设计本身，不硬拆成只支持小门与以后再做大门的玩法版本 |
| C9 | 门必须有可用世界位置：自身锚点直接使用；无自身锚点时，仅在活地狱门宿主配置允许且有真实外层宿主锚点时借位。无可用位置不能点火，已点燃门熄灭；不以交互玩家或 viewer 兜底 |
| C10 | 在现有宿主位置配置增加活地狱门项；玩家身上的活背包内部的门可经配置借玩家宿主位置，沿用现有宿主锚点体系 |

**位置翻转留痕**：最初无位置禁用/熄灭 → 曾改为交互玩家位置兜底 → 当前恢复无可用位置熄灭，并明确加入配置控制的真实外层宿主借位。被撤回的是随意借用操作者/viewer，不是玩家作为活背包真实宿主。原版用被传送实体位置，不是一律玩家位置。

### 2.3 原点五问

| 问题 | 本稿答案 |
|---|---|
| 作用对象 | 同一真实容器的边界、门面、点击玩家和待传物品；可用世界位置用于传送且是门存续条件，自身位置或配置允许的真实宿主借位均可 |
| 输入粒度 | 点火/点击是交互事件；结构看活黑曜石占位，不看某件 ItemStack 身份。建议同拍按维护时读到的布局，不追踪瞬时取放 |

## 3. 结构与门面建议

### 3.1 围闭检测

从点火目标对非活黑曜石位置做上下左右连通搜索：

1. 活黑曜石才是墙，普通黑曜石与其他物品不算门框。
2. 任一方向越出真实逻辑网格，视为外泄，候选失败。
3. 搜索结束且无外泄，得到被围住区域，再校验点火准入。
4. 容器外沿不是免费门框；完整黑曜石框贴边本身可以成立。

使用现有 `ContainerContext.resolveNeighbor(slot, dir, size, width)`（源码 `:265–322`）。返回 `-1` 必须判外泄；只遍历省略无效邻居的 `getNeighbors/fillNeighbors` 会误把容器边缘当墙。列数和逻辑槽走统一布局链，不跨行、不跨缺槽。

搜索量随实际访问槽数线性增长，不枚举固定门型、不假设容器最多54格。同菜单玩家背包与箱子槽不是一个真实容器，不能拼门。

### 3.2 创建与维持

```text
有效但未点燃结构 ──有可用位置并点火──→ 门面存在
门面存在 ──必要边界与可用位置仍有效──→ 保留
门面存在 ──必要边界失效或无可用位置──→ 删除门面和点燃状态
已熄灭 ──补框/恢复位置或重新开借位──→ 有效但未点燃结构
```

**确认没有可用位置时熄灭**，包括没有自身锚点且宿主借位关闭，或开启借位但真实宿主锚点不存在。门灭必须删除持久点燃状态，不能留永久点火种子；恢复位置或重新开启配置不自动复燃。仅区块卸载或GUI路径暂缺证明不是权威“失去位置”事件，见 §5。建议维护已点燃区域，只保留或清除，不自动扩大、合并或点亮新封闭区。

替换同槽另一堆活黑曜石不因身份变化灭门；建议 count 只参与“是否仍有构件”，不放大门数/吞吐。共享隔墙拆除、缩放、内插黑曜石及孔洞的失效单位见 Q4。

### 3.3 分层

门面是容器状态层，不是占槽的 `nether_portal` 假物品。门面与普通货物可在同槽存在：货物离槽不删除门，门灭不删除未发出的货物。活物品与活流体如何共存见 Q2/Q8，不照搬流体挤没、焚毁规则。

## 4. 状态、生命周期与持久化

### 4.1 现有对应物与接入

活流体源属于容器，活桶只参与倒/汲；`LivingFluidFunction.canApply()` 恒 false，通过静态自维持与 `HasContainerData` 运行。参照的是**容器状态归属与触发器解耦**，不是要求门必须用流体数据或规则。

门域建议沿相同调度接入：不匹配单件物品、自维持静态 true、容器级执行。`shouldTickWithoutOwnItems(null)` 是注册期声明，不是每拍动态位置判定。没有黑曜石也要运行以清失效门面。

持久数据走 `ContainerDataKey.savedWith`、`ContainerDataStore`、`ContainerContext.getOrCreateContainerData/persist`。建议保存各已点燃区域逻辑槽集合；合并门面图、围闭搜索结果与渲染快照是派生值。不要新增另一份容器身份/状态目录。

依据：[活流体](../tech/living-fluid-tech.md)、[数据模型](../system-design/data-model.md)、[容器基础设施](../system-design/living-item-infrastructure.md)、[D-core-07/08、D-fluid-01/02、D-container-11/12/13/20/23](../decisions.md)。

### 4.2 生命周期表

| 状态 | 归属 | 移走/取消活化 | 换槽/同拍移动 | 拆分/合并 | 卸载 | 回收/重建 |
|---|---|---|---|---|---|---|
| 构件身份 | 原有活标记 | 更新墙布局，不携门 | 按当前占位重验 | 建议不按 count 倍增 | 宿主保存 | 重读真实槽 |
| 点燃门面 | 容器持久数据 | 必要框失效或确认无可用位置时清门 | 不随单件框材移动；换外层宿主仅重验位置，区域变化见 Q4 | 不复制各门状态 | 暂停推进，保留状态，不把卸载视为无位置 | 回填后先校验位置与边界，失败清除；不凭几何复燃 |
| 传送起点 | 本次解析结果 | 不保存为门属性 | 每次读自身锚点或配置允许的真实外层宿主位置 | 不适用 | 不锁住旧位置 | 重新解析，不用“最后一次查看者” |
| 待传货物 | 原有真实槽 | 取走后不发送 | 提交前重读 | 超大堆分批，剩余在源 | 留源，不补发 | 实际库存为准 |
| 已交接掉落物 | 原版真实实体 | 原库存不再拥有 | 走实体生命周期 | 原版合并/拾取 | 原版实体保存 | 不从门账本补发 |
| 显示快照 | 客户端派生缓存 | 门灭清空包 | 不串其他槽组 | 不适用 | 可清缓存 | 首开权威快照 |

完整内容保留容器交接建议同时移交门数据，恢复后先校验可用位置与边界；目的形态确认无可用位置时删除点燃状态，随后恢复位置也不复燃。只保留物品内容的声明不是自动搬新 key：UUID/SavedData 与无 UUID 快照须接既有 `ContainerHandoff`/迁移路径，更新热数据和持久副本。不保留内容的销毁销毁门。

玩家库存的通用 `ctx.persist` 当前不覆盖 Player 附件，须参考活流体的库存身份分支。源世界物品实体已经交接成功后，不因为传送返回 null 再填回源槽。

## 5. 位置与交互

### 5.1 位置选择

解析返回完整的 **`ServerLevel + Vec3`**，点火、维护、玩家传送、自动传货共用同一判据：

1. `ctx.getAnchor()` 有自身锚点时直接用，不受借位配置控制。
2. 自身锚点为空时，仅在 `GameplayConfig.portalUsesHostAnchor()` 为 true 后读取 `ctx.getHostAnchor()`。
3. 所选真实参考物无法提供有效服务端世界与位置时，返回无可用位置；不能退化成点击者/查看者。

| 情况 | 当前设计 |
|---|---|
| 方块容器 | 用真实方块位置；建议中心点，大箱统一取点 |
| 实体容器 | 实体当前 `level()/position()`；自身位置不门控，`getBlockPos()==null` 不能判无位置 |
| 玩家自己的物品栏 | 库存主人是自身宿主，直接用其位置；不是任意玩家兜底 |
| 玩家身上的活背包内部 | 背包无自身位置；开启 `host_anchor.portal` 后用真实外层 `AtPlayer` 宿主位置 |
| 箱子/实体容器中的活背包内部 | 同一配置允许后用真实外层 `AtBlock/AtEntity`，不绑定成点火玩家位置 |
| 末影箱、无真实宿主位置的远程库存 | 不借 owner/viewer；无可用位置不能点火，已有门熄灭 |
| 自身无位置且配置关闭/宿主锚点失效 | 删除已有门面和持久点燃状态；货物保留；开配置或恢复位置不复燃 |

**配置项已预留，门玩法尚未实现**：`GameplayConfig.SPEC` 的 `[host_anchor]` 下新增 `portal = false`，getter 为 `portalUsesHostAnchor()`，与现有项同走 SERVER 加载/重载事件刷新与 volatile 缓存。默认关闭遵循现有借位项惯例；开启是加强玩法，不控制本来就有自身位置的方块/实体门。不另建JSON或借用TNT配置。

现有注册未指定独立文件名，由 NeoForge SERVER 配置机制落在存档 serverconfig 下。配置声明与默认值守卫已补，实际点火/清门消费者与GUI位置接入仍待实施；仅修改配置不代表门可用。

沿 `ContainerAnchor.AtBlock/AtPlayer/AtEntity` 和既有两层宿主语义取点，门面仍按活背包自身UUID保存；真实世界与位置须成对，不把玩家世界与别处容器坐标拼接。已有 [D-container-15/16/19/25](../decisions.md) 的自身/借位职责不变。

**GUI/tick 必须一致**：活背包 tick 已传入真实外层 `getAnchor()` 与 hostSlot；当前 `ItemFormContainers.handleOf` 返回的菜单 Handle 只有 handler/UUID/columns，GUI重建 ctx 的 hostAnchor=null。这是信息缺口，不一定证明背包真的无位置。实现必须在现有来源/解析接缝核实真实宿主；拿不到证明就拒绝本次交互，但不能仅凭这份临时ctx清掉另一权威ctx里的门，更不能用viewer补位。权威维护确认无位置或配置禁用时才按C9熄灭。

### 5.2 准入与操作

| 对象 | 允许/建议 | 拒绝/待定 |
|---|---|---|
| 点火 | 活打火石右键真实内部空槽，且有自身位置或配置允许的真实宿主借位 | 普通打火石、无效/幽灵/结果槽、无可用位置；全内部空要求见 Q2 |
| 门框 | 活黑曜石占位 | 普通黑曜石和其他物品不作框 |
| 玩家 | 空光标右键有效门面 | 无效菜单、门灭、官方权限/冷却拒绝；货物非空时入口见 §8 |
| 普通货物 | 本体和组件不变，按确认量实体化 | 无写入/抽取权限不发送，不能靠副本修改报成功 |
| 活物品货物 | 暂不设自动隔离例外 | 具体阻挡/手动搬设备玩法见 Q2 |

服务端顺序：解析真实目标和逻辑槽 → 用自身/配置借位的统一规则校验位置 → 重验结构/交互 → 执行。无可用位置不点火、不扣耐久；权威维护发现无可用位置时清门，但不清原槽货物。自动tick不需要查看者参与寻址。

成功点火损耗建议沿现有活打火石原版损坏管线；失败不扣，重复点亮不重建不扣。已经取消原版点击而服务端拒绝时，只同步真实状态，不补演原版放置。

## 6. 货物：参考原版，分清库存交接与实体过门

### 6.1 原版能复用的范围

原版不存在任意 `ContainerContext` 槽位“一步传到另一维度并原子恢复”的接口。它分别提供库存取出/掉落与实体门户处理：

- `Inventory.removeItem` 返回实际取出栈；普通掉落不替第三方 `ContainerContext` 校验写回。
- `Containers.dropContents/dropItemStack` 拆分物品并生成实体，通常不检查 `addFreshEntity` 的 bool。
- `Player.drop`、`Entity.spawnAtLocation` 有各自的玩家/实体位置、捕获掉落及事件语义，不是任意库存的成功确认协议。
- **真实 ItemEntity 已存在后**，原版负责等待、冷却、目的地计算、找/建世界门、跨维度事件、传送和合并。

本机查证入口在 `libs/src/neoforge-21.1.219-merged/net/minecraft/world/` 下的 `entity/player/Inventory.java`、`entity/player/Player.java`、`level/Containers.java` 与 `entity/Entity.java`；实际版本以 [gradle.properties](../../gradle.properties) 为准。参考算法不等于照抄其忽略出生失败的写法。

### 6.2 推荐：真实源掉落物，再交给原版门户

这是**待确认的实现/失败语义建议**，替代此前目标直接出生作为唯一推荐：

```text
门面槽真实货物
→ 独立快照与 STANDARD 抽取校验
→ 现有 consume 确认扣量
→ 在所选来源位置注册真实 ItemEntity
→ 登记原版地狱门接触
→ 后续正常实体 tick 走原版门户处理
```

源出生使用 `new ItemEntity(sourceLevel, origin.x, origin.y, origin.z, confirmedPayload)` 与 `sourceLevel.addFreshEntity(entity)`；载荷必须来自独立操作前快照、count 等于实际确认扣量，不能只复制 Item 丢组件。

确认注册后使用稳定的原版门户实例：

```java
itemEntity.setAsInsidePortal(
    (Portal) Blocks.NETHER_PORTAL,
    BlockPos.containing(origin)
);
```

这是“门面中货物进入门户”的容器映射，不在源世界放置假传送门方块，也不新建自定义 Portal。原版目的地计算使用实体真实位置；出生点已选好，因此货物无需另写容器坐标换算器。不存在源世界门方块时，原版采用默认源轴/中心偏移；碰巧来源方块带水平轴时仍走原版读取行为，不宣称虚拟门几何已映射成世界矩形。

非玩家等待阈值为 0，源码已核实 `ItemEntity.tick` 先 `super.tick` → `Entity.baseTick/handlePortal` → `PortalProcessor` 先读取 inside 再清除标志并比较阈值。新鲜非空实体、无门户冷却、允许过门且物品更新 hook 未截断时，一次标记在下一实际实体 tick 即触发首次原版尝试。依据 `ItemEntity.java:131–136`、`Entity.java:430–448`、`PortalProcessor.java:15–28`。不额外等待，不把一次标记称为永久接触；首次尝试无需真实世界门再次重标记，也不新增隐形无限重试管理器。

**失败语义建议**：

1. 实体出生未成功、货物尚未交付时，做受限源恢复。
2. 真实源实体已成功接管后，库存交接完成。目标不存在、权限拒绝、旅行事件取消等正常原版失败通常留掉落物在源世界，**不再填回库存**。
3. 这意味着失败货物可能出现在容器自身或配置允许的真实宿主旁，而不是永远留门面槽。用户若要求任何发送失败都留库存，就不能假称完整原版实体链天然满足，需另选目标直接出生方案。
4. 原版目标注册使用 void 的 `addDuringTeleport`，`changeDimension` 非 null 不证明加入成功；源删除后目标注册被取消仍有损失风险。保留原版事件链不等于原版提供跨世界原子保证，该边界必须验收，不能报已解决。

### 6.3 源交接恢复：现有入口优先，不先建凭据框架

**更正此前判断**：`consume` 虽只返回 int，但已有公开静态 `ContainerContext.rollbackSlot(ctx, slot, expected, why)`（`:361–369`），并非项目完全没有恢复入口。对同一服务端调用内的受限交接，不必先新增 consume receipt 类型。

建议：保存独立 `before` → `consume` → 按确认数量生成独立 `expectedAfter` 并回读 → 尝试源实体注册。明确拒绝且确认实体未交付、源仍属于同一容器/槽并严格匹配 `expectedAfter` 时，调用既有 `rollbackSlot`，传 `before.copy()`，再用未暴露的 before 回读校验并同步。

**不能**：源已注册/已被事件交付时回填；源槽已变时覆盖；只因 `changeDimension` 返回 null 或掉落物被合并移除就恢复；先生成货物再赌源扣成功。

现有 consume 的旧活引用与 rollback 的参数污染仍需独立快照守卫。若测试证明确有缺陷，在现有方法内最小修正，不预建持久事务、单槽 receipt、新数量原语或通用跨世界框架。异常事件已复制/交付货物、后端拒写恢复失败不能普遍补偿，沿契约留痕，不冒充原子性。

### 6.4 数量与权限

| 项目 | 选型 |
|---|---|
| 门面创建/清除 | 只改容器数据，不生成假门物品，不扣框材 |
| 货物扣除 | 现有数量原语，独立快照与实际回读；禁止裸 setItem 清槽 |
| 模拟 | 不写库存、不生成实体、不建世界门、不进入实体 tick/维度生命周期 |
| 权限 | 默认 STANDARD，查抽取；不照抄流体 PHYSICAL 特例 |
| 超大堆 | 建议每实体载荷不超过 `min(99, stack.getMaxStackSize(), 当拍预算, 实际量)`，剩余留源，不强截整源为64 |
| 倍率/速率 | 框块数量不凭空增加门数/产量；每拍批数与面积吞吐见 Q6/Q7 |

当前 ItemStack NBT CODEC count 为1～99，而网络 STREAM_CODEC 的 VarInt 不设同一上限；ItemEntity 保存与跨维度 NBT 复制必须考虑前者。依据官方 `ItemStack.java:103–114/131–171`、`ItemEntity.java:332–334`。实体化分批是载荷边界，不是新增等待窗口。

SlotAccessor 工厂可能展开活箱子内容，不能误把“门面槽货物本体”变成内部库存。现有回滚/原语的选择见[槽位操作](../guides/slot-ops.md)与[API 契约](../system-design/api-contract.md)。

## 7. 玩家传送与原版对齐

### 7.1 推荐入口

玩家交互时解析自身锚点或配置允许的真实宿主锚点，不采用点击者兜底，不先移动玩家到箱子旁。公开 API 足够：维度比例 → 目标 WorldBorder 裁剪 → PortalForcer 搜/建世界门 → BlockUtil 目标门矩形 → 原版出口组合公式与 PortalShape 避碰 → DimensionTransition → 真实玩家 changeDimension。

玩家身上的活背包在配置允许时采用真实玩家宿主位置，与原版实体位置输入可一致；这是已证明的宿主借位，不是未知容器兜底。是否委托原版目的地方法或统一适配，由实现保持同一位置与出口语义；无可用位置不执行传送。

官方入口：`DimensionType.getTeleportationScale`、`WorldBorder.clampToBounds`、`PortalForcer.findClosestPortalPosition/createPortal`、`BlockUtil.getLargestRectangleAround`、`PortalShape.findCollisionFreePosition`。无需 Invoker/反射；虚拟源轴/偏移建议固定默认，不把 GUI 凹形当世界矩形。源/目标轴的速度/yaw 旋转沿原版出口公式。

回调参考原版声音与 `Entity.placePortalTicket`，不一律 DO_NOTHING；玩家官方可取消维度事件只由实际 changeDimension 派发一次。GUI 点击等待/冷却、坐骑仍见 Q9/Q10。目的地预计算可能建世界门，玩家最终事件取消不会自动撤销所建世界门。

### 7.2 对齐清单

| 原版行为/判据 | 本玩法处置 |
|---|---|
| 世界矩形 `PortalShape` | GUI 四邻自由封闭，有意偏离 |
| 框破坏灭门 | 门面删除、补框不复燃；区域失效单位待定 |
| 实体当前位置换算 | 门的自身位置或配置允许的真实宿主位置决定起点；真实货物出生位置确定后原版使用其位置，不借交互者 |
| 无自身位置的物品形态 | 容器映射：经 `host_anchor.portal` 允许借真实宿主；无可用位置门灭、开配置不复燃 |
| `NetherPortalBlock.getPortalTransitionTime` | 玩家按 invulnerable 与 gamerule，默认阈值80/1；非玩家0。GUI 玩家点击映射另定 |
| `PortalProcessor` 的后置递增比较 | 不把阈值机械当精确秒数；一次登记不是永久接触 |
| `Entity/Player.getDimensionChangingDelay` | 普通实体默认300t、玩家10t；冷却期间接触可刷新 |
| `Entity.handlePortal` | 原版检查目的地启用、权限与冷却；直接 changeDimension 不包办前置步骤 |
| `NetherPortalBlock.getPortalDestination` | 下界去主世界，其他去下界；比例为 sourceScale/targetScale；目标门搜索/创建沿官方 |
| `DimensionTransition.DO_NOTHING` | 仅空的完成回调，不是关闭找门 |
| 普通火点门 `BaseFireBlock.inPortalDimension` | 正常主世界/下界点火；末地/模组维度不从目的地方法反推能点门 |
| 世界门 POI | 不自动识别容器门，使用世界出口不等于建立容器门返回配对 |
| 原版掉落与实体过门的 best-effort | 复用实体链，但不复制忽略源出生失败的写法，不宣称原子交易 |

查证源码以 §6 同版本目录为根，入口定位：`NetherPortalBlock.java:113–225`、`PortalProcessor.java:27`、`Entity.java:2257–2296/2719–2764`、`Player.java:468`、`DimensionTransition.java:19`、`BaseFireBlock.java:162`。

## 8. GUI、反馈与保存接缝

### 8.1 交互和显示

沿 `GuiInteractionHelper.tryInteract` → `GuiInteractionPacket` → `InteractionRegistry.registerHandler`；空槽/门面匹配参考活桶既有专门分支，不重建通用规则系统，不拦全部普通右键。

服务端重验菜单、真实槽/逻辑映射、光标和门面。当前 packet 直查与回退的双槽号/同号歧义需守卫，不能用物品内容相同证明槽身份。若允许空光标点有普通货物的门面，当前 `isValidTarget` 只放空/活物品，需要门 action 专用放行，不能无条件放宽所有动作。

| 反馈 | 权威/精度 | 建议通道与覆盖 |
|---|---|---|
| 门面有无/范围 | 决定受理，服务端权威 | 容器快照；客户端渲染/命中同源，多viewer与首开一致 |
| 紫色动画 | 装饰、本地自演 | Foreground事件，原版 atlas `minecraft:block/nether_portal` sprite |
| 点火/使用提示 | 操作指引 | 当前光标提示与服务端失败反馈；不拿画面授权 |
| 音效/粒子 | 成功反馈 | 当前选定起点/操作者与官方资源，不伪造真实容器位置 |

绘制参考 `ContainerFluidOverlay` 的位姿重置与Z抬升，按实际 GUI 槽坐标画二维门面，不必3D renderSingleBlock。透明度/纹理拼接/物品数量可辨性需实机。快照按真实库存分组，不机械复制流体最近三份缓存就宣称支持所有混合菜单。

### 8.2 状态维护顺序

恢复已点燃数据 → 校验自身/配置借位的可用位置与必要边界 → 无位置或框失效时删点燃状态 → 更新持久值 → 发送门面/空快照 → 只对有效门面处理货物。无位置清门，货物仍保留原槽。

门面真正变空时 `persist(KEY, EMPTY)` 后仅移除门 key，不调用整容器 removeDataByKey 波及水/电力。无Level时也要借已有viewer/菜单身份清图，不能为了发包伪造世界位置。完整交接与Player附件需要领域接入，共同 key 不自动兜全部保存；重进后先回填再校验，不因只peek到空热表漏清门。
