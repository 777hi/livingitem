# 活魂符换位玩法设计

> **状态**：设计稿（已拍板未实施）—— 活魂符"换位"动词与食物语义翻转，不是现状；实施前别当 §0 读。
>
> **定案来源**：2026-11-11~12 与用户讨论。用户否决"手持食物光标吸引"（复杂度高玩法薄）与"推挤"
> （三格关系复杂、布局系统性漂移），选定"**交换位置**"作为活魂符在"走 / 吃"之后的第三个动词。
> 用户已确认：① 食物语义从"站着吃不移动"翻转为"吃一份并换位进入"；② 换位是活魂符的功能逻辑，
> 在所有允许它运行的容器统一执行，**不按容器类型设开关**；③ 换位与吃+换位均按成功 `I−1`（未获异议）。
>
> 实施与验收判据以本文 + [living-maid-tech.md](../tech/living-maid-tech.md)（落地后）为准。

## 零、玩法原点

| 问题 | 定案 |
|---|---|
| 作用对象 | 活魂符在容器内**随机选中的相邻目标槽**（与现有走位同一邻槽口径）；越界/世界/玩家/其它容器不参与 |
| 输入或变化粒度 | 目标槽的类型 / 数量 / 活化身份（与现有走位判定同粒度）；行动瞬间取快照并重验，同拍多次变化只认行动时最终状态 |
| 方向含义 | **位移**（女仆进入目标槽）+ **被动转移**（目标物品来到女仆原槽）；食物分支附加**消耗 1 份** |
| 首次出现 | 无基线概念——换位是行动结果不是观察；活化后即按碰撞表行动 |
| 忙碌窗口 | 不适用；每枚每拍至多一次行动，由整秒门 + `1/I` 现有门控保证 |

**正例与负例**：

```text
正例：[活魂符][铁×30][空]
      选中右 ⇒ 换位 ⇒ [铁×30][活魂符][空]        （I−1）

正例：[活魂符][苹果×64]
      选中右 ⇒ 吃1个+换位 ⇒ [苹果×63][活魂符]    （I−1，pending+1）

负例：[活魂符][活熔炉][空]
      目标是活物品 ⇒ 挡路失败，不换位            （I+1）

负例：[活魂符][石×64]（source 槽 limit=1）
      石×64 装不进原槽 ⇒ 整体失败，不部分交换    （I+1）
```

## 统一碰撞表（核心规则）

随机方向确定后（**不预过滤、不重掷**，沿现有走位纪律），按目标槽内容分派：

| 目标槽 | 行为 | I |
|---|---|---|
| 越界 | 失败 | +1 |
| 空 | 现有移动（不变） | −1 |
| 非活化居家餐（TLM `DefaultMaidHomeMeal` 判据） | **吃 1 份**，剩余堆与女仆**换位**（女仆进入食物槽） | −1，pending+1 |
| 非活化普通物品 | **换位**（女仆进入，整栈来到女仆原槽） | −1 |
| 活化物品 | 挡路失败（居民/机器不是货物，活物品隔离延伸） | +1 |
| 食物但不合格（黑名单 / pending 满 / 不可抽取） | 挡路失败 | +1 |
| 换位不可行（整栈装不进原槽等准入失败） | 失败 | +1 |
| 过期条目 / 精确写不支持 / 后端违约 | 技术中性 | 不变 |

**食物分支的分解**：`consume(target, 1)` 之后，剩余局面自然退化——N=1 ⇒ 目标空 ⇒ 走现有移动路径；
N>1 ⇒ 与剩余堆换位。即"吃"不再是独立于"走"的结果，而是换位动词上的附加消耗。

## swap 原语（ContainerContext 契约扩展）

**为什么现有抽象不够**：`move`/`moveStack` 家族全部以"目标可容纳（空或可合并）"为前提；
两个非空槽互换无法用两次 move 表达（双向被占，两步都失败），且中间态会暴露给同拍其它功能。
⇒ 换位是缺失的槽位原语，进入 `ContainerContext` 原语家族（maid 域只调用，不绕 `check_stack_ops` 棘轮）。

| 项 | 定案 |
|---|---|
| 签名 | `swap(source, target)`（整栈互换；一空一非空不是 swap 的职责，走 move） |
| 准入 | `STANDARD`（容器同意的转移）：双向抽取模拟 + 双向准入模拟（`simulateInsertItem(source, targetStack) ≥ targetStack.count` 且反向 ≥ 1） |
| 原子性 | 验证式：快照双槽 → 精确写 → 逐槽回读 → 任一失败恢复双快照并留痕；不部分交换 |
| movedSlots | 成功后登记两槽（复用 `onSlotsMoved`，同拍旧条目失效语义与 move 一致） |
| 组件保全 | 精确写整栈，组件随物品走（含活魂符自身的 clock/pending） |

**食物分支执行顺序**（利用 swap 可逆性做补偿）：

```text
1. 预检：非活 + TLM居家餐 + pending容量 + swap双向模拟
2. swap(source, target)          ⇒ 女仆在target，食物堆(N)在source
3. consume(source, 1)            ⇒ N−1（走既有抽取权限链）
4. commitItemComponents(target, soul, soul+pending+1+I−1)
失败矩阵：
  步骤3失败 ⇒ 再swap一次（swap自身逆操作）回到原状，I+1，整体失败无净变化
  步骤4失败 ⇒ 已换位已吃，技术中性，按"宁失勿复"保留事实，pending不加
备选顺序（先consume再swap）被否决：consume无undo，换位失败时食物已损，produce回填可靠性差。
```

## 横切检查表摘要

- **生命周期**：本玩法**不新增任何状态**——I 与 pending 已随物品组件存在，换位只是位置事件；
  无槽位运行态、无基线、无缓存。1.1 表全行"不适用（无新状态）"。
- **状态粒度**：无新增容器级可见物；客户端预览仍 per-item（现有移动插值/脉冲机制不变）。
- **准入**：双向——target 须接纳女仆（count=1），source 须完整接纳 target 整栈；
  活物品在两侧都挡（女仆不可被换出给活物品？不——女仆是发起方；活物品作为**目标**时挡路，
  作为**女仆原槽新住户**时同样挡（活物品进不了普通空位逻辑由其自身准入管，swap 模拟自然拦截）。
- **反馈**：无新通道——走路插值复用（旧槽→新槽）；被换物品瞬移（物品渲染常态）；
  吃脉冲/吃声仍由 pending 增长驱动；tooltip 行动概率语义不变（仍是每秒尝试，非换位成功率）。
- **容器能力**：相邻槽解析走现有 `ContainerLayoutResolver` 统一链（女仆已在用）；
  对外承诺资源收付 ⇒ swap 契约测试必须断言**后端实际槽值**与双向收付守恒（按模板 §2.2 矩阵）。
