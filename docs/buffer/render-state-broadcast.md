# 渲染态广播：把「世界可见的活物品状态」收成一套（未定案 · 设计探讨）

*创建: 2026-10-26 · 状态: **未定案**，本文只是形状提案，不是排期。*

> ⚠️ **本文是「探讨层」，不是现状描述。** 代码尚未改动；动代码前先回本文逐条确认。

---

## 1. 为什么现在要谈这个

「让客户端看见活物品在世界里的样子」这件事，目前有 **4 条独立通道**：

| 通道 | 服务的活物品 | 服务端 | 客户端缓存 |
|---|---|---|---|
| 方块容器里的活工具 | 活工具 / 活武器 | `LivingToolHostSync` | `LivingToolHostClientCache` |
| 玩家背包里的活工具（给别人看） | 活工具 / 活武器 | `LivingToolPlayerSync` | `LivingToolPlayerClientCache` |
| 箱子宿主的信标光束 | 活信标 | `BeaconChestHost` | `BeaconHostClientCache` |
| 玩家宿主的信标光束 | 活信标 | `BeaconPlayerHostSync` | `BeaconPlayerHostClientCache` |

四条通道各自实现了一遍「**收集 → 按距离定向 → 与上次发给他的比 → 逐维度 flush → 客户端整表替换 + 维度校验**」。
四份代码，四种去重口径（手写白名单 / `ItemStack.isSameItemSameComponents` 全量 / `List.equals` / 判"翻转"）。

**代价已经付过两次：**

- 2026-10-23：`flush` 逐维度调用却 `lastSent.clear()` ⇒ 每 tick 重发空包。只在 `LivingToolHostSync` 修了（抽 `mergeRecords` + 加测试），**另外三处原样还在**。
- 2026-10-26：`LivingToolHostSync` 去重键只比「物品种类 + 记忆」，动画状态翻转不触发重发 ⇒ 方块容器里的活工具「有模型、不转圈」。**从模型上线（09-20）起就没通过。**

两次都不是"某个人不小心"，是**同一段逻辑存在四份、修了一份**的必然结果。

---

## 2. 根上的判据：一份数据，两个问题

- **它影响渲染吗？** 不影响就不进键（耐久是状态，但渲染不读它 —— 进键纯属自找刷包）。
- **重复送达会出错吗？** 会出错 ⇒ 事件（必须去重）；无害 ⇒ 状态。

2026-10-26 事故的根因**不是"状态不该去重"**，而是**去重的单位错了**：现在比较的是
**手写字段清单**（物品种类 + 记忆），发送的是**整个 ItemStack**，两者是两份清单、会漂移。
正确做法是让「**比较单位 = 发送单位**」（一个 `State` record）—— 那时状态段照样去重，
而且不可能漏。

---

## 3. 长期形状：一个三元组

```
服务端  TargetedBroadcast<T>      收集 + 定向 + 去重 + 逐维度合并
契约    Structure / RenderState   结构段（变了才发） + 状态段（每 tick 覆盖）
客户端  DimensionScopedCache<T>   维度校验 + 整表替换 + clear
```

### 3.1 服务端：`TargetedBroadcast<T>`

把四份 `flush` 的骨架收成一份，调用方只提供两件事：

- `List<T> entriesFor(ServerPlayer viewer)` —— 这个玩家该看见哪些条目（半径 / 排除自己 / 维度）
- `boolean sameEntry(T a, T b)` —— 两条条目是否"渲染等价"

内部统一处理：`lastSent` 表、逐维度合并（照 `mergeRecords` 的既有不变量）、半径常量、离线淘汰。

### 3.2 契约：结构段 / 状态段

包内一条目拆两段：

```java
record Entry<S>(BlockPos pos, Structure structure, S state) {}
```

| 段 | 内容 | 策略 |
|---|---|---|
| `Structure` | 物品种类 + 记忆（慢变、可能较大） | **变化检测**，变了才发 |
| `state` | 挖掘进度 / 瞬时动作 / 预计总 tick（快变、极小） | **变化检测**，但比较单位就是发送单位 |

⭐ 为什么状态段也敢用变化检测（2026-10-26 用户拍板：**不设每 N tick 保底覆盖**）：
`State` record 既是**发送内容的完整定义**，也是**比较的单位** —— 加字段时你在同一个 record 里加，
比较自动跟上。这与本次事故的根因（比较字段集合与渲染读取集合是**两份手写清单**）是本质区别。

流量：稳态下只在「开始挖 / 挖完 / 交互」时发，**每挖一格约 2 个包**，闲着零包。
极速工具（1 格/tick）会退化成每 tick 2 包 —— 与挖掘活动绑定，不是恒定开销。

### 3.3 客户端：`DimensionScopedCache<T>`

四份缓存除了泛型参数完全一样（`volatile` + 不可变 List + 维度比对 + `clear()`）。
抽一份，顺带把"换维度 / 换存档不串台"这条不变量收在一处。

## 5. 状态段的四条硬约束

写新的 `RenderState` record 时必须满足：

1. **小** —— 按"每 tick 覆盖"计费，目标 < 32B/条目。
2. **幂等** —— 同一状态发两次，客户端结果必须相同（否则重发会抖）。
3. **无事件语义** —— 表达"现在是什么"，不表达"刚刚发生了什么"。事件用翻转位或 revision 表达。
4. **"闲"要能表达** —— 可空字段（`null` = 没在动）比"缺字段"好：缺字段会让客户端停在旧值。

### 5.1 判据：不是「会不会变」，而是「重复送达会不会出错」

| 重复送达的后果 | 归类 | 策略 |
|---|---|---|
| **会出错**（播两次脉冲、扣两次耐久） | 事件 | **必须去重** |
| **无害** | 状态 | **不该去重** |

⭐ **把事件「时间戳化」就能把它降级成状态**：不记"发生了一次"，而记"最近一次发生在 tick `T`"，
消费方用 `now - T < 窗口` 自己算要不要播 ⇒ 重复送达无害、漏一 tick 下一 tick 自动补上。
`LivingToolAction(tick, target)` 就是这个手法，也是活工具能整体走"状态段"的前提。

⚠️ **时间戳化的边界**：**同一 tick 内多次同类事件时失效**（只记得最后一次）。
连击 / 蓄力若要求"每一次挥击都播一次独立动画"，就得要事件队列 —— 那时这一条不成立，
那类数据只能回到"事件 + 去重 + 保证恰好一次"。

### 5.2 范例：活工具（K2 的实际分类）

| 数据 | 性质 | 为什么 |
|---|---|---|
| 物品种类 | 结构 | 换物品才变 |
| `LIVING_TOOL_MEMORY` | 结构 | 录制时变、之后长期不变，体积最大 |
| `LIVING_TOOL_DIG_TICKS` | 状态（派生常量） | 每次 `freshStart` 重算一次，跟着 progress 翻转 |
| `LIVING_TOOL_PROGRESS` | 状态 | "现在在挖 X、从 T 开始" |
| `LIVING_TOOL_LAST_ACTION` | 状态（**事件时间戳化**） | 客户端只问"距现在多久"，不关心"发生过几次" |
| `digLanded` / `useLanded` | 状态 | 每 tick 重算，只影响透明度 |
| 耐久 | 状态，**但不是渲染数据** | 渲染不读它 ⇒ 不进键（进了就刷包） |

⇒ **K2 里没有任何「必须恰好一次送达」的东西**，这是它能整体改成"状态段每 tick 覆盖"的前提。

## 6. 被否掉的方案（先找对应物，答不上来才新建）

| 方案 | 否掉的理由 |
|---|---|
| 用原版 `BlockEntity#getUpdateTag` 搭车 | 可见性口径（32 格）确实一致，但**状态的归属不是 BE**（活物品是物品），且实体容器（船 / 驴）没有 BE ⇒ 覆盖不全 |
| 用 `ContainerContext#syncSlotToClients` 一条通道打通 | 它的可见性语义是「**菜单持有者**」，服务的是槽位内容 / 图标；世界渲染要的是「路过就看得见」。**两个消费者语义不同，通道不能合并** |
| 客户端自己从裂纹 / 世界状态推算动画 | 判据要维护两份，必然走偏（`L48` 已踩过：客户端复刻 `scanForTarget` 连错三处） |
| 继续给每个包手写去重键 | 要求"渲染器加字段时记得改去重键"，靠人记；两次事故已证明会漏 |

## 7. 三步走（2026-10-26 修订）

| 步骤 | 内容 | 状态 |
|---|---|---|
| **① 止血** | 合并口径抽成 `living/util/BroadcastDedup#merge`，四个同步器共用 | ✅ 已落地 |
| **② 防复发** | `ToolRenderState` record 收口「渲染依赖」：服务端比较与客户端渲染同源 | ✅ 已落地（**零协议变更**） |
| **③ 消重复** | `DimensionScopedCache<T>`：四个客户端缓存合一 | ✅ 已落地（调用点零改动） |

### 7.1 明确不做的（附理由）

| 方案 | 否掉的理由 |
|---|---|
| `TargetedBroadcast<T>` 服务端骨架 | ① 已拿走它最有价值的部分（merge 口径 / 离线淘汰）。剩下四个 `flush` 循环差异比看起来大：收集时机（tick 中登记 vs flush 现算）、是否排除自己、半径口径（3D vs 水平）。硬抽会变成「三开关 + 四 lambda」的框架，省的行数不够付配置成本 |
| 协议分段（结构段 / 状态段） | ② 用「一个 record 同时是**提取点**与**比较单位**」达到了同样目的，且不必改包格式、不必两端同版本 |
| 状态段每 N tick 保底覆盖 | 用户拍板：比较单位 = 发送单位后不会漂移，不需要周期重发兜底 |
| `PlayerSync` 跟进同一套 | 它只画待机环，不读 progress / action，没有动画需求 |
| `ToolRenderState` 通用化 | 等第二个消费者（活 TNT / 活熔炉的世界渲染）出现再说 —— 现在只有一把工具在用 |

## 8. 已定（2026-10-26 用户拍板）

- **状态段不设保底覆盖** —— 只用「变化即发」。安全性来自「比较单位 = 发送单位」，不来自周期重发。
- **条目身份用容器键**，不用 `BlockPos`。反例：两艘船同一格 / 带箱驴站在箱子上 /
  玩家背包没有坐标 / 活背包跟着玩家跑（键形全集见 `ContainerKeys`）。
  代价：字符串 20~40B（vs `BlockPos` 8B）。若嫌大，用「kind 字节 + payload」的紧凑联合
  （方块容器塞 pos、实体容器塞 UUID），比裸字符串省一半。
