## 0. 基础设定：我们究竟要封装什么

**活潜影箱 = 一个可随物品搬运的内部容器 + 对内部活物品的运行驱动 + 明确的边界连接。**

它的价值不只是增加存储格，而是让玩家把熔炼工厂、电路、流体装置、工具组合装成一个模块：
其它活物品是棋子，活潜影箱是棋盘；搬走棋盘，不必拆散上面的机器。

### 0.1 通用性与三个不同的承诺

| 承诺 | 含义 | 本稿推荐 |
|---|---|---|
| 运行封装 | 内部活物品复用原有功能与容器 tick 管线 | 核心目标；不由 GUI 是否打开驱动 |
| 边界连接 | 边界槽能与邻箱 / 父槽发生指定交互 | 核心目标；先明确地址、方向、尺度与时序 |
| 世界桥接 | 放置后，内部功能通过真实宿主与世界交互 | 保留目标；按既有锚点与能力面接入，不先预定新 BE |

**兼容所有活物品，包括未来新增功能**，应当意味着：提供共同的容器能力，功能只声明自己需要什么。
不能变成「每新增一个活物品，必须再写一份潜影箱专用 tick」。

但通用容器能力不能替功能决定玩法：无世界锚点时如何降级、设备是否允许跨边取材、位移是否能穿透，
仍由对应功能契约决定。§8 按能力族验收，不维护一份不断增长的功能复制清单。

### 0.2 玩法原点五问（候选口径）

| 问题 | 建议答案 |
|---|---|
| 作用对象 | 本箱内部槽位；边界仅连接同方向的直接邻接对象，不观察无关父槽 |
| 输入粒度 | 信号读上一拍已结算的方向性输出；库存交易读真实最新槽值；观察功能读公开语义状态，不读整棵组件树 |
| 方向含义 | 内部网格四方向；跨边保持输入/输出朝向与边上的通道编号，不能只携带「一个信号值」 |
| 首次出现 | 活化分配容器身份；首次运行正常执行一拍；首次接线没有可信上一拍输出时输入为 0；移入/换槽只重建外部接线，不更换内部身份 |
| 忙碌窗口 | 不新建整箱业务冷却；功能沿用自身冷却。跨边输入按拍替换，不排队重播历史值；库存失败本次返回失败，由原功能决定重试 |

正例与反例（槽号全部 0 起）：

```text
正例：父容器同一行 [A] [B]
      A[17] 的向右输出 → B[9]，逐行对接，不改内部坐标。

反例：父容器第 1 行末尾 [A]
      父容器第 2 行开头 [B]
      父槽号虽然差 1，但不是左右邻居；不得跨行接通。

反例：[未活化潜影盒] 或 [普通活箱子]
      存储能力不等于封装边界，不自动向里面展开运行或接通引脚。
```

## 1. 创始定义与必须保住的直觉

创始构想：容器 C 的相邻槽里放活潜影箱 A、B。A 的第 18 格（0 起槽 17，第二行最右）
放向右输出的活漏斗；它的输出越过 A 的右边界，落到 B 的第 10 格（0 起槽 9，第二行最左）。
内部也能与 A 在父容器中相邻的普通槽交互，反过来同样成立。

### 1.1 同尺度的边界连续性

```text
A（9×3）右边界             B（9×3）左边界
A[ 8]  ─────────────────→ B[ 0]
A[17]  ─────────────────→ B[ 9]
A[26]  ─────────────────→ B[18]
```

上下相邻时逐列对接：A 的下边界 `18..26` 对 B 的上边界 `0..8`。
四个活潜影箱在父容器中 2×2 排列，**邻接示意**可以画成 18×6。

这不是「所有行为等价于原生 18×6 容器」的承诺：封装边界有信号延迟，流体、应力与电力账本
可能仍独立，跨尺度还会发生多路合并。空间连接、时间推进、资源账本必须分别定义。

### 1.2 跨尺度是端口，不是无损放大

父容器一格只有一个槽，而子箱左右边有三个槽、上下边有九个槽。
因此「普通父槽 ↔ 一整条子边」没有天然的一一对应关系。

| 连接 | 候选规则 | 为什么 |
|---|---|---|
| 子箱 ↔ 相邻子箱 | 同方向、同通道号逐槽映射 | 保住创始漏斗布局，不引入全局坐标 |
| 父层普通槽 → 子边的信号 | 将父槽朝本箱发出的出边广播到该边各端口 | 一个父输出接多引脚，不复制库存资产 |
| 子边 → 父层普通槽的信号 | 只取朝外出边的最大值 | 明确多路合一；不能取槽位所有方向的最大值 |
| 子边 → 父层普通槽的货物 | 各内部设备按正常时机竞争同一个真实父槽 | 接收多少、源扣多少；不会因三个端口复制三份 |
| 父层漏斗 → 子边的货物 | 沿接收边枚举候选槽，按已提交量消耗本次预算 | 普通槽没有行号，不能假装可自动选中某一通道 |

**建议的货物仲裁**：多候选边界槽采用轮转起点（round-robin）；本次允许部分交付，累计不能超过
原功能预算。轮转位置是可丢弃运行态，不成为物品存量或无限交易队列。
指定通道 / 自定义端口映射可以后讨论，不在第一版加配置系统。

### 1.3 多层嵌套如何穿透

建议将穿透拆成两类，不使用一条递归规则包办：

- **库存地址**：遇到边界后沿父关系找直接邻接对象；若目标是活潜影箱，则展开它的接收边。
  若该边槽又是活潜影箱，可继续展开。若本箱在父容器中也处于同向边界，则继续向外解析。
  普通槽即终点；所有递归都受共同深度与环检测约束。
- **信号**：不跳过封装级。内层先发布到它在父层所占槽的方向性输出，父层再发布到外层边界。
  每经过一条封装连接推进一拍，不能穿越多层直接读最深层本拍值。

候选代价：再遇到一个子箱会把一个接收槽展开为多个引脚，货物用 §1.2 的候选列表规则，信号用
广播 / 聚合规则。**这不保留无限嵌套后的所有独立通道**；若要求无损通道，需要另定显式映射。

### 1.4 递归预算

保留早期 **最大嵌套 4 层**作为候选上限：进入第一件物品形态活容器计第 1 层，每次进入更深
活容器减一份预算；外面的世界箱子 / 玩家物品栏不算一层。
活背包与活潜影箱混合嵌套时必须消费同一条预算，不能各开一个 ThreadLocal 深度计数绕过上限。

四层不等于四次调用：单链是四次，树形布局是所有被访问的子容器之和。
性能按实际访问槽位和边界交易计量。若压测显示深度不足以限成本，再讨论总工作量上限及公平分配，
不先引入一个全服扫描器或悄悄跳过后半批箱子。

## 2. 实现骨架：复用什么，真正新增什么

### 2.1 现有对应物

现状查证入口，不是新增类清单：

- `LivingBackpackFunction`：功能内部构建 ctx 并递归 `processContext`。
- `ItemFormContainers` / `ItemFormContainerContext`：物品形态内容来源、UUID 身份、列数、持久化。
- `ContainerContext.resolveNeighbor`：本容器局部邻槽几何，不返回跨容器地址。
- `SlotAccessor` / `SlotAccessorFactory` / `TransferPipeline`：跨容器传输及过滤、货物、交互语义。
- `ContainerTickHook`：开始与写回阶段；`HasContainerData`：本容器流体→应力→红石→电力顺序。
- `ContainerViewers` / `ContainerContexts`：查看者与 GUI 槽所属的唯一入口。

源文件查证可调用 `python tools/gen_code_map.py --query <类名>`；真实路径与依赖以源码为准。

### 2.2 候选职责与新增理由

| 职责 | 建议落点 / 对应物 | 现有抽象为什么不够 |
|---|---|---|
| 活化、递归驱动、取消活化 | 潜影箱领域的 `LivingItemFunction`，复用活背包路径 | 缺潜影箱功能，不缺另一套顶层调度 |
| 实际库存与 handler | 自有 UUID 库存库，向 `ItemFormContainers` 提供标准内容视图 | 容器级 SavedData 不拥有 27 槽物品；参考活背包，将内部库存作为独立真身而非祖先组件副本 |
| 本体所在关系与配置提交 | 父 ctx / 槽位绑定 + 既有组件提交协议 | UUID 库存不证明本体仍在原槽，也不替代活化身份、配置的真实父槽写回 |
| 跨边地址与端口映射 | 容器层的无领域邻接契约，映射实现归潜影箱领域 | 现有 `int` 邻槽不能描述「另一个 ctx 的第几槽」，更不能表达多候选接收边 |
| 上拍 / 本拍边界输出 | 各领域发布自身快照；用既有 tick 开始 / 写回挂点 | 本拍实时可变账本不能提供与遍历顺序无关的旧输入 |
| 多窗口 | 一个菜单 + 一个 Screen 的窗口管理 | 原版没有窗口布局，但已有 carried、点击、Slot 与同步 |

**不新增**全局扁平槽数组、通用物品扫描展开、所有功能的第二份 tick、独立库存回滚引擎、
逐功能巨型 `switch`。同样不假称「框架零改动」：局部 `int` 之外的边界能力与多窗口槽所属确有扩展需求。

### 2.3 邻接契约只管定位

示意类型（提案，尚未实现，名字不是实施约束）：

```text
SlotRef     = 本次可用的 ContainerContext + 逻辑槽号
PortRef     = SlotRef + 从该槽向外的方向
Connection  = 邻接类型 + 接收端 PortRef 列表
```

同容器普通邻槽仍走现有无分配 `resolveNeighbor`，不把全部热路径改成地址对象。
需要穿透的功能才在局部邻接失败、或邻槽是封装设备时询问边界契约；无接线能力默认保持旧行为。

映射层不内置 `getNeighborSignal/getNeighborFlowLevel/pushItem` 三合一业务接口。
它回答「在哪里、朝哪边、是否属于封装内部连接」；领域回答「读什么、怎么处理、是否有资格写」。
这样未来功能复用定位能力，不迫使潜影箱核心 import 每个领域。

### 2.4 一个模块的运行链路

```text
既有宿主 processContext
  → 分组识别活潜影箱
  → 潜影箱功能核验当前槽、活化身份、UUID 与递归预算
  → 绑定本体当前父槽关系，按已提交 UUID 取权威库存视图
  → 构建内部 ctx（内部键按 UUID，不按父槽）
  → 内部 processContext 正常推进一次
      → 功能 tick
      → 流体 / 应力 / 红石 / 电力
      → 领域写回与边界输出发布
  → 释放本次递归绑定；不拿旧 shulkerStack 整栈覆盖父槽
```

边界交易可以解析尚未轮到 tick 的邻箱内容，但**得到内容视图不等于让它提前 tick**。
身份初始化必须实际提交到宿主后才登记视图；避免第二个访问者拿到另一份未保存 UUID。
映射只覆盖被封装玩法触达的对象，不每拍遍历世界所有物品能力。

## 3. 状态与库存：参考活背包，优先 UUID 外置库存

### 3.1 活背包给出的对应物与身份分工

**查证结论**：活背包不是递归 `CONTAINER` 库存。精妙背包以 `STORAGE_UUID` 寻址自己的
`BackpackStorage`，`BackpackWrapper.getInventoryHandler()` 返回该库存的标准视图；
本模组再用 `CONTAINER_UUID` 寻址流体等容器级数据与运行缓存。

参考的是这份分工，不复制第三方实现或引入精妙硬依赖：

```text
现有活背包：
  物品 STORAGE_UUID   → 精妙 BackpackStorage → 实际物品库存 handler
  物品 CONTAINER_UUID → 本模组 ContainerDataSavedData / 运行缓存
  LivingBackpackFunction → ItemFormContainerContext(handler, uuid) → processContext
```

可复核入口：`SophisticatedBackpackSource.contentHandler`、`LivingBackpackFunction.tickOne`、
`ContainerUuids.discard`；内容外置与客户端可见性见
[活背包技术文档 §6「客户端同步」](../tech/living-backpack-tech.md) 的源码查证记录。
本机有第三方源码时可追 `BackpackWrapper.BackpackStorageContentsSource`、
`BackpackStorage.getOrCreateBackpackContents` 与 `InventoryHandler.saveInventory`。

两套 UUID 在活背包中合理，因为本模组**不拥有精妙库存**：取消活化只清本模组容器数据，
不删除精妙库存身份和内容。不能把 `ContainerUuids.discard` 当成销毁外部库存的通用入口。

### 3.2 候选架构：一份容器身份，分别管理库存与运行数据

活潜影箱是本模组自有容器，建议**先使用同一容器 UUID**索引库存与容器级数据的不同存储，
不因精妙有两个身份就再造一个 STORAGE_UUID。若今后允许普通潜影盒也继续使用外置库存，
库存身份需跨取消活化存活，那时再明确独立生命周期，而不是提前引入双 ID。

| 数据 | 推荐载体 | 含义 |
|---|---|---|
| 本体身份与配置 | ItemStack 组件 / 放置态身份载体 | 活化标记、容器 UUID、方向等；不携带整棵内部库存 |
| 实际 27 槽库存 | 自有库存 SavedData，按容器 UUID 寻址 | 唯一持久内容与标准 handler；拟新增，不是现有 API |
| 有持久契约的容器级数据 | 现有 `ContainerDataSavedData`，按同一 UUID 及领域 key 保存 | 流体等领域资产，不混入库存列表 |
| 运行态与边界快照 | 既有容器运行缓存 + 按拍输出 | 非存量、可重建；不因 GUI 关闭而清空 |

**现有 `ContainerDataSavedData` 不是物品库存库。** 新库存层的必要性是让深层模块拥有独立真身：
内部组件变化只提交该模块的槽，不需要重新组装每个祖先，也不每次同步整个子树。
代价是普通化交接、库存持久化/恢复和按需内容同步；下文明确这些责任，不宣称现有框架已全部解决。

```text
活潜影箱 A 的物品：UUID=A
库存库 A：27槽，其中一槽放着 UUID=B 的活潜影箱
库存库 B：27槽

B 内物品变化 → 写库存 B + 标脏 + 同步 B 的授权窗口
A 内指向 B 的物品、A 的父物品内容都不因 B 的这次变化重写。
```

创建库存时必须完成「原版内容导入、真实本体 UUID 提交、内嵌内容移除」的可验证交接，再允许它运行。
失败不得清空原物品或留下两份可用库存；仅 `getOrCreateItem` 改了一份读取副本，不是交接成功。
读路径不盲目创建：有 UUID 却缺库存记录视为异常并拒绝操作，不能当空箱保存覆盖丢失内容。
空库存记录可显式保存，或者采用可区别“合法空箱”和“记录丢失”的编码；不得凭空记录推断二者等价。

### 3.3 库存视图与真实提交

`ItemFormContainers.Source.contentHandler(stack)` 可按已提交的 UUID 返回自有标准库存 handler，
内部 ctx 复用 `ItemFormContainerContext`；世界放置态与菜单也必须取同一份 handler，不各建副本真身。
同一服务端同一 UUID 的活动视图共享实际槽值，禁止每次从旧 NBT 各自解码成互不相通的可写列表。

- 读取槽返回副本，修改仍走既有数量原语 / `commitItemComponents`，不能用改引用代替提交。
- setter 精确改指定库存槽，实写后回读同一权威库存；变化才标脏、更新修订/通知、进入现有同步通道。
- 模拟不改库存、序列化数据或通知；失败必须真实回读，不让尚未提交的临时 list 假装成功。
- A→B 跨箱仍走现有传输内核；B 少收/拒写时，只恢复本次源槽未交付余量，不恢复整库旧快照。
- 同一物理槽、整库与源范围重叠、重复候选等自环检查继续按最终后端和实际范围判断。

**库存所有者绑定仍需要，但用途变了**：它验证物品仍在当前父槽、活化身份/UUID/访问资格未变，
以及获取锚点和接线；不负责每次将深层库存向外拼成组件树。
本体配置、UUID 初次提交、普通活箱子的内嵌内容，以及第三方组件库存的修改，仍须提交真实父槽。
权限或定位失效后，不能因持久库仍有数据就继续自动运行/远程取货；取消活化后旧 handler 必须失效，
不能拿到已退役记录继续写或偷偷重建库存。

### 3.4 仍需适配的设备接缝与大小约束

外置库存不是把所有旧功能自动变正确。活箱子 accessor 与骨粉等就地交互若只修改读出的副本，
仍需确认实际设备槽组件已提交，再结算源消耗。`frame` / `SlotEntry.stack` 只用于枚举定位；
执行前重取当前设备，身份变化跳过，身份未变也不能继续用旧组件计算。

本体不递归携带活潜影箱库存，避免了主路径上的祖先组件膨胀，但以下成本仍存在：

- 单槽物品可能包含书、附魔或普通 `CONTAINER` 子树；插入与增长仍需符合该槽存储/网络约束。
- 实际库存、持久库规模与递归 tick 工作量须压测，不能凭 UUID 宣称无性能上限。
- 内容窗口、Tooltip、流体/端口显示走按需 S2C；客户端不直接访问 SavedData。
- 超限允许取出救援，不静默夹 count 或删组件；原功能的消耗/产出不能假报未提交结果。
- 转回普通原版 `CONTAINER` 时可能重新遇到递归大小限制，交接不能先删库存再发现装不回去。

递归 `CONTAINER` 留作**被降为备选的候选**：若最终不愿承担外置库存与原版形态接入成本，可使用
最新真实根读取、沿单路径组装、根级组件提交，失败恢复保留兄弟更新的方案；它不再是主提案。

### 3.5 生命周期与普通化候选表

| 状态 | 换父容器 / 换槽 | 取消活化 | 拆合 / 复制 | 暂时卸载 | 缓存回收 / 重建 |
|---|---|---|---|---|---|
| 实际 27 槽物品 | 库存 UUID 不变，物品移动引用 | 先完整交还普通潜影盒或明确结算，提交成功后再删库存 | count≠1 不运行/存取；复制政策见 §8.2 | 保留，停止推进，不补算离线产物 | 从 SavedData 恢复，不因 handler 过期删除库存 |
| UUID 与持久容器数据 | 身份保留，父关系重建 | 库存交接成功后，清本箱容器级数据与身份 | 两个物品同 UUID 的共享风险必须显式处理 | 持久值保留 | 由现有身份/领域契约恢复 |
| 各功能运行态 | 同一内部身份沿原域规则续用 | 清本箱运行态，不递归取消子箱活化 | 不自行复制运行态 | 暂停，不承诺跨重启继续全部进度 | 原领域决定哪些可丢弃、哪些必须持久 |
| 边界旧输出 | 本体运行数据可留，旧连接资格失效 | 撤销、断开 | 不继承复制品旧接线输出 | 过期视为 0 | 首拍从 0 建立，不重播旧包 |
| 窗口访问关系 | 重新校验可达性；旧槽绑定失效 | 撤销旧 handler/窗口访问 | UUID 不能代替实例可达性 | 失去访问即关闭 | 必须重新获服务端授权 |

**取消活化交接顺序（候选）**：验证导出可表示且无共享身份冲突 → 将原库存内容完整提交到普通本体
→ 确认交接后清本箱库存记录、持久容器数据、运行态及活化身份。失败保留原活化对象与库存，
需要活化钩子允许中止该交接，不能先让框架剥光状态。子箱若仍活化，则保留它的 UUID 引用与独立库存；
不为了普通化父箱递归展开/取消子箱。这样的内容是否允许留在普通盒内，必须与原版准入例外一起定案。

**销毁与离线不是一回事**：库存记录不按 TTL 清理。明确销毁时先按已定规则掉落/交付或湮灭内容，
再退役库存；不因某个引用消失就推断最后一份引用已没了。活视图 TTL 仅回收可用 handler 引用，
不会自动删除持久库存。崩溃跨文件保存、重复身份与失败恢复属于交接验收，不冒充普遍事务保证。

## 4. 时序：边界寄存，内部每拍只推进一次

### 4.1 信号交换的明确算法

保留早期 **1 tick 边界延迟**。这是本模组的确定性选择，不以「原版跨区块固定延迟」作依据。

```text
本拍开始 / 首次访问边界输出：
  取得本拍冻结可读的历史输出（只能来自早于本拍的结算）。

每个内部容器：
  从冻结输出读取本拍输入；正常运行一次。
  将本拍已结算方向性输出写入待发布快照。

下一拍：
  待发布值成为可读历史输出；本拍再写新值不会改变可读旧值。
```

实现可以按 tick 戳懒切换读/写缓冲，不必先全局扫描所有箱子。
但首次访问发生在 A 读 B、而非 B 自己 tick 时，也必须正确切换；每次发布需保留本拍可读旧值。

每条输出带可用性判据：容器身份、有效所在关系、拍号与当前连接一致；移走/取消活化不允许靠旧快照
继续供电。若停 tick 或没有可信上拍结果，边界输入为 0，不无限沿用缓存。

**验证目标**：在库存不变化、拓扑固定的布局中，调换 A/B 处理顺序，边界信号结果与延迟一致。
不将此承诺扩大为整个世界所有库存操作均与遍历顺序无关。

### 4.2 不重跑 processContext

`processContext` 同时推进功能、冷却、流体与容器级账本；不是可以反复调用的组合求值函数。
既然接受下一拍传播，边界交换只提供下一拍输入，不在交换后第二次运行内部。

将来若确需同拍组合重算，必须先从原域拆出「不推进时间、不收付资产」的纯计算边界，
并明确收敛/振荡处理。第一版不做。

### 4.3 库存仍然是本拍真实交易

库存搬运不复制信号缓冲：按当前源、目标及实际提交量执行。
旧接线可帮助定位，但执行前必须再次核对真实宿主/UUID；交易失败不保留一份幽灵待交付货。

多设备竞争按现有执行顺序与 §1.2 的候选槽轮转结算；不新增全局交易收集 / 拓扑排序阶段。
同拍移走一件设备后，旧 `SlotEntry` 与地址必须失效，不能让旧扫描条目再操作新设备。

### 4.4 不用静态边界推断整箱休眠

固定输入不等于内部静态：熔炉生产、中继器倒计时、振荡电路与流体蔓延均可能继续。
第一版照常推进；后续只缓存已经证明稳定的组合部分。
没有功能声明或可验证的静态判据，不跳过整个内部 tick。

## 5. 各功能逻辑怎样接到边界上

### 5.1 活漏斗：换目标地址，不换传输引擎

候选执行链路：

1. 原功能确定输入/输出方向、冷却和预算。
2. 局部邻槽存在且不是封装设备，保持原路径。
3. 越界或相邻槽为活潜影箱，询问 §2.3 的连接，得到真实 ctx + 逻辑槽 / 接收边候选。
4. 对每个有效目标使用该 ctx 的槽 accessor；普通精确货槽优先 `PlainSlotAccessor`，factory 保留
   provider 与过滤装饰；货物隔离、槽交互和目标策略仍接回原管道分支。**整库**
   `NeighborSlotAccessor` 或 `LivingChestAccessor` 不能冒充 B[9]。
5. 跨容器数量移动仍调用 `SlotAccessor.transferAmount`；源扣减、容量、写后校验与违约撤销沿现有内核。
   仅构造 accessor 再调用数量内核，不等于自动执行了所有原管道规则。
6. 以累计真实交付量结算原功能预算；同步实际改动的容器，推进轮转起点。

目前不存在可直接使用的「跨 ctx `ContainerContext.move` 重载」。同容器数量原语与跨容器入口
按 [slot-ops §3](../guides/slot-ops.md) 分工，不新增第六个数量原语。

**精确槽承诺**：创始布局要落 B[9]，不得回退为 B 的最低空槽。B[9] 满则本次等待。
若 B[9] 本身是另一个容器设备，则它按自己的 accessor 语义响应；那是设备内部存取，不是写错普通槽。
边界不给搬走活容器本体增加新豁免，设备隔离规则不变。

**交易自环检查**：实写前以最终后端身份和实际访问槽范围判断，而不是仅比较 ctx 对象或 UUID。
排除源/目标最终为同一物理槽、整库目标包含源槽、源整库与目标范围重叠；候选端点按实际地址去重。
不能禁止所有同根交易：同根 A→B 正是合法场景。无法证明不重叠时拒绝该候选；
递归环检测和现有数量内核均不能替代这项地址检查。

### 5.2 熔炉、耕地、酿造等邻槽功能

熔炉需要输入 / 燃料 / 输出相邻槽，不是「只运行自身进度」的自包含设备。
建议这些功能复用同一边界定位能力，但**各域明确哪些方向允许穿透**：

- 取输入/燃料仍保留有效材料与活物品隔离；边界不是准入豁免。
- 完成配方后的消费/产出仍沿原域操作单元、顺序与部分交付规则。
- 多候选边接入若不能表达原域“一槽一份”语义，先要求精确端口，不能悄悄批量消费。
- 交互目标的组件修改须先提交真实目标，再按原域协议结算源；回滚库存不能自动回滚世界副作用。

### 5.3 红石：读取远端出边，接收节点自行计算

内部封装连接与普通世界面输入不是同一来源。建议明确区分：

| 来源 | 信息 | 接收语义 |
|---|---|---|
| 本容器邻槽 | 当前容器红石方向性边 | 沿现有本地规则 |
| 封装端口邻槽 | 上拍对应方向出边 + 接收所需元件语义描述 | 按目标节点自身规则处理，并保留封装延迟 |
| 普通世界面输入 | 既有 `faceInput` | 保留现行定向元件准入，不让粉自动接收所有世界输入 |

A 右边界输出 12 到 B 左边界：交换层交付 12；若 B 是粉，由粉节点计算为 11。
铜无损、切铜分轴、中继器刷新、比较器主输入/侧输入等规则仍由红石域定义，交换层不统一再减一次。
需要元件连接判据时输出只携带该判据需要的描述，不把整箱 ItemStack 树复制进边界包。

父层本体槽需表现为**可发出四向信号的封装端口**：红石快照/传播类型要有显式扩展接线，
不能靠不存在于红石 mask 的潜影箱功能写一份数据就宣称父层已会传播。
最小落点由红石域接入边界契约、认领端口状态；容器核心不 import 红石实现。

引脚只指朝外的边。9×3 有 24 个方向性边界端口，但只有 20 个不同的边界槽；
角槽有两个独立方向，不能按一个 slot→signal 覆盖。

### 5.4 侦测器、比较器与其它只读功能

- 内部侦测器观察普通邻槽，沿现有公开状态接口；候选跨边精确观察只读取连接目标的公开状态。
- **父层侦测器观察潜影箱本体，不观察全部内含组件。** 建议本体公开活化身份与结算后的四向端口输出；
  不公开内部计时、缓存历史与每拍组件树，避免里面烧一件东西导致外面每拍脉冲。
- 父层活比较器与原版世界比较器的内容充满度 / 特殊检测按各自契约接入；不能自动读取深层所有库存。
- 多路目标如何观察/比较需原域另定；无法表达时只读本体，不新增「整棵树变化即事件」机制。

### 5.5 流体：先封闭水盆，跨边界供流作为明确例外候选

**现行约束**：[D-fluid-11](../decisions.md) / [活流体 §0](../tech/living-fluid-tech.md)
规定「物品过境，水不过境」。第一版每箱流体独立运行，跨箱资产搬运仍走既有载体/传输玩法。
本文的边界提案不默默改这一条。

若以后希望芯片水路贯通，应单独定案「封装连接例外」，并让流体域拥有以下语义：

1. 边界输入携带流体类型、上游实际流格 level、方向与可信供给信息，不只是一整数。
2. 接收目标层与实际层都承认边界供给；仍用原流体节拍 / 到达时间 / 阻挡 / 反应算法推进。
3. 跨边不是新可汲取的源；不能从一个 flow 包生成永久容器资产。
4. 源消失、接线断开后停止供给；两箱互相引用旧流格不能组成永续“假水源”。
   若引入源 UUID/供给代次或可验证来源链，须先证明当前目标层不足以解决，再选择最小扩展。
5. 水流推动过界仍需沿物理移动的原域规则与真实数量内核，不照抄漏斗 STANDARD 策略。

早期 `setFlowLevel(aLevel+1)` 没有兑现上述语义，当前也没有这个可直接调用的方法。
因此保留供流目标，但不把它当成“小改一行就已解决”。

### 5.6 应力、电力和远程路由

候选默认：**内部账本独立**，不是靠信号端口把所有网络合并。

- 应力在内部按流体力场计算；若多个内箱都向同一个世界接口输出，须先定义聚合、方向抵消与
  去重提交。不能让多个 `ctx` 对同一目标最后写者获胜，也不直接把子账本抄进父账本。
- 电力保留内部铜网络 / 相位 / 储能账本。边界传红石不等于共享相位或共享灯中电量。
  需要跨箱输电时，先定义资产端口与结算，不拿“读取一个强度”冒充能量转移。
- 末影箱路由身份、玩家绑定与全局频道沿原域规则；不因为嵌套自动创建新的频道命名空间。
  物品形态可用视图登记沿 `ItemFormLiveViews`，但 TTL 视图不是操作权限或持久库存真身。

### 5.7 工具、信标、TNT、地图等世界行为

物品内部仍有两个概念：**内部容器身份**与**最外真实宿主锚点**。
沿 `ContainerAnchor` / `getHostAnchor` 传递真实参考物，不在子箱内发明虚拟世界坐标。
各功能自己选中心/眼睛/下方，沿现行玩法开关与无锚点降级；嵌套不自动开启随身加强。

若第一层物品 ctx 的 `getAnchor()` 为 null，更深层不能只重复传这个 null；应传已确认的真实宿主
信息，同时保留「使用继承锚点须由功能显式选择」的约束。
TNT 爆炸消费归它所在内部库存，世界爆炸中心归真实锚点；无锚点行为沿 TNT 主域，不复制机制。
工具 / 女仆 / 信标的可视化还需要区别同一宿主上的多个嵌套实例，单个 hostSlot 不足时用可重建位置链，
不能将位置链当持久容器 ID。

活塞等结构位移暂不默认穿透：跨边位移要定义整栈、连推链、边界多候选与同拍旧信息作废，
不能由漏斗已能传货推出所有位移免费支持。

## 6. 世界中的潜影盒：先复用原版宿主

### 6.1 放置态只有一个权威库存与一个驱动点

优先保留原版潜影盒的颜色、方块外观与开合；**活化态实际库存仍归 UUID 库，不再以原版 BE 列表作
第二份真身**。是否能沿原版 BE 的扩展/能力入口提供同一 handler，须先验证，不能承诺零改动。

- 活化放置/拾取只迁移本体身份、配置与所在关系，库存仍在同一 UUID 条目；不每次复制 27 槽物品。
- GUI、方块 ItemHandler、漏斗自动化、比较器等必须访问同一权威库存；不能让菜单读外置库、管道读空 BE。
- 活化标记、UUID 与端口映射状态必须接到实际保存/放置/掉落路径；仅物品上有标记不等于 BE 知道。
- `CONTAINER` 与原版 BE 库存转换只承担普通形态和活化/取消活化边界，沿 §3.5 的成功交接后退役原则。
- 由既有容器发现/tick 入口处理已加载放置态。不能又在原版 BE ticker 里重复跑一拍活物品。
- GUI 打开不驱动运行；加载与宿主支持边界沿现行容器契约。

若原版 BE 的库存 API 无法在所有消费面表达外置真身，再以此具体缺口讨论局部适配或新 BE。
不能为保留原版类型而容忍两份可写库存，也不先以示例类名倒推新架构。

### 6.2 六种朝向的网格基准（候选约定）

定义 normal = 潜影盒 facing；内部上方向 top 与右方向 right 组成网格平面。
候选采用 `right = top × normal` 的右手基准（世界向量：东 +X、上 +Y、南 +Z）：

| facing / normal | 内部上 top | 内部右 right | 内部下 | 内部左 |
|---|---|---|---|---|
| UP | NORTH | EAST | SOUTH | WEST |
| DOWN | NORTH | WEST | SOUTH | EAST |
| NORTH | UP | WEST | DOWN | EAST |
| SOUTH | UP | EAST | DOWN | WEST |
| EAST | UP | NORTH | DOWN | SOUTH |
| WEST | UP | SOUTH | DOWN | NORTH |

这是**候选显示/接线约定**，须用六面 GUI 与相邻盒实测确认，不以旧稿 EAST 示例作兼容负担。
同 facing 邻盒沿网格四向逐通道对接；朝向不同暂不连接逐引脚内部总线，仍可走普通世界红石接口。

法线方向与其反面不属于四条网格边。建议第一版不为这两面新增数字信号端口；
既有原版比较器/物品能力如何工作仍保留，不能将「无新增端口」写成“这两面所有能力都禁用”。

### 6.3 世界红石输入 / 输出

先复用 [红石面信号机制](../tech/living-redstone-tech.md) 的查询与更新路径：

- 普通世界输入读取邻块对应面的信号，沿既有面输入准入，不给粉偷偷增加世界播种。
- 输出取本面向外引脚的聚合值，转换到世界信号范围，保留弱/强输出原有区别。
- 只有输出变化、连接变化或宿主撤销时才通知邻居；撤销也必须通知归零。
- 两个活潜影盒的逐引脚总线若已建立，就不再从同一相邻面叠加一份聚合世界输入，避免双路/反灌。
- 世界接口查询只读已发布快照，不在 `getSignal` 内递归运行设备。

网格基准旋转扩展、世界面方向反转、普通世界输入与内部端口来源区别需一起守卫。
物品/流体世界自动化仍沿能力面；多通道精确世界输入是另一个玩法，不由普通整库 handler 推导。

## 7. GUI：一个正式菜单，多个可拖动窗口

用户构想保留：右键打开工作台，窗口可拖动、层叠、多开，展开嵌套箱方便对照布线。
一个玩家只有一个菜单和 Screen，不妨碍一个 Screen 画多个面板、一个 Menu 提供多个容器的槽。

### 7.1 首选结构

```text
服务端：一个 AbstractContainerMenu
  ├ 玩家物品栏槽
  ├ 窗口 A 的 27 槽 → UUID=A 的权威库存 handler
  ├ 窗口 B 的 27 槽 → UUID=B 的权威库存 handler
  └ 唯一 carried + 原版 clicked/broadcastChanges

客户端：一个 Screen
  └ 窗口位置、层叠、焦点、命中 → 稳定菜单 slotId
```

不设计每窗口一份 carried，不先重写右键分堆、拖拽分配、双击收集；Shift 快移目标由本菜单明确。
原版 Screen 的部分命中/拖拽函数有固定坐标和私有状态，复用范围须原型验证，不能承诺仅改渲染即可。

### 7.2 窗口映射与旧点击

建议同一工作台会话分配有上限的窗口槽块；本会话内一块绑定一个容器，关闭后不立即复用给另一个。
服务端核验绑定和可达性；客户端收到映射后才激活点击，未绑定 / 已关闭槽拒绝读写。
避免旧点击 slotId 被新窗口解释成另一个库存。

超过窗口预算时明确提示；另开工作台会话再重建，不靠动态删除菜单列表把所有后续槽号挪动。
若选择可复用槽块，必须新增可靠映射代次校验，不能指望原版 stateId 自动提供业务绑定防护。

### 7.3 身份不等于访问权限

打开窗口时，服务端从允许访问的根容器沿实际槽/UUID 关系验证目标：

- 目标当前确实存在、可打开、仍在访问范围内。
- 嵌套链满足预算、没有环；玩家不能仅提交知道的 UUID 就读任意库存。
- 每次点击与打开子窗口时重新校验关键绑定；移走、取消活化或根权限失效时关闭相关访问。
- 多人同时操作以真实最新槽值与原版菜单权威结算，不依据客户端库存预测执行资产收付。
- carried 在菜单关闭/失效时沿原版清理归还，不因关一个子窗口删除手持物品。

窗口布局、大小、层叠是客户端偏好；服务端记录的是允许访问的容器与槽映射。
窗口开着不等于容器应该继续 tick，二者保持独立。

### 7.4 接入现有交互与同步

自有窗口提供明确锚点，解决“猜哪件物品”，但不能删掉接入责任：

- `ContainerContexts.resolve(player, slot)` 必须按菜单槽块得到对应 ctx 和逻辑槽。
- `ContainerViewers` 必须支持同一菜单声明多个有效容器，不能只取 `handleOfMenu` 的单一 Handle。
- 两条容器数据同步轨仍只走唯一 viewer 入口，不为窗口各写一份判断。
- 内容通过正式菜单槽同步；流体层、运行态、引脚状态按容器身份和窗口槽映射分别路由。
- 活按钮、方向设置、Tooltip、地图等 GUI 交互沿既有规则，服务端重新解析目标。
- 自有菜单坐标包含窗口布局，不得被服务端列数学成容器的新网格；内部权威列数固定为 9。

父层未打开时不发送完整深层库存；按当前授权窗口发送。原版本体槽只同步 UUID 与必要配置，
外置内容需要独立窗口/Tooltip 请求与 S2C，不能假设原版父槽同步已经包含内容。
普通 `CONTAINER` 设备以及普通化导出仍有体积成本，沿 §3.4 验证。

## 8. 接入验收与真正待拍板的规则

### 8.1 运行能力族，不再维护逐功能复制表

| 能力族 | 验收重点 | 机制归属 |
|---|---|---|
| 自主计时 / 生产 | 关界面继续；固定边界不休眠；每拍推进一次 | 原功能 + 内部 processContext |
| 邻槽材料 / 产出 | 精确地址、方向、操作单元与隔离 | 边界定位 + 原域数量规则 |
| 容器设备存取 / 就地交互 | 读取副本后仍提交真实宿主；失败不假报交付 | 组件提交协议 + 原设备 accessor/交互 |
| 信号 | 出边、上拍输入、方向连接、角槽独立端口 | 红石域接入 |
| 只读公开状态 | 本体与深层内容区分；不观察每拍内部历史 | 原公开状态契约 |
| 流体 / 力场 | 独立容器资产、节拍、物理推力；不默认跨水 | 流体域 |
| 能量 / 网络 | 账本不自动合并、世界出口不重复或覆盖 | 应力 / 电力主域 |
| 世界动作 / 渲染 | 锚点继承选择、无锚点降级、多层实例区别 | 原功能 / 渲染主域 |
| 结构位移 | 连推与旧信息作废；不默认跨封装 | 活塞主域 |
| 远程路由 | 身份可寻址与操作资格分开 | 原路由主域 |

新增功能落在哪个能力族，就验证对应接缝；只有确实新增了一种不可表达能力时，才补共同契约。

### 8.2 嵌套 UUID 命名空间与复制

建议 UUID 标识内部容器实例，**不编码父 UUID / 父槽路径**；换外层宿主不改变内部身份。
同拍活视图、渲染位置链与窗口槽号都是定位关系，不能取代 UUID。

环检测用祖先 UUID 集合；同一实例本拍正常运行只能一次。混合活背包的去重/深度约束也需共同遵守。
重复 UUID 不一定是真环：外置库存下，两件物品携带同一 UUID 会共享内容，父库存还可能直接/间接
持有指向自己的引用。必须区分路径循环、重复引用与正式复制，不能只按物品对象判等。

**建议复制规则，但待定案**：正式复制生成新子树身份，不共享原实例运行账本；不以“重新生成 UUID”
为借口搬空库存或暗复制 SavedData 中的资产。流体等持久容器资产复制政策须独立明确。
检测到重复身份时不能默默最后写者覆盖：显式降级/提示，或在已授权复制路径完成身份重建。
创造模式、原版中键、放置克隆和第三方复制都需验证，不能只覆盖一个 GUI 按钮。

### 8.3 待拍板规则表（建议不是事实）

| 规则 | 本稿推荐 | 定案影响 |
|---|---|---|
| 跨尺度信号 | 输入广播、输出按朝外出边 max | 端口多路合一，不能再宣称全空间等价 |
| 父层货物候选 | 接收边轮转，按确认量部分交付 | 影响漏斗投料布局与公平性 |

| 边界衰减 | 交换不额外减，节点自行处理 | 替换旧“每次穿透统一 -1”假设 |
| 初次 / 断线信号 | 无可信上拍输出为 0，断线立即撤销资格 | 首拍行为与缓存生命周期 |
| 实际库存载体 | 参考活背包，UUID 外置库存，递归 CONTAINER 降为备选 | 新库存层、按需同步与普通化交接；不把现有容器级持久层误当库存库 |

| 应力 / 电力出口 | 账本独立；聚合出口另定 | 不承诺多子箱自动向同一世界接口相加 |
| 原版/活比较器检测 | 优先遵守直接容器内容口径，不递归总量 | 世界自动化与父层检测值 |
| 重启/卸载进度 | 依原域持久契约，不补算离线 tick | “随物品运行”不等于“所有进度永不丢” |
| 体积与工作量预算 | 先实测；超限可抢救，不静默截断 | 生长型组件与大规模封装的可支持边界 |
| 复制资产 | 新身份、不共享运行态；存量复制政策待定 | 存档资产与创造复制语义 |

## 9. 建议实施顺序与验收闸门

**本节是候选验证路线，不是已经批准的排期。** 每一阶段先证明接缝，再扩玩法，不靠“能看起来运行”验收。

| 阶段 | 最小交付 | 必须证明 |
|---|---|---|
| A 内部容器 | 潜影箱功能、UUID库存/标准handler、单层运行与普通化交接 | 内容独立真身与标脏；首次身份真实提交；卸载不丢；交接失败不清库存 |
| B 同级库存边界 | 两箱普通精确货槽 + 普通父槽连接 | B[9] 精确落槽；目标满/拒写/回滚不复制；兄弟箱更新不覆盖 |
| C 信号端口 | 父层本体端口类型、上拍快照、逐引脚接线 | A/B处理顺序无关；粉只衰减一次；中继器一次计时；断线归零 |
| D 多窗口 | 一个菜单、两个窗口、子窗口导航 | 原版 carried/分堆；遮挡不命中；旧slot映射被拒；多viewer正确 |
| E 混合嵌套 | 共用深度预算、环/重复身份、真实锚点 | 每实例一次推进；深层写回与接线失效；不是各给四层 |
| F 放置态 | 原版潜影盒保存/放置/掉落、旋转、世界红石桥接 | 唯一权威库存/驱动点；六向映射；破坏撤销；普通盒行为不变 |
| G 特殊能力 | 按 §8.1 接入存储设备、就地交互、世界输出 | 骨粉/活箱子副本真实提交；应力多出口与资产账本规则成立 |
| H 规模与可视化 | 嵌套树压测、引脚 Tooltip/命名、优化 | 实际大小与耗时可复算；优化不让自主设备停摆 |

### 9.1 规则 → 验证场景

以下是计划的守卫场景，不表示对应测试已经存在：

| 规则 | 新守卫 / 游戏内场景 |
|---|---|
| 真库存提交 | 同UUID多视图立即互见；读副本后组件正式提交；no-op/拒写不交付；本体身份仍须真实父槽提交 |
| 持久与交接 | 空记录/丢失记录区别；保存重载；离线不清库存；活化/普通化失败保留单一真身；放置/拾取不复制库存 |
| 兄弟更新不覆盖 | A→B后A继续运行；B拒写后只恢复A未交付余量，保留其它槽更新；深层B变化不重写A本体 |
| 复制与退役 | 同UUID重复引用可观测；不复制UUID冒充新库；取消/销毁后旧handler不能继续写或重建；普通化含活子箱的准入 |
| 精确跨边搬货 | A[17]→B[9]；B[9]满且B[0]空仍不得重定向；目标拒写/源扣减失败总量核验 |
| 交易自环 | 不同ctx同物理槽、整库目标包含源、多候选重复端点全部拒绝；同根不重叠A→B仍允许 |
| 跨尺度不复制 | 三内部漏斗竞争一父槽；父层投料多个候选，总交付≤一次预算 |
| 接线几何 | 父容器行尾/行首、末行不足、上下九通道、左右三通道、角槽四向区别 |
| 一拍一次 | 中继器/熔炉/流体计时；边界变化不重跑；同UUID重复到达不重复推进 |
| 冻结信号 | 固定库存下AB/BA顺序；三箱链每连接一拍；首次连接、拆线、移动、卸载恢复 |
| 领域规则不偷换 | 铜/粉/切铜/中继器连接；普通世界输入仍不播种粉；水不过境 |
| 深度与身份 | 潜影箱/活背包混合链、树形四层、路径循环、创造复制、多副本降级 |
| GUI安全 | 一carried、两窗口；关闭/重开旧点击；根移走/距离失效；两个玩家并发 |
| 世界桥接 | 六向放置/掉落；关闭GUI仍运行；一个物品/BE只有一份库存；销毁后输出清零 |
| 生命周期 | 移入另箱保持内部身份；取消本箱不取消子箱；持久数据按主域恢复 |
| 体积与性能 | 多分支嵌套树、附魔/书本/长组件、生长超过插入时大小、超限仍能取出救援 |
| 原域交互 | 活箱子存取、骨粉目标副本、流体倒汲、方向设置、Tooltip与活按钮解析同一ctx |

### 9.2 文档与实现同步

实施前定案 §8.3 中该阶段实际涉及的规则，再补对应 tech §0 / 契约与决策留痕。

## 10. 早期稿的纠偏与保留理由

此处保留影响后续选择的旧判断，不重复整份历史伪代码：

| 早期判断 | 复核 / 修正 | 对设计的约束 |
|---|---|---|
| 必须建全局扁平槽视图再跑所有系统 | 局部 ctx + 跨容器地址可表达直接接线，不需要改各领域槽号为 long | 不扁平化不等于不扩邻接入口 |
| 局部演化是细胞自动机，所以全部功能自动适用 | 功能含生产、交易、世界动作与网络账本；共同容器能力可复用，业务不能由类比推导 | 保留功能封装，不发明统一业务演化器 |
| 4层=4次，性能不随嵌套增长 | 仅单链如此，树形遍历总量仍随分支数增长 | 按真实访问量压测，不写不可复算性能保证 |
| 边界不变就跳过内部tick | 内部可自主计时、生产、振荡、蔓延 | 不用静态输入作整箱休眠充分条件 |
| 原版跨区块红石固定1tick延迟 | 本地合并源码中粉邻居更新与通知队列不支持该前提 | 保留封装延迟作为设计选择，不冒充原版事实 |
| 交换后局部再次演化 | 整拍入口会重复推进；现有processed守卫也不是纯重算接口 | 先用上拍/本拍缓冲，不重跑整拍 |
| 三通道BoundaryExchanger足以兼容所有功能 | 统一地址与业务分工更稳定；熔炉、观察、位移等不止三方法 | 定位契约不 import 各领域，实现方保留业务规则 |
| 边界穿透统一-1 | 粉已按节点衰减，铜等规则不同 | 交换出边，避免双重衰减 |
| setFlowLevel(aLevel+1)就解决供流 | 当前没有该API，实际层/目标层、来源撤销及D-fluid-11都未解决 | 初版不跨水，供流例外另定 |
| 修改组件+同步整个外箱就一致 | 读取可为副本；同步不能证明真实宿主提交，兄弟副本会覆盖 | 必须现取内容、沿正式入口确认写回 |
| 优先递归CONTAINER，库存外置只作备选 | 参考活背包的UUID内容库与标准handler，深层模块独立提交更符合功能封装 | UUID外置改为主提案；原版交接、同步、复制与清理代价须同时落实 |
| 多窗口必须重写拖拽，隐藏菜单只是折中 | 一个正式菜单可承载多槽组，Screen管理窗口；原版点击和同步可优先复用 | 原型证明命中与动态映射，别先重写库存协议 |
| 自建GUI消灭菜单/viewer问题 | 消灭的是反推物品实例，多个子容器仍须唯一槽所属与viewer匹配 | 不绕开已有交互与同步唯一入口 |
| 世界桥接必需新BlockEntity | 原版潜影盒与容器世界桥接已有对应物 | 先追保存/能力/事件入口，再按具体缺口选择注入或新类型 |

原版对齐查证入口：`RedStoneWireBlock` 的邻居更新、`CollectingNeighborUpdater` 的当前队列处理、
`ShulkerBoxSlot.mayPlace`、`ShulkerBoxBlockEntity.canPlaceItemThroughFace`、
`BaseContainerBlockEntity.applyImplicitComponents/collectImplicitComponents`、
`AbstractContainerMenu.addSlot/clicked/broadcastChanges`。

**准入注意**：原版槽检查栈级 `canFitInsideContainerItems`；BE 自动化入口还显式排除
`ShulkerBoxBlock`。仅改其中一处不能保证套娃全通。必须先查 NeoForge 官方栈级接口与事件；
确实缺口才做局部 Mixin，且只作用于本稿定案的活化例外，不放宽所有普通潜影盒。

红电信息时代仍可把它作为 ALU / 寄存器 / 控制器的封装地基，见
[红电系统](../system-design/红电系统.md)。依赖是单向的：红电使用封装能力；
潜影箱不为了某个电路或当前活物品名单改变自己的容器身份与库存规则。
