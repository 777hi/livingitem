### 0.2 总体判断

工程基础明显强于个人 alpha 模组平均线：测试是真断言且覆盖 bug 史；文档有 11 项机械核验；
架构有棘轮（层纪律 / mixin 前缀 / 容器键收敛）；近期 bug 修复都有根因分析。

主要风险不在代码风格，而在两处：

1. **服务端热路径没有故障隔离** —— 单个容器或第三方实体容器异常会让整个服务端 tick 抛出。
2. **质量门禁只在一台机器上生效** —— CI 绿不等于门禁绿；`doc_check` 的无 XML 分支可被跳过；
   `check_container_keys` 在主开发平台直接崩溃。

### 0.3 证据边界

| 结论类型 | 含义 | 本计划中的处理 |
|---|---|---|
| **已核实** | 读过代码 / 跑过工具 / 对照过原版源码 | 直接进批次 |

| **待拍板** | 涉及口径或取舍 | 见 §7，拍板后再动代码 |

## 2. 全程约束（每批都必须满足）

1. **一个批次 = 一个可独立回滚的提交**；批次内不夹带无关重构。
2. **行为修复必须有回归测试**；确实无法单测的（GUI 手势、区块缓存、客户端渲染）
   必须在 §6 实机清单里逐条勾掉。
3. **不引入新机制前先找对应物**（AGENTS「设计铁律」）：本文提到的 `FailureThrottle`
   是唯一的工具类新增，理由是"限频逻辑需要单测，且 living 层没有同类抽象"。
4. **异常隔离不得吞 `Error`**（OOM / 栈溢出必须照常炸）；只接 `RuntimeException`。
5. **回滚路径不得丢物品**：任何 `insertItem` 的返回值都必须被消费。
6. **字符串 / 键语义单一来源**：UUID 解析走 `ContainerKeys` / `ContainerUuids`，
   缓存键走 `ContainerIdentity.getCacheKey()`，不新增第三份实现。
7. **文档与测试计数同步**：每批结束跑 `./gradlew test` + 四个门禁；
   AGENTS 的「合计测试用例 N 个」按实测改。

### 批次 2：服务端 tick 异常隔离（1 天，优先）

**目标**：单个容器 / 第三方实体容器异常时，**跳过它、记录一次、继续其余容器与收尾**。

#### 2.1 新增限频报告器

`living/util/FailureThrottle.java`（唯一新增工具类）：

```java
public static void report(String key, RuntimeException e);
// 首次：ERROR + 完整栈；同 key 60s 内：计数抑制；每 5 分钟输出一次汇总（仍失败 key 数 + 抑制次数）
// 容量上限（如 256 key），满后淘汰最旧，避免隔离机制自己泄漏
```

仅服务端线程调用；测试需 `configure(windowMs, maxKeys)` / `reset()`。

#### 2.2 隔离入口

`ContainerLivingItemHandler` 增加：

```java
public static void processIsolated(TickableContainerContext ctx, Level level) {
    try {
        processContext(ctx, level);
    } catch (RuntimeException e) {
        FailureThrottle.report(keyOf(ctx), e);
    }
}
```

`keyOf(ctx)`：优先 `ctx.getContainerKey()`，为空时退化为 `entity_<uuid>` / 类名。

#### 2.3 三个调用点全部改走隔离

`LivingItem.java`：

- 玩家背包循环（`processContainer(player.getInventory(), ...)`）。
- 区块循环：在循环内包住 `processContainerAt(...)`，单容器失败不影响同区块其它容器。
- 实体循环：包住 `new ItemEntityContainerContext(...)` 与 `new EntityContainerContext(...)` 两条分支。

`EntityContainerContext.handlerOf` 的 throw **保留**（I-C7 不静默），由隔离层接住；
日志归为"白名单 / 能力注册面不一致"，按实体类型只报一次。

#### 2.4 测试

- `FailureThrottleTest`：同 key 抑制 / 不同 key 各报一次 / 超过窗口再报 / 容量上限。
- `ContainerTickIsolationTest`：假 context 在 `getSize()` 抛异常，断言
  `processIsolated` 不向外抛；再次调用仍不抛。

#### 2.5 文档

- `docs/system-design/living-item-infrastructure.md` 加"异常隔离策略"小节：
  隔离边界、日志口径、为什么只接 `RuntimeException`。
- changelog 一行；AGENTS 进展一行。

**验证**：单测；另可临时在 debug 容器 tick 里 `throw new RuntimeException()`，
实机确认服务端不崩、日志只出现一次、其余容器继续工作。

**风险 / 回滚**：异常被吞可能掩盖 bug。缓解：首次完整栈 + 抑制计数 + 5 分钟汇总；
若排查期需要"炸出来"，加系统属性 `living_item.debug.isolation=false` 关闭隔离（默认开）。

**完成判据**：单测全绿；实机注入异常后服务端存活、收尾逻辑仍执行。

### 批次 4：末影箱回滚 + 邻居 UUID（1 天）

**目标**：回滚路径不丢物品；路由条目的源身份指邻居而不是注册者。

#### 4.1 回滚链

`LivingEnderChestAccessor` 的 rollback 改为逐级消耗余量：

```java
ItemStack remainder = stack;
if (rollbackPos != null) {
    remainder = ItemHandlerHelper.insertItem(handler, remainder, false);
    if (!remainder.isEmpty()) Block.popResource(level, rollbackPos, remainder);
} else if (rollbackContainerKey 是 cuuid_) {
    IItemHandler live = ItemFormLiveViews.find(uuid);
    if (live != null) remainder = live.insertItem(rollbackSlot, remainder, false);
    // live 不存在 ⇒ 源已消失：ERROR 记录后落地（不要静默）
} else if (玩家容器) {
    // 末影箱 / 玩家实体 handler，余量回玩家背包或 player.drop
}
```

要点：

- 每次 `insertItem` 都看返回值；
- 最终仍有余量 ⇒ `Block.popResource` / `player.drop` + WARN 记数量；
- 只有"连落地条件都不存在"才 ERROR，绝不静默丢。

#### 4.2 邻居源 UUID

`EnderRouteManager.registerRouteFromNeighbor`：

```java
UUID sourceUuid = ContainerUuids.ofHost(level.getBlockEntity(neighborPos));
```

用 `sourceUuid` 替换 `containerCtx.getContainerUuid()`；`null` 对应"该容器没有身份"的契约。

#### 4.3 测试

- `EnderRouteExtractTest` 加一例：假 handler 在 `simulate=true` 接受、真实插入拒绝，
  断言余量回到 `ItemFormLiveViews` 注册的源夹具。
- `EnderChannelRegistryDimTest` 加一例：邻居条目带邻居 UUID，源换形态时被清；
  注册者换形态不影响该条目。

#### 4.4 文档

`docs/tech/living-ender-chest-tech.md` §0 加两条规则：

- 回滚不得丢物品（余量必须落地）；
- 路由条目的 `sourceContainerUuid` 记**源容器**，不是注册者。

**完成判据**：两个测试转红→转绿；全量测试绿。

### 批次 6：容器缓存生命周期（1 天）

**目标**：区块卸载后，槽位追踪 / 容器级数据 / 运行时数据三张表都能回收。

#### 6.1 补齐位置索引

`POS_TO_CACHE_KEY` 目前只在 `entry(ctx)` 创建容器级数据时写入。让
`trackLivingSlots` 成功后也调用一次 `indexPositions(ctx, cacheKey)`（先 `containsKey` 判重），
使 `removeDataByPos` 能覆盖"只有槽位追踪、没有容器级数据"的容器。

#### 6.2 卸载队列（不在事件里直接删表）

`ChunkEvent.Unload` 可能不在主线程，因此在 `ContainerLivingItemHandler` 加：

```java
private static final Queue<UnloadRecord> PENDING_UNLOADS = new ConcurrentLinkedQueue<>();
// UnloadRecord(ResourceKey<Level> dim, BlockPos pos)

public static void enqueueUnload(ResourceKey<Level> dim, BlockPos pos);
public static void flushPendingUnloads(MinecraftServer server); // 主线程，tick 开头
```

`LivingItem.onChunkUnload` 只入队；`onServerTick` 在处理容器前
`flushPendingUnloads(server)`：解析 `server.getLevel(dim)` 后逐个
`removeDataByPos(level, pos)`。`removeDataByKey` 已同时清 `LIVING_SLOT_ITEMS`
并登记运行时作废，三项一起收口。

#### 6.3 测试

- 假 context（带 positions）→ `trackLivingSlots` → `removeDataByPos` →
  断言 `LIVING_SLOT_ITEMS`、`CONTAINER_DATA` 清空且运行时作废入队。
- 卸载队列：入队两条不同维度 → flush → 只处理能解析到 level 的条目。

**风险 / 回滚**：卸载队列可能与区块重载竞态。队列在下个 tick 统一处理，
若期间同位置重载，`removeDataByPos` 会先删后建 —— 与现有"拆箱再放回"路径同构；
如实测有异常，退化为"只清 `LIVING_SLOT_ITEMS` + 运行时缓存，不动 `CONTAINER_DATA`"。

## 7. 待拍板问题

1. **异常隔离边界**：是否接受"所有容器 tick 都隔离"？
   备选是只隔离第三方实体容器，自家方块容器仍让异常炸出来（更響亮，但第三方容器 bug 会崩服）。
   倾向：全隔离 + 首次完整栈 + 汇总日志；开发期可用系统属性关闭。
2. **战利品箱策略**：保留区块缓存（简单、正确）vs 开箱事件驱动 rescan（省扫描）。
   倾向：先保留缓存，按实测压力再决定。
3. **水车 `@Redirect`**：删除 / 换 MixinExtras / 保留。
   倾向：先验证删除；若光照仍需处理，把光照逻辑移进 `RotatingWaterWheelModel`。
4. **性能目标**：是否仍按"上万容器"投入批次 7？
   倾向：发版前只做 7a（低风险），7b/7c 视实测。
5. **隔离日志去处**：是否加一条 debug 指令查询"当前被抑制的失败 key"？
   倾向：先不加，`FailureThrottle` 的 5 分钟汇总足够；确有需要再补。
