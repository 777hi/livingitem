### 0.2 总体判断

工程基础明显强于个人 alpha 模组平均线：测试是真断言且覆盖 bug 史；文档有 11 项机械核验；
架构有棘轮（层纪律 / mixin 前缀 / 容器键收敛）；近期 bug 修复都有根因分析。

主要风险不在代码风格，而在两处：

1. **服务端热路径没有故障隔离** —— 单个容器或第三方实体容器异常会让整个服务端 tick 抛出。
2. **质量门禁只在一台机器上生效** —— CI 绿不等于门禁绿；`doc_check` 的无 XML 分支可被跳过；
   `check_container_keys` 在主开发平台直接崩溃。

| 结论类型 | 含义 | 本计划中的处理 |

| **已核实** | 读过代码 / 跑过工具 / 对照过原版源码 | 直接进批次 |

## 2. 全程约束（每批都必须满足）

1. **一个批次 = 一个可独立回滚的提交**；批次内不夹带无关重构。
2. **行为修复必须有回归测试**；确实无法单测的（GUI 手势、区块缓存、客户端渲染）
   必须在 §6 实机清单里逐条勾掉。
3. **不引入新机制前先找对应物**（AGENTS「设计铁律」）：本文提到的 `FailureThrottle`
   是唯一的工具类新增，理由是"限频逻辑需要单测，且 living 层没有同类抽象"。
4. **异常隔离不得吞 `Error`**（OOM / 栈溢出必须照常炸）；只接 `RuntimeException`。
5. **回滚路径不得丢物品**：任何 `insertItem` 的返回值都必须被消费。
6. **字符串 / 键语义单一来源**：UUID 解析走 `ContainerKeys` / `ContainerUuids`，
   缓存键走 `ContainerIdentity.getCacheKey()`，不新增第三份实现。
7. **测试全绿**：每批结束跑 `./gradlew test --rerun` + 四个门禁；
   全量快照由 hook 自动记录，条数不进文档。

### 批次 2：服务端 tick 异常隔离（1 天，优先）

**目标**：单个容器 / 第三方实体容器异常时，**跳过它、记录一次、继续其余容器与收尾**。

#### 2.1 新增限频报告器

`living/util/FailureThrottle.java`（唯一新增工具类）：

```java
public static void report(String key, RuntimeException e);
// 首次：ERROR + 完整栈；同 key 60s 内：计数抑制；每 5 分钟输出一次汇总（仍失败 key 数 + 抑制次数）
// 容量上限（如 256 key），满后淘汰最旧，避免隔离机制自己泄漏
```

仅服务端线程调用；测试需 `configure(windowMs, maxKeys)` / `reset()`。

#### 2.2 隔离入口

`ContainerLivingItemHandler` 增加：

```java
public static void processIsolated(TickableContainerContext ctx, Level level) {
    try {
        processContext(ctx, level);
    } catch (RuntimeException e) {
        FailureThrottle.report(keyOf(ctx), e);
    }
}
```

`keyOf(ctx)`：优先 `ctx.getContainerKey()`，为空时退化为 `entity_<uuid>` / 类名。

#### 2.3 三个调用点全部改走隔离

`LivingItem.java`：

- 玩家背包循环（`processContainer(player.getInventory(), ...)`）。
- 区块循环：在循环内包住 `processContainerAt(...)`，单容器失败不影响同区块其它容器。
- 实体循环：包住 `new ItemEntityContainerContext(...)` 与 `new EntityContainerContext(...)` 两条分支。

`EntityContainerContext.handlerOf` 的 throw **保留**（I-C7 不静默），由隔离层接住；
日志归为"白名单 / 能力注册面不一致"，按实体类型只报一次。

#### 2.4 测试

- `FailureThrottleTest`：同 key 抑制 / 不同 key 各报一次 / 超过窗口再报 / 容量上限。
- `ContainerTickIsolationTest`：假 context 在 `getSize()` 抛异常，断言
  `processIsolated` 不向外抛；再次调用仍不抛。

#### 2.5 文档

- `docs/system-design/living-item-infrastructure.md` 加"异常隔离策略"小节：
  隔离边界、日志口径、为什么只接 `RuntimeException`。
- changelog 一行。

**验证**：单测；另可临时在 debug 容器 tick 里 `throw new RuntimeException()`，
实机确认服务端不崩、日志只出现一次、其余容器继续工作。

**风险 / 回滚**：异常被吞可能掩盖 bug。缓解：首次完整栈 + 抑制计数 + 5 分钟汇总；
若排查期需要"炸出来"，加系统属性 `living_item.debug.isolation=false` 关闭隔离（默认开）。

**完成判据**：单测全绿；实机注入异常后服务端存活、收尾逻辑仍执行。

### 批次 3：GUI 活箱子存放分支（2026-11-01 已实现，待实机 M-1/M-2）

**目标**：一次手势只产生一个效果；释放阶段不再补一次原版点击。**复查确认两条前提都成立**：① `tryInteract` 成功后只 `setReturnValue(true)` 没有 `return` ⇒ 落到存放分支叠两个效果；② 存放分支没置 `skipNextRelease` ⇒ 释放阶段被原版再执行一次。

#### 3.1 抽出可测判定 ✅

新建 `client/input/LivingChestDepositHelper.java`（与 `client/input/GuiInteractionHelper` 同目录同形态，不是新机制）。**与计划签名的偏差**：多加一个 `button` 参数 —— 原签名把左键判断留在调用方，等于「手势门禁」仍复制两份，收口不彻底。

```java
static boolean shouldDeposit(@Nullable Slot slot, boolean shiftDown,
                             boolean tabActive, boolean bookVisible);
static void sendDeposit(Slot slot, ItemStack stack, RegistryAccess registries);
```

把两处重复的 NBT 序列化 + `LivingChestAccessPacket` 发包收进来。

#### 3.2 改两个 mixin ✅（两条都做了，另加一处计划外的修正）

`AbstractContainerScreenMixin`：

- `tryInteract` 成功后立即 `return;`（当前会继续落到存放分支）。
- 存放分支成功后置 `this.skipNextRelease = true;` 再 `return;`。

`InventoryScreenMixin`：同样处理，`skipNextRelease` 走已有的
`AbstractContainerScreenAccessor.living_item$setSkipNextRelease(true)`。

#### 3.3 测试 ✅（`LivingChestDepositHelperTest`，计划 4 例 → 实做 7 例）
多出的是 `null` 槽位、非左键、未按 Shift 三条早退。踩到的坑记下来：**GLFW 鼠标键是 0 基的**（`GLFW_MOUSE_BUTTON_1 == 0`），测试第一版写 `1/2` ⇒ 正例假失败（生产代码用常量所以没受影响）。

| 场景 | 期望 |
|---|---|
| 空槽 | false |
| 槽内是活箱子 | false |
| 页签未激活 / 配方书不可见 | false |
| 普通物品 + 页签激活 + 书可见 | true |

#### 3.4 实机清单（必须做）

- 背包界面、箱子界面各 4 种组合：空手 / 手持物品 × 蹲下点击。
- 断言：只发生一次存放；释放鼠标不再拾取 / 放置；客户端与服务端槽位一致。
- 顺带验证：`tryInteract` 命中的交互（如活锄）不再叠加存放包。

**风险 / 回滚**：低。若实机发现 `skipNextRelease` 导致正常点击被吞，
按 `GuiInteractionHelper` 现有路径的同样逻辑排查（它已验证过该字段）。

### 批次 4：末影箱回滚 + 邻居 UUID（1 天）

**目标**：回滚路径不丢物品；路由条目的源身份指邻居而不是注册者。

#### 4.1 回滚链

`LivingEnderChestAccessor` 的 rollback 改为逐级消耗余量：

```java
ItemStack remainder = stack;
if (rollbackPos != null) {
    remainder = ItemHandlerHelper.insertItem(handler, remainder, false);
    if (!remainder.isEmpty()) Block.popResource(level, rollbackPos, remainder);
} else if (rollbackContainerKey 是 cuuid_) {
    IItemHandler live = ItemFormLiveViews.find(uuid);
    if (live != null) remainder = live.insertItem(rollbackSlot, remainder, false);
    // live 不存在 ⇒ 源已消失：ERROR 记录后落地（不要静默）
} else if (玩家容器) {
    // 末影箱 / 玩家实体 handler，余量回玩家背包或 player.drop
}
```

要点：

- 每次 `insertItem` 都看返回值；
- 最终仍有余量 ⇒ `Block.popResource` / `player.drop` + WARN 记数量；
- 只有"连落地条件都不存在"才 ERROR，绝不静默丢。

#### 4.2 邻居源 UUID

`EnderRouteManager.registerRouteFromNeighbor`：

```java
UUID sourceUuid = ContainerUuids.ofHost(level.getBlockEntity(neighborPos));
```

用 `sourceUuid` 替换 `containerCtx.getContainerUuid()`；`null` 对应"该容器没有身份"的契约。

#### 4.3 测试

- `EnderRouteExtractTest` 加一例：假 handler 在 `simulate=true` 接受、真实插入拒绝，
  断言余量回到 `ItemFormLiveViews` 注册的源夹具。
- `EnderChannelRegistryDimTest` 加一例：邻居条目带邻居 UUID，源换形态时被清；
  注册者换形态不影响该条目。

#### 4.4 文档

`docs/tech/living-ender-chest-tech.md` §0 加两条规则：

- 回滚不得丢物品（余量必须落地）；
- 路由条目的 `sourceContainerUuid` 记**源容器**，不是注册者。

**完成判据**：两个测试转红→转绿；全量测试绿。

### 批次 6：容器缓存生命周期（1 天）

**目标**：槽位追踪（`LIVING_SLOT_ITEMS`）与运行时缓存（`ContainerRuntimeCache`）在**所有容器形态**下都能回收；
容器级数据（`CONTAINER_DATA`）维持现有 TTL 路径。

#### 6.0 结论（2026-11-01 用户拍板）

**运行时数据是瞬态、可重建、可随时丢弃的。** 需要跨区块卸载 / 重启保留的数据**不得**放在
`ContainerRuntimeCache`，那类需求走 `ContainerDataKey` / DataComponent / 宿主附件。
⇒ 本批**不做落盘**，也不讨论“保留多久”；回收可以激进。

#### 6.1 现状缺口（源码核对，2026-11-01）

- `CONTAINER_DATA` 有 TTL（`cleanupStaleData` 每 1200 次容器处理扫一遍，120s 未更新即回收），
  `POS_TO_CACHE_KEY` 跟随回收；这两张不是永久泄漏。
- `LIVING_SLOT_ITEMS` / `ContainerRuntimeCache` 只依赖“容器继续 tick”清理：
  容器再 tick 且已空 / 玩家破坏（位置索引命中）/ 物品形态取消活化 / 停服。
- 因此以下形态与场景全部漏清：
  - 区块卸载（方块容器；卸载事件不清数据）；
  - 玩家下线（`player_<uuid>` / `player_<uuid>_ender_chest`）；
  - 实体卸载 / 死亡 / 移除（`entity_<uuid>`）；
  - 物品形态容器被销毁 / 丢失（`cuuid_<uuid>`；只有主动取消活化才清）；
  - 掉落物形态每次掉落生成新键 `item_entity_<uuid>`，拾取/消失后旧键残留；
  - 非玩家移除（活 TNT 爆炸、活塞、`/setblock`、结构生成）不触发 `BlockEvent.BreakEvent`。
- `POS_TO_CACHE_KEY` 只在 `entry(ctx)` 创建容器级数据时写入 ⇒ 只装活物品、没有红石/流体/电力的
  容器没有索引，**连玩家破坏也清不掉**。
- `ContainerRuntimeCache.removeSlot` 删空内层槽位后不删外层键 ⇒ 空壳残留。
- `ItemFormLiveViews#VIEWS` 是**惰性过期**：只在 `find()` 命中过期条目时才 `remove`。
  背包停止 tick **且再无人按该 UUID 取货** ⇒ 条目常驻到停服，且**强引用第三方 `IItemHandler`**
  （2026-11-01 A/B 复查发现；原 `shared-state.md` 误记为「每 tick 重建」）。

#### 6.2 设计（2026-11-01 已实现）

1. ✅ **`lastSeen` + 周期 sweep（主路径）**：新增 `LAST_SEEN`（`cacheKey → 盖章毫秒`），
   盖章点 = `trackLivingSlots` 首行（**每个进 `processContext` 的容器都盖**，含已无活物品的）；
   回收口 = `sweepUnseenContainers()` 由 L4 每 tick 调、内部 1 分钟节拍门控，
   过期键走 `removeDataByKey`（与「玩家破坏」同一条作废入口，不新建第二套清理路径）。
   阈值定 **5 分钟**（`UNSEEN_TTL_MS`），覆盖：区块卸载、玩家下线、实体消失、物品销毁、
   掉落物拾取、非玩家移除。
   > 口径修正：原判据写「时间/**游戏刻**」，实现取墙钟 `System.currentTimeMillis()` ——
   > 判的是「多久没被看到」，而游戏刻在区块卸载 / 维度差异下并不可比；且表是全服一张，
   > 逐维度比游戏刻会串。副作用：服务端卡顿时窗口被拉长，但数据本就瞬态可丢，无害。
2. ✅ **显式清理（立即路径，保留）**：破坏方块（位置索引命中）、物品形态取消活化 —— 未改。
3. ✅ **补位置索引**：`trackLivingSlots` 在**追踪条目首次出现**时调 `indexPositions(ctx, cacheKey)`。
   只在首现时建（稳态零成本），区块重载 / 清空再装入都会重建 ⇒ 不每 tick 重算位置。
   `ctx` 为 null（测试替身 / 无世界）时跳过索引，但仍盖章 ⇒ sweep 依然能兜底。
4. ✅ **修空壳**：`removeSlot` 删空内层 map 后一并删外层 `store` 键。
5. ~~**异步卸载只入队**~~ → **本项作废**（2026-11-01 更正，`D-container-21` → `D-container-22`）：
   `ChunkEvent.Unload` 实际在**服务器主线程**触发 —— `ChunkMap.scheduleUnload` 的
   `thenRunAsync(body, this.unloadQueue::add)` 中第二个参数是 **executor**（只是入队），
   body 由 `ChunkMap.tick → processUnloads`（`:517-519` `runnable.run()`）在主线程执行。
   ⇒ 两个卸载处理器**维持现状即可**，无需改造。运行时数据仍**不依赖**卸载事件（由 sweep 覆盖）。
   > 🔴 教训：`thenRunAsync(runnable, executor)` ≠ 「在异步池跑」，判据在**第二个参数的身份**。
6. ✅ **双箱：确认无需代码** —— 双箱两段坐标本来就映射到**同一个** `cacheKey`，
   `removeDataByKey` / sweep 天然按整键收 ⇒ 原计划里「保留另一半」的逻辑根本不用写。
   由 `ContainerCacheSweepTest.doubleChest_eitherHalfClearsWholeKey` 把这条钉住（防的是
   日后有人给两半起了不同键形）。
7. ✅ **实体 / 玩家 / 掉落物：不新加事件**，由同一个 sweep 覆盖（键空间相同，判据与键形无关）。
8. ✅ **新增同族缺口**（A/B 实验抓到的 `ItemFormLiveViews`）：`evictExpired(nowMs)` 并入同一节拍，
   不再依赖「有人查询」才回收。

#### 6.3 测试（已补，共 11 项：`ContainerCacheSweepTest` 10 + `ItemFormLiveViewsTest` 1）

- ✅ `ContainerCacheSweepTest`：sweep 过期键被清（四张表 + 整容器作废，8 项断言）/
  阈值内保留 / 持续 tick 不被收 / 只装活物品的容器破坏即清 / 双箱任一半 /
  无 ctx 也盖章也能收 / `removeSlot` 最后一个槽位删外层键 / 删中间槽位不误删外层键；
- ✅ `ItemFormLiveViewsTest.evictExpired_removesStaleEntriesWithoutAnyQuery`（TTL 内不淘汰、
  越界两条都淘汰）；
- ⚠️ **口径修正**：原计划要「方块 / 玩家 / 实体 / 掉落物**各一项**」。实现只覆盖
  方块形态 + 一个裸键（`bare_key`）—— 因为 sweep 判的是 `cacheKey` 的**出现与否**，
  与键形无关，四种形态的差异全在「谁给它盖章」，而那由 `trackLivingSlots` 统一承担。
  四类各写一条会是同一个断言抄四遍。真机上「下线 / 实体消失」是否真被收，仍需实机验证（M 项）。
- ~~卸载队列：事件只入队、不碰 tick 表~~（随 6.2-#5 作废；卸载路径已有 `ContainerChunkCacheChunkLoadTest` 覆盖）。

**风险 / 回滚**：sweep 阈值过短会让“走远再回来”的进度丢失（按 2026-11-01 口径可接受）；
过长则内存回收慢。阈值做成常量 `UNSEEN_TTL_MS`，实测再调。
**实机待验（新增 M 项）**：① 箱子装满活熔炉 → 走远 5 分钟以上 → 回来，进度归零但**不报错**；
② 玩家下线再上线，背包活物品不继承上一世的运行时状态；
③ `/livingitem debug cache` 末尾新增的「跨tick表 追踪容器/盖章键/位置索引/待作废」行，
观察 `LAST_SEEN` 规模是否稳定不涨（走远一圈再回来应回落，不单调上涨）。

> 另记录我复查时的一次**假阴性**：第一轮 grep 带 `head -12` 把输出截断了，

1. ✅ **配方书不可见页签吞点击**（真 bug，已修 2026-11-01）

   `isVisible() && !player.isSpectator()` 里（`RecipeBookComponent.java:327`），

   而标签按钮此时由 `render` TAIL 的 `isVisible` 守卫**画都没画** ⇒
   「点在一个看不见的位置、什么都没发生，原版那格还被短路」。
   修：HEAD 里先复刻同一条守卫（不另加判空，与原版写法一致），顺带删掉下面那处因此 redundant 的

   `CreateCompat.isLoaded()` 是缓存过的静态布尔（`living/compat/create/CreateCompat.java:15-17`），
   且短路顺序把廉价判据放在前面 ⇒ 每次物品渲染多出的成本是「一次静态读 + 两个比较」，
   不是可观测热点。**是否根本不需要这个 mixin** 仍是未验证的假设（
   `RotatingWaterWheelModel#applyTransform` 已做旋转，GUI 光照另有处理）⇒ 这需要**实机 A/B**
   才能定，不能靠读代码删掉。保持待办，实机项 = M-6。
3. ✅ **地图缩略图纹理未 release**（真 bug，已修 2026-11-01）
   2026-10-27 审查 P3-4 补的是 `onClientLogout(TEXTURE_CACHE::clear)` —— **登记了，但登记的是裸 clear**：
   `DynamicTexture` 本体由 `TextureManager.byPath` 持有并占着 GPU 资源，只有 `release`/`close` 才回收
   （判据：`TextureManager#release` 是 `byPath.remove` + `safeClose`；`#register` 也靠 `safeClose`
   淘汰同 location 的旧纹理 —— 本类 `isClosed()` 防的正是那条路径）。裸 clear 只是丢掉我们这边的引用。
   修：照齐同族里一直写对的 `LivingMapOverlay#releaseTextures`（逐个 `release(location)` 再 clear）。
   → `client/render/LivingMapIconDecorator#releaseTextures`
4. ➡️ **配方书每帧分配**（真问题，但属性能项 ⇒ 转批次 7 与 R-08 一起拍板）
   实测机理：`LivingChestRecipeTab#renderContents` 每帧调 `collectLivingChestItems()` ——
   扫 36 格背包 + 每个活箱子一次 `ItemContainerContents.copyInto(NonNullList<27>)` + `new ArrayList<>`
   + 搜索再建一个 list ⇒ 高帧率下每秒数千次栈复制；`accountLivingChestItems()` 走同一函数。
   不随手改的原因：任何缓存都要回答**失效条件**，而客户端没有背包变动事件；
   可选方案（按 client tick 记忆化 / 按容器 revision 记忆化 + 自研失效）都有行为可见性代价，
   属 R-08 那一族「先定性能目标再动」的决定。→ 见批次 7
