## §0 背景：信标撞破的两个框架假设

| 假设 | 出处 | 被谁撞破 | 后果 |
|---|---|---|---|
| **A「脏 = 被调用」**（`update` 无条件标脏） | `ContainerRuntimeCache` | 信标（第一个**遥测准静态**的域：等级/柱高只在金字塔变化时动） | 有活物品的容器恒脏 ⇒ 每 tick 全量包 |
| **B「客户端任意时刻只有一个容器」**（单槽缓存） | `LivingItemClientCache` | 末影箱包（每 tick 直发主人、无 viewer 匹配） | 20 包/秒恒流冲掉当前 GUI 的快照 ⇒ 容器里 tooltip 全丢 |

两天的修复（viewer 门控、多枚一条、跨维度丢数据、喂锭列宽分叉……）大多是在给这两个假设打补丁。
本文提出三个更根本的方向，并评估**现有 16 个活物品域里谁可以直接用上**。

## §1 提案 A：纯函数型遥测的「客户端推导」通道 ⭐最高优先级

### 现状

信标的遥测（等级 / 9 列柱高 / 列存在性 / 再生档）是**「容器内容 + 列宽」的纯函数**。
而**能显示 tooltip 的时刻，客户端手里一定已经有这些内容**：

| 场景 | 客户端有内容？ | 依据 |
|---|---|---|
| 悬停背包 / 手持 | ✅ | 背包客户端全知 |
| 悬停世界容器 GUI | ✅ | 菜单槽位已同步 |
| 悬停末影箱 GUI | ✅ | 菜单同样同步（`SimpleContainer` 替身由菜单填充） |
| 本机光束门控（亮不亮） | ✅ | **现在就是客户端本地算的**（`LivingBeamRenderer.renderPlayerHost`） |

⇒ 整套「服务端算 → 打脏 → 发包 → 客户端缓存 → 悬停取数」对这个域是**多余机制**。

### 方案

框架提供一条显式的「客户端可推导」契约（二选一，落地时再定形态）：

- **方案 A1（轻）**：域**不发布遥测**，自己在 `addToTooltip` / `GatherComponents` 里从
  `mc.player.containerMenu` 的槽位调自己的纯函数；
  - 代价：域要自己处理「菜单为空 / 槽位对不上」的兜底，重复一小段定位逻辑；
- **方案 A2（推荐）**：框架加 `ClientDerivableSegment` 接口——
  ```java
  interface ClientDerivable { RuntimeSegments derive(AbstractContainerMenu menu, Slot hovered); }
  ```
  框架在 tooltip 路径上：**先问客户端推导 → 拿不到再回退推流**。
  - 域只写纯函数，零缓存、零路由、零包；
  - 未开 GUI 的场景（光束、buff）继续走现有的宿主包（那是另一条链路）。

### 收益

- 消灭这个域**全部**的缓存竞态类 bug（末影箱冲缓存、容器里不显示、20 包/秒、背包/容器双缓存路由）；
- 面板与 buff 用**同一个纯函数**，天然一致（现在是「服务端算好序列化过去」，多一层漂移面）；
- 客户端不需要「信标遥测」这个缓存槽——`LivingItemClientCache` 的容器分区可以少一类。

### 代价与边界

- 破坏「所有域统一推流」的一致性 ⇒ 必须**显式声明**而非隐式特判（否则未来域不知道有这条路）；
- **只适用于纯函数型遥测**：进度/相位/冷却这类服务端时间轴状态推流才是对的；
- 末影箱「不在 GUI 时的光束」仍需宿主包——但那本来就是独立链路，与 tooltip 无关。

### 现有域评估（谁真能用上）

| 域 | 遥测内容 | 可客户端推导？ | 判定 |
|---|---|---|---|
| **活信标** | 等级 + 9 列柱高 + 位图 + 再生档 | ✅ 纯函数（容器内容 → 等级） | **唯一直接可用** |
| 活熔炉 | 燃烧剩余 / 烹饪进度 | ❌ 服务端时间轴 | 推流保持 |
| 活酿造台 | 酿造倒计时 / 燃料 | ❌ 同上 | 推流保持 |
| 活漏斗 | 冷却 / 传输进度 | ❌ 同上 | 推流保持 |
| 活涂蜡铜块（发电机） | 相位 / EMA / 功率 | ❌ 服务端运行态 | 推流保持 |
| 其余 11 域 | 不发布遥测（或只有组件静态值） | — | 不涉及 |

⭐ **诚实结论**：A 的价值不在「马上能让一堆域受益」，而是**给未来所有「内容派生型」域
留一条正确的路**（例如未来的活附魔台、活讲台、活蛋糕——凡是「等级/状态 = 容器内容」的域）。
今天只有信标一个用户，但它的 bug 史证明了这条路的必要性。

## §2 提案 B：统一宿主模型（Host）

### 现状：**三套同构的「谁在世界里发光/显示」同步**

| 子系统 | 服务端 | 包 | 客户端缓存 | 备注 |
|---|---|---|---|---|
| 活信标·玩家 | `BeaconPlayerHostSync`（UUID + 等级 + 玻璃色） | `BeaconPlayerHostPacket` | `BeaconPlayerHostClientCache` | 自己那份跳过（本机渲染） |
| 活信标·箱子 | `BeaconChestHost`（位置 + 等级 + 玻璃色 + **开盖**） | `BeaconHostPacket` | `BeaconHostClientCache` | 开盖按容器、光束按枚 |
| 活工具 | `LivingToolHostSync` / `LivingToolPlayerSync` | `LivingToolHostPacket` … | `LivingToolHostClientCache` … | 位置集 + 内容去重 |
| 活流体 | `FluidFlowServerSync`（`RenderTarget` 三分类） | `FluidFlowSyncPacket` | `FluidFlowClientCache` | 单槽 `chestLikeTarget` 提示 |

四套的结构几乎一致：**「实体/方块在某个位置有可见物 → 定向 S2C → 客户端整表替换 → 渲染器循环」**，
却各自演化出了不同的坑（信标的跨维度丢数据、流体的 last-writer 提示被翻）。

### 方案

抽一个 `Host` 模型 + 一套同步：

```java
record Host(
    HostKey key,            // 玩家 UUID / (容器键, 槽位) / 工具 UUID
    Vec3 origin,            // 光束/模型起点
    Vec3 direction,         // 玩家宿主 = 头颅法线；方块宿主 = 竖直
    Optional<BlockPos> lid  // 可选：方块宿主的开盖位置（活信标专用）
) {}
```

- 一套 `HostSync`：定向 + 内容去重 + 维度隔离（**把「登记表是全局还是每维度」做成显式契约**，
  这正是信标踩过的跨维度 bug）；
- 一套客户端缓存：`Map<HostKey, Host>` 整表替换；
- 渲染器循环统一 —— 「自己那份跳不跳」「多枚怎么聚合」是**渲染策略**而不是数据模型。

### 收益 / 代价

- 代码量估计减 40%~50%（四套同构逻辑合一）；新域接「世界可见物」不再各写一套；
- 代价：抽象要一次做对（`HostKey` 的形状决定「每枚一条」还是「每容器一条」）；
  **必须先定 D（§4）再定 B**，否则又会在数据层做聚合。

### 现有域评估

| 域 | 可迁移 | 说明 |
|---|---|---|
| 活信标（两套） | ✅ | 直接受益，热路径 |
| 活工具（两套） | ✅ | 与信标玩家宿主同构（UUID + 位置 + 去重） |
| 活流体 | ⚠️ 部分 | `RenderTarget` 是「渲染目标分类」，与 Host 不同层；但其 `chestLikeTarget` 单槽提示属 §4 的反面案例 |
| 其余域 | — | 无世界可见物 |

## §3 提案 C：判定层用「协议 / 能力」，不用「类型白名单」

### 已有成功案例

信标宿主判据从 `instanceof ChestBlockEntity` 升级为 `LidBlockEntity`（原版接口）——
一行覆盖原版箱 / 陷阱箱 / 铁箱子全家 / 未来所有带盖容器，且**删掉了反射 compat**。
教训：**遇到「第 N 个特例」时找协议接口，而不是加第 N 个 compat**。

### 还能再进一步：宿主资格 = 「被发现」∩ 能力

铁箱子本来就被容器基础设施**发现**（有能力面、被 tick），却被信标自己的白名单挡在门外。
正确的层级关系应是：

```
世界容器（被 ContainerChunkCache / processContainerAt 发现）
   └── 活信标宿主 = 其中「方块容器 ⇒ 必须 LidBlockEntity」的子集
```

而不是「发现层一份清单 + 域里一份平行白名单」。这样新模组接进来只要能被发现，
宿主判定就不用动。

### 剩余的类型白名单

| 位置 | 性质 | 建议 |
|---|---|---|
| `ContainerCompatibilityConfig.resolveColumnsFromContainer` | 列宽推断的 fallback 表（Tier 2；Tier 1 已是规则文件） | **保留**——它是「猜宽度」不是「判资格」，规则表已能覆盖模组；但新模组优先走 `container_rules.json` |
| 信标 `isLiddedChest` | ✅ 已协议化 | — |

⭐ 结论：C 已基本做到，剩下的不是 bug 而是「下一层该长什么样」的记录。

## §4 提案 D：数据模型 per-item，视觉聚合在渲染期

### 案例（都来自本项目的真实回撤）

| 事件 | 错误做法 | 后果 | 正确原则 |
|---|---|---|---|
| 多枚信标 | 数据层按容器 merge（等级取 max、颜色取胜出者） | 信息不可逆丢失，后来改「每枚一条」被迫重构键控 + 开盖逻辑 | **数据层保留每枚完整信息；「一个容器画一条」若要，放渲染期聚合** |
| 开盖状态挂在 host 条目上 | 光束（per-item）与开盖（per-container）混在一个结构 | 「取走一枚不能关盖」写错（重构时实测踩到） | **副作用按容器键、可视化按物品键**，两者分开建模 |
| 活流体 `chestLikeTarget` | 单槽「最近一次非背包目标」提示 | last-writer 被末影箱包翻掉 ⇒ 水渲染到别的箱子界面（2026-10-06 第 ③ 次泄漏修复） | 同上：**别用「最近一次」状态替代分区** |

⭐ D 不是代码改动，是**设计纪律**：新域建模前先问「这个状态是 per-item 还是 per-container」。

> ✅ **已落地（2026-10-18）**：本节纪律已写进
> [living-item-design-template.md](../guides/living-item-design-template.md) §1.1-b
> （含「可见物 = 物品键 / 副作用 = 容器键 / 避免『最近一次』提示状态」三行反例表）。
> 新活物品设计时按模板填即可，无需回到本文。

## §5 优先级、风险与「何时做」

| 提案 | 价值 | 风险 | 建议时机 |
|---|---|---|---|
| **A 客户端推导遥测** | 高（消灭一类竞态 + 少一类缓存） | 中（要先定义契约形态；回退路径必须保留） | **下一个「内容派生型」域开工前**——现在只有信标一个用户，抽象还太早 |
| **B 统一宿主模型** | 高（四套同构 → 一套） | 中高（`HostKey` 形状定错会返工；必须先定 D） | 出现**第 5 个**「世界可见物」需求时；或动流体/工具同步前 |
| **C 协议判据** | 中（已基本达成） | 低 | 随时；新判据一律优先找接口 |
| **D per-item 纪律** | 高（防止不可逆数据建模错误） | 零（纪律） | ✅ **已落地**（2026-10-18 写进设计模板 §1.1-b） |

⚠️ 三个共同前提：
1. **不许为了抽象而抽象**——每条都要有「第二个用户」才配做（A 目前只有信标；B 有 3 个）；
2. **回退必须保留**——A 的推流回退、B 的旧包兼容都要有，否则边缘容器/旧存档直接坏；
3. **热路径审计**——缓存/同步是每 tick 的东西，抽象不能引入每帧分配。
