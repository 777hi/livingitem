## 0. 玩法定义（草案 —— 待拍板后定稿）

**语义**：**活滴水石锥 = 流体运输**。容器内流体的**方向阀**：按朝向，把「上游」的流体
滴到「下游」——整源搬运（源格 → 空槽重新成源），或海绵泵（湿海绵 → 空槽诞生源，
可选交互）。

**获取**：滴水石锥 + 活按钮（活化无门槛，`activation_rules.json` default allow）。

**核心循环**（不依赖活海绵的独立闭环）：水网里的源摆在 A 格 → **活滴水石锥**朝向 B 格 →
逐拍把源从 A 搬到 B。用途：把源**摆到消费端够得着的位置**（活耕地湿润 BFS 的水源位 /
转化台 / 刷石机接触格 / 管道抽取位），或把源**挪离危险位**（远离岩浆前沿）。

**规则（草案，违反即 bug）**：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **零私有状态**（桶哲学）：搬运是「上游 −1 源 ⇒ 下游 +1 源」的原子操作 | 不引入第三份水账本（活桶零私有状态是 2026-10-04 纠偏定稿） |
| 2 | **下游只进空槽 / 流动格 / 非活物品格** | 对齐倒水语义（`canBeReplaced`）；活物品格挡住（防挤没） |
| 3 | **岩浆源可运**（水与岩浆都滴，原版口径） | `FluidType` 跟着源走，零额外代码；海绵不存岩浆 ⇒ 锥是唯一岩浆搬运件 |
| 4 | 写入 `generatedSources` ⇒ **下一拍生效** | 与倒桶 / 汲走同层（fluid tech §3.6 三种改源路径的写入层级） |
| 5 | **不跨容器**：指向容器边缘 / 容器外 ⇒ 本拍不滴 | 「物品过境水不过境」；跨容器运输 = 提着活海绵走 |

**能力清单（目标）**：⬜ 整源搬运（方向阀 / 下游准入）· ⬜ 海绵泵（可选，对 `LivingSpongeData` 减 1）·
⬜ 岩浆源可运 · ⬜ 方向配置（`HasDirection`）

**验证入口**：§5 拍板后按设计模板 §2.2 补「规则 → 守卫」表；基建复用 `SimpleContainerContext` +
假 `FluidPresence`（活耕地湿润 BFS 测试先例）。

## 1. 原版事实存档（1.21.1 源码，2026-10-29 查证）

`PointedDripstoneBlock`：

| 机制 | 原版实现 | 容器版对应 |
|---|---|---|
| 滴注 | random tick：钟乳石**根**上方是**水源** → 概率（水 0.17578 / 岩浆 0.05859；NeoForge patch：模组流体走 `DripstoneDripInfo.chance`）→ `findTip` 向下找尖端（≤11）→ 沿 `canDripThrough` 格子（≤11）找 `canReceiveStalactiteDrip` 的**炼药锅** → `scheduleTick(50 + 距离)` → 锅 **+1 层**（一锅 1000mB 分 3 层） | 方向阀：上游槽 →（节拍）→ 下游槽（§2）；速率锚点用原版的 `50t` |
| 货种 | **水与岩浆都能滴**（岩浆概率更低） | 整源搬运 + 海绵泵对 `FluidType` 透明 ⇒ **岩浆源可运** |
| 泥→黏土 | 水滴滴在**泥**上 ⇒ 泥变黏土（非下界） | v1 不做；转化先例（滴注路径改写目标），远期挂 §6 |
| 生长 | random tick 0.0114，**滴水石块 + 水源** ⇒ 钟乳石向下 / 石笋向上（50/50），总长 ≤7 | v1 不做（运输已闭环），远期挂 §6 |
| waterlogged | 滴水石锥可含水（`SimpleWaterloggedBlock`） | 不映射（容器槽位无「含水方块」概念） |

## 2. 容器映射

### 2.1 方向与准入

- 方向 = `HasDirection`（WASD 配置，现成接口）；上游 = 逆方向邻槽，下游 = 顺方向邻槽；
- 下游准入对齐倒水语义（fluid tech §5.3）：**空槽 / 任意流动格** ⇒ 诞生源（覆盖）；
  **非活物品格** ⇒ 源与物品同格共存（转化台 / 焚毁流程自然接管）；**活物品格** ⇒ 不滴
  （防挤没；活物品 = 阻挡水流的方块，语义一致）；
- 下游被占 ⇒ 本拍不滴（等空）。

### 2.2 两种运输（都是零状态原子操作）

| 模式 | 上游 | 动作 | 下游要求 |
|---|---|---|---|
| **整源搬运** | 源格 | `removeGeneratedSource(上游)` + `registerGeneratedSource(下游, fluid)` | 空槽 / 流动格 / 非活物品格（对齐倒水 `canBeReplaced`） |
| **海绵泵**（可选交互） | 湿海绵（存量 ≥ 1000mB） | 海绵 −1000mB + `registerGeneratedSource(下游, fluid = 海绵所存流体)` | 同上 |

- 优先级：先试整源搬运，上游是湿海绵才走泵（待拍板 ①）；
- **岩浆源可运**（原版滴岩浆；`FluidType` 跟着源走，零额外代码）；
- 海绵泵出什么流体随海绵所存（活海绵可存任意已注册流体，2026-10-29 定调）；
  `LivingSpongeData` 的读写与准入见 [活海绵.md](活海绵.md) §2.1/§2.3；
- **可视化白拿容器流体渲染**：源在上游消失 / 下游诞生，`FluidFlowSyncPacket` 快照自然画出
  「水从这格退去、那格长出」——零新渲染代码。

### 2.3 速率与时钟

- **独立节拍 N t/次**（**不是**水的 5t——原版滴水远慢于水流）；
  锚点：原版 `scheduleTick(50 + 距离)` 的 50 ⇒ 建议默认 **50t/次**（2.5 秒一源 = 400mB/t），
  真机手感再调（待拍板 ②）；
- 时钟归类（fluid tech §3.6 统一时钟）：**物品自有节拍**（同活耕地节拍门先例）——
  若跟水的 5t 节拍就失去「阀」的意义；写入生效走「下一拍」层（与倒桶 / 汲走同层）。

## 3. 引擎契合度（为什么这件便宜）

1. **引擎零改动**：只用 fluid tech §2.3 的公开 API ——
   `isSource` / `sourceFluid`（查）+ `removeGeneratedSource`（汲走同款）+ `registerGeneratedSource`（倒水同款）。
   与活熔岩「一行行为注册」同级的最小接入面；
2. **宿主是普通 `LivingItemFunction`**：域归 `domain/water/`（`LivingDripstoneFunction`）；
   容器级数据经 `ContainerContexts` 反查（同 `LivingBucketInteractSupport` 路径）；
   物品形态容器 / 背包 / 潜影箱**嵌套免费**（物品形态 ctx 已打通）；
3. **零私有状态 ⇒ 无组件、无落盘、无取消活化清理**——比活海绵还薄一件
   （桶哲学：搬运不持有）；
4. **对称性合规**：活化侧设备影响活化资产（fluid tech §10 管道抽取的同款判据），
   不触 §6.1「非活化物品不得取活化资产载体」红线；
5. **与活海绵的耦合是单向可选的**：整源搬运完全不读海绵组件；海绵泵只在「上游槽是湿海绵」
   时才发生——**没有海绵，滴水石锥照样是完整的运输件**。

## 4. 原版对齐清单（初稿）

| 原版检查 / 行为 | 本实现 | 处置 |
|---|---|---|
| 水 / 岩浆都能滴 | 整源搬运 + 海绵泵对 FluidType 透明 | ✅ 对齐（岩浆可运） |
| 滴注目标 = 炼药锅（`canReceiveStalactiteDrip`） | 目标 = 空槽 / 流动格 / 非活物品格 | ⚠️ **偏离**（原因：容器里没有「锅」受体，源格本身就是受体；`canBeReplaced` 判据与倒水共用） |
| 概率制（random tick 0.175 / 0.0586）+ 延迟 50+距离 | 节拍制 50t/次 | ⚠️ **偏离**（原因：容器 tick 每拍必跑，概率制 = 不可预期；节拍制保留原版的「慢」） |
| 泥→黏土 / 生长 / waterlogged | v1 不做 | 📋 远期（§6） |
| 只能上下滴（垂直世界） | 四方向（`HasDirection`） | ⚠️ **偏离**（原因：容器是 2D 网格，「上→下」映射到朝向；影响：四方向都是一等公民） |

## 6. 坑登记簿 / 远期

- **泥→黏土**（原版滴注转化先例）：滴注路径上改写目标格物品——转化表思路的延伸，远期；
- **滴水石锥生长**（滴水石块 + 水源 ⇒ 延长运输距离？）：远期，运输闭环成立后再想；
- **指向容器外 / 容器边缘**：无下游 ⇒ 本拍不滴（不跨容器——「物品过境水不过境」，
  跨容器运输 = 提着活海绵走）；
- **多个滴水石锥接力**（A→B→C 链式运输）：v1 天然支持（每个锥独立做自己的搬运），
  无需专门机制——但链路每级 50t 延迟会累加，属预期；
- **性能**：无数据无海绵 ⇒ 两个 API 查询即返回，热路径开销可忽略。

## 7. 图标（活物品图标系统，声明式一行注册）

> 系统能力见 [icon-system.md](../system-design/icon-system.md)。

| 反馈 | 数据 | 通道 | 说明 |
|---|---|---|---|
| 方向 | `HasDirection` 数据 | **`.directional()`**（中继器 / 红石火把同款方向旋转，现成能力） | 图标随朝向旋转 |
| 基础外观 | — | `base` 变体直接引用原版滴水石锥纹理（`minecraft:` 路径，去原版化口径） | 零自绘 |

- **无状态 ⇒ 无状态变体**：滴水石锥零私有状态，「上游是海绵 / 源」「正在滴」都是
  **容器瞬态**，物品数据里不存在 ⇒ 不做变体（反馈三问：瞬态量仅开箱可见、非决策依据 ⇒
  不做，白幕教训「锦上添花类反馈默认本地自演」）；
- **真反馈白拿流体渲染**：滴注的可见结果 = 容器流体覆盖层（源在上游消失 / 下游诞生），
  `FluidFlowSyncPacket` 管线已有，零新代码；
- **活标识烘进模型层**（酿造台先例，2026-10-12）：滴水石锥变体引用**原版纹理** ⇒
  与原版同形，进专属 spec 后不再吃 `DEFAULT_DECORATOR` ⇒ 「活」识别度由变体 JSON 的
  **layer1（living 标记贴图）**承担（同 [活海绵.md](活海绵.md) §7——按「图标是否自辨」分流：
  自辨型如箱子不挂，原版同形如酿造台 / 海绵走 layer1）；
- 手持 / 掉落物回退原版外观（icon-system 既有有意取舍）。
