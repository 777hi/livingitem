## 0. 结论先行

当前测试不是“一个统一的东西”，而是三层混在一起：

1. **契约测试** —— 容器身份、槽位映射、布局、读写边界是否守规则；
2. **状态机测试** —— 流体 / 红电 / 电力 / 信标 / 耕地等领域的状态跃迁；
3. **事故回归测试** —— 每个真机 bug 补一条用例，常带日期与审查编号。

三层都很有价值，尤其第三层是项目最硬的资产。但**测试增长主要来自第三层**：
一条 bug 一条用例，能防“同一个 bug 复发”，不能防“下一个未知 bug”。
真正缺的是第四层：**不变量 / 接缝测试**（守恒律、能力面、流水线装配）。

一句话：**现在的测试更像一座“事故博物馆”，还不是一张“不变量网”。**

### 2.1 一句话总结

- **领域逻辑**：测得很细（流体 52 例、红电引擎 30 例、电力 137 例）。
- **容器契约**：测得很全（身份、键、布局、槽位映射）。
- **事故回归**：测得很真（大量用例直接来自真机日志与审查编号）。
- **接缝 / 流水线**：测得很薄（能力面、访问器、写回钩子、FakePlayer、记忆回放）。
- **不变量**：几乎只有“具体场景”，没有“随机操作下的守恒”。

## 4. 问题清单

### P-01 分布失衡，且与风险不匹配

容器 / 红电 / 流体 / 信标占一半用例；活箱子 / 末影箱 / 熔炉 / 活背包合计不到 5%。
这不是“测试写错了”，而是“测试跟着实现难度走”，没有跟着**事故风险**走。

### P-02 接缝类几乎未测

以下类在测试源码中 **0 引用**（静态扫描）：

| 类 | 作用 | 为什么危险 |
|---|---|---|
| `FilteredSlotAccessor` / `NeighborSlotAccessor` | 过滤 / 邻居槽访问器 | 传输边界的过滤与回滚 |
| `ContainerTickHooks` | 容器级写回钩子 | 流体 / 应力 / 相位的写回时序 |
| `LivingToolFakePlayer` / `LivingToolMemory` | 活工具回放核心 | 挖掘 / 攻击的真实副作用 |

> 2026-10-29 首轮接缝测试已补 `LivingChestItemHandlerTest`（5 项）与
> `LivingChestAccessorTest`（8 项），并当场抓出“插入副本、按原栈算余量”的复制 bug
> 与 16KB 估算门失效。这条经验值得保留：**接缝测试不是补覆盖率，是找真实缺陷。**

并且只有 **5 个测试类**调用 `processContext` / `processContainerAt`（真实流水线入口）。
大多数测试直接驱动领域方法，绕开了“上下文解析 → 分组 → tick → 写回”的装配层——
而这正是最近几次“单测绿、真机坏”的高发区。

### P-03 绿色缺口：测试在替债务背书（已修 2026-10-29）

`LivingChestInsertByteGateTest.estimatePath_stillPermits_documentedGap` 曾是**绿色通过**的，
断言“估算路径仍然放行超限物品”。同时 `living-chest-tech.md` 的 16KB 规则写成无条件约束。
两者矛盾：一条说“违反即 bug”，一条把违反钉成预期。

> 2026-10-29 已修：能力面改用 `RegistryAccess.EMPTY` 精确计量；旧绿色用例改为
> “无 registries 也拒绝”；新增 `LivingChestItemHandlerTest` 5 项 + 回滚豁免 1 项。
> known-gap 归零。教训保留：**已知缺口不能以绿色用例存在**；要么修，要么 `@Disabled` + ID。

> 这不是隐藏债务——test-map 里写得很清楚。问题是它**绿色**，而且没有 ID / 关闭条件，
> 下一代 AI 读到时会把它当现状。

### P-04 文档里的测试计数在漂移

- `test-map.md` 有 146 个类带“（N 项）”，静态比对 XML 有 **23 处不一致**
  （部分是多段计数 / `@Nested` 拆分造成的假阳性，但确有真实漂移）：
  - `ContainerFluidDataTest` 声明 26，实际 **52**；
  - `ContainerAnchorTest` 声明 9，实际 7；
  - `ChannelStateTest` 声明 10，实际 12；
  - `LivingItemRuntimeContainerPositionsTest` 声明 6（行内另有 3），实际 11。
- `unit-testing.md`（2026-08-22）里的示例计数也已过期：
  `ContainerRedstoneDataTest` 写 29（实际约 30 展开）、
  `ContainerCompatibilityConfigTest` 写 14（实际 16）。
- `doc_check` 第 3 项只校验**测试类文件清单**，不校验每个类的用例数。

**根因**：把“可从 XML 枚举的计数”写进了叙事文档。按项目自己的铁律 3，这属于清单型内容，
应当由脚本生成或干脆不写。

> 2026-10-29 已处理：`test-map.md` 删除全部“（N 项）”，改由 `tools/test_inventory.py` 生成；
> `unit-testing.md` 的示例改为类型 + 覆盖内容，不写死数字。`doc_check` 不校验用例数
> ——计数不是契约，不应该再手维护。

### P-05 tag 依赖与 `@Disabled`

3 个 `@Disabled` 都是“FML 单测环境不加载 item tags”。受影响的行为：

- 信标金字塔等级、喂锭档位；
- 活化规则 / 交互规则的 tag 路径；
- 部分测试改用 item 型 target 绕过 tag。

这些行为目前**只有游戏内验证兜底**，没有自动化回归。它们是真实风险，不是“测试没写”。

### P-06 第三方替身放在真实包名下

`src/test/java/net/p3pp3rf1y/...` 与 `net/byAqua3/...` 下有 8 个替身类，使用真实模组的 FQCN。
风险：

- 真实模组 jar 一旦进入测试 classpath ⇒ 重复类；
- 替身编码的是“我们对它的理解”，上游改 API 时替身不会变红。

### P-07 巨型测试类

`ContainerFluidDataTest` 61KB / 52 例，`ContainerRedstoneDataTest` 36KB，
`WaxedGeneratorFeedChainTest` 30KB。它们覆盖很拼，但：

- 单类失败定位成本高；
- 新增用例倾向“继续往里塞”，进一步加剧集中；
- 建议按“行为簇”拆成 `@Nested` 或独立类（不是现在必须做）。

### P-08 性能测试混在单测

`ContainerFluidPerfTest` 在普通 `test` 任务里跑 3.14 秒，并写 `build/_perf.txt`。
它不是正确性测试，应该：

- 打 `@Tag("perf")`，默认不跑或单独任务；
- 或在 CI 里单独跑并保留基线。

### P-09 `*IT` 命名与执行入口不一致

5 个 `*IT` 类（`RoundTripConservationIT` 等）**当前确实在 `gradlew test` 里执行**（XML 可见），
因为测试任务没有排除 `*IT`。但命名暗示“另有集成测试任务”，而实际没有。
风险：未来有人按惯例加 `exclude '**/*IT'`，这些类会静默消失。

> 2026-10-29 已修门禁侧：`doc_check` 第 3 项原先只统计 `*Test.java`，现在纳入 `*IT`
> （当前 152 个测试类）。执行入口仍保持一起跑，是否拆任务见 §8-3。

### P-10 没有“未测类 / 覆盖率”视图

408 个主类中，183 个从未在测试源码中出现字符串引用（静态扫描，非真实覆盖率）。
其中很多是客户端 / 注册 / 工具类（可以接受），但也混着 `PhaseInterpreter`、
`LivingChestAccessor`、`FilteredSlotAccessor` 这类关键接缝。
项目没有 JaCoCo，也没有“未测类清单”，所以这个数字没人看得到。

### P-11 单断言用例偏多（不是错，但要看住）

不少类接近“1 测试 1 断言”。这不一定是坏味道——一个强断言胜过十个弱断言。
需要防的是“只 assertNotNull / 只验证不抛异常”的用例。当前没有断言为空的测试类，
但建议把“断言是否真的在守行为”纳入 review 清单。

## 5. 建议的测试分层

| 层 | 名称 | 特征 | 放置 | 运行时机 |
|---|---|---|---|---|
| L1 | 纯函数 / 数学 | 不碰 `Level`，毫秒级 | 现有位置 | 每次 `test` |
| L2 | 领域状态机 | 直接驱动领域方法 + 替身 ctx | 现有位置 | 每次 `test` |
| L3 | 接缝 / 契约 | 能力面、访问器、写回钩子、回滚 | 新增 `living/.../seam` 或就地 | 每次 `test` |
| L4 | 集成 / 端到端 | `processContext`、真实菜单、真实 BE | `*IT` 或 `*IntegrationTest` | 每次 `test`（当前 15s 可承受） |
| L5 | 游戏内验证 | tag 依赖、渲染、鼠标手势、真实模组 | 文档清单 | 发版前 |

**标签约定**（建议，不强制立刻加）：

```java
@Tag("seam")        // L3
@Tag("integration") // L4
@Tag("perf")        // 性能量测，默认不跑
@Tag("known-gap")   // 已知缺口，CI 统计数量，只减不增
```

**known-gap 规则**（与整改计划一致）：

- 不允许绿色通过；用 `@Disabled("GAP-xxx: ...")` 或 `@Tag("known-gap")`；
- 必须有 ID、触发条件、影响面、关闭条件；
- CI 输出 `known-gap: N`，任何增加都失败。

## 6. 优先行动

> 顺序按“投入产出 + 与整改计划的依赖”排；第 1~3 项建议在整改计划批次 1 之后立即做。

1. **建测试台账（已完成 2026-10-29）**
   只读脚本 `python tools/test_inventory.py` → `build/test-inventory.md`：

## 7. 不建议做的事

- **不追求覆盖率百分比**。覆盖率告诉你“哪些代码被执行过”，不告诉你“守恒律是否成立”。
- **不重写现有测试**。事故回归是资产，保持原样，只补类型标签。
- **不引入新的测试框架**。JUnit + 现有替身足够；随机不变量测试用 `Random` + 固定 seed 即可。
- **不为每个新 bug 只加一条示例测试**。修 bug 时问一句：这条能不能升级成不变量测试？
- **不把 `test-map.md` 变成第二份用例清单**。它回答“守什么”，不要回答“有多少条”。
