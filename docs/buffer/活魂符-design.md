## §0 玩法定义（已确认的意图与建议规则分开）

### 0.1 三条原始玩法与已确认边界

本设计只承接三个目标，**不把宿主接入与活魂符玩法强行绑定**：
1. 女仆背包作为一种新的容器宿主，其中按原模组规则允许存放的活物品能够运行。
2. 存有女仆的魂符活化后，在容器界面里显示所存女仆的模型、待机动画与语音。
3. 活魂符在允许存放它的容器中自行走位，表现为物品换槽。

**容器能运行活物品 ≠ 容器必须接纳每一种活物品。** 女仆背包原本拒收魂符，
不构成第1条的兼容缺口；本联动不为第2/3条绕过该限制。

| 内容 | 定调 |
|---|---|
| 女仆背包 | 按当前装备背包类型读取可用容量，六列连续存储网格接入；保留原背包的准入、黑名单和穿脱机制（用户已同意） |
| 活魂符表现 | **存有具体女仆的魂符**活化后，在容器界面中显示这名女仆的模型，带待机动画和语音 |
| 走位 | 是活魂符的**服务端功能逻辑**，不是界面演出开关；不以 viewer / 开箱 / 鼠标悬停作为运行条件 |
| 如何走 | 读取所存女仆的饱食度H与背包可用容量C：在C分钟内均匀安排H次迈步机会，0不移动；方向从合法空邻槽纯随机选择，不交换其他物品 |
| 容量来源 | C取**魂符所存女仆的背包容量**，不是魂符当前宿主容量，也不是空槽数量；换箱子不改变C（用户已明确） |
| 演出覆盖 | 女仆模型仅在容器界面内显示；语音仅在该界面打开时播放。手持、掉落等维持魂符原表现 |
| 初期复杂度 | 先做简单逻辑；语音先复用普通待机音，不加天气、环境音选择逻辑 |
| 开发顺序 | **先完善设计稿，未解决的设计问题最后讨论**；本稿修订不授权功能实现 |

**语义**：活魂符把已经收存在物品中的女仆变成容器中的“会走动的活物品”。
女仆模型是这个物品的外观，不是额外放出一名世界实体。
女仆背包兼容是独立的宿主接入：复用现有容器 tick 管线，不给女仆或魂符单开扫描器。
活魂符使用同一功能框架，但其可存放宿主仍受 TLM 原有机制约束。

**获取**：空魂符收存已有女仆，得到 `smart_slab_has_maid`，再活化。
初始赠送魂符与已收存魂符不同，见 §1.1；先释放女仆、再收回即可进入这条获取链。

**核心循环**：放入支持的容器 → 活化 → 按所存容量C与饱食度H均匀计时 → 到点随机挑合法空邻槽 → 移动自身；
开界面才看到模型和走路动画，**关界面不会停止服务端走位**。
取消活化后女仆数据保留；对方块使用仍走 TLM 的原有释放流程。

## §1 源码查证：会改变设计的事实

### 1.1 开局 INIT 不等于“已经装有女仆”

| 形态 | 实际含义 | 对本设计的影响 |
|---|---|---|
| `smart_slab_init` | 赠送/初始凭证。赠送路径只写 `init_maid_owner`，没有具体女仆的 `maid_info`；使用时 `create`、主人/数量校验、`tame`、服务端 `finalizeSpawn`，此时才选模型 | 不能提前展示“其真实女仆”：女仆及随机模型尚未生成。不是简单缺 Owner，也不是损坏快照 |
| `smart_slab_empty` | 收存已有女仆的空载体 | 没有女仆模型可还原 |
| `smart_slab_has_maid` | 收存已有实体后保存的快照；`maid_info` 为 `CustomData`，含模型、语音包、主人、装备、背包等 | 可以还原显示身份；释放按原快照加载，不重新随机模型 |

证据：`item/ItemSmartSlab.java:66–128`、`:152–156`；`loot/SetInitMaidOwnerFunction.java:37–45`；
`item/AbstractStoreMaidItem.java:41–50`、`:88–113`。
`saveWithoutId` 的“WithoutId”不代表不存 UUID（原版 `Entity.java:1737–1754` 仍存 UUID）；
创造复制能重复 UUID，**不能以该 UUID 共享预览实例**。

**建议**：本稿先覆盖 HAS_MAID；INIT 若也要活化出一个女仆，需另定“何时生成、模型和主人何时锁定”
的玩法，不能以默认示意模型冒充实际结果。玩家把赠送女仆释放再收存，不受此区别限制。

### 1.2 模型预览已存在，不需要“幽灵”玩法

TLM 本来就把女仆画进 GUI：
- `client/tooltip/ClientMaidTooltip.java:104–137`：从魂符取显示信息，设置模型/名称/YSM 显示字段，
  调原版 `InventoryScreen.renderEntityInInventory`。
- `client/gui/entity/detail/MaidModelDetailsGui.java:23–29`：为详情界面创建独立的女仆显示对象；
  `:81–89` 只推进 `tickCount` 和 `walkAnimation`，**不调用完整实体 tick**。
- `EntityMaid.java:532–655` 的完整 tick 含事件、饰品与世界行为，不能当动画函数每帧调用。

下文统一称**预览女仆实例**：客户端临时显示对象，不 `addFreshEntity`，不占世界实体，
不复制一名可干活的女仆。复用女仆原有 Bedrock/Gecko/YSM 渲染链，具体动画覆盖仍要做渲染验证。
不能因 YSM 未测试就宣称“大概率失败”；原 tooltip 有 YSM 支持，先沿用其显示字段路径。
不全量 `load(maid_info)`：快照内的任务和背包扩展加载不等于纯显示，初期只提取需要的显示字段。

### 1.3 原背包拒收魂符：保留，不改造

`ItemSmartSlab.java:137–139` 对 HAS_MAID 返回 `canFitInsideContainerItems() = false`。
`BackpackSlot` 的 `mayPlace` → `MaidBackpackHandler.isItemValid` → `EntityMaid.canInsertItem`，
GUI 和 handler 真实/模拟插入都会拒绝，**加 IS_LIVING 标记不会自动放行**。
证据：`inventory/handler/MaidBackpackHandler.java:18–20`、`EntityMaid.java:388–393`，
原版合并源 `SlotItemHandler.java:26–29`、`ItemStackHandler.java:55–60`。

**这是 TLM 的既有机制，不是本联动必须消除的阻碍。** 用户要求女仆背包里的活物品运行，
未要求原本不能放入的物品也能放入。活魂符仍在 TLM 允许存放它的容器里显示和走位。
不修改 `MaidBackpackHandler.isItemValid`、`EntityMaid.canInsertItem` 或魂符的嵌套判据；
不接管拾取流程，不提出局部放行 Mixin。模拟/真实移槽同样遵守宿主原有准入。

### 1.4 普通背包 6 列，按当前装备开放可用格（接入方案已定）

`MaidMainContainer.java:105–118` 和 `inventory/container/backpack/BigBackpackContainer.java:18–33`
直接给出如下布局：

| 可用存储格 | 列数 | 相对索引 / 界面行位置 |
|---|---|---|
| 默认 6 | 6 | `0–5`，y=37 |
| 小 12 | 6 | 追加 `6–11`，y=59 |
| 中 24 | 6 | 追加 `12–17`，y=82；`18–23`，y=100 |
| 大 36 | 6 | 追加 `24–29`，y=123；`30–35`，y=141 |
| 工作台/熔炉/水箱的普通存储 18 | 6 | 普通背包存储区仍为六列；机器/合成/流体区域不是这些存储槽 |

列 x 坐标均为 `143 + 18 * column`，物理索引连续，但 y 行距是 22/23/18 等，不是统一18。
**旧稿“9列预期自动命中”撤回**；列数不能从 36 格总数猜。
默认物理槽 5 在菜单重复注册为同坐标的两个别名，不能当第七格，更不能画两名女仆。

末影背包另显示玩家末影箱的27格，界面有缺口，**不是把 maidInv 增至27/36格**。
该区域不能揉进女仆的实体键；末影箱继续按现有玩家末影箱身份运行，GUI 识别须另外核对。

### 1.5 所存女仆数据：可直接读，好感不是实时实体状态

**已证实读取路径**：`touhou_little_maid:maid_info`（TLM注册的`CustomData`组件）→ 女仆快照NBT根节点。
不是`minecraft:custom_data`里的子字段，也不需要实例化女仆或运行AI。
TLM自己已通过`CustomData.read(Codec...fieldOf(...))`读取模型/名称，可沿用此方式读取玩法输入。

```java
// 示意读取路径，不是已实现的联动代码
CustomData data = stack.get(InitDataComponent.MAID_INFO);
Optional<Integer> favorability = data == null ? Optional.empty()
        : data.read(Codec.INT.fieldOf("MaidFavorability")).result();
```

`copyTag()`也可取得独立NBT副本后按类型读取；**缺少/错误类型应视为未知，不把getInt默认0当真实状态**。
仅为读取一个字段不必每tick复制整个含背包的快照；解析边界按需要提取，暂不建一个覆盖全女仆系统的框架。

**代表性可读信息**（源码调查示例，不是承诺全部纳入首期玩法）：

| 信息 | 快照字段 / 类型 | 解释 |
|---|---|---|
| 好感值 | `MaidFavorability` / int | 本女仆的单个整数，不是按玩家分存的表 |
| 好感等级 | **由好感值推导**，不是单独`level`字段 | 此版本原规则：<64为0级、64–191为1级、192–383为2级、≥384为3级；正常增加封顶384 |
| 好感行为冷却 | `FavorabilityManagerCounter` / compound | `{行为名: 剩余冷却int}`；与好感值不同，不是它的内层point/level结构 |
| 经验与饥饿字段 | `MaidExperience`、`MaidHunger` / int | 经验不是等级；该饥饿整数不是已证实的动态饱食度，另有同名属性，区别见§1.6 |
| 模型与语音 | `model_id`、`SoundPackId` / string | 显示身份和原语音包信息；另有YSM显示字段 |
| 任务与日程 | `MaidTask`、`MaidScheduleMode` / string | 任务是资源ID，不能直接当已实现的行为能力；只读标签不等于回放任务 |
| 背包类型/数据 | `MaidBackpackType` / string，`MaidBackpackData` / compound | 原背包类型及其专用状态，数据结构由类型决定 |
| 背包/饰品等物品 | `MaidInventory`、`MaidBaubleInventory`等 / compound | 含Size和Items；读取可知装备与库存，不代表要让内部活物品递归运行 |
| 名字/主人/身份/生命 | `CustomName`（组件JSON）、`Owner`/`UUID`、`Health`（float） | 来自实体父类保存；UUID可能被创造复制，不作全局唯一预览键；最大生命不能只凭好感推算 |

数值与字段判据：`EntityMaid.java:1351–1391` 保存、`:1479–1480`读取好感；
`entity/favorability/FavorabilityManager.java:28–36`、`:112–126`为等级边界，`:323–335`为行为冷却保存。
等级阈值在此版本源码中定义，不凭本模组另造一套“好感等级”。

**快照何时形成、会不会继续变**：
- `AbstractStoreMaidItem.java:42–52`只在`maid_info`不存在时保存实体、发ToItem事件、写入组件。
  正常收存后女仆实体discard；符内好感、冷却、经验、饥饿等**冻结在收存时**，原魂符不继续tick这些数据。
- 正常释放从当前组件复制快照、校验主人、发ToMaid事件并`maid.load`，之后覆盖世界位置。
  再收存才会得到女仆后来状态的新快照，不能靠对旧stack重调store函数刷新已有组件。
- 快照含附属扩展可增改的信息；例如收存处理会先关闭home模式。不能把保存的所有原实体瞬态都当永久性格。

**后续玩法的边界**：
- 好感、经验等可继续作为后续玩法的只读输入；当前迈步明确读取饥饿值（§2.1），好感不参与速度或方向。
- 如以后想在符内增加好感、经验或喂食恢复饥饿，那是新的互动/更新玩法，需另定规则与原模组关系。
  不能在读取预览或基础走位时顺便推进原好感、冷却、任务或背包。
- 不把“本联动的成长/互动进度”冒称原好感；若需要新增状态按现有组件归属与生命周期设计，
  不先复制第三方整份数据到另一组件建立双重账本。
- 修改`copyTag()`副本不会写回物品。若未来决定修改，必须明确组件提交和所有联动副作用：
  好感等级改变还涉及属性及事件，直接改数字后`load`不能保证这些一起正确更新。
  此时不能把“能写NBT”当成“正确培养好感”的完成证明。

### 1.6 饥饿值字段的陷阱：有两个不同来源

本版源码核查不能把所有“hunger”都当作同一饱食度：

| 来源 | 已证实事实 | 对步行的影响 |
|---|---|---|
| `maid_info.MaidHunger`整数 | `EntityMaid.java:414`默认0，`:2162–2167`为直接getter/setter，无上限/截断；保存/加载为int。源码未找到本体消费递减或吃食递增，`:1652–1657`吃食只调用父类和事件 | 直接选它时，默认女仆收存就是0，按用户规则会停走；不能虚构“满值20”或自动解释为剩余饱食度 |
| `touhou_little_maid:maid_hunger`属性 | `init/InitAttribute.java:43–49`注明“女仆饱食度，本体暂未使用，供附属调用”；默认20，范围0到Integer.MAX_VALUE，是独立的double属性 | **用户已选择此来源**；读取已存属性，未保存默认项时按原默认20解释，不读取`MaidHunger`替代 |

属性若有实例，其序列化跟随父类`attributes`列表保存`id/base/modifiers`；未实例化的默认属性
可能不出现在列表里。原版`AttributeMap.getValue`在无实例时查默认值，不能把列表中缺少项当成0。
若选该来源应沿用原属性默认/保存修饰符求值，不能只读base然后忽略modifiers；
临时未保存的修饰符不能由魂符快照还原，须明确读取的是**已保存的状态**。
判据：原版`LivingEntity.java:722`、`AttributeMap.java:64–72`和`:116–123`、
`AttributeInstance.java:145–162`和`:181–198`。

**用户已选择饱食度属性**作为输入：H越低越少走、0不移动、方向纯随机。
不使用`MaidHunger`整数，也不把其0当20；只在原属性省略默认实例时恢复该属性的原默认20。
不合并两个来源、不加自有饥饿值，不修改女仆原消费/喂食机制。

## §2 推荐机制（玩法与输入已定，技术接缝待验证，非实现承诺）

### 2.1 如何走：所存背包容量定周期，饱食度定次数，均匀迈步

**用户已定玩法**：C取魂符所存女仆的可用背包容量，H取所存饱食度属性。
C分钟作为周期，在周期内均匀安排H次迈步；H=0不移动。方向仍是每步从当前宿主合法空邻槽
等概率随机选择，**只有方向随机，迈步时机不再按概率抽签**。
这里的“速度”是换槽频率，不是渲染帧率或走路动画时长。

```
周期长度 = C 分钟
迈步间隔 = 60 × C / H 秒
游戏tick间隔 = 1200 × C / H       // 正常20TPS；不使用昼夜时间驱动
H <= 0：不安排迈步
```

| H | 所存C | 均匀间隔 | 无阻挡、连续工作时的节拍 |
|---|---:|---:|---|
| 20 | 6 | 18秒 / 360tick | 6分钟20次 |
| 20 | 12 | 36秒 / 720tick | 12分钟20次 |
| 20 | 24 | 72秒 / 1440tick | 24分钟20次 |
| 20 | 36 | 108秒 / 2160tick | 36分钟20次 |
| 10 | 6 | 36秒 / 720tick | 6分钟10次 |

**两个来源不得混淆**：
- H读取`touhou_little_maid:maid_hunger`饱食度属性（§1.6），不读`MaidHunger`整数。
  按原属性默认和已存修饰符求值，省略默认项时20，显式0停走；默认20不是上限。
- C从本枚`maid_info.MaidBackpackType`解析TLM原背包类型，并查询
  `IMaidBackpack.getAvailableMaxContainerIndex()`，**不取当前容器getSize、不数空槽**。
  用已有`BackpackManager.findBackpack`解析注册类型，不新维护一份6/12/24/36手工表，
  使原有特殊背包/附属类型仍按原可用容量解释。原TLM对缺失/合法但未知类型保留或回退空背包，
  解析应沿用该规则；损坏字段安全失败，不默认为当前箱子容量，不伪造可用格数。
  判据：`EntityMaid.java:1493–1496`和`:2254–2256`。
- 魂符换到其他箱子，H/C不变，迈步间隔不变；物品数据真的被合法更新时才重算输入。
  容量作为输入不意味着能进入女仆背包、不意味着要tick快照内部库存。

**均匀计时的实现约束（建议，不另造生命周期）**：
- 首次参与功能后经过一个间隔再迈步，不在活化当拍凭空多走一次。
- tick取整须保留分数余量，非整间隔用相邻整数tick间隔交替逼近，误差不长期累积；
  H也可为小数，按公式表示长期频率，不为“周期内必须整数次”另造取整玩法。
- 每枚每tick至多迈一步，极大H使理论间隔小于1tick时钳到1tick，不循环补走。
- **计时跟随物品，不能跟着原槽位**；成功换槽不能洗掉节拍，手动换槽/换箱也不共享其他魂符计时。
  已查现有`ContainerRuntimeCache`及`onSlotsMoved`只作废槽缓存，不提供随物品迁移；
  因此用功能自有的最小计时组件记录deadline/分数相位，仅初始化、到点和输入改变时更新，
  普通tick只读，不每tick持久写。move自动复制组件；自有组件按功能归属取消活化清除，
  不借女仆UUID共享计时、不写入TLM的`maid_info`、不新造扫描器。
  已有槽内组件提交入口负责计时写回，不能直接改读取副本当作已提交。
  证据：`living/runtime/ContainerRuntimeCache.java:123–141`、`SimpleContainerContext.java:446–450`。
- 关GUI不停功能。卸载/未tick时间不兑现为多步；恢复时至多重新排下一次，不能瞬间补跑离线次数。
- 到点无路或提交被拒：跳过当次，下一次仍按均匀节拍；不攒次数、不在下一tick连试。
  因此“C分钟H次”是**有路且持续工作时**的节拍，不能保证满容器也成功移动H次。
- 参数H/C合法改变时从当前tick重排一个新间隔；H<=0时停止并清理活动计时，恢复正值后重新计时。
  相同时间基准内换槽/换箱保留deadline；跨维度时不能比较不同世界时钟，须重排而非误判成逾期。
  只同步必要状态，禁止每tick发送倒计时。

库存层保持：
- 候选只取同宿主有效四邻空槽，遵守原准入与抽取权限；按实际可走格等概率抽取。
- 不先抽方向撞墙算失败，不给食物、工具等物品类型寻路权重。
- 功能分组是tick开头快照；提交前重验源仍为本条目、目标仍空，移后不重扫当新条目。
- 原有`move(..., 1, STANDARD)`负责提交、守恒、回读和同步，不裸写、不绕过活物品隔离。
- 命令产生count>1的异常魂符锁住走位，不拆栈、不截断。
- **只读原饱食度和背包类型，不因走路扣饱食度，不自动喂食/恢复**。
  原魂符数据为快照，H=0不会靠等待自动恢复。

**后续可能性（非本期能力）**：基于槽位物品的寻路留作后续设计方向。
目前只分清节拍、目标选择和原语提交，不预建路径缓存、策略框架或新扫描器。

### 2.2 如何画：复用女仆预览，显示状态与换槽事实分开

- 复用 TLM 的显示字段/渲染器和详情界面的最小动画推进；每个客户端 tick 增动画时间、
  设置步行强度，渲染帧仅插值。**禁止每帧完整实体 tick**，也不 tick 已存女仆的任务/背包。
- 实例缓存按“当前界面 + 宿主身份 + 物理槽”分开。数据变化重建，关闭/换世界/资源重载清理。
  相同数据的两枚也分别维护动画与声音；哈希只可加速比较，不可作为身份或去重键。
- 若同步显示A消失、相邻B出现，按**物品类型 + 完整maid_info + 其他稳定组件**作唯一一对一匹配，
  **仅排除本功能自有计时组件**后迁移预览并演出A→B；到点timer更新必使旧源/新目标的fullstack不同。
  相同稳定数据的多枚无法唯一归属时，目标重新待机；不全局忽略组件比较、不串声音、不共享实体。
  此过滤只作用演出匹配，不改变库存守恒/组件提交或服务端判断。
  用户无需为缓存歧义拍板；不为视觉连续性先增加持久UUID/网络事件。
- 动画插值不改变真实点击槽位；操作以最新服务端内容为准。首次开界面不补演未看到的历史步伐。
- `ContainerScreenEvent.Render.Foreground` 可用于画模型，但它、`IItemDecorator` 都只是**事后叠加**。

  仅对真实、当前有活魂符的槽位及准备成功的预览抑制原图；Foreground只画本帧已登记项。
  假槽/拖放预测/未覆盖屏幕透传原图；画模型失败同帧恢复魂符并停止后续抑制。
  需实际实验验证光照、depth、裁剪和第三方screen覆写覆盖面，不能宣称静态查到方法就是渲染通过。
- YSM先沿用已有预览路径；普通模型、Gecko、YSM都列为渲染验收项，不预判某类必然失败。
  失败隔离须限频留痕，不能静默吞掉长期损坏而称完整支持。
- 语音直接复用 `MaidSoundInstance` 与原 `SoundPackId`，先只选 `MAID_IDLE`。

  `MaidSoundInstance.java:38–45` 持有女仆引用，**丢缓存本身不会自动停声**。

**均匀迈步执行顺序**：

```
读取本枚有效H/C → 计算max(1,1200*C/H)及分数余量
首次/输入或时间scope变动 → 提交新clock；本拍不走
尚未到点 → 只读，不写组件
到点 → 在源槽提交下一个clock（失败则不继续）
     → 基于提交后真实源，过滤有效/空/准入与抽取允许的四邻
     → 等概率选目标，重新核对源/目标
     → move(from,to,1,STANDARD)，搬走的栈已携带新clock
无目标/被拒 → 仍已消费当前迈步机会，下次按正常间隔
```

组件提交与move仍是两个原有操作，不伪装成全后端原子事务；计时提交失败不得继续搬旧栈，
move失败不得复制魂符或以原栈引用虚报。新clock不另外写到目标槽，目标由move搬入。
过期恢复不循环补跑，scope变更重排，按§2.1做生命周期守卫。

**计时组件与动画匹配的接缝**：
到点排期会改变源stack的clock，客户端上帧源与这帧目标fullstack不同。
预览迁移只忽略**本功能clock**，其余稳定组件及完整maid_info仍比较，并要求唯一一对一。
只用于客户端演出，不调用全局ignored集合改变物品比较/库存准入。
有歧义重置预览，不新增UUID或事件包解决纯视觉连续性。

`LivingItem.processEntityContainers`和`ContainerContexts.resolve`命中后都直接new`EntityContainerContext`。
女仆有能力面，但其范围包括装备/饰品，不等于要运行的背包。

**建议窄扩展**：在`EntityContainers`登记实体宿主Provider，提供认领、上下文构造与逐槽归属；
同一Provider选择用于准入与createContext，TLM实现放compat。原版双闸与原上下文路径原样保留。
这一个入口只补“第三方实体容器如何接入”，不升级成通用宿主/扫描/生命周期框架。
菜单实体解析仍由现有`MenuSlotOwners`注册提供，逐槽时必须确认实际handler/范围，
不能仅因整个菜单返回女仆实体就认领装备槽。

拟改：`living/container/EntityContainers.java:70–100`、`LivingItem.java:447–449`、
`living/container/ContainerContexts.java:116–125`、相关`MenuSlotOwners`调用。
新增SPI按既有R4登记惯例在`*Registration`调用，并在`tools/check_layers.py`注册入口清单加新方法，
不改棘轮基线掩盖违规。

#### M2. 原实体上下文允许注入存储handler

`EntityContainerContext.java:72–80`现在构造器固定从能力面获取handler。
增加接收已选存储handler的构造入口（原构造仍委托原handlerOf），复用其实体UUID、锚点、附件与非方块语义。
女仆使用TLM已有可写范围wrapper即可，不新造`IItemHandler`或数量写入机制。
范围、负槽号、逻辑↔物理映射要有测试，不能凭wrapper存在就宣称所有越界安全。

#### M3. 混合菜单必须按真实槽归属同步/读取

- `SimpleContainerContext.java:735–747`当前`wholeMenuIsMine`快路径以菜单位置免逐槽归属；
  女仆菜单装备/背包索引都从0起，需在实体宿主路径仍逐槽核对Provider的handler/存储范围。
  原方块路径不无故重构，同物理slot5别名同步正确处理。
- `client/render/LivingItemTooltip.java:64–71`当前非玩家槽一律读通用runtime缓存；
  `client/render/ContainerFluidOverlay.java:102–126`也按非玩家组+局部索引查通用快照。
  两处复用同一个窄的菜单槽归属判据，过滤TLM非存储槽，避免流体/仪器数据出现在盔甲或饰品上。
  不各写一个TLM黑名单，不靠global“最近看到的女仆”保存归属。
- 这是让**背包内原本允许的活物品**反馈正确，不是让魂符进入女仆背包。

#### M4. 开菜单运行时首包不能只认第一槽

`LivingItem.sendRuntimeSnapshotOnOpen:762–773`当前解析首个可识别槽就return，
而TLM `AbstractMaidContainer`先注册玩家槽，首包可能只发玩家背包而漏女仆背包。
改为逐槽解析现有上下文、按cacheKey去重发送菜单内已存在的相关快照。
继续使用`LivingItemRuntimeSync.sendSnapshotToPlayer`，不引入新快照协议或扫描。
女仆实体位置反查、tick runtime刷新/回收等既有路径可复用，不重建全同步系统。

#### M5. 只替换槽位图标，不替换全局物品renderer

官方合并源码`AbstractContainerScreen.java:298–308`的`renderSlotContents`内部：
`renderItem/renderFakeItem → renderItemDecorations`。这里有真实Slot/待绘stack，
故首选一个独立窄Mixin仅redirect两处图标调用，成功准备预览才抑制原图并登记本帧实例。
其余数量/耐久/冷却/装饰/高亮与点击链不取消；Foreground独立订阅只画登记实例。

原图失败回退必须可靠：准备失败直接透传；实际绘制异常恢复光照/pose/scissor/depth，
同帧回画魂符并禁止继续抑制。不能“吞异常、底图早已跳过、剩个看不见的槽”。
HUD快捷栏、carried和回弹栈不经过该接点，保持原魂符；界面内真实玩家快捷栏槽仍是容器槽位。
假槽/拖放预测栈不作为真实魂符演出。

当前可不改`GenericLivingModelWrapper`、`GenericContextAwareModel`、`LivingIconSpec`、
`LivingContainerOverlay`清单和全局ItemRenderer，不覆盖TLM原`IClientItemExtensions`。
第三方如精妙screen会覆写renderSlot绕过此接点，需要对应的独立条件窄适配或先保留原图；
未登记的路径不额外叠画女仆，不能称“已全场景渲染”。具体覆盖依实机实验验收。

### 8.5 包层与软依赖接线

- `living/container`只认识Provider契约，不认识TLM类；`living/compat/tlm`是L2外部API适配；
  `living/domain/maid`是L3业务，可调L2适配。L2不得直接new领域Function/调用领域Registration。
- `client/render/tlm`等属于L5，客户端Mixin也在`client/mixin`；
  不放`living/compat/tlm/client`，因为整个compat按L2计，会产生反向客户端依赖。
  通用Mixin若确需存在只住`living/mixin`，但本路线**没有原准入修改**。
- mod入口负责按阶段/Dist接线：通用组件注册、TLM守卫、Function登记、客户端事件分开。
  普通业务API不放Mixin包；所有未来Accessor/Invoker必须`living_item$`+显式成员。
- `build.gradle`加锁定TLM版本的Modrinth`compileOnly`且非传递；本地jar独立开发runtime，
  无本地jar的干净克隆仍能编译。metadata加optional依赖；若宿主注入仓库module过滤需放行TLM坐标。
  不把第三方jar打入本模组；本地开发运行所需前置依其metadata另核对，不靠“compileOnly拉到”保证能启动。
- 无TLM/专用服务器/模型资源重载三条路径必须验证；守卫类不能在签名或静态字段先链接客户端/TLM实现。
