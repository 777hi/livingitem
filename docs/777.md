## 1. 活箱子的新架构迁移

先看活箱子的现状——它其实**已经部分迁移了**，但方式很特殊：

```
其他活物品：自定义 DataComponent（LivingHopperData、LivingFurnaceData...）
活箱子：    直接用 Minecraft 原生的 DataComponents.CONTAINER（ItemContainerContents）
```

活箱子没有 `LivingChestData`，而是直接操作 `DataComponents.CONTAINER`。这其实是**对的**——因为活箱子的核心数据就是"27 槽位物品列表"，而 Minecraft 的 `ItemContainerContents` 正好就是干这个的。自己造一个 `LivingChestData` 包装一遍纯属多余。

但活箱子确实有几个需要迁移的点：

| 当前状态 | 问题 | 迁移方案 |
|---------|------|---------|
| `tick()` 是空方法 | 活箱子没有 tick 逻辑，但未来可能需要（如自动整理、过期清理） | 保持空实现，需要时再填充 |
| `insertItem()`/`extractItem()` 是 static 工具方法 | 其他功能类（活漏斗）直接调用 static 方法，绕过了架构 | 考虑通过 `ContainerContext` 提供统一存取接口 |
| 字节计算每次都重新序列化 | 性能浪费 | 可考虑在 `ContainerSnapshot` 中缓存字节用量 |
| 没有 `LivingChestData` | 与其他活物品的数据访问模式不一致 | **不需要创建**——`ItemContainerContents` 已经是最好的 DataComponent |

**结论**：活箱子的迁移工作量很小，因为它已经用了 DataComponent（原生的 `CONTAINER`），只是缺少一些架构对齐（统一存取接口、字节缓存）。不需要强行创建 `LivingChestData`。

## 2. 新旧架构的两全其美

这是更有价值的问题。让我逐项分析旧架构的"精华"能否在新架构中复活：

### 精华 1：编排器模式（Orchestrator）

**旧架构的精华**：
```java
// 新活物品只需选一个编排器，零代码
@LivingComponent(FuelProgressOrchestrator.class)
class MyNewSmelter extends LivingItem { }
```

**新架构的糟粕**：每个功能类自己手动编排 tick 逻辑，复制粘贴。

**两全其美的方案**：在新架构中引入 **函数式编排器**——不是旧架构的类继承体系，而是可组合的函数式管道：

```java
// 编排器 = 一组纯函数的组合
interface TickOrchestrator<D> {
    D tick(ContainerContext ctx, D data, int slot, int stackCount);
}

// 活熔炉 = 燃料编排 + 进度编排 + 转化编排
static final TickOrchestrator<LivingFurnaceData> FURNACE = 
    FuelOrchestrator.<LivingFurnaceData>create()
        .then(ProgressOrchestrator.create())
        .then(TransformOrchestrator.create());

// 新活物品只需声明编排器
class LivingSmokerFunction implements LivingItemFunction {
    static final TickOrchestrator<LivingFurnaceData> ORCHESTRATOR = FURNACE;
    // tick() 一行委托
}
```

**优势**：保留了旧架构的"零代码复用"，同时用纯函数组合替代类继承，与新架构的不可变 Record 天然兼容。

### 精华 2：组件间交互（Component Interaction）

**旧架构的精华**：组件通过 `context` 天然交互，`inheritFilter()` 就是组件间协作的产物。

**新架构的糟粕**：功能类之间没有交互机制，`ContainerSnapshot` 只解决了"读取邻居状态"的问题，但"响应邻居变化"没有统一方案。

**两全其美的方案**：在 `ContainerSnapshot` 层面引入 **事件槽位**——不是旧架构的运行时事件系统，而是快照级的声明式依赖：

```java
// ContainerSnapshot 已经知道谁指向谁
// 新增：当 sourceOf/targetOf 变化时标记 dirty
class ContainerSnapshot {
    boolean isDirectionDirty(int slot);  // 这个槽位的方向关系是否变化了
    boolean isFilterDirty(int slot);     // 这个槽位的过滤规则是否变化了
}
```

这样功能类可以：
```java
if (tick.snapshot.isFilterDirty(slot)) {
    // 重新计算过滤规则（只在变化时计算）
} else {
    // 复用上一次的结果
}
```

**优势**：不需要运行时事件系统，利用快照的不可变性做变更检测，零额外开销。

### 精华 3：用例验证（Test Coverage）

**旧架构的精华**：每个 bug 修复都是对真实场景的覆盖。

**新架构的糟粕**：重写时丢用例。

**两全其美的方案**：这个已经在做了——验证清单。但可以更进一步，把验证清单转化为**自动化测试**：

```java
@Nested
class ChainFilterTest {
    @Test
    void twoHopChain_blacklistPropagates() { /* 10.5 */ }
    @Test
    void mutualPointing_noFeedbackLoop() { /* 10.8 */ }
    @Test
    void tagLevelInherited_displaysAsTag() { /* 10.11 */ }
}
```

### 精华 4：语义清晰的方法命名

**旧架构的精华**：`inheritFilter()` —— "继承过滤规则"，意图一目了然。

**新架构的糟粕**：`collectFilterItems()` —— "收集过滤物品"，是实现细节而非意图。

**两全其美的方案**：在新架构中保留旧架构的**意图命名**，即使实现不同：

```java
// ContainerSnapshot 层面
public FilterData inheritFilter(int slot) {  // 意图：继承过滤规则
    return filterOf[slot];                    // 实现：从预计算数组读取
}
```

方法名表达"做什么"（继承），而不是"怎么做"（收集）。调用者不需要知道底层是预计算还是实时计算。

## 总结：两全其美的架构蓝图

| 维度 | 旧架构精华 | 新架构糟粕 | 两全其美 |
|------|-----------|-----------|---------|
| 编排复用 | 编排器模板 | 复制粘贴 | 函数式编排器管道 |
| 组件交互 | context 天然交互 | 无交互机制 | 快照级变更检测 |
| 用例验证 | 历史bug修复 | 丢用例 | 验证清单 + 自动化测试 |
| 语义命名 | inheritFilter（意图） | collectFilterItems（实现） | 意图命名 + 实现分离 |
| 类型安全 | ❌ 字符串键 | ✅ Record | ✅ 保留 |
| 不可变性 | ❌ 可变NBT | ✅ 不可变Record | ✅ 保留 |
| 容器缓存 | ❌ 无 | ✅ ContainerSnapshot | ✅ 保留 |

**核心思路**：新架构的工程基础（Record、DataComponent、ContainerSnapshot）全部保留，但在上面叠加旧架构的**语义层**——编排器管道提供复用，意图命名提供可读性，变更检测提供交互，自动化测试提供保障。

要动手改吗喵？我建议优先级是：
1. **意图命名**（最简单，改方法名就行）
2. **自动化测试**（最重要，防止再丢用例）
3. **函数式编排器**（中等难度，但收益大）
4. **变更检测**（最复杂，等有需求再做）
