### 代码审查结果

#### 🔴 需要修复的问题

**1. `ContainerStressData` 和 `ContainerFluidData` 中 `getNeighbors()` 方法重复**

两个类各自实现了完全相同的 `getNeighbors()` 方法，逻辑一模一样。这是典型的代码重复，应该提取为工具方法。

**2. `isSafeKineticBE()` 白名单检查重复**

`KineticBlockEntityMixin.isSafeKineticBE()` 和 `CreateIntegration.isSafeKineticBE()` 实现了完全相同的白名单逻辑，用字符串类名匹配。重复意味着修改一处容易忘记另一处。

**3. `LivingWaterWheelFunction.tick()` 是空方法**

`tick()` 方法体为空（只有 `if (level.isClientSide) return;`），活水车的所有实际逻辑都在 `postTickSync` 中完成。这违反了其他功能类的模式（tick 做逻辑，postTickSync 做同步），让人困惑。

**4. `WaterData` 中 `flow` 字段用字符串编码效率低**

`flow` 字段用 `"slot:level:fromSlot,slot:level:fromSlot"` 格式存储，每次读取都要 split + parse，写入要 StringBuilder 拼接。对于频繁 tick 的数据，这个序列化/反序列化开销不小。

**5. `ContainerFluidData` 每帧 BFS 全量重算**

`recalculate()` 每 tick 都从所有水源重新 BFS 计算整个流动状态，即使水源和活物品位置都没变。对于大容器（9×6=54 格），这是不必要的开销。

**6. `CreateIntegration` 直接 import Create 类**

`isDirectionCompatible()` 方法直接 import 了 `com.simibubi.create.content.kinetics.base.KineticBlockEntity`，违反了文档中说的"不直接 import 任何 Create 的类"原则。虽然 `CreateMixinPlugin` 保证了这个类只在 Create 安装时加载，但与设计原则不一致。

#### 🟡 可以优化的地方

**7. `LivingWaterBucketFunction.addToTooltip()` 中手动解析 flow 字符串**

Tooltip 中解析 `flow` 字符串的逻辑与 `ContainerFluidData` 的数据结构脱节，应该直接从 `ContainerFluidData` 获取信息，而不是从序列化字符串反序列化。

**8. `ContainerFluidData.FlowEntry` 不是 record**

`FlowEntry` 是可变类（字段直接修改），但 `registerSource`/`removeSource` 直接修改已有 entry 的字段。这与项目的不可变数据模型风格不一致。

**9. `LivingWaterWheelFunction.getWaterWheelItem()` 每次调用都查注册表**

虽然用了懒加载，但 `BuiltInRegistries.ITEM.get()` 在 Create 未安装时可能返回 `Items.AIR`，导致 `isWaterWheelItem` 永远返回 false。这不是 bug，但可以更明确。

**10. `ContainerStressData.calculate()` 遍历所有槽位**

`calculate()` 遍历容器所有槽位找活水车，但 `processContext` 中已经有 `waterWheelEntries` 了。可以直接传入已知的活水车槽位，避免二次遍历。
